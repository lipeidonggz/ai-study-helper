① 架构概览

为什么做这个检索存储结构设计——根因：学习类问题要的语义单元是一个结构（具体化陈述集合 + 关系网 + 证据），不是"一段相似文本"。而现有索引的原子是匿名文本块、组织维度只有文本/向量相似度——块没有语义身份，不知道"这是 O2 关于 containment 的主张""它属于局限类""这两条跨文互补"。所以它只能回表层相似的 top-k 列表，回答错了问题：把"取回支撑答案的证明结构"做成了"找相似文本"。换稠密还是 BM25 都改不了这个错位——根不在检索算法，在索引的原子与组织维度跟问题的认知单元不对齐。
由根因必然推出的架构要求（不是偏好）：
  • 原子要有语义身份：把断言 reify 成具体化陈述（rdf:Statement），携带 主题（dcterms:subject）/ 论述类型（claim_type）/ 出处（provenance）。
  • 组织要有语义结构：对象图——概念→具体化陈述（陈述边 hasStatement）、具体化陈述↔具体化陈述（论证边）、具体化陈述→chunk（归属边 groundedIn）、文档→具体化陈述（文档断言边 asserts）。
  • 证据不能在编译处断链：具体化陈述只是索引/地图，chunk 仍是事实源；编译产物绝不能成为最终事实来源，否则引用真实性审计链在编译处断裂（硬约束）。注：所谓"编译产物"即 LLM Wiki 范式——我们采用其"结构化索引"这一面，杜绝其"编译结果当事实源"这一面。
派生约束：第一层定位到内容单元而非文档（粒度与根因同源——按内容容量而非物理文件给单元定级）；不同访问模式（细节 / 概念定位 / 主题聚合 / 跨文对比 / 按类过滤 / 出处溯源）需要不同索引；引用要可溯源可审计——这是生成层的约束，反过来要求索引必须留证据链。
结论：以"内容单元 + 对象图"为路由与可审计骨架，原文单元仍是事实源；向量承担入口映射（query→概念/具体化陈述）与兜底（未建模/未命中），图承担主路由，不做 chunk 级重排器。

一句话：为在检索时按"问题的认知结构"取回证明集合（承接根因），把"从语料里取材料"建模成"入口（概念 / 具体化陈述）→ 共同落点（chunk）"的网状。用户问题先命中某个入口节点（概念 或 具体化陈述，取决于问什么），再经归属边落到具体 chunk（原文证据）。不是"概念 → 具体化陈述 → chunk"一条直线——概念和具体化陈述都可能作为入口、也都可能直接 groundedIn 到 chunk。路径见下。

② 组件定义

按"实体 / 具体化陈述 / 边"三组。实体是图里的节点；具体化陈述是特殊的一类（已 reify 的断言——由边对象化而来）；边是节点间的关系。所有构件均对齐标准 KG（RDF/OWL/SKOS/PROV-O），无自造词。

实体（节点）

  • 概念：稳定知识对象，可当主题聚合；canonical 名=其自身身份
  • 文档：信息内容实体；只走文档层关系
  • 异名：概念的演化叫法（非 canonical）；默认 altLabel，需时态/来源才 reify

具体化陈述（reified statement，rdf:Statement）

  • 具体化陈述：已 reify 成实体的断言（rdf:Statement，带 rdf:subject/predicate/object）。提升判据见决策 9（预测+修补：type_filter / argument_endpoint / concept_central）。
  • claim_type：具体化陈述的论述功能类型（rdf:type，如 LimitationStatement）
  • 出处：具体化陈述来自哪（provenance / PROV-O）

边（关系）

  • 概念结构边：概念↔概念（partOf / involves / precedes
    如 harness ⊇ linter    ）
  • 论证边：具体化陈述↔具体化陈述（support / attack / complement）
  • 归属边：具体化陈述/概念→chunk（groundedIn，证据在此）
  • 文档断言边：文档→具体化陈述（asserts，从文章找它的断言）
  • 陈述边 hasStatement：概念→具体化陈述（该陈述"关于"此概念；标准 dcterms:subject，检索时从概念反向遍历）

边界速记：实体是节点；具体化陈述是"由边对象化的断言"（reify 判据见决策 9）；claim_type是具体化陈述的类型标签；五种边各司其职（结构/论证/归属/断言/陈述）。无独立"维度/轴/主题"类别。

③ 架构决策

决策 1 · 具体化陈述必须 reify 成实体

理由：KG 模型里只有实体能作为边的端点去指向 chunk。概念（如"多Agent协同未解决"）是跨段议题，指向不了具体段落；只有"O2 承认它"这条断言才落在某段原文、需要 groundedIn。故断言必须 reify 成实体（具体化陈述）才能指向 chunk。
判据：要不要 groundedIn 到 chunk = 要不要 reify 成具体化陈述。一条信息若不指向具体段（只是概念间关联），不 reify；需定位到原文段，必须 reify。

决策 2 · 概念 ≠ 具体化陈述（宾语所指 vs 断言）

理由：概念是"所说的对象"（多Agent协同未解决），具体化陈述是"谁—如何—针对什么"的断言（O2 承认它）。同一概念可被多篇以不同方式论述（承认/展望），每条是不同的具体化陈述，但指向同一宾语概念。分开才能承载"不同的谁说了同一件事"。
反例：若把"多Agent协同未解决"直接当具体化陈述，就无法区分"O2 说它"和"A5 说它"——它们落在不同原文段，需要不同 groundedIn。

决策 3 · 删除"维度/轴/facet/比较轴"

理由：这些是我们为概括差异造的抽象，不是语料实体，也不是用户提问语言。普通用户问"怎么做防护 / 有何异同"（命中概念+具体化陈述+语义边），不问"防线放哪层"。查证 O2/A5 原文：两家讲的是"用什么工具设防"（linter/CI vs 沙箱/VM），从未出现"组织层/环境层"字样。
反例：若建"防线层级"实体，用户不会用它提问；它是分析者概述差异的抽象，建模反而引入噪音。

决策 4 · 多源对比无需"比较轴"

理由：对比 = 同一概念下的多条具体化陈述，经语义边（complement/attack/support）关联。P1（OpenAI 用 linter/CI）与 P2（Anthropic 用沙箱/VM），同为"给 agent 设防"，complement 直接连，不需要"比较轴"中介。
反例：若靠"防线层级轴"去切，反而把"用什么工具设防"扭曲成"放在哪层"，偏离语料真实表述。

决策 5 · 文档可经 asserts 找到其下具体化陈述

理由：文档实体可经 :asserts（对象属性）连到其下具体化陈述，构成"文档 → 具体化陈述 → chunk"链。查询：?doc :asserts ?p . ?p rdf:type :LimitationStatement . ?p :groundedIn ?chunk。文档是入口、具体化陈述是承载断言、chunk 是证据落点。
区分：文档层关系三样并列——cites（文档↔文档）/ partOf（归属）/ asserts（文档→具体化陈述），不可混用。

决策 6 · 具体化陈述 = 标准 rdf:Statement（RDF reification），非自造

理由：KG/RDF 对"主谓宾装不下完整语义"已有标准处理，三套方案——① RDF reification：把三元组对象化为 rdf:Statement 实体，用 rdf:subject/predicate/object 拆回，可挂任意属性；② N-ary relation / relation-as-class：把关系本身建模成类；③ Named Graph：按语境给三元组分组建图。咱们的"具体化陈述"正是 ①，是 RDF 内置标准模式，不是自造词。选 ① 因为它让单条断言可寻址、可命中——我们需要给每条断言挂出处/主题/claim_type，且要让它成为 groundedIn 与论证边的端点；named graph 适合按整组切分，n-ary 适合关系自身属性复杂的场景，都不如 reification 直接对应"单条断言可定位"的需求。补：多论元（如"经由 X 的手段"）在具体化陈述上用 roles（n-ary 角色限定）承载——即 "reification + 角色限定"的组合（对齐 RDF-star qualifier / PROV-O qualified relation）；故并非"不用 n-ary"，而是"以 reification 作载体、多论元作其角色"。
对照：hasStatement 不是标准 RDF 谓词，是自定义 ObjectProperty；其语义在标准里对应 dcterms:subject（具体化陈述"关于"某概念，Dublin Core 标准）。文档→具体化陈述用 :asserts（来源），概念←→具体化陈述用 dcterms:subject（主题），两者含义不同，不可混用。

决策 7 · 检索角色分工：向量=入口+兜底，图=主路由（不做 chunk 重排器）

理由：检索分两段——①入口映射（自由文本 query → 图入口节点）②图内遍历（概念→hasStatement→groundedIn→chunk、论证边、claim_type 过滤）。② 段纯图遍历、不需向量；① 段才是向量扛的活，也是去掉向量时必须用别的东西（符号/异名 + LLM）顶上的一步。故：入口向量打概念/具体化陈述（query→图节点），兜底向量打 chunk（图没命中 / 问题未建模时捞证据），图为主路由；不做 chunk 级重排器——证据侧重排由图信号确定性完成（到种子实体距离 / 命中数 / claim_type）。纯符号/异名入口被否：对 paraphrase、术语漂移脆弱（harness 多家叫法是反例）。
与 GraphRAG 的关系：本设计收敛到微软 GraphRAG 挖除社区块的主体骨架（索引即图 + 本地检索）；其"query→实体"用向量、"实体→邻域→文本块"用图，正对应该入口/主结构分工。差异在它给不了我们的部分——类型化具体化陈述+claim_type（对齐判官）、judge 对齐 grounding、确定性+学习任务视角、编译人工复核；且其"Global/community 摘要（编译结果当事实源）"被第 3 条硬约束否掉，仅取 Local 式 ground 到 chunk 的路。存储落地不必然上专用图库（语料千级块+几百节点，SQLite 建边表即可跑通）；"入口向量 vs 纯符号+LLM"与"向量入口命中 / 图遍历聚齐 / 兜底保真"待真实用例切片验证后再定。
核心判据（贯穿全文档）：能不能被独立提问 / 要不要挂属性 / 要不要被图命中 → 决定某对象要不要 reify 成实体。会不会被独立寻址 / 按类型捞取 / 跨源对比 / 进引用审计 → 决定要不要 reify 成具体化陈述（这是预测；grounding 到"证据 chunk 集合"是它的属性，不是触发）。这回答"什么该立为实体，什么该留在边/标签"。
2026-09-17 补（口径收窄，"进图标准"）：上面这条判据的正解是"能不能当路由键"，而不是"是不是知识"——图是索引层、不是事实源（事实在 chunk，边的 chunk_id 由证据句定位而来，字面量天然随 chunk 走）。故：① 纯度量值（0.1%、0 lines）不进图，chunk 兜着；② 影响边本身方向 / 极性 / 范围的限定（not software engineering、non-zero）必须保真——它决定这条边指向对不对的 chunk，优先级高于字面量；③ 结论性数值要进图的正确形态是 doc —asserts→ statement(object_literal=…)，不是"字面量边"、更不是伪实体。推论：当不了路由键的节点 / 边都不该进图（与"泛名词清洗"同一条原则）。

④ 编译层：从清洗后原文 → 对象图

编译层把语料"编译"成对象图（概念 / 文档 / 异名 + 具体化陈述 + 边）。它是索引 / 地图，不是事实源——每条产物都要能逐字指回原文（引文锚定），最终落到 chunk 作证据（见第 3 条硬约束、决策 6）。

本节怎么读：A 全景（十段流水线 + 每段状态，先建整体概念）→ B 已上线（断言层：Pass 1 → 体检 → 谓词清洗 → 谓词归一）→ C 已定稿、尚未接进线上（S6 归并 / S7 分类 / 引文锚定 / 落库与检索接线；S4.5 与 S5 已上线，留档说明也在这一节）→ D 关键决策→ E 输出 schema（含"两类谓词别混"的澄清）→ F 质检分工与验收→ G 未实现 / 待定清单。

B2 · Pass 1 抽取（提示词定稿）

Pass 1 ＝知识抽取器：把清洗后原文窗口抽成原子断言（含逐字短锚与 n-ary 角色）。system message 定稿如下（user message ＝ 窗口头信息 + 原文窗口）：

你是「知识抽取器」。把输入的「清洗后原文窗口」抽成【原子断言】列表（每条 = 一个 subject–predicate–object 的最小断言，可带角色），只输出严格 JSON。

# 输入
一段清洗后原文（纯段落文本、无编号、可能含多个主题）。

# 输出（严格 JSON；无多余文字、无代码围栏）
{"claims":[{"subject":"…","predicate":"…","object":"…","roles":{"instrument":["…"]},"evidence_texts":["逐字连续引文","…"]}]}
roles 可省略。

# A. 抽取范围
抽：针对某个「可被点名的知识对象」（有名有姓，如 containment / model layer / egress control / Claude Cowork；仅举例，不限于此），说了「可被引证之事」的断言——是什么 / 怎么运作 / 为什么 / 有什么局限 / 未来方向 / 与谁的关系 / 谁主张什么 / 分成哪类 / 属性 / 机制。
跳过：过渡 / 引子 / 钩子；只复述上一句的；无新断言的例子；主体是「我们 / 本文 / 这个改动」这类叙述 / 元主体。
拿不准就抽（宁多勿漏）。

# B. 原子性（一条 = 一个最小断言）
- 复合句（一句话两个意思）→ 拆成两条。例：`X is fast and Y is slow` → `X is fast` ／ `Y is slow`。
- 复合谓词（一个主语、两个动词）→ 拆成两条。例：`X reads and writes files` → `X reads files` ／ `X writes files`。
- 列表（一个位置多个项 A/B/C，主语或宾语皆可）→ 每条一个项；只拆「项的个数」，谓词不变、不新造动词。例：`X reads files, sockets, and env vars` → `X reads files` ／ `X reads sockets` ／ `X reads env vars`。

# C. 字段约定
- subject / object = 有名名词短语（可点名对象）；predicate = 动词。
- subject 取该断言所描述的、最具体、最像话题的核心实体。例：✗ `An important factor is caching` → ✓ `caching is an important factor`。
- 不作 subject：抽象类别 / 属性 / 从句；报告来源 / 元主体（telemetry / we / 本文 / 作者）。
- 动名 / 命题主语必须归约：以 granting / placing / supervising / limiting / having 或 "X that …"、"only when …" 开头的主语，改写为「施事（或核心实体）→ 谓词 → 该命题」。
- 定义 / 归类断言（is / is a / has…）：把被归类 / 被描述的实体放 subject。

# D. 角色（n-ary 关系的限定；写在 roles 里，不占 object）
- 「经由 / 通过 / 借助 / 用 X」这类「手段 / 工具」→ 放进 `roles.instrument`（可多值）；不要塞进 object、不要拆成新条、不要新造动词。
- 没有角色就不要输出 `roles` 字段（不要输出空 `{}`）。
- 例：`X repels attacks via sandboxes and VMs` → 一条：`{subject:X, predicate:repels, object:attacks, roles:{instrument:["sandboxes","VMs"]}}`。

# E. evidence_texts
- 每条 claim 给逐字原文引文数组。
- 每个元素 = 同一段原文内的一段连续文字；含标点、与原文逐字一致；不许拼接、不许改写。
- 跨段（即便相邻段）→ 拆成多个数组元素。
- 某段找不到逐字对应 → 放弃该段；整条都找不到 → 放弃该 claim。
Pass 1 验收标准（在 Pass 1 的 claim 上算；须多次跑、看稳定性）：① 召回——对召回金标准（backend/eval/compile/a5_recall_gold.json，段落级匹配）recall 应 ≈1.00（关键内容不漏）；② 证据可锚——每条 claim 的 evidence_texts 能逐字定位到 clean_T，≈1.00；③ 结构合规（Pass 1 自身）——subject/predicate 必填、object 可选（一元断言）、一条一项（原子性）、无空 roles。④ 稳定性（核心）：①②③ 须在多次跑批下一致达标（借鉴判官 repeat 稳定性）——单遍达标不算数，要多遍稳。从句主语/宾语归约、手段/路径→roles、措辞/粒度等，都属 Pass 2 的结构规范化，不计入 Pass 1 验收（Pass 1 尽力、Pass 2 兜底）。

B3 · 体检（质量门）

定位：线上必选一步，红线过了才进下一步（闸门已接：不过 → 任务 failed、不进入下一步，产物照旧落盘供人工排查）。三条原则——只做确定性动作（丢弃 / 确定性改写 / 标记，不做语义判断）、只给高置信项设红线、报告必须带样本清单。

红线 vs 告警线（2026-09-17 定，一次由实测逼出来的口径修正）：红线 ＝ 不可恢复的问题（过了才能进下一步）；凡能被程序确定性兜底（改写 / 丢弃 / 留给下游）的，只设告警线——不过也不拦，供人发现"抽取在退化"。
触发这次修正的是 O2 第一次泛化：它唯一不过的是元主语占比 10.9% vs 阈值 10%（差 1.9 条）。归因发现这个指标把两类东西塞进了一个桶——自称（we/our/us，所指确定＝文档主体，改写成文档主体是语义等价）与指代（this/it/they，所指不确定，改写成文档主体会造错，丢在体检又会让下游无从消解）。于是拆成两个指标，并顺手把"可兜底项不该判死"这条口径落实到全部指标上。
指标性质阈值动作为什么需要 / 为什么是这个档
召回（must 项）
recall_must		红线=1.00不过＝整篇失败人工金标准里 must 的核心断言，其所在段落是否被某条 claim 的证据覆盖。漏了就没有——不可恢复，所以是红线。没提供金标准时跳过（报告标注"未执行"）
引文可锚率
anchor_rate		红线≥0.95不过＝整篇失败只统计写了引文的 claim：引文能否在原文里逐字定位。低于阈值 ＝ 模型在编引文（幻觉探针）——编造的引文不可恢复，所以是红线
没写引文占比
evidence_missing		告警线≤0.20丢弃claim 完全没给引文（模型省字段或输出被截断）。丢掉即可、不涉及真假，阈值宽松
自称占比（we/our/us）
self_reference		告警线≤0.20确定性改写为文档主体自称的所指确定＝文档主体 → 改写是语义等价、不丢信息。比例高多半是文体（实践复盘文大量"我们做了什么"），过高才说明抽取在泛泛而谈
指代占比（this/it/they）
deictic_subject		告警线≤0.15保留 + 标记（交 S4.5）指代的所指不确定：改成文档主体会造错（this enables progressive disclosure 里的 this 不是作者），丢掉又会让下游无从消解。故原样保留 + 打 needs_resolution。这个比例 ＝ 待消解队列的长度，不是错误率
从句式主语占比
clause_subject		告警线≤0.02丢弃主语是 how to… / granting… / that…（≥3 词）这类从句式短语，不是干净概念 → 直接丢弃；比例高说明抽取质量在退化
谓词需清洗占比
predicate_dirty		告警线≤0.25标记（交 S3）谓词 ≥4 词或含并列 / 从句标记 / 否定 / 情态（修饰被揉进了谓词）。只标记不丢，交「谓词清洗」；比例高会拖累谓词归一的一致性
为什么"丢弃 / 改写 / 标记"三分：能确定性判死的（从句式主语）直接丢；能确定性修好的（自称）改写而不是丢；判不了、但下游能用的（指代、糊谓词）只标记、把活留给对应的下游步骤。越界即误伤——体检曾自己发明过一个"形容词式主语"检查，上线后实测只造成误伤（goal / that token 被误判），最后整条删掉：低收益的检查 ＝ 实际伤害。
体检的信息保真原则（2026-09-17 定）：体检只保信息，不做取舍——凡下游还需要的原料，一律"保留 + 标记"，不在这里丢。典型就是指代：一开始想"丢弃"，被沛东一句拦住——"丢在这里，后续步骤还怎么做指代消解？原料在前面就被扔了。" 于是改成保留 + needs_resolution，取舍留给 S5 的建图边界。这条与"先抽全再筛、前置有损不可逆"是同一个原则。

B4 · 谓词清洗（S3）

触发条件是确定性的：谓词 ≥4 词 / 含并列（and·or）/ 含从句标记 / 含否定 / 含情态词 之一。三条护栏：① 只改 predicate 字段（主宾与引文一个字不许动）；② 结果必须是原谓词的子序列——只能删、不能换（允许时态 / 单复数形态变化）；③ 被拒就保留原谓词并记 predicate_clean_rejected（记账，不静默吞）。
为什么必须排在归一之前：should not be implicitly trusted 这类整句谓词若直接强归，会被静默塞进某条宽关系、把否定吃掉——这正是项目最怕的"悄悄错"。先洗成 trusted + polarity: negative，否定才有归宿。
实测与事故：首跑 51 条清洗里 5 条被护栏冤枉（known→know / done→do / kept→keep / made→make / applied→apply），根因是子序列校验只折"单一词干"、认不出不规则形态 → 改成"词形变体集合"+ 约 60 条不规则动词表（误拒 5→1）→ 再补 has/had/does/goes/went/gone（误拒 1→0）。教训：护栏"严"要用对地方，且被规则拦下的一律留证据（有记账才可能第一遍就看出"5 条全是冤枉的"）。

B5 · 谓词归一（S4）——归一步的受控关系

只映射，不增删：给每条 claim 的谓词（清洗后的 predicate_clean 优先）选定受控关系表里的一个 id，写回 predicate_normalized 并标 predicate_status。输入不是短锚而是"锚句 ± 邻句"——短锚是为"LLM 复制保真 + 能定位"设计的，信息量不足以判关系；补上下文这一步由程序从 clean_T 无损切出（不让 LLM 再复制一遍）。实测：族级一致率 77.3% → 86.7%、跨族不一致 22.7%→13.3%（对齐 > 信息量）。

C · 已定稿、尚未接进线上（S6–S9）　＋ S4.5 / S5 已上线的留档说明

C1 · 指代消解（S4.5）——已上线，留档说明

为什么单独一步：① 它需要上下文——所指常在两段甚至更前（实测：[157] 需回溯 875 字符、[209] 需 ~1300 且跨标题），故窗口 = 锚句完整 + 前向 1600 字符（句界对齐、可跨标题），后向不额外留（实测"锚句之后的文本"被用到 0/95 条；同句内后向由"锚句完整"覆盖）；② 它是"改写／推断"——消解出的概念是原文里不在这个位置的词，所以不能覆盖 subject，只能新增字段（subject 原文保留 + *_resolved 供建图 + *_resolution_evidence 依据），可审计可回滚；③ 独立成步才能单独验收——Pass 2 当初就是被"一个 prompt 混了抽・合・分类"憋坏才拆三步的。
为什么不放别处：Pass 1 做不了（契约是"逐字引文 + 主宾照抄"，消解＝写出原文没有的词，冲撞"编译层不能成为事实源"）；S6 的"消解"是异名消解（VM vs virtual machine，两个已有东西是否同一），方向相反；塞进 S5 会让它变胖。
落地形态：三态 resolved / unresolved / not_anaphora（形式主语没有所指）；范围含宾语位（S5 的规则是"任一端不是实体 → 该 claim 不生成边"，宾语不消解＝整条丢）；依据护栏"只删不改"（省略合法、改词即编造；空依据不算通过）；输入显式给 anchor_quote（Pass-1 证据句，对齐 > 信息量）；响应解析要认两种形态（{"results":[…]} 与裸数组——模型偶尔返回裸数组，旧解析会只取第一个对象、整批静默丢）。
验收：金标准 eval/compile/a5_anaphora_gold.json（58 项，绑固定输入 a5_anaphora_input.json——Pass 1 非确定性，换一遍 claim 集就不可比）；闭环检查器第 ⑨ 项"指代闭环"（每个指代字段必须有状态 + 原字段没被覆盖）。

C2 · 图组装（S5）——已上线，留档说明：LLM 只规范端点，组图全部由程序做

职责切分（2026-09-17 定，本条是 S5 的核心口径）：LLM 只做一件事——把 claim 的端点（不规范的短语）转成"可点名的名词概念"（判据：能自然地问"什么是 X？"）；组图交给程序：一条 claim 至多一条边（列表早在 Pass 1 拆开）、方向由被动规则定、roles / polarity 从 claim 带、claim_idx 恒定。
为什么不让 LLM 出图（实测依据）：旧形态（LLM 直接输出 entities+edges，输入含块原文）实测——O2 的 314 条 claim 里 133 条（42%）被模型自己决定不建边且完全不记账、A5 是 170/379（45%）；还有 16 条边是"一条 claim 建了 2–3 条"；以及 36–44 个"声明了却没被任何边引用"的孤立实体（含从块原文顺手抽的概念）。病根是同一个：让 LLM 决定"图长什么样"。改形态后这四类问题在结构上不可能发生，且每条 claim 的处置都可对账。
输入：只给 claims（claim_idx + subject + object + 归一谓语，紧凑 JSON）——不给块原文（需要上下文的定指端点在 S4.5 已处理；给了反而诱导它从原文抽概念；实测输入可省 ~30%）。
端点取值：S4.5 已解的 *_resolved 直接用（不再送 LLM）；指代未解 / 光杆代词 → 端点不可用 → 该 claim 不建边；非指代的原文短语 → 送 LLM 规范化。
两条程序护栏：端点名可点名（非代词 / 非从句式 / ≤6 词 / 有字母）+ 不造名（实词须能在原文找到，容忍引号/逗号/单复数形态差异；S4.5 的 *_resolved 放行）。
对账：每条 claim 必落在「建边 / 因某端取不出概念丢弃（带原因）/ 谓词待定」之一——实体表＝边的端点集合，因此不存在孤立实体。
不出别名：同指判定属 S6（形归并 / 义归并 + 候选生成），S5 手里没有"这两个名字同指"的判据。
实测收益（同 O2/A5）：边 184→247 / 197→269、未建边从"10+133 黑箱 / 20+170 黑箱"变成 53 / 109 全部带原因、耗时 ~90 秒 → ~30–60 秒。
补充口径（2026-09-17）：summary 类未消解的 claim 走「文档级陈述」，不造概念节点。S4.5 把"判不出"分成两类：recheck（中心词在锚句前出现过 / 光杆代词 → 可能是窗口不足或模型漏解，值得复查）与 summary（指代词 + 抽象名词，且该名词在锚句前从未出现 → 多半是总结性指代，指向一串"我们还不知道…"的句子，原文没有可回指的名词短语）。
为什么 summary 类不硬解：解出来的名字必然是我们造的——不可引文锚定、与"编译层不能成为事实源"冲突、且每篇措辞不同、跨源聚合对不上；而它进图后是个 degree=1 的孤立节点（实测 [273]：these questions 若解出即
the open questions about agent-generated software —[has_property]→ ∅），对路由零贡献。
但也不能整条丢：这类句式（these questions / challenges / risks / limitations）恰好是作者陈述局限/展望的典型句式，而"按角色过滤"（各文的局限是什么）正是 claim_type 的核心用途——该路径走的是 文档 —asserts→ statement（带 claim_type）→ evidence chunk，并不要求 subject 是概念节点。
故处置：summary 类的 claim → 保留 subject 原文 surface、about 为空、挂在 doc 上（asserted_by）、证据锚回 chunk —— 不造概念、不丢断言、可锚定。已知代价：它们不参与概念路由（跨文的纯概念问法捞不到），若将来需要，可把 about 指向上文原文已有的概念并标 about_source: context（该口子尚未开：S5 已按"不造概念"落地，这类 claim 现在停在「不建边 + 记账」；真正挂 doc 的 statement 由 S7 的 reify 统一产出，见 G 表）。
顺带记一个观察：[273] 锚句所在 chunk 的 section 是 What we're still learning ——原文其实用章节标题给这片内容起过名字。但拿它当节点＝重新引入"topic 节点"，与决策 3（不设独立 topic 类别）冲突，故不开口子。

D · 关键决策（编译层）

决策 8 · 编译源 ＝ 清洗后原文，粒度 ＝ 内容单元（token 上限 12k）

理由：只有清洗后原文（切片为 chunk 的输入）有完整上下文；chunk 拆散论断、缺上下文，即便"引用锚＝连续块组"也是拆后聚合。长书不能整本喂 → 编译粒度取"内容单元"（容量≈文章 10–40 块＝章节/小节），语义边界优先、token 上限 12k（约 1.5–2.5 万字）兜底，超限在小节/段界切、留 overlap。内容单元是虚概念、仅编译时用、不落库；跨单元同概念需归并（sameAs / denotes）、声明合并、去重。
判据：内容单元＝编译窗口，非存储实体；只有编译产物（概念 / 具体化陈述 / 边 + 证据 chunk 集合）落库。状态：◐——O2 / A5 实测是按"整篇即一个单元"跑的（单文件 <12k）；12k 切分与多文件遍历未实现（见 G）。

决策 9 · reify 判据 ＝ 预测 + 修补（替代"对齐 chunk"）

"某断言将来会不会被独立寻址 / 按类型捞取 / 跨源对比 / 进引用审计"本质是预测，无法预先完美定 → 预测（编译时命中任一触发即 reify：claim_type 在被查词表 / 概念中心度 / 需作论证端点）＋ 修补（查询与回答时再用 dense 兜底、判官 miss promote、周期清扫补回来，见 C6）。立场性（谁—这么认为）不单列为触发——由 asserted_by + provenance 承载。grounding：具体化陈述 → 证据 chunk 集合（多对多，判官"声明组"口径）；chunk 已补清洗后原文偏移（chunk_offsets：chunk_id / source_id / section_path / file_idx / start_pos / end_pos），偏移按文件计——多文件源用 file_idx 区分、各文件坐标从 0 起；单文件源（如大 PDF 书）file_idx 恒 0、偏移即全书全局。
状态：◐——"预测"侧的三个触发还没实现（S7）；chunk_offsets 已建成，"修补"侧未实现（C6）。

claim_type 词表 · 结论（最终包括哪些）

核心 ＝ {LimitationStatement, OutlookStatement}（论述角色过滤的硬需求，对应"各文局限 / 展望"这类按角色过滤的查询）；不当类型 ＝ Stance（"谁这么说"走 文档→asserts→chunk）、Definition（概念定义→概念路径）、Method / Mechanism（机制→概念路径）、Comparison（异同→同概念多条陈述经论证边浮现）；其余动态 promote——当某概念陈述集异构、且用户真按某角色过滤时，走 reify 修补侧升级成类型，词表不预先拍死、数据驱动可伸缩。
约束与理由：claim_type 是路由过滤标签，不是"论文话语结构标注"——只在三种情况才需要（① 概念陈述集异构，概念路径分不开；② 用户按单一论述角色过滤；③ 别的路径——概念 / 结构边 / 论证边 / 出处边 / 生成——带不到）。权威词表（AZ/CoreSC：Background/Method/Result/Conclusion/Limitation/Future Work；Argument Mining 的 claim/premise、interpretation/evaluation/agreement/disagreement；SemMedDB 谓词）以穷举标注全部句子为目标，我们的 claim_type 只需覆盖"被 reify + 要按角色过滤"的交集，故权威角色大多并非检索所需；且问题空间（学习者按"角色"过滤的题型）本就很窄、由产品定位固定，语料量只是二阶因子（再多文档只提高概念陈述集异构 / 激活度，更多来源的异名 / 术语漂移落在入口 / 异名侧，均撑不大类型集合）；LLM 把"理解"挪出了类型系统（入口映射、回答生成 + 判官、其它结构边各自接活）。原则：分类粒度由"它服务的决策 / 查询"决定，不由数据丰富度决定。
状态：○——词表已定稿，但赋值本身还没实现（S7）。

F · 质检分工与验收

阶段质检分工（各层量什么）：原则——每层只对自己的职责负责，别把下游该干的活算成上游的错。① 抽取（S1–S2）对着「原文」量：召回（金标准，段落级；红线）、引文可锚（红线，兼作幻觉探针）、结构合规（谓词不含从句·并列·时态变体）、忠于原文（程序只查高置信的格式类硬错；主宾倒置 / 曲解判不了 → 抽样人审或 LLM 抽检）、覆盖一致性（多遍对比、句级三态「都抽 / 都不抽 / 只有一遍抽」，线上关闭、仅调试期开）——抽取的稳定性 ＝ 同一段原文两遍都覆盖到了，而非两遍断言字面相同。② 谓词归一（S3–S4）对着「固定输入」量：标签一致率（同一份抽取产物跑两遍）、跨措辞标签一致率（is/be、has/includes、grows/grow 必须同标签）、语义保真（抽样）——主语 / 宾语的异名不归它管。③ 实体合并（S6）对着「节点」量：形合并三层护栏 + 出处共现置信度 + 义合并候选判定——"同一断言的主宾字面一致率低"是这一层的输入规模，不是抽取的缺陷指标。
采样温度：编译层全链路 temperature = 0（COMPILE_TEMPERATURE，作用于 Pass 1 / 谓词清洗 / 谓词归一 / S4.5）——确定性任务不给随机性，与评测侧判官的 JUDGE_TEMPERATURE = 0.0 对齐。依据：同输入 37 个指代目标，温度 1.0 三遍 resolved 23/35/33（判不出 12/0/2）；温度 0.0 三遍 35/35/35、逐条三态一致率 1.000。注意温度 0 不等于完全确定（Pass 1 抽取数量仍有两三成之外的残余波动），"多遍稳定性"照旧要单独量。
校验层 + 质量门（一等设计项）：人审基础件（编译 prompt / claim_type 词表 / grounding 规则 / 校验门）+ 程序结构校验（id / 词表 / grounding 一致性）+ 判官 / 引用审计自动门（覆盖性 / 引用真实性）+ 定时抽样；噪声爆炸半径锁死在"路由"（chunk＝事实源、编译＝索引），进不了"事实"。
图里收什么（宽提取 + 受控关系筛选）：Pass 1 宽提取保召回，图的边只收"能归入受控关系"的那些；不做"先段落主旨、再抽三元组"的中间摘要——理由：① 主旨是有损压缩，丢掉的正是关系细节（数字 / 条件 / 边界断言）；② 主旨句无法引文锚定，会破坏"编译层不能成为事实源"这条硬约束（凡破坏可锚定的中间产物都不进编译层）；③ 前置有损会让损失不可逆。代价已声明：能归入宽关系的未必重要（图变大，是成本不是正确性问题）、重要但谓词糊的会暂被待定——靠 chunk / 向量兜底 + 待定清单回收。细节检索一律由向量 + chunk 兜底，问答侧做"入口向量 / 图路由 / 兜底保真"三段融合。
实现提示（如何用偏移 / 划内容单元 / 控输出上限）：① 编译层按 (source_id, file_idx) 定位"清洗后原文"文件；② 在该文件内切出内容单元——语义边界优先的连贯窗口（section_path 仅启发式、非强制切分点；整篇 <12k token 时整篇即一个单元），超限才在小节 / 段界切、留 overlap——内容单元划分是编译层职责，不在 chunk / 偏移层做；③ Pass 1 在该内容单元内再按窗口（~5k 字符、段落界切）逐窗抽取（局部抽取不需要全局，窗口小则不触发输出上限）；④ 图组装 / 合并 / 分类按批（~40 条/批）（单次输出超限 → 分批 + 程序合并，claim_idx 偏移、实体按 name 去重；JSON 截断有"重试 + 拆半批"兜底）；⑤ 对每条陈述，用 evidence_texts 定位 + 与 chunk 区间重叠，得证据 chunk 集合。单文件大 PDF：file_idx＝0、内容单元即该文件（偏移即全局）。

⑤ 待确认的范式思考：LLM 时代的知识图谱——"图是索引层"（2026-09-17 起草，待验证）

为什么记这一节：沛东看完 S5 产出后提出一个直觉——我们可能摸到了"知识图谱 × LLM 如何融合"的某种范式：传统 KG 要求图谱承载全部知识；而有了 LLM 之后，图谱既可以被 LLM 帮着建，也不必再承载全部知识（因为 LLM 提供了在线语义推理能力）。本节把它写成一个待确认的假说并附业界对照。注意这是假说、不是结论——图谱的检索效果尚未验证（验证方案见本节末）。
一句话范式：把"知识"分三层各司其职——原文承载事实（无损、可逐字回锚）→ 图承载"可控词汇上的路由与连接"（浅、可枚举、可回溯）→ LLM 承载在线语义对齐、推理与表述。配套判据：进图的标准不是"这是不是知识"，而是"能不能当路由键"。

五条要点（各带本项目实证）

① 事实下沉到原文——图的"不完备"不再是缺陷：S5 实测 A5 109 条 / O2 53 条 claim 未建边（属性式谓词占 52% / 68%），但 attack success rate 那条边所指向的 chunk A5:3 里就写着 roughly 0.1% on single attempts——事实一直在，只是不在图上（边的 chunk_id 由证据句定位而来，属构造保证）。
② 图只承载路由键：判据从"要不要挂属性 / 要不要被图命中"收窄为"能不能当路由键"，并推出"当不了路由键的节点/边都不该进图"（与"泛名词清洗"同一条原则）。
③ 推理与对齐交给 LLM ⇒ 图可以很浅：浅到 39 条族级关系、浅到 acts_on 这种收容桶都能用；传统 KG 最贵的四件事（本体设计、公理维护、一致性检查、全量同义对齐）在 LLM 在场时都可降级——这就是"知识获取瓶颈被松绑"的具体形式。
④ 图的正确性标准要分层（最反直觉的一条）：不可错＝边的方向 / 极性 / 范围（它决定路由到哪个 chunk：platform —supports→ knowledge work 丢掉 not software engineering，就会指向"看起来相关、结论相反"的证据，而账本上是绿的）；要完备＝每条 claim 的处置必须可对账、枚举能力必须可验证；可容忍＝字面量、程度、精确分类（影响答案精细度，而精细度由 chunk + LLM 提供）。
⑤ 建图的工程范式：LLM 做语义转换（抽取 / 规范化 / 判断），程序做结构与记账（建边、定方向、roles / polarity 传递、全量对账、护栏）；配"宽提取 + 受控归约"与"可锚定是硬约束"——后者传统 KG 里不存在（KG 本身就是事实源）。

三条边界（什么时候这套范式不成立）

① 覆盖型问题仍需枚举能力：LLM 无法证明"没有遗漏"，"这篇里所有的风险"是枚举语义——图的不完备在这儿又变成硬要求（走编译侧对账 + 召回金标准）。
② 越强的 LLM，越不需要图：若图的价值建立在"模型不够聪明"上，它会随模型变强而蒸干。故图的正当性必须锚在LLM 结构上做不到的事——枚举 / 跨源连接 / 可审计的出处链（这正是上一轮把立项理由收敛到这三件的原因）。
③ "在线推理"的代价是确定性：同一问题不同结果、说不出为什么、可能编——所以配套不是更严格的本体，而是引用红线 + 遗漏透明 + 判官这类外部校验。
