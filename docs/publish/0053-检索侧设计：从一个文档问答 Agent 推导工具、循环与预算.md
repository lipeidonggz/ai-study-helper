> **30 秒判断**：检索侧设计不是先挑一个 RAG 框架，也不是把 top-k、RRF、reranker 调得更复杂。真正决定能力边界的是：**系统有哪些检索动作、每个动作能证明什么、Agent 怎样在多次动作之间推进，以及预算在哪里统一收口。**
>
> 本文从一个文档学习问答 Agent 的 18 条用例出发，收敛出 5 个检索工具、1 个 ReAct 循环和 1 套预算规则。核心结论是：**默认纯 Agent，不做前置路由器；工具负责取证据，Harness 负责执行和预算，模型负责选择下一步。**
>
> **适合谁读**：正在做 RAG／Agent 检索的人；工具越加越多、但说不清每个工具边界的人；把规则全堆进提示词、多轮后上下文失控的人；以及正在纠结“经典 RAG 还是 Agentic RAG”的人。
>
> **本文怎么读**：沿用本系列前三篇的结构——先讲**方法**，再用一个真实实例演示。标着「实例｜」的段落可以跳过，不影响读方法。
>
> **前置阅读**：系列前四篇。①《[Agent 开发为什么要测试驱动升级版](https://juejin.cn/post/7696916617436889115)》讲方法由来；②《[需求定义四步：用一个文档问答 Agent 演示“先定义、再动工”](https://juejin.cn/post/7697089423960719396)》定义问题空间与质量属性；③《[金标准：用一个文档问答 Agent 演示“什么算对、怎么判”](https://juejin.cn/post/7697089423961014308)》把“答对”落成可执行判定；④《[由检索需求反推存储](https://juejin.cn/post/7697269670269321225)》先定了“块＋元数据＋双索引”的存储形态。本文接着回答：**这些块怎样被 Agent 稳定地取出来。**
>

>
> **证据标记**：**✅ 实测**＝有可复现实验数据支撑；**🤔 推断**＝由机制、既有实验或设计要求推出。本文的存储结论承接前篇既有实验；检索侧目前主要是设计推导，**尚未完成 pure Agent 与预路由方案的对照实验**，因此不宣称性能已经胜出。

**先交代几个名词**

- **经典 RAG**：查询一次，取 top-k，然后直接生成。
- **Agentic RAG**：Agent 根据当前证据决定下一步：继续检索、换范围、澄清或回答。
- **纯 Agent**：入口不做问题分类，所有问题都由同一个 Agent 循环决定是否检索、检索什么。
- **Action／Observation**：模型选择一个动作；Harness 执行后，把结果作为观察返回给模型。
- **工具契约**：工具的输入、输出、空结果、错误、顺序、范围和版本规则。它决定工具能力，也决定模型能否正确使用工具。
- **collection 快照**：某一时刻完整、不可变的一套文档、块、向量和关键词索引。
- **Agent 运行预算**：本文简称“预算”，主要指模型上下文上限、本次请求累计对话 token 和工具调用轮次，不指财务预算。

## 0. 六步，一页

| 步骤 | 回答什么 | 产出 |
| --- | --- | --- |
| ① 从用例提能力 | 用户的问题需要哪些“检索动作” | 能力清单 |
| ② 收敛工具 | 哪些动作可以由同一工具稳定完成 | 少量工具 |
| ③ 写工具契约 | 每个工具能查什么、返回什么、不能证明什么 | 输入／输出／错误／范围契约 |
| ④ 定 Action／Observation | 模型和 Harness 怎样交接 | 文本协议＋执行 envelope |
| ⑤ 设计循环与预算 | 多轮怎样继续、停止、重试、降级 | 状态机＋预算规则 |
| ⑥ 过质量属性 | 可观测、可复现、可维护、可安装等会反向改什么 | 设计修正＋待验证项 |

一句话：

> **先定动作，再定工具；先定契约，再写提示词；先定预算归属，再谈多轮。**

## 1. 为什么存储之后，还要设计检索执行

前一篇已经回答了“知识怎么存”：第一阶段用增强的向量块——块＋元数据＋向量索引＋关键词索引；检索策略是经典 RAG 与 Agentic RAG 共用同一套索引。

但存储只决定“理论上能取什么”，还不决定“实际会取成什么样”。

同一个块库，可能被设计成：

- 每次都只做一次 top-5 检索；
- 让模型自由拼参数，什么都交给它决定；
- 工具先自行做预算和截断，Harness 再加一道预算检查，形成两套边界；
- 所有规则都堆进系统提示词，工具契约只写“return list”。

这些实现都能跑，但能力完全不同。检索侧要补的，就是把存储层的能力组织成**模型能选、系统能执行、结果能验证**的动作。

核心变化是：

> **设计单位不是“一次检索”，而是“一个可组合的检索动作”。**

## 2. 从 18 条用例收敛出五个工具

### 2.1 先按能力归组，不按问题逐条加工具

**实例｜文档学习问答 Agent**

| 能力 | 代表用例 | 检索要做什么 |
| --- | --- | --- |
| 单点事实 | 是什么／在哪里／对吗 | 语义或关键词命中目标块 |
| 单点但需多块 | 为什么／怎么做 | 命中后再补同节上下文 |
| 证否与归属 | 文档里有没有 X／这是谁说的 | 精确字符串扫描，不能靠 top-k |
| 跨源对照 | 多篇异同／哪个对 | 逐篇限定范围，再比较 |
| 要全／枚举／整节 | 有哪些／所有要点 | 按范围取全部块 |
| 整体图景／换形态 | 概览／整理成表 | 先看大纲，再按节读取 |
| 消歧 | “OpenAI 那篇” | 列文档、缩小候选，再澄清 |

这张表读成一句话：

> **单点类靠候选召回；证否、枚举、跨源、整节靠范围控制和多轮。**

### 2.2 五个动作已经够用

| 工具 | 解决什么 | 关键限制 |
| --- | --- | --- |
| `list_documents` | 库里有什么、按来源／标题／别名消歧 | 只返回元数据，不证明正文内容 |
| `get_outline` | 看文档结构、选择章节范围 | 返回结构，不是内容证据 |
| `search_blocks` | 找语义相关候选 | 固定 Top-5，不声称全集 |
| `list_blocks` | 按整篇或章节取全 | 每次一篇；章节包含后代 |
| `scan_term` | 精确字符串、证否、原词归属 | 只证明这个字符串是否出现 |

这里最有价值的三条边界是：

1. **`search_blocks` 没有命中，不代表文档没讲。** 它只返回候选，不是全集。
2. **`scan_term` 只能证明指定字符串在有效范围内没有出现，不能证明这个概念不存在。** 同义词扩写可以提高语义召回，但不能把“没找到”升级成“概念不存在”。
3. **`list_blocks` 要全，`search_blocks` 要找相关。** 两者的完整性承诺不能混。

**实例｜两种请求为什么走不同工具**

- “Anthropic 那篇里，local VM 的隔离边界是什么？” → 先消歧，再 `search_blocks` 找候选，必要时 `list_blocks` 补同节内容。
- “这篇文档里有没有出现字符串 `MCP`？” → `scan_term`。这是对确定字符序列的检查，不需要改写。
- “这篇文档讨论 MCP 吗？” → `search_blocks`。没有召回只能说明没找到相关证据，不能回答“文档没讲”。

如果已知缩写或别名，例如 `Model Context Protocol`，可以逐个用 `scan_term` 辅助检查；但 `count=0` 仍然只对“实际扫描过的写法集合”负责，不代表概念全集已经穷尽。

## 3. 为什么默认纯 Agent，而不是先做路由器

最常见的架构是：先训练／写一个分类器，判断问题该走“单点 RAG”还是“Agentic RAG”。看起来更省，但它把不确定性提前放到了入口。

| | 前置路由 | 纯 Agent |
| --- | --- | --- |
| 判断发生在哪 | 入口 | 每轮 Thought |
| 分错后 | 整条路径走错 | 下一轮还能修正 |
| 出错定位 | 分类器＋下游两处 | 一条循环轨迹 |
| 简单问题 | 路径更短 | 需要模型自行判断是否直接回答 |
| 复杂问题 | 依赖分类器预见所有类型 | 可以按观察动态展开 |

当前选择是：**默认纯 Agent，不做前置路由；快车道只作为延迟后手。**

这不是说纯 Agent 一定更快或更准。**🤔 推断**：它只是把不确定性从“多个入口”收敛到“Thought 一处”，更容易观测和纠正。快车道必须通过延迟门槛后才允许加入。

**实例｜H1 门槛**

简单学习类问题只有在同时满足两个条件时，才考虑快车道：

- 首字延迟 P50／P90 达到目标；
- 通过率满足既定的 N／K 统计规则。

否则先保留纯 Agent，避免为了理论上的延迟收益增加第二套路径。

## 4. 工具契约：工具不是函数列表，而是能力边界

### 4.1 一个工具要回答的九件事

| 要素  | 要确定什么                     |
| --- | ------------------------- |
| 粒度  | 一个工具只做一件事                 |
| 输入  | 哪些选择交给模型，哪些参数由系统固定        |
| 输出  | 返回证据、元数据还是结构              |
| 空结果 | “没找到”和“调用失败”怎样区分          |
| 错误  | 参数无效、范围不存在、上游失败怎样表达       |
| 预算  | 工具只返回完整结果，Harness 做唯一一次准入 |
| 确定性 | 相同输入、相同快照、相同参数下顺序稳定       |
| 描述  | 什么时候用、什么时候不能用             |
| 版本  | 契约变化怎样复核和回滚               |

### 4.2 三个容易被低估的契约

**第一，分数只进 trace。**

`search_blocks` 返回块引用、标题、来源和全文，不返回检索分数。分数对模型的帮助很小，却会诱导它使用未经校准的阈值；分数留给 trace，用于调试和调参。

**第二，快照在请求开始时固定。**

一次问答里可能连续调用多个工具。如果后台刚好重建完成，前半轮读旧 collection、后半轮读新 collection，trace 就失去可复现性。因此：

> 请求开始时固定 `collection_snapshot_id`；本次所有工具共用该快照；新快照只原子切换“活动指针”，不回写进行中的请求。

**第三，章节范围必须说明是否包含后代。**

`list_blocks(section_paths)` 选择一个二级标题时，必须明确是否包含它的所有子节。否则“把这一节取全”可能在实现上只取直属块，完整性承诺直接失效。当前定义是：**选择某个 section path，就包含该节及全部后代。**

### 4.3 错误和空结果不是一回事

公共错误示例：

```json
{
  "error": {
    "code": "scope_not_found",
    "message": "section path not found",
    "retryable": false
  }
}
```

需要区分：

- `no_match`：范围有效，但没有相关候选；
- `scope_empty`：范围有效，但里面没有块；
- `collection_unavailable`：当前没有可读快照；
- `invalid_argument`：空查询、空数组、非法路径；
- `upstream_unavailable`：query embedding 等服务失败；
- `internal_error`：工具内部异常。

如果这些状态都退化成“空列表”，Agent 就无法知道应该换查询、换范围、澄清还是报告系统故障。

## 5. Agent 循环：模型做选择，Harness 守边界

### 5.1 职责分工

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 模型 | Thought、Action、是否继续检索 | 文件 I/O、预算裁决、伪造 Observation |
| Harness | 解析 Action、执行工具、生成 Observation、维护 History、执行预算 | 判断内容是否充分、替模型写答案 |
| 工具 | 执行一个检索动作，返回业务 payload | 决定下一步、做上下文预算、静默截断 |

每轮流程：

```text
预算检查
  → 模型输出 Thought + Action
  → Harness 解析
  → 工具执行
  → Observation 进入 History
  → 模型检查证据是否足够
  → 继续 / Finish
```

### 5.2 两个预算不能混

**上下文预算**限制“下一次对话模型调用最多带多少 token”。**请求预算**限制“本次问题所有对话模型调用累计消耗多少 token”。

为什么还需要请求预算？因为 History 每轮都会重放，前一轮的 Observation 会在后续调用中反复计入。只限制单次上下文，不能约束整次问答的总消耗。

**实例｜初版预算**

- 最多 8 次工具调用；
- 单次上下文默认 100k；
- 请求累计对话 token 默认 400k；
- 预留 4k 给最终回答。

embedding 的 token 单独记录，不与对话模型 token 相加。两家 tokenizer 和计价单位不同，混算出来的数字没有解释力。

### 5.3 预算由 Harness 做一次，不做第二道截断

初版工具返回范围内全部结果和 `result_tokens`，自身不判断预算。Harness 在结果进入 History 前做唯一一次准入：

- 放得下：完整进入；
- 放不下：丢弃本次结果，返回 `context_budget_exceeded`；
- 整次请求累计耗尽：返回 `request_budget_exceeded`。

为什么不给工具加分页？

> **分页只能减少“一次返回多少”，不能减少“最终读完需要多少”。**

如果完整结果本身放不进上下文，分页只会把同一次失败拆成多次调用和更多累计成本。

## 6. 提示词：不要写 18 条 if／else

提示词的作用不是重复工具契约，而是规定跨工具的行为规则。当前按下列层次组织：

| 区块 | 负责什么 |
| --- | --- |
| `role` | 产品定位与能力边界 |
| `tools` | 注入工具描述 |
| `collection_status` | 当前快照是否完整；部分入库时列出缺失文档 |
| `response_protocol` | Thought／Action 格式 |
| `observation_protocol` | Harness 状态与 payload 的关系 |
| `scope` | 越界、歧义与澄清 |
| `evidence` | 文档事实、模型补充与证据边界 |
| `coverage` | 枚举、跨源和遗漏透明 |
| `citation` | 什么内容必须标来源 |
| `answer` | 答案形态 |
| `termination` | 何时停止 |

### 6.1 工具契约与提示词各管什么

- 工具自己说明“我能做什么、参数是什么、返回是什么”；
- 提示词说明“多个工具之间怎样协作、什么时候停止”；
- Harness 用代码强制执行“工具白名单、预算、状态解析”等确定性规则。

不要把能由代码强制的规则只写在提示词里。提示词是行为引导，不是权限系统。

### 6.2 证据规则必须写成可执行句

例如：

- 文档事实必须有块支持；
- `search_blocks` 没命中不能证明“文档没讲”；
- 用户要“全部”时，Top-k 不能冒充全集；
- 多源比较要逐篇取得证据；
- 部分 collection 必须声明 `failed_documents`。

### 6.3 引用是内部键，展示是另一层

模型输出机器引用键：

```text
【来源：doc_id#block_id】
```

前端再把它解析成文档标题、来源名和块预览。面向非技术用户的产品，不能把内部 ID 原样当成最终引用文案。

## 7. 最大架构权衡：完整性与上下文预算

**实例｜比较四篇文章的主旨**

假设每篇约 40k token，四篇就是 160k。再叠加提示词、工具定义、历史轮次和最终回答，单次上下文很快超界。

| 方案 | 用户会得到什么 | 问题 | 结论 |
| --- | --- | --- | --- |
| 不限量读取 | 小范围一次拿全 | 需求材料总和过大时直接失败 | 不采用 |
| 固定前 N 块 | 成本稳定 | 用户要全时只得到一部分 | 不采用 |
| 分页读取 | 单次返回更小 | 最终总量没减少，累计成本更高 | 不采用 |
| 工具返回全量＋Harness 准入 | 预算内完整，超界明确失败 | 超大范围不会直接得到答案 | 第一阶段采用 |
| 预摘要／Wiki | 总览更省 token | 视角取舍、编译成本和回源问题 | 实测后再引入 |

这里最关键的区分是：

- **“遗漏透明”不是和成本冲突的一方**；
- 当预算不足以完整覆盖时，明确告诉用户缺了什么；
- 不能返回半套结果，再把它说成完整。

## 8. 质量属性会反过来改设计

检索方案不是过了功能用例就结束。下面这些约束会直接改变接口和运行方式：

| 质量属性 | 对设计的具体影响 |
| --- | --- |
| 正确性／完整性 | 范围查询、精确扫描、快照完整性、部分入库必须可见 |
| 一致性 | 固定排序、固定检索参数、同一请求固定快照 |
| 成本 | 单次上下文与累计 token 两套预算；embedding 成本单记 |
| 可观测性 | 每次回答都能从本地 viewer 还原轮次、工具、证据和预算 |
| 可复现性 | 记录 prompt／loop／tool／model／collection 版本；区分证据复现、检索重放和统计重跑 |
| 可维护性 | 工具、提示词、配置、索引 schema 有兼容和回滚边界 |
| 可安装性 | 单机桌面版不能要求用户另装数据库、容器或观测平台 |
| 安全 | 文档是不可信输入；工具只读；Harness 强制白名单 |

其中最容易被混为一谈的是“可复现”：

> 可复现不等于模型每次输出同一段文字。它至少分成：输入能否还原、检索能否重放、模型输出在重复运行中是否稳定。

* * *

## 9. 这次刻意不做什么

| 暂不做 | 为什么 | 什么信号会推翻 |
| --- | --- | --- |
| 前置检索路由器 | 增加判断入口，纯 Agent 尚未证明低效 | 简单题延迟持续不达标，且快车道通过验证门槛 |
| 自动重排 | 先看混合检索＋Agentic 是否已足够 | 失败样本显示候选已召回但排序持续错误 |
| 上下文自动剪枝 | 会改变 History，影响审计和缓存 | 多轮上下文成为主要瓶颈 |
| 独立 evidence assembler | 初版完整 payload 已可进入 History | 重复证据和上下文噪声持续导致失败 |
| Wiki／图作为硬依赖 | 第一阶段用例不要求预编译知识形态 | 面状覆盖、关系／条件取全出现稳定缺口 |
| 本地模型推理 | 单机部署与资源约束不适合 | 产品目标改为完全离线 |

## 10. 常见误用

| 误用 | 后果 |
| --- | --- |
| 只设计 top-k，不设计动作 | 证否、枚举、跨源类问题永远没有确定答案 |
| `search_blocks` 没命中就说文档没讲 | 把候选召回误当全集 |
| 工具自己截断一次，Harness 再检查一次 | 两道预算、两处失败语义，难以解释 |
| 把所有规则都塞进提示词 | 提示词膨胀，确定性约束仍无法保证 |
| 给模型返回未校准的检索分数 | 模型消费了不该由它判断的内部信号 |
| 一次请求中途切 collection | 前半轮和后半轮基于不同语料，trace 无法重放 |
| 新链接入才算“可复现” | 模型随机差异和版本差异混在一起 |
| 把本地 viewer 换成外部平台作为前提 | 观测组件反过来拖垮单机安装 |

## 11. 一页速查

**原则**：检索侧设计的单位是可组合的检索动作，不是一次 top-k。

**六步**：用例提能力 → 收敛工具 → 写契约 → 定 Action／Observation → 设计循环与预算 → 过质量属性。

**五个工具**：`list_documents`／`get_outline`／`search_blocks`／`list_blocks`／`scan_term`。

**三条边界**：

- `search_blocks` 是候选召回，不是全集；
- `scan_term` 证否字符串，不证否概念；
- `list_blocks` 的范围包含后代章节。

**一个循环**：模型选下一步，Harness 执行、记录、预算；证据足够或运行边界到达时停止。

**一套预算**：单次上下文＋累计对话 token；工具返回完整结果与 `result_tokens`；Harness 做唯一一次准入；不分页。

**一条底线**：完整取不下时，明确失败或声明缺口，不悄悄给半套结果。

**一句话**：**先把取块动作、证据边界和预算归属设计对，再谈 prompt、reranker 和更复杂的知识形态。**

## 附录 A｜工具契约摘要

| 工具 | 核心输入 | 核心输出 | 不能证明什么 |
| --- | --- | --- | --- |
| `list_documents` | 来源／语言／标题片段 | 文档 ID、标题、来源、别名、规模 | 正文内容是否存在 |
| `get_outline` | 一个或多个 doc_id | 章节 path、直属／子树规模、首句 | 章节正文事实 |
| `search_blocks` | query、可选 doc_ids | Top-5 块、`empty_reason`、`result_tokens` | 全集与“文档没讲” |
| `list_blocks` | 单篇 doc_id、可选 section_paths | 范围内全部块与 token | 相关性排序 |
| `scan_term` | term、可选 doc_ids | 全部命中、snippet、count | 概念等价、语义近似 |

公共错误至少包括：`invalid_argument`、`scope_not_found`、`collection_unavailable`、`upstream_unavailable`、`internal_error`。

## 附录 B｜检索侧对入库侧的接口要求

入库侧最终产物不是一个“能查的数据库”，而是一份可被检索侧可靠消费的 **collection 快照**：

- 快照状态和完整性可见；
- 文档有稳定 ID、标题、来源和别名；
- 章节树可唯一定位，并包含直属／子树统计；
- 块保留完整原文、字符位置和内容 hash；
- 对话上下文与 embedding 使用两套 token 口径；
- 向量索引、关键词索引与快照一一绑定；
- RRF 等检索常数进入 manifest；
- 部分失败不能静默当成功；
- 旧快照支持生命周期管理，并在能力降级时如实展示；
- `doc_id#block_id` 能解析为可展示、可点击的引用。

完整的工具契约、提示词结构、质量属性检查表和入库接口见：[检索侧设计完整记录](https://github.com/lipeidonggz/ai-study-helper/blob/v1.0/memory/0057-retrieval-pure-agent.html)。
