# LLM-Wiki 到底好在哪？从 WeKnora 的实测看：它本质是再编译一层，值多少取决于原语料结构

**副标题**：一个工业级实现、一份语料、五条路线、30 道题的实测记录

**先交代两个名词**：

- **LLM-Wiki**：标题里这个词，指《Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki》（arXiv:2605.25480）提出的那套做法——把语料**编译**成互相链接的 Wiki 页，再把**检索自主权交给 LLM**（让模型自己搜、读页、顺着链接跳）。**本文把这篇论文当参照（主要出现在 §5），不当主线**——主线是下面这份实测。
- **WeKnora**：本文的被测对象（腾讯开源的检索增强知识库），选它的理由见 §1.1。

**系列位置**：本文是"LLM-Wiki 拆解"系列的第三篇（总论 → 编译篇 → **检索篇**）。前两篇分别拆了那个主张和它的编译；这一篇拆最后一个机制：**检索**。

---

## 0. 结论先行

LLM-Wiki 本质上是对知识做**再编译**——把原始文本编译成"适合 LLM 使用"的结构（条目化、互链、可枚举、可遍历）。所以它比 Agentic 好多少，**取决于原语料还剩多少"不规整"可以编译**：原文越规整，这一层能带来的增益越不明显。

**我们实测的结果和这个判断一致。** 三句话：

| | 结论 |
|---|---|
| **① 这份语料让编译层几乎无事可做** | wiki 路线 0.601 vs 同代 agentic 块检索 0.595——只差 **0.006**，而且换口径还会翻号（§4） |
| **② 但"把检索权交给 LLM"本身是有用的** | 对经典单次检索领先 **+0.26**；机制是"能多轮去找"，不是"检索器更聪明"（§2、§6） |
| **③ 论文那边量到的是另一个数量级** | 它的消融里"去掉 Wiki 结构"掉 **0.061～0.070**，约是我们实测的 11 倍；四条解释都验不了——论文没给源码（§5） |

**一句话**：**"LLM-Wiki 更好"这句话成不成立，一要看原语料有多"不规整"，二要看对手是谁。**

### 先说清：这两件事的证据地位不一样

- **"对手是谁"是真对照**：同一个实现、同一份语料、同一个回答模型，只换对手，结论就变（数字见 §2.1、结论见 §2.2）。
- **"语料结构"我们只有一份语料**：所以 §3 是先给命题、§4 是"这份语料落在命题的哪一格"，不是跨语料对照。

### 三条边界

1. **单语料**：MuSiQue 的 30 道题（2／3／4 跳各 10 道），而且它偏难（2/3 的题是 3–4 跳）。
2. **单模型族**：所有对照都在 DeepSeek 家族内（`flash` ⇄ `v4-pro`），跨家族没测。
3. **没做消融**：没做"给经典管线同等预算的多轮检索"那一步。"赢在遍历"是**三条排除之后的推断**（§6.1 末尾有专门口径）。

## 1. 怎么测的

### 1.1 被测对象：为什么选 WeKnora

被测的是 **WeKnora**（`Tencent/WeKnora`，Go 实现，本地锁定 `v0.8.2`），向量模型 `qwen3.7-text-embedding`、重排 `qwen3-rerank`、对话模型 `deepseek-flash`。

选它有两条理由，一条是技术性的，一条是工程性的。

**技术性理由：它把"编译成 Wiki 页面，再让 agent 遍历"和"经典块检索"做在同一个产品里。** 这让我们能在同一份语料、同一个回答模型下，把五条路线横向摆开——而不是拿两个不同项目的数字互相猜。

**工程性理由：它是一个成熟的工业级产品，不是论文的参考实现或教学项目。** MIT 许可；**2,569 个 Go 文件、约 65 万行，其中近一半（1,229 个）是测试文件**；12 条 CI；Helm／Docker Compose／Homebrew／小程序／CLI／MCP Server 一套交付面；CHANGELOG 里单版本就有几十项改动，PR 编号已到 **#3589**。这带来两个后果：一是它的行为足够"真实"，值得当选型对象；二是**它迭代很快，所以本文锁定了版本号**。

顺带交代候选比较：我们也看过更贴 Karpathy 那一版描述的候选（`nashsu/llm_wiki`），但**它的检索侧没有 agent 工具循环、也没有逐步可观测性**，只能当"编译实现对照"。⇒ 在我们能找到的开源实现里，**同时具备"编译成页面"与"agent 工具循环"、且带逐步可观测的，只有它。**

### 1.2 语料：先看它长什么样

题来自 **MuSiQue** 的可答子集，取 2／3／4 跳**各 10 道**（刻意分层，为的是看趋势），语料是这 30 道题涉及段落的并集：**572 个段落文件**。

| 维度    | 实测值                                                                                                                            |
| ----- | ------------------------------------------------------------------------------------------------------------------------------ |
| 段落大小  | 字符数中位 **464**、最大 1,858 —— **短段落**（一段≈2–5 句）                                                                                    |
| 段落与实体 | **一个实体≈一段**（文件名就是条目名）                                                                                                          |
| 编译产物  | **4,094 页** ＝ 摘要页 572（与 572 个源段落**1:1**）＋ 实体页 2,820 ＋ 概念页 701（后两类是从正文里**抽出来并跨源聚合**的派生页，正文中位仅 263／322 字符）＋ 索引 1；页间链接 **23,393** |
| 题面直给  | 金标段落的标题**字面出现在题面里**的占 **29%**（2 跳 **50%**、3 跳 30%、4 跳 18%）                                                                     |
| 入口难度  | 纯关键词检索（BM25，top-10）能覆盖全证据链的只有 **20%**                                                                                          |

**先说结论，后面会反复用到**：这份语料**对 wiki 友好**（短段落、一实体一段、题面常常直接点名实体），但它**链条很长**（2/3 是 3–4 跳）。前者利好"页面"，后者利好"遍历"。

### 1.3 五条路线

同一套输入（同一份语料、同一个回答模型、同一批 30 题），只换检索路径：

| 路线 | 检索路径 | 说明 |
|---|---|---|
| **A** quick | 经典 RAG，**无重排** | 向量＋关键词 → 一次生成 |
| **B** quick＋rerank | 经典 RAG，**加重排** | 上面那条加上 `qwen3-rerank` |
| **C** smart | **Agentic RAG** | agent 循环，工具＝块级检索（`search_knowledge`／`read_document`／`list_documents`） |
| **D** wiki | **Agentic Wiki** | agent 循环，工具＝页级检索（`wiki_search`／`wiki_read_page`／`read_document`） |
| **E** hybrid | 混合 | WeKnora 自带预设：wiki 导航 ＋ 块级引用 |

### 1.4 指标与口径

**主指标是 F1（词级）**：把预测答案与金标准归一化（小写、去标点）后切成词，算两者的**词级精确率与召回率**，取**调和平均**。它衡量的是"**答得像不像**"——**部分正确也给分**：金标准是 `Miller County` 时，回答 `Elden, Missouri is in Miller County` 也能拿到一部分分。这对本文很关键，因为多跳题的答案常常是一小段话而不是一个词。

配套还记三样：**EM（Exact Match）**——归一化后必须**完全一致**才算对，是"**答得对不对**"的严格版；**分跳（2／3／4 跳）的 F1**，用来观察趋势；以及**成本**——**每题 token**（从容器日志的逐次 usage 取，按 `purpose` 分类）、**端到端耗时**，agent 路线另记**工具调用次数**。每条路线**跑 3 轮**——理由见 §2.4，那是一件用错误判断换来的事。

## 2. 主结果

### 2.1 五条路线的三轮均值

| 路线                       | F1        | 抖动       | EM        | 2 跳      | 3 跳      | 4 跳      | 时延／题     | token／题   | 工具／题 |
| ------------------------ | --------- | --------- | --------- | -------- | -------- | -------- | -------- | --------- | ---- |
| A quick（无 rerank）        | 0.318     | 0.017     | 0.222     | 0.55     | 0.28     | 0.13     | **2.2s** | **5,029** | 1.3  |
| B quick＋rerank           | 0.316     | 0.031     | 0.244     | 0.55     | 0.23     | 0.17     | 3.6s     | 4,741     | 1.9  |
| D **wiki**               | 0.523     | 0.100     | 0.467     | 0.76     | 0.47     | **0.34** | 7.9s     | 90,035    | 17.8 |
| C **smart**（Agentic RAG） | 0.529     | **0.165** | 0.456     | **0.83** | 0.49     | 0.27     | 16.2s    | 298,125   | 20.0 |
| E **hybrid**             | **0.559** | 0.099     | **0.489** | 0.81     | **0.67** | 0.20     | 13.6s    | 246,661   | 17.2 |

> **表里的"抖动"是什么**：三轮 F1 的**最大值与最小值之差**。数字越小，说明这条路线在三次重跑之间越稳。本文多处用它来判断"某个差距值不值得当真"：差距小于抖动，就当它不存在。

> **EM 为什么也留在表里**：EM 只认完全一致，所以 EM 与 F1 的差距能回答一个具体问题——**F1 是不是被"部分匹配"抬高了**。这张表里 EM 普遍比 F1 低 0.06～0.10，且排序与 F1 完全一致，说明名次不是靠部分分堆出来的。唯一一处背离在 §6.1：换模型后 F1 不动、EM 反降——那是句式问题，不是知识问题。

**三条读数：**

1. **经典的两种做法没差别。** A（无重排）0.318 vs B（加重排）0.316——重排在这份语料上**没有可见增益**，却多花 60% 时延。
2. **agent 化是断崖式的**：0.32 → 0.52～0.56，**+0.20 以上**。成本也断崖：**token 涨 20～60 倍，时延涨 3～7 倍**（因为 agent 走的是"多次短调用"，不是"一次巨长调用"）。
3. **三条 agent 路线彼此的差距，落在抖动里**：0.523／0.529／0.559，最大差 0.036，而 agent 路线自己的抖动就有 0.10～0.17。

### 2.2 选型建议（先给结论，依据在后面各节）

先给结论，依据都在后面各节（括号里是出处）：

1. **基座还是"单次检索"的，如果有多跳检索的需求，把检索权交给 LLM 是划算的**：+0.26 F1，代价是 20～60 倍 token、3～7 倍时延。
2. **基座已经是 agent 的，先别急着再叠一层"编译成页面"。** 这类语料上实测增量只有 **0.006**（§2.3、§4）。先自问一句"**我要页面层解决哪一件事**"——本文的判断依据是 §3.1 那三条（文档是不是长到需要重组？同一实体是不是散落在多份文档里？问题用词与原文错位大不大？）；三条都"否"，就该预期增量接近零，本文这份语料正是三条全否。
3. **通用手段先做减法**：重排在这份语料上没有可见增益；top-k 加倍是**负收益**；换更强的同家族模型也**没有增益**（§6.1）。三样都试过了。
4. **深链上还需进一步提升**：4 跳一档，三条 agent 路线只有 0.20～0.34，且题目之间差异极大。

### 2.3 把 5 道有据可查的坏题剔掉

30 道题里有 5 道是"题本身有问题"（#13 题面词义陷阱、#16 证据是表格、#17 前提与语料矛盾、#25／#28 同链且中间实体不唯一）。剔掉后重算：

| 路线 | F1 | token／题（均值） | token（中位） | 时延（均值） | 时延（中位） |
|---|---|---|---|---|---|
| B 经典 | 0.340 | 4,765 | 4,903 | 3.0s | 2.6s |
| D wiki | 0.601 | 67,463 | 40,564 | 6.8s | 5.3s |
| C smart | 0.595 | 121,729 | **15,969** | 9.5s | **3.7s** |
| E hybrid | **0.631** | **57,787** | 24,007 | 8.1s | 5.6s |

**① F1：wiki 0.601 vs smart 0.595，只差 0.006。** 这是全文最重要的一行。

**② 成本：均值和中位的排序是相反的。**

- **均值看**：全 30 题时 wiki 最省（90k ＜ hybrid 247k ＜ smart 298k）；但**剔掉难题后 hybrid 反而最省**（57,787），wiki 退到第二。⇒ "wiki 更省"**不稳健**，取决于包里有没有会"点火"的题（附录 A.3）。
- **中位看**：**典型题上 wiki 反而是三条 agent 路线里最贵的**（42,676；剔题后 40,564），smart 最便宜（18,769／15,969）。时延同理（中位 5.7s vs 4.8s）。

⇒ 一句话：**wiki 是稳压器，smart 是赌一把。** wiki 的典型题贵一些、但不容易炸；smart 的典型题最便宜、偶尔炸穿。

### 2.4 为什么每条路线都跑 3 轮

因为**单轮结论在本实验里翻了四次**：

| 单轮得到的结论                                    | 多轮之后                              |
| ------------------------------------------ | --------------------------------- |
| 加了重排应该更好                                   | 0.316 vs 0.318，**无差别**            |
| hybrid 单轮最差（0.522），"没跑成 wiki-first"        | 三轮均值它**最高**（0.559）                |
| 换更强的模型（V4 Pro）F1 从 0.316 掉到 0.171，"强模型反而差" | 是被一个实现细节吃掉的，去掉后**升到 0.359**（附录 A.1） |
| 换模型后 Pro 单轮 0.359 ＞ flash，像"换模型有用"         | 三轮均值 0.330 vs 0.318／0.322，**无差别** |

⇒ 本文所有结论都用**多轮均值 ＋ 抖动**；单轮数字只在说明"为什么不能信单轮"时出现。

## 3. 命题：LLM-Wiki 的增益，取决于原语料还剩多少"不规整"

要把"LLM-Wiki 好不好"问成一个可检验的问题，先得看清它**本质上在做什么**：它是对已有知识做**再编译**——编译成一种"适合 LLM 使用"的结构：条目化的页、显式的双向链接、可枚举的目录、可逐步遍历的入口。

于是它的增益来源就清楚了：**它补的是原语料"不像知识"的那一部分。** 原文越乱（长文档里混着多个主题、同一实体散落在多份文档里、措辞与提问方式错位），这一层补得越多；反过来，**如果原语料本身就已经"像知识"了，这层编译就没有多少可补的**。

从这个命题可以直接推出一张预期表（**右列是推论，不是实测**）：

| 原语料特征 | 编译层能补什么 | 预期增益 |
|---|---|---|
| **长文档、主题混杂** | 切分、重组、摘要 | 大 |
| **同一实体散落多源** | 合并成页、建双向链接（跨源连接） | 大 |
| **措辞与原文错位大** | 提供结构化入口与遍历路径 | 大 |
| **短单元、一段一条目、题面直接点名** | 几乎没有可补的 | **趋近于零** |

**这张表本文没有做跨语料对照来验证**——它是外推条件，不是结论。但它给了本文一个可检验的方向：**我们这份语料落在哪一格？**（另一件事——对手是谁——见 §2 与 §5。）

### 3.1 什么语料会让它值钱（把上表展开，仍是推论）

要让"编译成页面"真正产生增量，语料至少得具备下面三条之一：

| 条件 | 为什么它会放大"结构"的价值 |
|---|---|
| **长文档** | 段落长到需要重组、摘要、切分时，编译才有内容可做（我们这份段落中位 464 字符，编译前后信息量几乎相等） |
| **跨文档关系多** | 同一实体／主题散在多份文档里时，页合并与双向链接才产生"跨源连接"的价值（我们这份的证据链只跨 2–4 段，题面还常常直接点名） |
| **措辞与原文错位大** | 问题用词与原文差异大时，字面/关键词进不去，才需要语义检索或遍历（我们这份 2 跳题有一半是字面点名） |

这份语料恰好三条都不具备——下一节就是把它落到数据上。

## 4. 实测：这份语料正落在"编译层没什么可补"的那一格

结论先放：**在这份语料上，"编译成页面"这一层本来就没什么可发挥的空间**——所以量到 0.006 并不意外。

### 4.1 三个输入侧事实，各自把什么压平了

三个事实（数值见 §1.2，这里不重列）各自压平的东西不一样：

| 语料事实 | 它压平了什么 |
|---|---|
| **短段落**（中位 464 字符，一段≈2–5 句） | **摘要页与源段落 1:1**（1,054 字符 vs 464 字符，就是那段的重写）⇒ 页面层没有"让证据更完整"的余地 |
| **一实体≈一段**（572 段↔572 个条目名） | **检索单元已经是知识单元**：问"某实体是什么"，原文本身就是一整条；抽出的 3,521 个派生页，其价值在"把散落多处的说法聚起来"，而这份语料是**短链型提问**（A 的 B 的 C 是什么），不是聚合型 |
| **题面字面点名**（金标标题字面出现在题面里 29%；2 跳 50%） | **入口那一跳退化成关键词题**——这对"任何能字面匹配的检索"都容易（wiki 的正则入口 ✓、经典路线的关键词分支 ✓、smart 的 hybrid ✓），**不是 wiki 专属优势** |
一个容易误读的地方：**572 个条目 → 4,094 页并不矛盾**。4,094 ＝ **572 个摘要页**（与源文档 1:1，就是那段的重写，正文中位 1,054 字符）＋ **3,521 个派生页**（从这 572 段正文里抽出来的实体/概念，正文中位只有 263／322 字符——比如 `entity/republican-party` 把散在好几段里关于共和党的说法聚成一页）

⇒ 所以这份语料不是"对 wiki 有利"，而是**把"结构"这个自变量摁平了**。

**而且"没赢"不能记在"页面层没建好"头上**：它不只是建好了 1:1 的摘要页，还建了 **3,521 个派生实体/概念页与 23,393 条链接**，每次返回都带出链/入链（§1.2、§5.4、附录 A.2 都核过）。

⇒ 与 §3 的命题一致：**这份语料落在"编译层没什么可补"的那一格**，所以 wiki 与 agentic 之间只有 0.006（§2.3）。

## 5. 那论文为什么那么好？

**如果你读过那篇论文，读到 §2 大概会卡一下**：它报的 MuSiQue 是 Dense 0.611 / LLM-Wiki 0.739（+12.9 个 F1 点）；更关键的是它的消融——"去掉 Wiki 结构"这一项，F1 掉 **6.1～7.0 个 F1 点**（论文原文 *"a consistent drop of 6.1–7.0 F1 points"*；换算成绝对值就是 **0.061～0.070**）。那是在说：**光"编译成结构"这一层就值 6～7 个点。**

我们量到的对应差距是 **0.006（＝0.6 个点）**——同一把尺子下**差约 11 倍，整整一个数量级**；而且这个 0.006 连正负都不稳：全 30 题时是 smart 领先 0.006，剔掉 5 道坏题才是 wiki 领先 0.006。

（量纲提醒：这篇论文全篇用"F1 点"，**1 点 ＝ 0.01 绝对 F1**。下面出现的数字一律换算到绝对值。）

这一节就是回答这个问题的。

### 5.1 先把我们这边的数字摆出来

| 对手是谁 | 结果 | 差 |
|---|---|---|
| **经典单次检索**（向量＋重排，top-10，一次生成） | wiki **0.601** vs 经典 0.340 | **+0.26** |
| **同代的 Agentic RAG**（同样 LLM 自主多轮，只是检索单位是块） | wiki **0.601** vs smart 0.595 | **+0.006**（落在抖动里） |

同一层页面、同一套工具、同一个回答模型，只换对手：**前者领先 0.26，后者领先 0.006。** 换句话说，"值不值"的答案，**主要是对手给的，不是方法给的**。

### 5.2 再看论文那边量的是什么

先看它主表里的对手：闭卷、BM25、稠密检索（**top-5 段落 ＋ 一次生成**）、RAPTOR、GraphRAG、LightRAG、HippoRAG 2——**七个里没有一个具备"LLM 自主多轮"的工具循环**（最接近的 HippoRAG 2 也只是在知识图谱上做多跳路由，不是让模型自己决定下一步看什么）。它报的 MuSiQue 是 Dense 0.611、LLM-Wiki 0.739（**+0.13**）。就主表而言，它赢的是我们上表里**第一种**对手。（它对 ReAct／IRCoT／Self-RAG 这类方法只在相关工作里做**定性**比较，附录 A 那张表是"知识组织范式"对照，不是实验。）

### 5.3 但它的消融和我们的实测冲突

论文的消融里有一组和我们最像的对照，**而它的结论和我们相反**。消融表里有一行叫"**去掉 Wiki 结构**"：**保留同一套 agent 框架**，只把检索底座从"Wiki 页 ＋ wikilink ＋ 目录索引"换成"**扁平块**"（模型仍然可以反复检索调用，只是拿到的是互不相连的块）。结果：F1 掉 **6.1～7.0 个 F1 点**（＝绝对 0.061～0.070）。那一行几乎就是我们的 **C（agent ＋ 块）对 D（agent ＋ 页）**——**它说结构值 6～7 个点，我们只量到 0.6 个点（0.006），而且符号不稳**。

### 5.4 这个冲突有四种解释，其中一种已经排除

先说**没被排除的四条**：

1. **对手不等价，而且不等价的方式很关键**：论文那个"扁平块"臂，是**把一套为页面设计的 agent 框架直接跑在块上**——它的遍历策略本来就依赖"先读目录索引拿到全局结构、再挑页读"（论文自己写了这句）；底座一换成互不相连的块，这套导航就没了依托，agent 只能盲搜。而我们的 smart 是**为块而生的 agent**（语义检索 `search_knowledge` ＋ `list_documents` ＋ `read_document`），是块检索的**强形态**。⇒ 我们比的是"两条各自拿手的路线"，它比的是"同一条路线只换底座"。
2. **题集构成不同**：它 57% 是 2 跳、我们 33%。但按我们的分层数据，2 跳恰恰是 smart 更强的那一档（0.826 vs 0.764）——**方向反了**，这一条非但解释不了 +6～7，反而放大了疑问。
3. **模型不同**：它统一用 GLM-5.1，我们用 DeepSeek。我们只排除了"同家族换更强模型"（§6.1），跨家族没测。
4. **两边的"Wiki"不是同一种东西**（这一条上一篇已经拆过）：论文的编译有它自己的选页机制、页面 schema 与 Error Book 回灌；而 WeKnora 的编译实测是**少一截的**——页内剥离极保守（源删掉后正文几乎不动，−45 字符起）、去重召回只比标题（别名不参与，会长孪生页）、删除之后没有重放路径、块级引用只增不减、目录跨批"混轴"、目录会漂移、删除留悬空链接；此外单篇输入 **32,768 字符截断**（超出的部分根本不产生新条目），还有几个规模常数（目录池 400／整池喂 ≤60／提示词里 150）。⇒ 论文消融里"去掉 Wiki 结构"掉 6～7 分，**未必等于"去掉 WeKnora 这层页面"也掉 6～7 分**。

**一条已经被排除的可能：不是"我们没给跳转能力"。** WeKnora 的 wiki 工具会把每页的 `[[slug|标题]]`、`<links_to>`／`<linked_from>` 出链入链列表、以及**保留 `[[…]]` 标记的正文**一起交给模型（实测：wiki 路线 801 个工具事件里 **562 个带链接字段**），`wiki_read_page` 的说明也明写"returns the full markdown content, metadata, and links… read specific pages when you know their slug"。**"页 ＋ 链接 ＋ 目录"这套结构在我们这边是齐的、可跳的**——所以论文那 6～7 分不能用"我们缺链接能力"来解释。

### 5.5 为什么这个冲突结不了案（我们也结不了，选型的人更结不了）

上面四条里，每一条都要动到论文那一侧；而**论文没有给出代码或复现声明**——我们手上这份 arXiv HTML 全文（含附录 A–H）里，`code is available`／`open-source`／`release`／`reproduc*` 的命中**全是 0**（仅有的几处 GitHub 字样是 arXiv 页面自带的"Report GitHub Issue"）。于是那 6～7 分**无法分解**成"编译质量／agent 框架／题集差异"各占多少。这不只是我们的麻烦，**也是选型者的麻烦**：他要判断"值不值得照论文实现一遍"，只能自己补上论文没写的那些东西（编译提示词原文、选页机制、命名与合并规则）。

⇒ 本文的立场不是"论文错了"，而是：**在这个实现、这份语料上我们量不到那 6～7 分，而这个差距在论文不给源码的前提下，谁都验不了。**

### 5.6 顺带一个旁证（另一件事：题集构成，不是语料内容）

顺带一条相关、但不完全同一件事的旁证：**除了语料内容，题目的构成也会左右结论。**

论文的 MuSiQue 用的是"**原始数据集顺序的前 500 条**"。我把 MuSiQue dev 数了一遍：可答 2,417 条（2 跳 1,252／3 跳 760／4 跳 405），而**前 500 条可答的构成是 57%／26%／17%**（偏 2 跳）；我们的题集是 **33／33／33**。把我们的分跳成绩按论文那个配比重算：F1 **0.331 → 0.416**（EM 0.244 → 0.316）。

⇒ 同一个方法、不同的题集构成，分数差 0.085——这也是为什么本文**不做**跨实现比绝对分数。

**所以这条线（语料）的结论落到一句话**：在这类语料上，结构的增量接近零；换到 §3.1 那三条具备的语料会怎样，我们没测，也不下结论。

## 6. 对手这一侧：那 +0.26 买到了什么（遍历，不是结构）

**这一节是 §2.2 第 1 条的机制依据**——它讲的是"对手是单次检索、还是 agent"这件事，与 §3–§5 那条线（语料结构）无关。

§2.1 那张表里，agent 路线领先经典 +0.26。这 0.26 买到了什么？**结论：买到了"能多轮去找"，而不是"检索器更聪明"。**

### 6.1 三条排除

**排除一：不是模型能力。**

做法：把**经典路线固定住**（quick ＋ rerank、top-k 10，同一份语料、同一批题，同一套改写提示词），**只换模型**，各跑 3 轮。因为**改写也由模型执行**，所以要同时看两个位置——下表第一列的"作答／改写"就是这两个位置，三个组合分别是"都弱／只把作答换强／都换强"。

（这一节的 0.330 比 §2.1 的 B 路线 0.316 略高，差别来自这里改用了一套更短的改写提示词、顺手关掉了附录 A.1 那条"意图闸门"。两组数据各自的三轮都稳定。）

| 模型组合（作答／改写） | F1 | 抖动 | EM | 时延 | token／题 |
|---|---|---|---|---|---|
| flash／flash | **0.330** | 0.017 | **0.244** | **2.5s** | 2,845 |
| Pro／flash | 0.318 | 0.056 | 0.189 | 2.8s | 2,853 |
| Pro／Pro | 0.322 | 0.066 | 0.189 | 3.3s | 2,874 |

**没有增益。** 更硬的一条：**30 题里有 21 题，两个模型的三轮均值完全相同**——它们在**同一批题上一起对、一起错**（差的只有 4 题，2 题偏 flash、1 题偏 Pro、1 题基本抵消）。

顺带一个格式细节：Pro 的 EM 反而更低，因为它爱写成整句 `Paul Bettany's spouse is Jennifer Connelly.`——EM 判 0，F1 给满分。所以那不是知识差，是句式差。

**排除二：不是"给更多上下文"。**

把经典路线的 top-k 从 10 调到 20，各跑 3 轮：

| 配置 | F1 均值 | 含答案的块进了上下文 | 进上下文的块数 |
|---|---|---|---|
| A · top-k 10 | **0.318** | 14/30 | 8.4 |
| A · top-k 20 | 0.293 | **18/30** | 16.9 |
| B · top-k 10 | **0.316** | 14/30 | 6.8 |
| B · top-k 20 | 0.286 | **17/30** | 11.0 |

**证据量确实上去了（14/30 → 18/30，+29%），但 F1 反而降了**，而且降幅集中在 4 跳。⇒ **瓶颈不在"能不能找到"，而在"找得准不准"**：k 翻倍后多塞进来 8–10 条块，却只让 4 道题补到了答案句，其余大半是干扰段——信噪比一掉，模型反而被带偏。

**排除三：不是"单次检索做得不够好"。**

把 9 轮 × 30 题按"金标段落有几段进了上下文"分桶（我们的语料一段一文件，所以标题匹配＝段落匹配）：

| 覆盖情况 | 题次 | F1 |
|---|---|---|
| 金标段落**全命中** | 108/270（**40%**） | **0.520** |
| 部分命中 | 135/270（50%） | 0.206 |
| 全未命中 | 27/270（10%） | 0.129 |

分跳看：**全链命中率 2 跳 70%、3 跳 30%、4 跳 20%**；**30 题里有 16 题，在 9 轮里一次都没凑齐过完整证据**。

原因是结构性的：**多跳题的远端段落与题面没有词面/语义重叠**（问题只提到第一跳的实体，中间实体根本不出现），所以靠一次 query 的 top-k 永远够不到。我们试过把 k 从 10 提到 20，远端那一段还是不在。

### 6.2 正面证据：迭代抹平了"检索器强弱"的差距

我们在这份语料上离线跑了一个**纯关键词检索器**（BM25，top-10），和实测的经典路线对照：

| 单次检索器 | 全链命中 | 2 跳 | 3 跳 | 4 跳 |
|---|---|---|---|---|
| BM25（纯词袋） | **20%** | 5/10 | 1/10 | 0/10 |
| 标题字面命中优先 ＋ BM25 补足 | **20%** | 5/10 | 1/10 | 0/10 |
| **经典路线**（embedding ＋ rerank，9 轮 270 题次实测） | **40%** | 70% | 30% | 20% |

⇒ **单次检索这一步，语义的贡献约两倍**（而且 BM25 进窗口的是 10 个**整段**，经典路线是 10 个**块**≈7 段——槽位更少、覆盖反而更高）。把两种入口与"能不能多轮"合起来排：

- 单次关键词 → 全链 **20%**
- 单次语义 → 全链 **40%**
- **关键词入口 ＋ 迭代**（wiki）→ F1 **0.601**
- **语义入口 ＋ 迭代**（smart）→ F1 **0.595**

**语义与关键词之间那道两倍的沟，被"能不能多轮去找"抹平了。**

### 6.3 这个增益的形状：不随深度增长

| 跳数 | 经典（B） | wiki | smart | **agent 领先幅度** |
|---|---|---|---|---|
| 2 跳 | 0.55 | 0.764 | 0.826 | **+0.21 ～ +0.28** |
| 3 跳 | 0.23 | 0.470 | 0.492 | **+0.24 ～ +0.26** |
| 4 跳 | 0.17 | 0.335 | 0.268 | **+0.10 ～ +0.17** |

**领先幅度在 2–3 跳就封顶，到 4 跳反而缩小。** ⇒ agent 化的增益**不随深度增长**，不是"越难越有用"。（4 跳上，连经典路线的全链命中都只剩 20%，agent 的绝对分也只有 0.27～0.34——**深度是硬约束**）

## 7. 选型结论，以及结论的边界

### 7.1 结论

1. **有多跳问题、又不想上知识图谱的 → Agentic 是更好的选择。** 它对经典单次检索是 **+0.26 F1**，代价是 20～60 倍 token、3～7 倍时延（§2.2）；而且不需要为语料先付一次编译成本。
2. **要不要再叠一层 LLM-Wiki，先用"语料结构"做初判。** 问三个问题：文档是不是很长？同一实体是不是散在多份文档里？问题用词与原文错位大不大？**三条都"否"，编译层的增益预期就接近零**——本文这份语料正是三条全否（§3、§4）。
3. **但初判只是初判，必须做测试验证。** 本文自己的实证是：同一个 0.006 会随口径翻号、4 跳上三条路线只有 0.20～0.34、同一道题连跑 8 次成本差 19 倍（§6.3、附录 A.3）。这类系统的选型证据，不能是"跑一次看看"。
4. **"把一次检索做得更强"没用，"改成多轮检索"才有用。** 三件常规手段都试过了——加重排、把 top-k 翻倍、换更强的同家族模型，在这份语料上都没有增益（§6.1）；而 +0.26 那部分收益只出现在**结构变化**上（单次检索 → 多轮检索，§6.2）。

### 7.2 三条边界（结论不能外推到哪）

1. **一份语料**：MuSiQue 30 题，偏 3–4 跳，而且**把"结构"这个变量压平了**（§4.1）。所以这次观测能推翻"编译成页面普遍有效"，但**不能**推出"编译成页面在别的语料上也没用"——那需要 §3.1 里那三条具备的语料，本文没有。
2. **一个模型族**：所有对照都在 DeepSeek 家族内（`flash` ⇄ `v4-pro`）。跨家族（比如换成别的厂商的强模型）没测；本文能说的只是"同家族换更强"这条不成立。

## 8. 一个更一般的教训：Agent 选型，判断力与验证方法比"结论"更重要

做完这一轮，比"wiki 好还是 agentic 好"更值得留下的是方法论上的一个变化：

**Agent 类系统的"好不好"没有普适答案——它同时取决于数据形态、业务问题的形态、以及对手是谁。** 于是选型的重心从"挑一个更强的方案"，变成"**按自己的数据与业务特点做判断，再用小心的验证方法把判断钉住**"。本文自己就是这条的实证：

- **单轮结论会骗人**：本实验里四次单轮反转（重排、"hybrid 最差"、换模型、换模型后单轮看着领先）（§2.4）；
- **同一个数会翻号**：wiki 与 agentic 的 0.006，全套 30 题时是对方领先、剔掉坏题才反过来（§2.1、§2.3）；
- **同一个系统的成本能差 19 倍**：同一道题连跑 8 次，0.43M～8.13M token（附录 A.3）；
- **换模型会改路由**：换模型后 9/30 题被一个提示词判成"需要联网"，整轮不检索（附录 A.1）。

⇒ 这些都不是"哪个方案更强"的问题，而是"**验证得够不够小心**"的问题。

## 9. 下一步的引子：三条路线各占一段

30 题这个样本够小，所以我们做了一次逐题拆解——拆出来的东西指向一个更有意思的问题：**它们的优势是互补的。**

### 9.1 30 题里只有 3 题分化

按"3 轮里对 ≥2 轮"判定：

| 判定 | 题数 |
|---|---|
| 两条路线都对 | **17** |
| 两条路线都错 | **10** |
| wiki 主场（wiki 对、smart 错） | **2**（#20、#21） |
| smart 主场（smart 对、wiki 错） | **1**（#9） |

⇒ **27/30 同命**——这是"两者无显著差异"最直观的表述。

### 9.2 但分层看，三条路线各占一段（而且三轮内一致）

| 跳数 | wiki | smart | hybrid | 最强 |
|---|---|---|---|---|
| 2 跳 | 0.764 | **0.826** | 0.811 | **smart**（也最稳） |
| 3 跳 | 0.470 | 0.492 | **0.669** | **hybrid**（三轮全胜） |
| 4 跳 | **0.335** | 0.268 | 0.198 | **wiki**（三轮全胜） |

分化题的现场也各自有故事：#9（2 跳）smart 三轮全对且极省（工具 4/8/4），wiki 答对那一轮用了 **34** 次工具；#20（3 跳）hybrid 3/3、smart 1/3；#21（4 跳）**三条路线全在摇摆**（wiki 错-对-对、smart 对-错-错、hybrid 错-错-对）——证据都在，胜负取决于最后的取舍，是采样问题不是能力差异。

### 9.3 三个待解问题

有意思的是 **hybrid 路线本身就是一次融合尝试**，而它的分层表现恰恰说明这个融合方式不对：它在 3 跳赢麻了，却在 **4 跳上比两条纯路线都差**。于是下一步的问题很具体：

1. **"按预期跳数路由"这条，前提不成立。** 跳数在提问时**不可观测**——用户不会告诉你这题要几跳，题面本身也不透露（这正是多跳题的设计目的）。所以"先估跳数、再选入口"得先解决"**估跳数**"这个独立课题；而猜错的代价不小——3 跳题给 wiki 是 0.470、给 hybrid 是 0.669（§9.2）。⇒ 要做融合，**先从下面两条（机制）入手，再去找可观测的路由信号**。
2. **为什么融合之后在深链上反而最差？** 是导航策略在深链上过早收敛／被页级摘要带偏，还是预算分配问题？
3. **wiki 在深链上的优势到底来自哪？** 是页间链接能"接力"（结构），还是它更早止损、不瞎猜（页检索 48.6% 返回空，附录 A.3）？这两个机制对应**完全不同的改法**。

（口径提醒：每档只有 10 题 × 3 轮，所以"各自主场"方向明确但样本小，宜读成"分层上呈互补态势"。）

## 附录

### A. 被测实现的四个真实行为

这一节不是"该不该用 LLM-Wiki"的问题，而是**"这个实现实际上怎么跑的"**。四件都是被数据撞出来的，**也都不是我们环境搭歪——它们是被测系统的一部分，所以我们没有改掉它**。

### A.1 一段提示词 ＋ 一处代码，就能让"整轮不检索"

现象：换成更强的回答模型后，有一条路线的成绩从 0.316 **暴跌到 0.171**。30 题里 **9 题**回答成"我无法联网／请补充信息"，而那些题的**检索结果为空**——**根本没检索到任何东西**。

日志里的直接原因：

```
stage=QueryUnderstand action=prompt_override intent=web_search
stage=SearchParallel   action=skip reason=intent_no_search
```

机制是两段：

1. **提示词**：默认的改写提示词是"三合一"模板（改写／意图分类／图片描述），意图 9 类、"从上往下取第一个命中"，**`web_search` 排在 `kb_search` 之前**；而 `web_search` 的判据是 *"asks for real-time, latest, or external information **unlikely in the knowledge base**"*——**这是一个关于知识库内容的判断，而这段提示词里没有任何知识库信息**（只注入当前时间、用户问题、输出格式）。模型只能拿"话题先验"顶替：影视、歌曲、体育、历史、带 "newly/latest" 字样的问法，就判 `web_search`。
2. **代码**：`NeedsRetrieval()` 里，`intent == web_search` 时直接返回 `WebSearchEnabled`。我们的请求没开 web 搜索 ⇒ 返回 false ⇒ **块检索和实体检索一起被跳过**。判错一次，整轮断供。

**它的规模**：13 个经典轮次 × 30 题里，**34 题次被跳过（8.7%）**；而且**不是随机**——#19 在 12/13 轮里被判错（"newly declared independent country" 勾住了 real-time），#27／#7 则在同一个模型下来回翻（这一步的调用硬编码了 `temperature: 0.3`）。换模型则整体换一批题踩（Pro 那轮 30%）。

**为什么值得写**：这不是"某个模型不听话"，而是**产品行为**——用户问一个知识库问题，有一定概率被系统判成"这需要联网"，然后什么都不查。而且**同一条 agent 路径根本不走这一步**，所以这个坑只在经典管线上存在。

### A.2 每个文档会多出一个"摘要块"，而且它参与检索

核对检索结果时发现的：**经典路线拿回来的上下文里，平均 1/4 是"某段的中文改写"**。22 个经典轮次合计 6,026 条引用 ＝ text 4,542 ＋ **summary 1,484（24.6%）**，各轮稳定在 23–27%。

来源是入库流程：每个文档入库时，WeKnora 会调一次 LLM 生成文档画像（`{summary, gist, topics, doc_type, typical_question}`），把 `summary` 写进文档描述，**再新建一个 `chunk_type=summary` 的块并索引进向量库**。我们这份语料是英文、租户语言是中文，所以这些摘要块是**中文**的。

**它的实际代价**：把这 1,484 条剔掉重算，金标段落覆盖从 1,128 掉到 1,060——**摘要块的"独家"贡献只有 68 段（6%）**，而它占了 24.6% 的槽位 ⇒ **约 94% 是冗余占位**（那段本来就有原文块被检索到）。

**为什么没修**：因为**我们比的是 WeKnora 的实现**——先把它改掉再比，测的就不是它了。这条作为"被测系统的行为"记下来（它同样影响任何"中文租户 + 英文语料"的场景）。

### A.3 成本没有上限，只有"配置给的一堵墙"

我们拿一条腿上最凶的那道题（4 跳，#28）**连着跑了 8 次**（同 agent、同知识库、同提示词）：

| | 总 token | LLM 调用 | 用时 | 收尾 |
|---|---|---|---|---|
| 最省的一次 | **434,193** | 10 | 19s | 直接给答案 |
| 最贵的一次 | **8,133,131** | 45 | 246s | "我搜遍了知识库" |
| 其余 6 次 | 632k ～ 7.44M | 14 ～ 49 | 29 ～ 205s | 混合 |

**同一道题，成本差 19 倍；八次全错。** 而且方向反直觉：**便宜的那几次是"直接作答"，贵的那几次是"反复搜索后放弃"——花掉的 token 买的不是答案，只是它多确认了几遍自己找不到。**

三条附带结论：

1. **"越跑越贵"是抽样幻觉。** 我们一度看到三轮成本单调上升（1.97M → 2.36M → 3.77M），但**后 5 次连着跑**的跨度依然是 17 倍（7.44M → 0.43M）——跟时段、外部负载都无关，就是每次独立抽样。
2. **上限是配置给的。** 最贵那几次几乎都正好撞在各自的 `max_iterations` 上（wiki 30、hybrid 40、smart 50）。最坏成本 ≈ `max_iterations × 每轮上下文`（wiki≈0.9M、hybrid≈6M、smart≈8M）。**这个天花板是一个配置参数，不是模型自己收敛出来的。**
3. **根源是"没有否信号"。** 块级检索几乎不返回空（0.5%），所以 agent 提的每个问题看起来都有结果、**没有"这里没有"的信号**；页级检索有 **48.6% 返回 0**，wiki 路线因此更容易止损。**同一个"停止"问题，两条路线表现完全相反**——这是机制层最值得继续挖的一条。

### A.4 纠错层：有台账，没有回灌；而且台账没被用过

这一层的实现是「体检 ＋ 自动修 ＋ 台账」，缺的正是最关键的"回灌"：

| 常见纠错机制该有的成分 | WeKnora 有吗 |
|---|---|
| 自动发现（体检） | ✅ `RunLint`：孤儿页／断链／失效引用／缺交叉引用／空内容／重复 slug 六类，带 severity 与 `auto_fixable` |
| 自动修（只修确定性那部分） | ✅ `AutoFix`：只碰 `auto_fixable` 的，例如剥掉指向已删知识的引用、该页再无活源就删页 |
| 问题台账 | ✅ `wiki_page_issues` 表（slug／issue_type／description／suspected_knowledge_ids／status）＋ `wiki_flag_issue`／`wiki_read_issue`／`wiki_update_issue` 三个工具 |
| **把反复犯的错写成约束、回灌下一轮编译** | ❌ **没有**——全仓没有任何编译路径读这张表 |

**实测：台账从未被写过。** 三层证据：

1. **工具当时确实在手里**——运行时日志里 wiki 路线的 `allowed_tools` 是 `["wiki_search","wiki_read_page","read_document","wiki_flag_issue"]`（出现 82 次）。这一步专门核过：代码里有个 `withoutWikiWriteTools()`，会在"没有可写 wiki 库"时把 `wiki_flag_issue` 剥掉；**实测它没被剥**，所以不是权限挡掉的。
2. **调用次数为 0**——所有问答记录里，wiki 路线的工具构成是 `wiki_search` 1018 ／ `wiki_read_page` 428 ／ `read_document` 156，`wiki_flag_issue` **0 次**。
3. **产出为 0**——`wiki_page_issues` 表全库 **0 条**，`wiki-stats` 的 `pending_issues` 也是 0。

**边界**：这说的是"在我们这个使用强度下（30 题 × 3 轮 × 3 条 agent 路线 ＋ 一次 572 段的编译）一次都没发生"，**不是**"功能坏了"或"永远不会被用"。

**读法**：**一个只有"记录"、没有"回灌"的纠错机制，在实际使用里很可能就是没人会去写的那张表。**

### B. 材料、口径与复现

**被测对象**：`Tencent/WeKnora`（标准版 Docker Compose），对话模型 `deepseek-flash`（对照用 `deepseek-v4-pro`），向量模型 `qwen3.7-text-embedding`，重排 `qwen3-rerank`（DashScope）。

**语料与题集**：MuSiQue 可答子集，取 2／3／4 跳各 10 题（30 题）；语料＝这 30 题涉及段落的并集，**572 个段落文件、1,408 个块**（836 个 text ＋ 572 个 summary）。Wiki 编译产物：**4,094 页**（摘要 572／实体 2,820／概念 701／索引 1）、页间链接 23,393、孤儿页 3。

**五条路线**：A `quick`（无重排）／B `quick＋rerank`／C `smart`（Agentic RAG，`search_knowledge`／`read_document`／`list_documents`）／D `wiki`（Agentic Wiki，`wiki_search`／`wiki_read_page`／`read_document`）／E `hybrid`（`hybrid-rag-wiki` 预设）。每条路线 **3 轮 × 30 题**。

**口径声明**：

- **token** 取自容器日志的逐次 usage（带 `purpose` 与 `session_id`），按 `(时间戳, purpose, prompt, completion, session)` 去重后按题聚合；"每题 token"＝ prompt ＋ completion。
- **抖动** ＝ 三轮 F1 的最大值与最小值之差（不是标准差）；表头出现时亦同此义。
- **"剔 5"** ＝ 剔除 5 道有据可查的坏题（#13 题面词义陷阱／#16 证据是表格／#17 前提与语料矛盾／#25＋#28 同链且中间实体不唯一）。
- **时延** ＝ **端到端耗时**：从发起请求到 SSE 流结束为止（含检索与生成，不含排队与客户端渲染）；**工具调用**与 **LLM 调用**分开记（一次 LLM 调用可含多个并行工具调用，所以工具数远大于调用数）。
- **"全链命中"** ＝ 该题所有金标段落都有至少一个块进了上下文，按标题匹配（一段一文件）。
- **纯关键词对照**是我们**离线**在同一份 572 段语料上跑的 BM25（k1=1.2, b=0.75, top-10），**不是** WeKnora 的行为。
- **"语料/题集特点"这一项只有一份语料**：§4 给的是画像 ＋ 边界 ＋ 一个题集构成的旁证，不是跨语料对照。

**复现路径**（脚本在本仓库 `experiments/weknora/`）：`download_musique.py`（取数）→ `prep_musique_corpus.py`（切 30 题与语料）→ `weknora_musique.py`（建库／投喂／编译）→ `weknora_qa_eval.py`（`agents`／`ask`／`score`／`recall`／`tokens`／`mkarm`）。数据产物在 `data/tmp/weknora-musique/`。

**同系列**：《把知识库编译成 Wiki，再把检索权交给 LLM》（总论）·《能增、能删，但不幂等：拆开 WeKnora 的知识编译》（编译篇）· 本篇（检索篇）。
