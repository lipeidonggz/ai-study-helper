# 一个连文档都没有的 GraphRAG 功能：我把 Dynamic Community Selection 逐行核了

> **30 秒判断**：本篇基于 `graphrag 3.2.0`。上一篇说到 Global Search 有个结构性麻烦——**"这次该看多细"这个判断被外包给了用户，而用户手里只有一个失准的层号**。GraphRAG 其实留了另一条路：**Dynamic Community Selection**，它把这层判断从用户手里收回来，交给系统按问题逐社区打分。我把它的算法、打分器、三组实测和一年半的功能史都核了一遍。结论：**方向是对的，但它现在还不具备被直接依赖的条件**——官方文档提它 **0 次**，打分提示词**不可配置**，而"打分失败"的默认值与"判定相关"的阈值**恰好是同一个数**。
>
> **一句话结论**：它换掉的只是第 0 步（选材料），后面四步原样复用。代价是所有成本从本地变成"每个候选社区一次 LLM 调用"——而且**越不相关反而越贵**，因为根层全军覆没时会触发"整层全评"的兜底。
>
> **适合谁读**：正在用 GraphRAG 做全局问答、并且被"选哪一层"折磨过的同学；也适合任何想在设计里加"自适应粒度"的人——它踩到的坑很有代表性。
>
> **阅读成本**：约 14 分钟。1–3 节是机制与算法；4 节是三组实测；5 节是打分器的实测与局限；6 节是成熟度信号清单。
>
> **证据标记**：**✅ 实测**（本文四组实验）· **📄 源码**（`graphrag 3.2.0`）· **📎 官方文档／GitHub** · **🤔 推断**。

---

## 0. 为什么单独看它

上一篇的结论是：Global Search 让用户填"社区层级"，而这个旋钮**在结构上做不到它承诺的事**——它不等于"只取某一层"，也不保证"调大就更细"。

那有没有别的路？有。GraphRAG 里有一条可选路径，思路完全不同：**别让用户猜，让系统按问题一个社区一个社区地判断"这份材料要不要"**，要就收下、并继续往下看更细的子社区。

这条路叫 **Dynamic Community Selection**。它有几个值得先知道的特征：

- **默认关**，得显式开（CLI 是 `--dynamic-community-selection`）；
- **官方文档几乎没写它**——`docs/query/global_search.md` 里 "dynamic" 出现 **0 次**；
- 它的选择逻辑**一年半没动过**（功能史见第 6 节）。

所以"它能不能替代层号"这个问题，只能自己读代码回答。下面是我核出来的东西。

---

## 1. 它只换了第 0 步

先把位置放准：Global Search 一共五步（选材料 → 装配上下文 → map → reduce → 返回）。**Dynamic 只替换第 0 步**，第 1–4 步一个字节都没改。

两条路的差别只有"材料从哪来"：

| | 默认路径 | Dynamic |
| --- | --- | --- |
| 选材料的方式 | 用户填层号 N ⇒ 取 `level <= N` 的全部报告 | **从根层开始，逐社区按问题打分**，相关的收下并下探它的子社区 |
| 输出形状 | 固定范围的报告集合 | **一组可能跨层的社区**，父子通常二选一 |
| 成本 | 纯本地（读表） | **每个候选社区一次 LLM 调用**（× `num_repeats`） |
| 谁来做"该看多细"的判断 | 用户 | 系统 |

算法本身很短（📄 `query/structured_search/global_search/community_context.py`）：

```text
起点 = level 0 里"有报告"的社区
循环：
  并发给队列里每个社区打分（0–5）
    ≥ threshold(默认 1) ⇒ 收进结果 + 把它的 children 入队
    keep_parent=False   ⇒ 把这个社区的 parent 从结果里剔除
  队列 = 下一轮要评的子社区
直到队列空
```

三个直接推论：

1. 输出是**一组可能跨层的社区**，不是一个层；
2. `keep_parent=False` 做的恰好是"**子相关就丢父**"——和上一篇讲的默认路径里那个失效的 roll-up 是同一个语义，**这里反而是生效的**；
3. 选出来的报告之后仍走同一套装配（打散、切批、map、reduce），所以那些损耗**原样继承**。

### 1.1 一条容易漏读的兜底机制

如果某一轮队列空了、而且**至今一个相关社区都没有**，并且下一层存在且 `<= max_level`，代码会把**那一层的所有社区**塞进队列，再评一轮。

设计意图像是"保底召回"。但它的成本方向跟人的直觉相反——下一节单独说。

---

## 2. 打分器：四件必须知道的事

这一环是整个功能里最值得核的部分，因为它同时决定了"收哪些"和"花多少钱"。

| 事实 | 含义 |
| --- | --- |
| 提示词要求打 **0–5** 分，返回 JSON `{reason, rating}` | 别再信函数 docstring 里那句 "0 to 10"，那是过期的 |
| 评的"材料"默认是**报告全文**（`use_summary=False`） | 我们的库里 `full_content` 平均 2,934 字符、最长 4,870 ⇒ **每次打分的 prompt 都不小** |
| `num_repeats > 1` 是**多数投票** | 取票数最多的那个值（并列取小），**不是取平均**——"重复几次取均值"是想当然 |
| **JSON 解析失败 ⇒ 默认给 1 分** | 代码注释写着 "so the report is kept"。而**默认阈值正是 1** ⇒ 一次失败的调用等于"判定相关"：既收下它，又继续下探它的子社区 |

最后一条是这条路最值得写成文章的失败模式：默认路径的失败是"**丢一批**"（安静地少一块），这里的失败是"**多花一轮 ＋ 引入噪声**"（安静地变贵、变脏）。

还有两件事是我查完才确认的：

- **打分提示词不可配**。`graphrag init` 生成的配置里只开放了 `map_prompt` / `reduce_prompt` / `knowledge_prompt` 三项，`DynamicCommunitySelection.__init__` 虽然有个 `rate_query` 形参，但工厂函数不传它。（📄 `query/factory.py`）
- **打分是孤立判断**——一次只把一份报告和问题丢给模型（"这份材料对回答这个问题有帮助吗？"），**不跟别的社区比**。好处是它天生没有"批内相对分不可比"的毛病；代价是阈值必须独自承担"多少算够"的绝对尺度，而它默认只有 1/5，是个没有任何先验的裸参数。

### 2.1 已钉住的三个坑

1. **有社区没有报告 ⇒ 剪枝到那里就断。** 我们一份语料里 64 个社区只生成了 **52 份报告**（缺 12 个）。翻索引日志，同一个 run 里正好 12 条 `No report found for community`，名单与缺失清单**一个不差**。而 `DynamicCommunitySelection` 只把"有报告"的社区放进层级表，遇到没报告的子社区**只在 debug 日志里跳过**——代码里还留着一句 `TODO check why some sub_communities are NOT in report_df`。
2. **根层空 ⇒ 构造就炸。** 构造函数直接取 `self.levels["0"]`：如果索引里根层一个社区都没有报告，这里会 KeyError。我们根层 13 个社区只有 12 份报告，**刚好没踩上**。（📎 上游 issue #2382 报的就是这个；对应的修复 PR #2413 **已关闭、未合入**。）
3. **`level` 是字符串。** 数据模型是 `str`、读表时转字符串、算法里也用 `self.levels[str(level)]` ⇒ 配置和日志里的 `"2"` 与 `2` 不能混着理解。

另外一条不算坑但值得知道：算法回传的统计只有 `llm_calls / prompt_tokens / output_tokens`，**逐社区的评分明细 `ratings` 只进 debug 日志**，不上浮给调用方——想拿它做分析得自己接日志。

---

## 3. 一个反直觉的成本曲线：越不相关，反而越贵

把第 1 节那条兜底机制和打分规则放在一起看，会得到一个跟直觉相反的曲线：

- **问题跟语料高度相关**：根层几个社区都高分 ⇒ 收下它们、继续下探 ⇒ 只沿着相关分支往下走，**很快就收敛**；
- **问题跟语料完全不相关**：根层全军覆没 ⇒ 触发"整层全评"的兜底 ⇒ 逐层放大到 `max_level` ⇒ **把每一层的社区都评一遍**。

也就是说，**"没有相关内容"这种最该便宜的情况，反而是最贵的**。这一点在第 4 节的跨域实验里被实测证实了。

顺带说清 `max_level` 的角色：它**不是主控**。真正决定"下探到多深"的是打分结果；`max_level`（默认 2）只在这条兜底路径上当上限用。同理，老的 `community_level` 参数在这条路上语义变成了 **cap**——读表时仍按 `level <= N` 先砍一刀，只是跳过 roll-up。

## 4. 三组实测

实验条件：一份 7 篇中文技术笔记的小语料（32,363 token），索引出 **143 个社区**；查询用 `community_level=2` ⇒ 默认路径要扫 **141 份报告**。每组问题都跑"默认路径 vs Dynamic"两遍，比 `llm_calls`、prompt token、**选中的社区集合**、map 批数和答案。

### 4.1 「同域·密集」：问这批资料里的核心话题

问题落在语料最密集的那个域（LLM 评测）。结果：

- Dynamic 选中了目标域社区的 **91%**——可以说"它找对了"；
- 但**总 token 打平（−4%）**，延迟 **+26%**。

原因不复杂：这类问题"哪儿都相关"，打分几乎全过 ⇒ 选择的收益被"每个候选一次调用"的成本吃掉。**当语料本来就高度聚焦时，Dynamic 只是把一份成本换成了另一份。**

### 4.2 「同域·稀疏」：问一个只散落在少数几篇里的子话题

这一组是**正面样本**：

- map 批数 **32 → 6**；
- 总 token **−32%**；
- 答案反而更长（因为上下文里少了不相关材料的干扰）。

这说明它的机制是有效的——**当"相关信息本来就少"时，它能把材料量压下来。**

### 4.3 「跨域」：需要 5 篇文档共同回答（核心判据）

这组是设计上最该赢的场景。结果是**喜忧参半**：

- **需要的 5 篇文档全部覆盖**（没被剪死）——召回这一关过了；
- 但**总 token +53%、时间 +33%**，答案还更短。

我一开始以为是剪枝剪错了，翻了打分明细才发现根因：

> **135 个被评的社区里，74 个恰好是 1 分——而默认阈值就是 1。**

也就是说，大量"其实不太相关"的社区，被"恰好等于阈值"的分数收了进来。**这不是剪枝太狠，是阈值太松**——而阈值松的原因，又把我们带回到第 2 节那句话：它默认是 1/5，没有任何先验支撑。

---

## 5. 打分理由长什么样（以及为什么它救不了抖动）

模型不是只吐一个数字，它同时给了理由。我把根层 17 个社区的打分重放了一遍，拿到 17 条理由。举两条典型的：

- 对**明显不相关**的社区，它给 0 分并写道："……与问题主题无直接关联，**需用户自行类比迁移**"——这个判断是讲得通的，甚至比"相关/不相关"更准确；
- 对**部分相关**的社区，它给 2–3 分，理由里会指出"只覆盖了问题的某一个侧面"。

**但这些理由被系统丢掉了。** 打分函数只返回 `rating`，不返回 `reason`；`reason` 只出现在 debug 日志里。这意味着：

1. **你无法从系统里拿到"为什么剪掉了它"**——想审计只能自己接日志；
2. **五档被压成两档**。默认阈值 1 的含义其实是"只要不是 0 分就要"，于是 1/2/3/4/5 这几个档位的差别在选材阶段**完全消失**，只在 `rank` 排序那一侧还留有一点作用。

更要紧的是**抖动**。我把同一批社区重放了几次，同一个社区、同一个问题，分数出现 **1→5、2→0** 这种跨越式变化。

这意味着一个很现实的结论：**在打分本身不稳定之前，调阈值是没有意义的。** 阈值是用来切"够不够相关"这把尺子的，而尺子本身在晃——把阈值从 1 调到 3，你只是换了一个刻度去切一条抖动的线，既不能提高精度也不能提高召回，只会让结果更不可预测。

所以我给自己的结论是：**要用这条路，先解决抖动的来源**（它可能同时来自评分标准的模糊、模型对"相关性"这个词的理解不一致、以及上面说的孤立判断——没有参照系）。而这三样官方一样都没给：提示词不可配、阈值无语义、稳定性无保证。

## 6. 成熟度：把信号摆在一起看

我没有用"我觉得它不成熟"来下判断，而是把能查到的信号列出来（📎 GitHub PR / changelog / 仓库文件）：

| 信号 | 事实 |
| --- | --- |
| **文档** | `docs/query/global_search.md` 里 "dynamic" 出现 **0 次**；仓库里有一份 example notebook，但**没有进导航** |
| **入口** | CLI 开关默认**关**；`graphrag init` 生成的 `settings.yaml` 里**没有**那五行配置，要调得手写 |
| **发布定级** | 功能合入的 PR（#1396，2024-11-12）发布定级是 **`patch:`**——不是 feature |
| **维护强度** | 2024-11-12 合入 → 之后只有两次小 bug 修（#1450 / #1591）→ **再往后 5 次改动全是重构，选择逻辑一年半没动** |
| **测试** | 对应的单测文件**没有 `test_` 前缀**，CI 收集不到 |
| **已知缺陷** | 根层无社区会 KeyError（issue #2382），修复 PR #2413 **已关闭、未合入** |
| **可配置性** | 打分提示词**不可配**；官方"按领域调提示词"的承诺只覆盖索引侧（map/reduce/knowledge 三项） |

这些信号合起来说明的不是"这个功能不能用"，而是：**它没有被当成需要维护承诺的功能对待**。你要用它，得自己拥有三样东西——**打分提示词、阈值语义、打分稳定性**。

## 7. 小结：三句话

1. **方向是对的**：把"这次该看多细"从用户手里收回来，交给系统按问题逐社区判断，这正是默认路径最大的结构性问题（层号做不到）的解法。
2. **代价是实打实的**：所有成本从本地变成每个候选一次 LLM 调用；而且**越不相关越贵**。三组实测里只有"同域·稀疏"是明显划算的（token −32%），最需要它的"跨域"那组反而 +53%。
3. **它现在还不具备被直接依赖的条件**：文档 0 提及、提示词不可配、阈值无语义、打分有抖动，而"打分失败"的默认值与"判定相关"的阈值**恰好是同一个数**。要用它，先准备好自己那三样东西。
