> **30 秒判断**：金标准不是"答案要点清单"，而是**一组判官能直接执行的判定项**——它同时定下了"谁来判、判到什么粒度、什么情形算失败"。金标准写不好，评测就是在**朝一个错误的目标优化**：分数在涨，但你不知道涨的是什么。
>
> **适合谁读**：正在给 Agent 建评测体系、却卡在"这条用例什么算对"的人；金标准写成了要点列表、交给判官后判定不稳的人；以及准备把评测接进自动化流水线的人。
>
> **本文怎么读**：和上一篇同一个结构——每个步骤先讲**方法**，再用一个真实实例演示。实例是一个"文档学习问答 Agent"的 18 条用例。**标着「实例｜」的段落可以跳过**，不影响读方法；把产品换成你的，五步不变。
>
> **前置阅读**：系列三篇。①《[Agent 开发为什么要测试驱动升级版](https://juejin.cn/post/7696916617436889115)》讲这套方法的由来；②《[需求定义四步：用一个文档问答 Agent 演示"先定义、再动工"](https://juejin.cn/post/7697089423960719396)》把"用户会问什么、什么算答得好"定下来；③ 本文接着它，把"什么算答得好"变成**判官能逐项执行的判定项**。
>
> **结构速览**：§0 五步一页；§1 先定金标准，再谈实现；§2–§6 逐步演示（方法＋实例）；§7 常见误用；§8 一页速查；**附录：18 条用例定稿**。
>
> **证据标记**：**✅ 实测**＝有可复现实验数据支撑；**🤔 推断**＝由实测或机制推出的判断。没标的多为框架性表述。

**先交代几个名词**

-   **用例**：一次可复现的测试。一条完整的用例＝**输入 ＋ 环境 ＋ 金标准**。
-   **金标准**：这条用例"什么算对"的定义。
-   **判定项**：金标准里可判定的一条条小项。分两类——**必选**（R）与**边界**（X，即"不许出现什么"）。
-   **确定性检查**：结果要么真、要么假、不依赖模型判断的检查——引用块是否存在、是否被截断、数值是否相等。
-   **判官**：拿金标准去判答案的角色或程序。可以是一段程序、一个 LLM，也可以是人。
-   **聚合**：把各判定项的结论折成"这条用例过没过"。

## 0. 五步，一页

| 步骤             | 产出什么                     | 怎么算这一步做对了           |
| -------------- | ------------------------ | ------------------- |
| **① 先定判官**     | 分工（谁判语义、谁做确定性检查）＋ 一条聚合规则 | 每条判定项都能落到"谁来执行"     |
| **② 拆判定项**     | 两栏：必选 ＋ 边界               | 每条都能回答"什么算满足／什么算违规" |
| **③ 写成可执行的判定规则** | 一个 id ＋ 判定标准（R）或判定动作（X）  | 判官读完不用再猜"要查什么"      |
| **④ 用例集先齐类型**  | 每类问题至少一条 ＋ 跨类型的失败面       | 类型不齐，失败模式必漏         |
| **⑤ 定判定参数**    | N／K、抖动口径、速度指标、判定实现       | 能跑、能复现、能解释          |

顺序同样不能倒：**判官定不了，标准就写不清；标准写不清，跑多少次都没意义。**

## 1. 先定金标准，再谈实现

### 1.1 金标准不是"答案长什么样"

一种很常见的写法，是把金标准写成**答案要点列表**：这条答案应该提到 A、B、C。这看起来没错，但它回答的是"**答案长什么样**"，不是"**怎么判它**"。

区别在哪？要点列表交给判官后，判官只能"感觉提到了没有"；而判定项写清了"查什么、什么算满足、什么算违规"，判官才能逐项打勾，程序才能聚合。

### 1.2 一次对照：人工抽读 vs 按判定项核

**实例｜一次真实对照**

**✅ 实测**：同一批答案，人工抽读判定"通过"；换成按事实边界逐条核的判官，判为**失败**。

这个差异本身就是一条教训：**人看一遍觉得"挺像"，和按判定项核对一遍，是两件事。** 人工不仅会疲劳，还会**自我说服**——你越懂这些材料，越容易把"它想说的"当成"它说了的"。

### 1.3 所以金标准是"基础件"

金标准、判官提示词、系统提示词、工具行为契约，都属于**基础件**：它们错了，后面所有统计都在朝错误方向优化。

配套纪律是一条硬规矩：**AI 可以起草、可以提议修改，但不得自审自合入。** 金标准要人工逐条过，判官口径要人工读一遍——AI 看不见自己的盲区，让它自检是无效的。

## 2. 第 1 步：先定判官

### 2.1 方法

**为什么顺序是这个**：**判官怎么判，约束了金标准怎么写**。判官如果是 LLM，你就不能写"检查这句话是不是越界了"这种没有判定标准的要求；判官如果是程序，你就不能写"看整体组织得清不清楚"这种语义判断。

**分工原则：按认知任务分，而不是按"重要程度"分。**

> **LLM 做"逐项识别"，程序做"确定性检查"与"聚合判定"。**

LLM 吃语义：这一项满足了没有、这句话算不算越界。程序管两件事：**确定性检查**——引用块是否存在、是否属于被点名的那一篇、输出是否被截断、格式字段是否齐、精确数值是否相等；以及**聚合判定**——必选全满足 且 边界零违反 ⇒ 通过。

关键的一句话：**不要拿程序去替换语义判断**，只把"逻辑运算"和"确定性检查"从 LLM 手里拿回来。

**判定流程五步**：

| 步骤 | 谁做 | 做什么 |
| --- | --- | --- |
| ① 预处理 | 程序 | 取答案与该用例的判定项结构 |
| ② 确定性检查 | 程序 | 引用块是否存在／是否属于被点名的那一篇、输出是否截断、格式字段是否齐、精确数值是否相等 |
| ③ 语义判定 | LLM | 逐项给结论 ＋ 依据原句；**一次调用只做一类认知任务** |
| ④ 聚合 | 程序 | 按唯一一条规则算出 通过／失败／挂起 |
| ⑤ 白盒归因 | 程序 | 仅失败或挂起后按需做：检索充分性 → 引用 → 提炼，只产归因记账，不产生新的判定 |

第 ③ 步的结论是**三态**：必选项为「满足／未满足／不确定」，边界项为「有违规／无违规／不确定」，并且都要附**依据原句**。

**为什么用三态而不是分数？** 不是分数一定有害——配好评分锚点、把红线单独拎出来，分数制也能用。这里选三态，是因为**现阶段不需要那么复杂**：判定项本来只需要回答"满足没有"，三态 ＋ 聚合已经能跑起来；而评分锚点是一笔额外的设计与校准成本。等真的需要比较"好多少"时再引入分数也不迟。

所以聚合只有一条规则：

> **R（必选）必须全满足、X（边界，含通用红线）必须零违反 ⇒ 通过；任一不满足 ⇒ 失败；出现"不确定" ⇒ 挂起。没有阈值、没有权重。**

### 2.2 我们的判官

**实例｜一个文档学习问答 Agent**

-   **程序做**：引用块是否存在、是否属于被点名的那一篇、输出是否被截断、格式字段是否齐、精确数值是否相等。
-   **LLM 做**：这条必选满足了没有、这句话算不算越界；一次调用只做一类认知任务，逐项给三态结论 ＋ 依据原句。
-   **程序聚合**：R 全满足 ＋ X 零违反 ⇒ 通过；出现"不确定"⇒ 挂起。

举个例子：同一条答案里，"有没有真的引用到那篇文档"由程序核；"这个说法算不算把 93% 当成了拦截率"由 LLM 判。两边都不越界——程序不猜语义，LLM 不算数。

## 3. 第 2 步：把"什么算对"拆成判定项

### 3.1 方法

**只有两栏：必选 ＋ 边界，不设"可选"。**

-   **必选**：全满足才算过；
-   **边界**：一条都不能违反。

不设"可选"是有意的："可选"意味着"做不做都行"，但判官无法判断"这条到底算不算可选"——它只会变成一个永远打勾的项，白白增加噪声。真想让某个要点宽松一点，就把它写成必选、但在判定标准里写明"满足其一即可"。

**边界有两个来源**：

| 来源 | 内容 | 要不要在用例里写 |
| --- | --- | --- |
| **通用边界** | 全局适用的红线：引用无伪证、来源可溯源、遗漏透明、边界合规 | **不重复抄**——只定义一次，全局生效 |
| **专有边界** | 这条用例自己的"不许说" | 要写 |

通用边界有一条例外：**触发条件由用例本身决定时，要写一句**。

-   引用无伪证、来源可溯源——触发条件由**答案**决定（答案给了承诺就得查），每条答案都要问，**不用写**；
-   遗漏透明、边界合规——触发条件由**用例**决定（这条题就是要全的、这条题就是越界的），**要写明**，免得判官漏判触发。

### 3.2 一道题拆出来的判定项

**实例｜第 2 类（是什么／取值）的代表用例**

输入：**"Anthropic《How we contain Claude》里，Claude Code auto mode 能拦住多少比例的过度行为？"**

| 判定项 | 类型 | 判定规则 |
| --- | --- | --- |
| R1 拦截率 | 必选 | 答案是"约 83%"（保留"约／roughly"，不写成精确的 83.0%） |
| R2 对象与时点 | 必选 | 答案说明它是 auto mode 在"过度行为执行之前"拦下的比例 |
| X1 与 93% 混淆 | 边界 | 是否把"拦截率（83%）"与"用户批准权限提示的比例（93%）"对调或混说 |
| X2 单靠模型层 | 边界 | 是否说成"83% 说明模型层已经足够／可以单靠模型层" |
| X3 扩大成全部攻击 | 边界 | 是否把"拦下过度行为"扩大成"拦下所有攻击／外泄" |
| X4 指标归错 | 边界 | 答案里出现的数字，是否都被归到了正确的指标名下 |

注意这条用例**没有写任何一条通用红线**：引用无伪证、来源可溯源的触发由答案决定，不用写；这条题不属于"要全"类、也不是越界请求，所以遗漏透明和边界合规都不触发。四条红线一条都不用写——这就是"通用边界不重复抄"。

## 4. 第 3 步：把判定规则写成可执行的

### 4.1 方法

> **一个 id ＋ 一段可执行的判定规则**。必选写成「判定标准（什么算满足）」；边界写成「判定动作（查什么、什么算违规）」。

几条经验：

-   **不必再写一遍"判定问题"**——判定标准本身就是要判的那件事，多写一遍只会让判官在两套措辞里选。
-   **判定规则里要写清"执行必需的信息"**：比如只说"是否把两个数字混淆"是不可执行的，判官需要知道这两个数字**各自是什么**。
-   **清单型要逐项列出**：判官只能打勾，不能"感觉提到了"。
-   **质量型判断要改成可核的动作**：把"像不像……"这类印象式要求，改写成能逐条核对的动作。
-   **互斥分支不能拆成两个必选**：同一件事的两条互斥路径（"能定就选、不能定就澄清"）要写成**一个**判定项、在判定标准里用"满足其一"；拆成两个必选会被"全满足"这条规则直接判死。
-   **反例尽量写**：写明"什么不算"——相邻内容不算、模型的元陈述（"资料缺失／未覆盖全文"）不算文章内容。
-   **点要正交**：同一母题的概括与细节不拆成两个点，否则会逼判官做粒度判别，制造假阳性。
-   **表述豁免**：内容类判定项统一写"意思一致即可、表述不限；精确数字／名称／出处须准确"。
-   **输入要自然化**：题面不得出现内部代号（素材编号、内部用例 id），要用真实用户会说的说法——否则模型会去猜你的编号体系。

写完逐条自查：类型齐不齐、三要素（输入／环境／金标准）全不全、是不是只有两栏、每个判定项是不是都有 id ＋ 判定标准（R）或判定动作（X）、反例写没写、题面自不自然、有没有重复抄通用边界。

### 4.2 坏写法 → 好写法

**实例｜同一批用例上的返工记录**

| 坏写法                  | 为什么不行                     | 好写法                                     |
| -------------------- | ------------------------- | --------------------------------------- |
| "是否把 83% 与 93% 混淆"   | 判官不知道这两个数字各自是什么含义，只能猜     | "是否把『拦截率（83%）』与『用户批准权限提示的比例（93%）』对调或混说" |
| 把"能定就选、不能定就澄清"拆成两个必选 | 两条互斥，永远不可能同时满足，被聚合规则判死    | 合成**一个**判定项，判定标准写"满足其一"                 |
| 在判定动作里写"为什么这算违规"     | 判官不需要理由，只需要判定条件；解释会挤占判定内容 | 只写"什么算违规"                               |
| 题面里写素材编号             | 模型会去猜编号体系，答案被带偏           | 用真实用户会说的篇名与说法                           |

## 5. 第 4 步：用例集先齐类型

### 5.1 方法

如果问题空间分了 15 类，那么**每一类都至少要有一条代表用例**。理由很直接：**类型不齐，失败模式就会漏，架构决策的依据也跟着漏**——你会以为系统没问题，其实只是没测到。数量可以后面补，类型必须先齐。

按问题类型铺完，仍然会漏掉几类**跨类型的失败模式**——它们不属于任何一个问题类型，必须单独补。

### 5.2 18 条是怎么来的

**实例｜一个文档学习问答 Agent**

前 15 条＝问题空间的 15 类各一条代表用例，输入原则上取每类第 1 个示例问句（指代明确版）。

后 3 条＝跨类型失败面：

| 补充用例 | 考什么 |
| --- | --- |
| 跨源消歧 | 题面刻意模糊、库里有多篇同域文档时，**要求用户澄清**，而不是自己挑一对就往下答 |
| 越界请求 | 题面越界（如"帮我按这份文档写个学习计划"）时，**指出问题**（越界 或 指代不明） |
| 静默失败／截断 | 材料注定讲不完时，答案被截断**且明确声明"内容未完"** |

### 5.3 写不出金标准，就是产品定义有洞

**实例｜"整体图景"那一类**

**✅ 实测**：写"整体图景"这一类（"把 A 和 B 合起来看，它们画了什么图景？"）的金标准时，第一版**根本写不出来**——想了半天也说不清"什么样的回答算好"。

最后解决它的不是打磨措辞，而是**回头补产品定义**：把"整体图景"定义为"一句可辨认的总纲 ＋ 若干支撑面 ＋ 两篇的核心概念都必须被覆盖"。

所以有一条可复用的检验：**某一类写不出"什么算对"，先别硬写——那是产品定义有洞，回头补定义。**

## 6. 第 5 步：跑起来才需要的参数

### 6.1 方法

金标准写完，评测还跑不起来——还有一组参数要一起定。

**① 跑几次算过：N 和 K**。同一配置跑 **N** 次，其中 **≥K** 次满足该用例的金标准（且红线零违反）⇒ 该用例通过。为什么要跑多次？因为单次结果可能只是运气——判官单次判定不稳定是机制性的（温度设为 0 也一样）。

**② 抖动与一致性**。跑 10 次过 9 次，最后只落一个"通过"——波动就被丢掉了。所以要把波动显式报出来，而且要覆盖三件事：

-   **报什么**：报 N 次里通过／失败／挂起的**分布**，以及跨次翻转**发生在哪条判定项上**；
-   **分两层**：**生成侧抖动**（Agent 每次答案在变）与**判定侧抖动**（判官自己翻转）分开记——别把工具误差算成产品不稳定；
-   **和数据联动**：用实测抖动反推 N／K 够不够（波动大 ⇒ N 要更大，或 K 要放宽）。

**③ 速度：用首字延迟，不用总时长**。产品是流式的，用户等的就是"第一个字"。所以在 Agent 场景里，总时长 ∝ 工具轮次 ∝ 答案要多全——拿它当准出，等于**惩罚"查得多、答得全"**。

**④ 判定实现**。最后要把金标准变成能跑的程序，产出三样：**分工映射**（每条判定项归到程序／LLM／人，一次性做完，不写进用例表）、**判官提示词**（一次调用一类认知任务）、**程序侧判定器与聚合器**。

### 6.2 我们的取值

**实例｜一个文档学习问答 Agent**

-   **N／K**：起步取统一值 **N＝10、K＝9**，先不按类区分，跑一轮看效果再校准。
-   **抖动**：**✅ 实测**——12 条答案跨 6–9 遍判罚，其中 10 条完全一致、2 条发生翻转；但更要紧的结论是"**缺项集合单遍不可信**"。
-   **速度**：指标定为**首字延迟**；上限是简单类 10 秒、复杂类 30 秒。参照值：同批题里单源单题 4.6–9.6 秒，多源单题 15.3–73.3 秒（工具调用 6–42 次）——这正是为什么不能拿总时长当准出。
-   **判定实现**：三样产出如上；其中"精确数值是否相等"这类由程序核，"这个说法算不算越界"由 LLM 判。

## 7. 常见误用

| 误用 | 出在哪一步 | 问题出在哪 |
| --- | --- | --- |
| **把金标准写成答案要点清单** | ② 拆判定项 | 那描述的是"答案长什么样"，不是"怎么判" |
| **把互斥的两条路拆成两个必选** | ② 拆判定项 | "全满足"这条规则会直接把它判死——逻辑上永远过不了 |
| **判定规则写在两套措辞里** | ③ 写判定规则 | 既写"判定问题"又写"判定标准"，判官要在两套说法之间选 |
| **判定规则里不带执行必需的信息** | ③ 写判定规则 | 只说"是否把两个数字混淆"，却没说两个数字各是什么含义 |
| **用"尽量""原则上"这类软词** | ③ 写判定规则 | 判官无法执行；软的地方应该写成"满足其一" |
| **把解释性文字写进判定规则** | ③ 写判定规则 | 判官只需要知道"什么算违规" |
| **用例只堆数量、不凑类型** | ④ 用例集 | 类型不齐，失败模式就漏 |
| **没定评分锚点就用分数** | ① 定判官 | 分数本身不是问题；没有锚点、又把红线混进总分，才会变成"总体印象"和"底线被平均" |
| **单次结果当结论** | ⑤ 判定参数 | 判官单次不稳定是机制性的，必须看多次并报抖动 |
| **AI 自审自合金标准与判官口径** | 全程 | AI 看不见自己的盲区，基础件必须过人工复核 |

## 8. 一页速查

**五步**：先定判官 → 拆判定项 → 写成可执行的判定规则 → 用例集先齐类型 → 定判定参数。

**分工**：LLM 逐项识别，程序做确定性检查与聚合；不拿程序替换语义判断。

**金标准两栏**：必选（全满足）＋ 边界（零违反）；通用红线不重复抄，只有"触发由用例决定"的两条才写进用例。

**判定项形状**：id ＋ 可执行判定规则；R 写判定标准，X 写判定动作；三态结论 ＋ 依据原句；**本版用三态聚合，不用分数、权重、阈值**（够用、实现简单，以后需要再上）。

**用例集**：先把问题类型的代表用例凑齐，再补跨类型的失败面（消歧／越界／静默失败）。

**参数**：跑 N 次、≥K 次过；报抖动要报分布与翻转项、分开生成侧与判定侧；速度用首字延迟，不用总时长。

**一句话**：**金标准不是"答案要点"，而是一组"判官能逐项执行的判定项"——写不出可执行判定规则的地方，先回头补产品定义。**
