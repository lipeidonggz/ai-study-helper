# GraphRAG 增量索引拆解：它"增"了什么，以及它不肯重算的那部分

> **30 秒判断**：你打算把 GraphRAG 用在会持续更新的语料上，或者已经在用、想知道"能不能只更新新内容"。这篇把它的增量索引（`graphrag update`）从头拆开：新内容怎么进来、四张表怎么合、哪一部分它明确拒绝重算，以及由此产生的 7 个后果。
>
> **一句话结论**：它不是一个"增量维护"的机制，而是 **append-only 的追加**——新文档单独跑一遍完整流水线，再把几张表拼到旧索引上；**社区不重算、实体度不重算、删掉的文档算出来了但被丢掉**。
>
> **适合谁读**：在为"知识库会持续更新"做选型的同学；或者已经在用 GraphRAG、准备上第二次索引的人。
>
> **阅读成本**：约 18 分钟。1–3 节是机制（流程与四张表的合并规则），5 节是后果清单，6 节解释"为什么不能重算"，7 节给了一套判断"某个能力是不是还停在半成品"的方法，8 节是选型建议。
>
> **先说清证据边界**：这篇的结论来自**读 graphrag 3.2.0 的源码 + 官方文档与 CHANGELOG**，**我没有跑一次真机增量**。所以每条都标了出处：**📄 源码** / **📎 官方文档** / **🤔 我的推断**。凡是推断的地方我都会写明。

---

## 0. 为什么增量值得单独看一篇

上一篇我写的是 GraphRAG 的索引本身：十步流水线、产出六张表、哪里会静默出错。那篇讲的是**第一次**跑会发生什么。

但真正决定一个索引方案能不能长期用的，往往是**第二次**跑：语料变了以后怎么办。

这件事在 GraphRAG 里尤其要紧，因为它建的是一张**全局的**图——社区划分、社区报告，本质上都是"看整个语料"得出的结论。而"全局"和"增量"这两个词，天生就是矛盾的。所以增量索引这条线，几乎是一个方案的软肋所在：**它怎么处理这个矛盾，就决定了它能用在什么场景**。

一句话概括这篇的发现：它没有试图解决这个矛盾，而是绕开了——**新的归新的、旧的归旧的，两套结构并排放着**。

---

## 1. 它跑的是什么：一条 18 步的流水线

入口是一条 CLI 命令：

```bash
graphrag update --root .
```

它做的事，是把方法名从 `standard` 换成 `standard-update`，然后执行**三段拼起来**的流水线，一共 18 步（📄 `index/workflows/factory.py`）：

1. **1 个读增量步骤**：`load_update_documents`
2. **9 个标准链步骤**：`create_base_text_units` → … → `generate_text_embeddings`（就是上一篇那十步，去掉读全量输入那一步）
3. **8 个合并步骤**：`update_final_documents` / `update_entities_relationships` / `update_text_units` / `update_covariates` / `update_communities` / `update_community_reports` / `update_text_embeddings` / `update_clean_state`

关键在**第 2 段和第 3 段是分开的两次执行**。运行时它会把目录切成三份（📄 `index/run/run_pipeline.py`）：

```text
output/                        ← 当前索引（最后会被合并结果覆盖）
update_output/
  └─ 20260926-101530/
       ├─ previous/            ← 把上一轮的 output/ 全表复制一份备份
       └─ delta/               ← 这一轮新内容的"小索引"，独立一份
```

于是流程变成：

1. 把当前的 `output/` **全部复制**到 `previous/`（📄 `_copy_previous_output`，逐表读出来再写一份）；
2. 用新文档在 `delta/` 里跑**一整套标准链**——注意是整套，切块、抽实体、聚类、写报告、算向量，一个不少；
3. 用 8 个 `update_*` 步骤，把 `previous/` 和 `delta/` 的几张表**合起来**，写回 `output/`。

所以"增量"省下的是**对存量语料的重复抽取**（也就是最贵的那部分 LLM 调用），但**流程一步没少**：新内容仍然要走完整的十步。

> 顺手记一个部署上的坑：这个"备份"是全表复制，每次增量都会在 `update_output/` 下留一份完整快照。更新频繁的话，磁盘是按"每次一份索引"的量级长的。

### 1.1 一个容易踩的配置陷阱

如果你在 `settings.yaml` 里写过 `workflows`（我上一篇就是这么做的，为了让索引只跑六步），那么 **`workflows` 会直接覆盖掉 `--method` 选出来的流水线**：

```python
workflows = config.workflows or cls.pipelines.get(method, [])
```

📄 这是 `PipelineFactory.create_pipeline` 的原话。也就是说，`graphrag update` 选的"更新链"是个**兜底默认值**，你一旦显式列了 `workflows`，它会跑你列的那条链，而不是更新链。想用增量，要么去掉这个配置项，要么把 18 个步骤手动列全。

## 2. 差异是怎么算出来的：按标题比对

哪些文档算"新"？它的判据非常朴素——**按文档标题比对**（📄 `get_delta_docs`）：

- 新输入的标题集合 − 上轮 `documents` 表的标题集合 ⇒ **新增**
- 上轮标题集合 − 新输入的标题集合 ⇒ **已删除**

两个细节值得留意：

**① 判据是标题，不是内容。** 标题取自文件名（或 front matter）。所以"同一个文件改了内容"会被判成**没变化，跳过**；而"改了个文件名"会被判成**删了一份旧的、加了一份新的**。

**② 被删除的文档，算出来了，然后丢掉了。**

这个我觉得是整条链路里最值得看的一处。`get_delta_docs` 返回的 `InputDelta` 里明明有 `deleted_inputs`，但唯一的调用方只取了 `new_inputs`：

```python
return delta_documents.new_inputs
```

📄 我全包搜了一遍 `deleted_inputs`：除了 `incremental_index.py` 里的定义与赋值，**整个 graphrag 包里没有任何地方读它**。

后果是：**你把文档从 `input/` 里删掉，索引里一切照旧。** 它的 chunk、实体、关系、社区报告全都还在，仍然会被检索到、仍然会出现在全局综述里。这不是"覆盖不全"，而是**把一份已经不存在的内容当成当前知识在回答**。

（顺便：3.0.3 的 CHANGELOG 里有一条 "Add … remove … operations to vector store API"——能力是有的，但增量链里没有任何删除调用。📎）

## 3. 四张表分别怎么合（这一节是干货）

`delta/` 和 `previous/` 都有同样的几张表，合并规则却是**每张一套**，各不相同（📄 `index/update/*.py`）：

| 表 | 合并键 | 合并规则 | 我注意到的坑 |
| --- | --- | --- | --- |
| `documents` | 行号 | 新表的行号从旧表最大值往后顺延，然后直接拼接 | 简单、无坑 |
| `entities` | **`title` 精确匹配** | 匹配上的新实体映射回旧实体的 id；`text_unit_ids` **取并集**；`description` 收成一个列表；`frequency` 按证据块数重算 | **`degree` 保留旧值不重算**（源码里就是 `"degree": "first"`，还留着一行 TODO） |
| `relationships` | **`(source, target)`** | 编号顺延后按两端分组；`description` 收成列表；`weight` 取**平均**；`combined_degree` **重算**；最后过滤掉悬空边 | 重算发生在"过滤悬空边"**之前**——被丢掉的那些边，度数已经算进去了 |
| `communities` | 社区编号 | 新批次的编号整体偏移（`旧最大值 + 1`），父指针一起重映射；然后**直接拼接** | ① 编号 `-1`（不属于任何社区）原样保留；② **所有社区的 `title` 被统一改写成 `Community N`**，原来那个有意义的标题没了 |
| `community_reports` | 同一套社区编号映射 | 直接拼接 | 新旧报告混在一张表里，查询侧不区分批次 |

### 3.1 补充一条：合并之后还会再调一次 LLM

这一点容易漏。合并把同一实体的多条描述收成了**列表**，然后更新流程会调用摘要步骤，把这些描述"汇总成一段"——而汇总器对**描述条数 ≥ 2** 的条目会真的去调 LLM（📄 `SummarizeExtractor`：0 条返回空、1 条原样返回、多于 1 条才调模型）。

谁是"条数 ≥ 2"？**新旧两批都出现过的实体和关系**。也就是说，增量省掉了存量语料的抽取，但**要为所有跨批出现的实体/关系再付一次摘要的钱**。加上第 1 节那个"delta 跑完整链"的事实，一次增量的成本大致是：`新文档的抽取` + `跨批实体的描述重汇总` + `delta 的社区报告` + `两次嵌入流程`（delta 一次、合并后一次；重复文本会命中缓存，所以不等于双倍计费，但确实要跑两遍）。

### 3.2 于是它到底"增"了什么

一句话：**新内容独立成图 ＋ 表级拼接**。

只有"实体/关系的记录级合并"算真正的合并——它们确实按名字拼到了一起，没有在同一张表里出现两份。而**结构级的东西（社区划分、实体度数）不做重算**：旧社区树原封不动留着，新批次的社区树编号偏移之后并排放进去。

## 4. 先说它的好处，这部分是实在的

我不想把这套设计说得一无是处，它确实解决的问题是"**存量不重跑**"，而这在 LLM 索引里是最贵的一项。另外三条也是实打实的：

| 好处 | 说明 |
| --- | --- |
| 不用重抽存量 | 省掉对已有语料的全部抽取调用，这是它最实在的收益 |
| 旧实体会被新证据补全 | `text_unit_ids` 取并集，所以一个老实体的"证据块集合"会随更新变大，局部检索反而更全 |
| 记录级去重是有效的 | 按标题合并确实拦住了"同一实体在表里出现两份"，新关系也正确接到了旧实体上 |
| 基础检索几乎不受影响 | 向量库是 upsert 语义，块向量检索不需要全局结构，加新内容就能查 |

所以真正的问题不在"能不能查"，而在**"要全局结构的那类问题"**。

## 5. 它解决不了的 7 件事

这是我读完代码之后整理的清单。每条我标了证据强度——**📄 的是读代码确定的机制**，**🤔 的是我基于机制的推断**（没有实测）。

| # | 问题 | 机制 | 后果 |
| --- | --- | --- | --- |
| 1 | **跨批主题永远不会出现** | 社区是"旧树 + 新树"并排，没有跨批重聚 📄 | 而"跨整个语料综合"正是 GraphRAG 的立身之本；同一个主题现在被拆成两批各说一遍 |
| 2 | **重复计入，指标虚高** | 同一主题新旧两批各有一份报告，map 阶段各自出答案 🤔 | 看起来"覆盖更全了"，但增量部分是另一批对旧话题的复述；`comprehensiveness` 这类指标会被冗余污染 |
| 3 | **层级粒度不可比** | 旧树的层号与"旧的全量语料"对应，新树的层号只对应"新批次" 📄 | 选"同一层"时两边颗粒度不同，却被放在一起打分 |
| 4 | **度数口径混用** | 实体 `degree` 不重算 📄 | 老实体是**旧全量图**的度数，新实体只有 **delta 小图**内的度数，同一张表两套口径 |
| 5 | **删除不落地** | `deleted_inputs` 算完丢弃 📄；向量库只写不删 📄 | 已删内容仍可被召回、仍参与全局综述 |
| 6 | **成本单调涨，覆盖不涨** | 全局检索每次扫该层的**全部**报告 📄 | token 和延迟随每次更新上涨，而新增部分常常是重复表述 |
| 7 | **查询侧完全不消费"批次"** | `period` 在 query 配置与 query 代码里**零出现** 📄 | 新旧产物被当成同质语料混用，用户无从知道哪部分来自哪次更新 |

第 4 条我想多说一句，因为它最容易被说错。准确的情况是：

- **实体**的 `degree` 确实不重算，源码里就是取第一条（`"degree": "first"`，旁边还有一行 TODO：*we could probably re-compute this with the entire new graph*）；
- **边**的 `combined_degree` 反而**重算**了——所以"度数完全不管"是不对的；
- 但重算用的是合并后的边表，**发生在过滤悬空边之前**，被丢掉的边已经计入度数；而且实体度数被查询侧当作实体排序键（📄 `rank_col="degree"`），也就是说这个脏账并不是纯摆设。

我在对这条的时候意识到一件事：**"某张表没更新"这种判断，必须落到具体字段和具体那一行代码，不能靠印象。** 我一开始也以为"度数整个不重算"，翻完才分成两半。

## 6. 为什么"社区不能增量重算"不是偷懒

到这儿很容易得出一个结论："不就是没做吗，把受影响的社区重算一遍不就行了？"我一开始也是这么想的。但翻完算法性质和这条线的文献之后，我认为这是个**算法层面的取舍**，不是工程欠账：

1. **Leiden 是全局优化。** 它优化的是整张图的模块度（一个全局求和）。加几条边，最优划分**可能在任意位置变化**，而不只是在新节点周围。
2. **解空间里有大量近似最优划分。** 不同划分的分数可能只差一点点，成员却差很多（near-degenerate）。加上算法本身带随机性——GraphRAG 为此**专门固定了随机种子**（代码注释写着 *to guarantee clustering stability*）。需要锁种子，本身就是"输出对细节敏感"的自证。
3. **"只重算受影响的社区"会卡在接缝上。** 重算区和冻结区的边界不对应任何一致的最优划分，得到的是"既不是旧最优、也不是新最优"的混合体——而且**没有目标函数能判它合不合格**。真要做，只能上"局部模块度 + 边界冻结"，效果不可验证。
4. **想保质量就只能全量重算，而全量重算不只是重跑聚类。** 社区变了，**所有受影响的社区报告都要重写**（每份报告都是一次 LLM 调用）；更麻烦的是报告 id 等于正文内容的 sha512（📄 `finalize_community_reports.py`），重写之后 id 全变——**缓存、引用、评测基线一起失效**。增量省下的抽取钱，可能还不够付重写报告的钱。

而且层级会放大影响：层级是递归切出来的，一次小插入可能改变分支的**深度**（同一个主题上一轮落在第 2 层、这一轮落在第 3 层），而全局检索是"选一层、扫全量"——于是**一次小小的增量，会整体挪动全局问答的取材范围**。

这不是没人想过。动态社区检测是一条活跃的研究线（DynaMo 2017、DyPerm 2018、Constrained Spectral Clustering 2019、Flow stability 2021，以及今年还在出的新工作），研究了近十年，**仍然没有成为默认做法**——因为"增量带来的结构漂移"必须和"结构可比性"做交换，而 GraphRAG 的价值恰恰建立在"结构是全局的"之上。

## 7. 顺带一套方法：怎么判断一个能力是不是"还停在半成品"

这次我最想推荐给你的不是某个结论，而是这套判断方式。读开源项目时，文档怎么写、issue 怎么回，都不如**把这三样排在一起看**：

**① 看文档覆盖。** 一个从 0.4.0 就进代码的能力，如果官方文档里没有介绍页，基本可以判断它还没被当作"对外能力"。

这个案例我实际查了一遍（📎）：

- `docs/index/` 下 8 个页面（含 `methods.md`、`default_dataflow.md`、`outputs.md`）里，**没有任何一处介绍增量索引**；方法文档只讲了 standard 和 fast 两种；
- 配置文档里只有一句：`update_output_storage` ——"a secondary storage location for running incremental indexing"；
- 唯一真正"提到它"的地方是 `outputs.md` 的字段表：`period`（ingest 日期）和 `size`（社区实体数）的说明都写着 **"used for incremental update merges"**；
- 开始指南（`get_started.md`）里完全没有 update 这个命令。

**② 看 CHANGELOG 有没有后续推进。** 只有"引入"那一次、之后全是外围修补，就是搁置。这条线的时间线（📎）：

```text
0.3.3  Add entrypoints for incremental indexing
0.4.0  Add Incremental Indexing（+ 配置 + text units 更新
       + Calculate new inputs and deleted inputs on update）
0.4.1  Add update cli entrypoint（+ 修可选 covariates 更新）
2.0.0  Rework the update output storage structure
       + Properly increment text unit IDs during updates
3.0.2  load_update_documents 支持 async iterator
3.2.0  仅依赖升级
```

从 2024 年初引入到现在的两年里，全是**存储重构、ID 修复、异步改造**这类外围动作，核心的"合并语义"没有动过。

**③ 看那个"算出来却没人用"的东西有多久了。** 这是最强的信号：`Calculate new inputs **and deleted inputs** on update` 是 0.4.0 那一批进来的——也就是说，**"检出被删除的文档"从第一天就算出来了，两年后依然没有被任何地方使用**。

一个能算出删除、却不落地的系统，说明设计者当初想到了这一步，但**没有把它做完**。

## 8. 那我该怎么选

### 8.1 先问两个问题，再谈选型

1. **语料的更新速度，和我能接受的索引刷新周期，差几个数量级？** 全局结构是"慢变量"，它需要一段时间窗才能收敛出主题；如果语料变得比刷新还快，"全局主题"还没形成就已经过时了。
2. **我要的是"全局结构"还是"局部检索"？** 前者只配低频刷新，后者可以随写随更（向量库加进去就能查）。

### 8.2 持续更新场景的四种对策

| 对策 | 做法 | 代价 |
| --- | --- | --- |
| **分层刷新率** | 高频只做切块 + 向量；低频才做结构重算 | 两套路径要维护，新鲜度不均 |
| **分域建图** | 按主题/来源/时间窗切成稳定子域，各自建图各自重算 | 跨域连接丢失——而那正是图谱类方案想解决的事 |
| **滑动窗口图** | 新内容建小图、老图冻结，查询跨多图 | 等于默认接受"结构分批"，并且需要查询侧配合 |
| **接受滞后并声明** | 把索引当快照，明确标注"数据截至某时间"，定期整体重建 | 最新的内容可能不在索引里 |

### 8.3 一句话判据

> **索引的刷新周期，要和语料的演化速度同量级。**

这条能提前挡掉一大类"建的时候爽、维护起来废"的全局索引方案。按这个判据：

- 语料基本不动（书、法规、一次性的研究集）⇒ 增量索引够用，甚至可以直接全量重建；
- 每月补几次 ⇒ 用增量做"临时可见"，再定期整体重建；
- 每天新增 ⇒ 别指望增量维护全局结构，要么分域、要么接受滞后并明说。

---

## 9. 小结

增量索引这件事，我的结论是：**它的名字比它的本事大。**

它确实解决了"存量不重跑"，方法也算干净（新内容独立成图 + 表级拼接，记录级合并按名字拼好）。但它带来的是**两套并排的结构**，而不是一个持续演化的结构。所以：

- 如果你的用法偏**局部检索**（找到相关的块、看某个实体相关的内容）——它够用，而且证据集会越来越全；
- 如果你的用法偏**全局综述**（把整个语料的面貌讲清楚）——它会持续变差：跨批主题不出现、同主题反复计入、层级颗粒度越来越不可比，成本还一路涨。

如果你正打算上这套东西，我建议至少做两件事：**把删除也走一条确定的清理路径**（哪怕只是标记 + 定期重建），以及**明确告诉使用者索引截止到什么时候**。这两件事它的代码里都没做。
