# 0026-2 判官与 Agent 的分时分层双迭代：评测反哺开发的分寸

> 系列：RAG 评测工程（0026 实践复盘）· 状态：初稿，待作者审校
> 对应原始记录：memory/0026 阶段 C5 收口（2026-09-06）
> 摘要：用判官驱动 Agent 迭代，最大的坑：分不清"系统变好了"还是"尺子变严了"。fail 先归因四层、同轮只改一层，两者都收敛到用户价值，不收敛到彼此。

## 30 秒判断

如果你在同时维护一个"被测系统"（Agent / RAG）和一把"测量尺子"（LLM 判官 / 评测集），你会发现两者在互相迭代——改判官让 Agent 的通过率大变，改 Agent 又让判官看起来不准。这篇文章给出一个分工框架，把这种纠缠拆开：

**判官是度量衡，Agent 是被测物。fail 必须先归因分层（判官 / 用例 / 检索 / 生成），再按序单层修复；判官只许因"判错了"而改，Agent 只许因"没达到金标准"而改；两者都收敛到用户价值，而不是收敛到彼此。** 配套两条护栏：判官版本化、套件防膨胀。

适合谁读：正在用 LLM-as-Judge 驱动 Agent 迭代的工程师。需要知道"评测驱动开发"是什么意思，但不需要 RAG 细节。

## 1. 一个把问题暴露出来的反例：reason-first 那次改动

我们当时已经花了很大力气把判官调到与人工判定一致，然后做了一次看起来纯粹是"判官侧"的改进：把引用判官的输出结构从"先结论后依据"改成"先依据后结论"（reason-first，经验来自覆盖判官）。

结果：全量 20 条从 20/20 pass 变成 10 fail / 4 pending / 6 pass。

单看这个数字，你可能会说"判官改坏了，回滚"。但我们逐条看现场，发现真正发生的是：这次判官改动**改变了 Agent 的 fail 集**——原来被放行的欠标行为（作者行不标 byline、缺席断言瞎挂）现在被揪出来了。也就是说，Agent 的"真实质量"没变，变的是测量尺子的分辨率。

这本身不是坏事——判官变严了，暴露了 Agent 的真问题。但它揭示了一个危险：**你分不清"这次改动让系统变好了"还是"这次改动让尺子变严了"**。如果我们在同一轮里又顺手改了 Agent，归因就彻底混了：fail 到底是 Agent 改坏的，还是判官改严的？

这就是"判官与 Agent 相互迭代"的核心风险：**归因混淆与互相拟合**。互相拟合更隐蔽——判官被调到"同意 Agent 现在的输出"（而不是"判对用户价值"），Agent 被调到"骗过判官现在的规则"（而不是"满足金标准"）。两者都收敛到彼此，唯独不收敛到用户。

## 2. 框架：分时分层双迭代

把迭代节奏拆成两个维度：

**分时**：判官永远领先 Agent 半步，冻结期错开。判官不稳的时候不许动 Agent（否则你分不清红是谁造成的）；判官冻结了，Agent 的改动才可归因。

**分层**：fail 必须先归因到四层之一，再动手：

1. 判官 / 金标准缺陷（尺子坏了）；
2. 用例 / 语料缺陷（题出错了）；
3. Agent 检索 / 注入（料没给够）；
4. Agent 生成 / 行为（料给了没用对）。

五步循环：

1. **冻结基线**：判官版本 + 用例集 + 判定口径固定，跑基准产出 fail 清单；
2. **归因分层**：把每条 fail 分到上面四层；
3. **按序单层修复**：同一轮绝不混改判官与 Agent，一次只动一个变量；
4. **冻结判官全量回归**：比较口径用 repeat + 逐句/逐点分布，不只看 run 级通过率；
5. **扩用例**：问题域驱动 + 根因驱动探针互补，回到 1。

## 3. 两条更新准则

准则的价值在于给"能不能改"一个可仲裁的判据，避免"感觉不对就改"：

**判官只许因"判错了"而改。** "判错"的定义是对照人工 / 原文可证：金标准点表写得有歧义、判官把 A 点内容判给 B 点、排除句被当成锚——这些是判官错。改完必须用历史输出池重放，确认旧样本上的判定按新口径仍然成立。

**Agent 只许因"没达到金标准"而改。** "没达到"的定义是判官（已冻结）按金标准判出的 fail。一次一变量，禁止把用例内容写死进系统提示词（那是把题目的答案背下来，不是会做题）。

两条准则合起来的含义：判官与 Agent 都不许以对方为基准来改，**都只能以用户价值（金标准所代表的东西）为基准**。判官校准自己的"判得准"，Agent 校准自己的"答得好"——两者通过金标准间接对齐，而不是直接互相拟合。

> 术语锚 · 金标准：每条用例预先人工写定的"正确答案应该长什么样"（我们的形态是清单型点表 + 覆盖探针）。它是判官和 Agent 共同的外部参照系，也是防止互相拟合的锚。

## 4. 两条护栏

**判官版本化**：判官口径一变，旧 run 的判定就作废或必须标注版本。否则你会拿着旧尺子量的数据跟新尺子量的数据比大小，得出幻觉结论。我们实践中每次判官改动都重放历史输出池，而不是"相信新判官顺手重跑一遍就完"。

**套件防膨胀**：每个根因类只保留代表探针。评测套件会自然膨胀——每发现一个新失败形态就加一条用例，最后变成历史输出样本的补丁集。护栏是：探针必须钉住唯一根因类 / 不变式，同类只留代表，新用例必须回答"它守住了哪个此前没守住的不变式"。

## 5. 实践中的样子：一次真实的归因分拣

判官冻结后跑一批真实输出（Run#128–131），同一批数据可以干净地分成三类：

- **Agent 生成侧波动**：a5-e2 6/20 漏写、transparency 8/20 未声明——注入块完全相同，输出时有时无，是采样波动不是检索差异；
- **检索不充分**：o2-e2/e3/e4/e5、a5-c3、a5-e1 稳定 20/20 缺失——对应原文章节根本没被注入（Redefining the role of the engineer / merge philosophy / 三层防御等）；
- **判官残余噪声**：1–2/20 的偶发假阳性——已确认是机制性噪声，交 repeat 统计吸收，不再单点强压。

如果判官没冻结，这三类会搅在一起：你修了检索，却发现"覆盖矩阵全绿"仍然达不到，因为还有生成侧波动；你以为是判官误报，其实是 Agent 没把材料写进回答。分时分层让每一步都只面对一个变量。

## 6. 可带走的清单

1. 判官和 Agent 一定要分时：一方冻结期，另一方才能动；
2. fail 先归因四层（判官 / 用例 / 检索 / 生成），归因不清不动手；
3. 同一轮只改一层、一次只动一个变量；
4. 判官只许因判错而改，改完用历史输出池重放；
5. Agent 只许因未达金标准而改，禁止把用例内容写死进提示词；
6. 回归比较看 repeat + 逐句/逐点分布，不只看 run 级通过率；
7. 判官版本化，旧 run 标注或作废；
8. 套件防膨胀：一根因一类，只留代表探针。

## 7. 边界声明

- 单一项目（RAG 学习助手）、单一判官模型、温度 0；框架本身不依赖这些，但具体阈值（如"1–2/20 算噪声"）需按项目重标。
- "判官只许因判错而改"依赖一个前提：你能可靠地人工判定"判官错了"（对照原文 / 金标准点表）。人工复核是这套框架的地基，省不掉。
- 本文讲的是"单轮评测 + 判官驱动"的迭代纪律；如果评测本身要自动化到 CI 门禁，还要叠加更多工程（版本化、数据留档、回归池），不在本文范围。
