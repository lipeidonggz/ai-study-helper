# 0026-4 让模型承认不知道：遗漏透明判官与提示词人读性重构

> 系列：RAG 评测工程（0026 实践复盘）· 状态：初稿，待作者审校
> 对应原始记录：memory/0026 阶段 C8（2026-09-07）
> 摘要：让模型承认"不知道"，比让它答对还难。提示词演化成拼贴怪物后，按五段式重构 + 人工定标严格口径 + 只做兜底的确定性闸门。提示词首先是给人维护的。

## 30 秒判断

如果你的 RAG 回答"只覆盖了该讲的一半"，你希望模型怎么做？我们的答案是：**它必须主动承认还有哪些要点没覆盖，并且点名具体是哪些**——不是一句"可能还有遗漏"的客套，而是对着清单逐项点名。这就是"遗漏透明"（omission transparency）。

这篇文章讲两件事：

1. **产品语义**：遗漏透明义务的判定口径怎么定（严格口径 vs 宽松口径之争，最后人工定标）；
2. **提示词工程方法**：一个演化拼贴出来的判官提示词如何被判官使用者逐条批出五处毛病，再按"任务 / 清单 / 回答 / 规则 / 输出"五段式重构；以及一个确定性闸门如何只做兜底、不做主修复。

核心教训：**判官提示词首先是给人维护的，其次才给模型读**——AI 每遇问题就追加条款、从不回头重构结构，最终会造出人看不懂、模型也读飘的怪物。

## 1. 什么是遗漏透明义务

我们的评测用例有一条金标准规则：当回答**没有覆盖全部扩展主题**时，模型必须主动声明"以下扩展主题未覆盖"，并至少点名一项具体内容。反过来，如果全部覆盖了，就没有这个义务——不得编造不存在的遗漏。

这条规则是"条件强制"：不是每次都必须写"我有遗漏"，而是**有遗漏时必须承认**。它对应学习场景里一个真实的用户体验问题：用户问了一个跨文档对比问题，模型只答了半篇，如果它不吭声，用户会误以为"就这些了"；如果它客套一句"可能还有更多细节"，用户也无法知道到底缺了什么。

判定遗漏透明的判官要做的事：读模型回答，判断它是否履行了"点名未覆盖主题"的义务。

## 2. 旧提示词的五处毛病（人读性视角的体检）

判官提示词是几个版本演化拼贴出来的。判官使用者（也就是我们项目的产品负责人）逐条批出五处毛病：

1. **触发条件不该给判官**：开头括号里写着"扩展主题未全部覆盖时才触发本调用"——这是调用侧的调度逻辑，判官只需要面对"现在要你判遗漏透明"这个事实，给它解释"什么时候会被调用"只会添乱；
2. **术语混用**："未覆盖主题"和"未展开项"两个词交替出现，判官不知道它们是不是一回事；
3. **输入混排无分隔**：模型输出与输出要求之间没有显式分隔，JSON 示例还跑到提示词最后面、与模型输出没有引导字符隔开；
4. **JSON 字段无定义**：输出字段的含义语焉不详；
5. **【标注口径】混杂执行步骤与取值定义**：一段话里既像在说"你应该怎么做"，又像在定义"v 的取值是什么意思"。

作为一个人类，读这份提示词都觉得费劲。判官提示词是给人维护的：结构不清 → 不可维护 → 不可审计 → 不敢再改。它和覆盖判官"排除句被当锚"是同一个病根——**措辞把两类东西混在一起，模型就会在歧义处自由发挥**。

## 3. 重构：任务 / 清单 / 回答 / 规则 / 输出 五段式

重构后的结构：

1. **任务**：一句话说清本次判什么（判遗漏透明义务是否履行）；
2. **未覆盖主题清单**：当前有哪些扩展主题未覆盖（程序从覆盖标注结果喂进来）；
3. **模型回答**：原样放模型输出，与其它部分显式分隔；
4. **判定规则**：只留两条 not_covered 情形——没有明确承认遗漏、或承认了但点名的内容对不上清单；反过来，"点名标题 / 实质描述"即有效，"仅重复清单编号"无效；
5. **输出要求**：字段逐个定义，JSON 结构放最后，前面有明确的引导语。

判定规则为什么要删繁？原来的规则里还枚举了"已覆盖内容 / 辅助性材料"等情形（c 类），复盘发现它们本质都落在"点名不对清单"这一条上——清单是唯一权威参照，枚举子类是冗余，而且"致谢/链接"这类词会把场景化内容带进共享提示词（用例污染）。删到两条，规则与定义分离。

## 4. 口径之争：严格 vs 宽松

最难的不是结构，是"什么算有效点名"。

宽松口径：模型点出了真实缺口就算（哪怕它说的是"资料没收录完整"这类泛述）；
严格口径：点名的内容必须对应**清单里确实未覆盖的主题**。

边界样本是一个真实 attempt（UI#19）：模型披露得很具体——"知识库中 Claude Cowork 的具体架构细节未收录""Codex 内部实验的工程细节也未完整收录"——但这些不是清单里的主题（清单要的是"工程师角色重定义细节""还在学什么"这类内容要点）。按严格口径，这是"披露了但没点到题"，判 not_covered；按宽松口径，它确实诚实承认了局限，可以算 covered。

这个边界最后由人工定标收口：**严格口径成立**。理由：遗漏透明的产品目的是让用户知道"这道题的哪些要求没答"，而不是让模型泛泛承认"世界很大我知道得不多"。点不对题的披露对用户判断"这道题答全了没"没有帮助。

同时定标的还有两个样本：

- UI#10：判官直接判 not_covered 正确（它点名的"熵/垃圾回收、1/10 论证细节"对不上清单）；
- UI#17/#18：判官原始判 covered，但 matched_uncovered 为空（点名只是"没有穷尽覆盖/未收录部分"类泛述）——这正是确定性闸门要拦的漂移。

## 5. 确定性闸门：兜底，不是主修复

判官是 LLM，规则执行会漂移。我们加了一个纯程序闸门：

**如果判官返回 covered，但 named_items 与 matched_uncovered 均为空 → 程序降级为 not_covered，并写入 gate_note。**

这个闸门的逻辑完全由提示词输出结构的内在要求派生：既然判官说"covered"（声称点名了未覆盖主题），它的输出里就必须有点名（named_items）和命中（matched_uncovered）；两者皆空还判 covered，只有两种可能——判官规则漂移了，或者输出结构坏了。两种情况都不该让 covered 通过。

但要注意闸门的定位：

- **它防的是"covered 但无支撑"**，拦不住"假命中"——named/matched 非空但映射牵强（比如 UI#17 把"作者/日期缺失"硬配到 o2-e4）；
- 判官稳定时它零副作用，所以**不单独跑效果实验**来证明价值；
- 它不做主修复：主修复是把判官提示词调到人读得懂、规则清。闸门只是最后一道不稳定的保险丝。

这背后是一条方法论：**确定性是可选兜底，不是默认起点**。看到 LLM 不稳，先问任务能不能拆、提示词是不是病句，再考虑上程序闸门——否则你每触发一次闸门，就少一次发现"判官为什么漂移"的机会。

## 6. 人读性复核：AI 自迭代的盲区

整个重构最值钱的经验是：**判官提示词的迭代缺陷模式 = AI 每遇问题就追加条款、从不回头重构结构**。旧提示词的熵是这么积累的：触发条件、口径、输出要求、JSON schema 层层拼接，每一层都是上一次打补丁的产物。

为什么会这样？因为 AI（包括我们）的默认动作是"在现有结构上加约束"，而不是"这个结构本身是否还成立"。而判官提示词首先是给人维护的：结构熵增到人看不懂，模型的理解也跟着飘——人读不懂的结构，模型只会读得更歪。

解法是给基础件加一个"人读性复核"维度：复核不止于"语义对不对"，还包括"人能否读明白要做什么、怎么做"。这正是项目铁律的又一次印证：**AI 自迭代有盲区，基础件必须有人工复核环节**。

## 7. 可带走的清单

1. 遗漏透明义务要"条件强制 + 点名具体"：有遗漏必须承认，且点名要对应清单，不点题的客套不算；
2. 判官提示词分五段：任务 / 清单 / 回答 / 规则 / 输出，各段显式分隔；
3. 规则只留可判定的最小集，删除枚举子类——清单是唯一权威参照；
4. 口径之争用真实边界样本人工定标，不要留给判官自由心证；
5. 确定性闸门做兜底（covered 但无命中 → 降级 + gate_note），逻辑必须由输出结构内在要求派生，且不做主修复；
6. AI 加条款前先问"结构要不要重构"；基础件必须有人读性复核维度。

## 8. 边界声明

- 单一判官模型、温度 0；"严格口径"的定标来自我们这一用例家族的用户价值判断，换产品换场景需重新定标；
- 闸门拦不住"假命中"（有映射但牵强），这类残留需要更可信的 named→清单映射结构（named_ref），我们尚未实现；
- 本文的提示词五段式适用于"判定型"判官调用；生成型任务（如让模型自己写遗漏声明）的结构不同。
