0038 · WeKnora 缺陷实录：粒度/领域配置只接了一半管道

一分钟摘要：WeKnora 的 wiki_config.extraction_granularity（focused／standard／exhaustive）只控制 Pass 0 候选抽取；引用匹配那一阶段还有一个"补 slug"的次要任务，它既不带粒度指引、也不带用户的领域指令。实测：同一份文档，focused 下 Pass 0 老老实实只抽 6 项（符合"3–7 条"要求），引用阶段却补了 14 项——最终 20 页里 70% 来自不听指令的那条通道。

第一部分 · 问题、证据与修复建议

1. 问题（一句话）

用户配的"抽取粒度／领域重点"只对 Pass 0 生效；引用阶段有一条独立的"补 slug"通道，它不读这两项配置，且能自己产出页面。结果是：focused 只兑现了一小半——用户以为会得到 7 个左右的页面，实际拿到 20 个。

两个对照都能读出来：

· 补 slug 通道不服从：focused 下反而补得更多（+14 vs standard 的 +9），且补的都是 focused 明令排除的类型——次要主题（人在回路监督、审批疲劳）与实现细节（工具输出攻击面、持久记忆投毒、多智能体信任升级、智能体身份）。

4. 影响（谁会踩）

  • 想用 focused 控索引膨胀的人：聚焦档的核心卖点就是"只留主要对象、避免索引被顺带提到的东西撑大"，而现在这条泄漏几乎抵消了它一半的效果。
  • 想用 extraction_instructions 指定领域重点的人：Pass 0 会听你的，但引用阶段仍按自己的标准继续补条目——用户设的"视角"其实只管上半场。
  • 想比较三档粒度的人（比如我们）：只看 candidates= 会得出"focused 极有效"的错结论；必须看合并后候选数／落库页数。

注：这不必然意味着作者"漏了"。另一种解释是"有意让发现与裁剪解耦"——发现交给模型、裁剪交给下游。但即便如此，至少文档与配置语义需要对齐：现在的字段说明是"Pass 0"，而界面文案给人的印象是"控制这套 wiki 抽多少"。

5. 最小修复建议（三个选项，按代价从小到大）

选项改法代价／风险
A. 让补 slug 也看粒度（推荐）把 Granularity／GranularityGuidance 传进 WikiChunkCitationPrompt，并在 "Secondary task: new slugs" 里加一句"严格按 {{.Granularity}} 的范围补"（focused 时可要求"除非是文档主要对象，否则不要新增"）改动小（一个提示词 ＋ 一处调用）；风险是会让 focused 的召回更窄——但那正是用户要的
B. 给补 slug 加开关新增 wiki_config.allow_discovery（或 discovery_scope），默认开；想要"严格 focused"的人可关掉更明确，但多一个配置项；需要同时决定默认值
C. 只改文档／界面文案把字段说明与界面提示改成"仅控制 Pass 0 候选抽取；补充发现不受此影响"零风险，但用户拿到的仍是"半个旋钮"

我倾向 A：既然 extraction_instructions（领域重点）已经在 Pass 0 生效，那"补 slug"不读它更像是管道没接完；A 是把手接上，B 是加阀门——两者可以同时做（A 打底、B 给极端需求）。

Title: wiki_config.extraction_granularity only governs Pass 0 — the citation stage's "new_slugs" discovery ignores granularity (and extraction_instructions)

### What happens

`wiki_config.extraction_granularity` (focused / standard / exhaustive) is only applied to Pass 0
candidate extraction. `WikiChunkCitationPrompt` has a secondary task that can add
entities/concepts that are not in the candidate list (`new_slugs`), and that call receives
neither the granularity guidance nor the user's `extraction_instructions`. The newly
discovered slugs are then merged into the item set and end up as wiki pages.

### Why it matters

With `focused`, Pass 0 honors the guidance (it extracted 6 items for a 28,956-char document,
matching the prompt's "at most 3-7 items"), but the citation stage added 14 more — i.e. 70% of
the resulting 20 pages came from the stage that ignores the setting. `focused` therefore only
halves the page count instead of shrinking it to the document's main subjects. The same
asymmetry applies to `extraction_instructions`: it steers Pass 0 but not the discovery channel.

### Where (v0.8.2, commit 3e8b0bf)

* `internal/types/wiki_page.go:529` — the field comment itself says "ExtractionGranularity
  controls how many candidate slugs **Pass 0** extracts per document".
* `internal/application/service/wiki_ingest_cite.go:97-105` — Pass 0 receives `Granularity` /
  `GranularityGuidance` / `CustomInstructions` / `InstructionScope`.
* `internal/application/service/wiki_ingest_cite.go:284-288` — the citation call passes only
  `CandidateSlugs` / `ChunksXML` / `Language`.
* `internal/agent/prompts_wiki.go:260` (`WikiChunkCitationPrompt`) — "### Secondary task: new
  slugs" has a fixed criterion ("Only add genuinely new, substantively-discussed items"), and
  the template contains no `{{.Granularity}}` / `{{.GranularityGuidance}}` placeholder at all.
* `internal/application/service/wiki_ingest_cite.go:463` (`mergeCitationsIntoItems`) — the
  returned `new_slugs` are appended to the entity/concept slices, so they become pages.

### Minimal reproduction (same document, two fresh knowledge bases)

1. create a `type=wiki` KB with `wiki_config.extraction_granularity = "standard"`, ingest the
   document, then read the ingest stats line:
   `candidates=43 chunks=70 batches=3 cited_chunks=68 uncited_slugs=0 new_slugs=9`
2. create a second `type=wiki` KB with `extraction_granularity = "focused"`, ingest the same
   document:
   `candidates=20 chunks=70 batches=3 cited_chunks=56 uncited_slugs=0 new_slugs=14`
   (Pass 0 extracted 6 items; the other 14 came from the citation stage)

`candidates` is the post-merge total; `new_slugs` counts the items added by the citation stage.
Read them with: `docker compose logs app | grep "mapped knowledge"`.

### Suggested fixes

* (preferred) thread the granularity through to the citation prompt and make the secondary task
  respect it — e.g. with `focused`, only add items that are primary subjects of the document;
* and/or add an explicit switch (`wiki_config.allow_discovery` / `discovery_scope`) so a strict
  `focused` run can suppress discovery entirely;
* at minimum, align the field docs / UI hint with the actual scope (Pass 0 only).
