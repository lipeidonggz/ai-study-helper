地图 · 先建立全局认识（一屏看完）

0 · 这是什么，读完能得到什么

GraphRAG 的"索引"＝把一堆原始文档，变成一组"能被检索和总结的结构化材料"的过程。它主要干两件事：先把语料抽成一张实体关系图，再把图切成一片社区森林（每个顶层社区各自是一棵树，彼此不相交），并给每个社区写一份报告。

读完这份你能：① 说清索引产出什么、每样给谁用；② 用最小配置把索引跑通（并知道最小链条为什么最小）；③ 知道跑完先检查什么（因为它的失败大多是静默的）；④ 知道参数挂在哪一步、该怎么挑；⑤ 知道它不擅长什么。

本文引用的两篇语料（后面提到就只用括号里的简称，不需要看别的材料）：
· Anthropic 篇：《How we contain Claude across products》——Anthropic 官方工程博客（2026-05），讲 Claude 三个产品怎么用沙箱、虚拟机、出网管控把"爆炸半径"框住。英文，约 2.9 万字符。
· 判官篇：《判官不稳定时，先别换判官——一次 LLM-as-Judge 的完整排查实录》——沛东自己写的 LLM 判官评测排查实录。中文，约 2.7 万字符。
两篇都是万把 token 量级的小语料：观察产出形状够用，但代表不了真实知识库的规模。

1 · 它产出什么（输入 → 六张表 → 谁消费）

输入就是 input/ 下的文档（一个 txt 也能跑；文档标题默认取文件名）。产出是几张 parquet 表，各自的角色差别很大——这是最该先看的一节：

表一行是什么在系统里的角色被谁消费
text_units一个文本块（chunk）事实源——引用最终落到这里basic / local 检索、报告生成
entities一个实体结构：图的节点社区聚类、local 检索、报告生成
relationships两个实体间的一条关系结构：图的边同上
communities一个社区（含层级、父子、成员）索引层的组织方式（不是事实）报告生成、查询侧选社区
community_reports一个社区一份 LLM 写的报告给 LLM 读的材料（不是给机器查的）global search（map-reduce）、local search
documents一篇文档辅助（标题 / 全文 / 时间）切块与溯源

✅ 实测：以上表名与字段来自三次实验的实际产出；"谁消费"部分见 0031 与 0029。

1.1 这里的"图"，不是 RDF 那种知识图谱

名字里都有"图谱"，但 GraphRAG 的图跟 RDF / 本体式知识图谱是两套东西。差别集中在"一条边怎么表示"上：

RDF / 本体式知识图谱GraphRAG 的 relationships 表
一条边长什么样三元组（主语，谓词，宾语），如 Claude foaf:knows X（source，target，description）——根本没有谓词列
谓词从哪来受控词表 / 本体，可枚举、可推理、可约束方向没有词表。关系"是哪种"，只体现在那句自然语言描述里
同一对节点多条关系可以（不同谓词各一条）合并成一条：按 (source, target) 分组，描述接成一段、weight 相加 📄
边上额外的字段一般只有谓词description、weight（LLM 打的关系强度）、combined_degree（两端度数之和）、text_unit_ids（证据块）
方向由本体定义由抽取时的措辞决定，没有约束保证（方向错了就指到错的 chunk）
性质断言（说它是事实）索引——事实在 chunk 里，边靠 text_unit_ids 指回去

拿判官篇真跑出来的两条边看最清楚（来自 data/tmp/graphrag-exp-juejin/output-v4/relationships.parquet）：

source: 判官            target: LLM-AS-JUDGE
description: “判官”（LLM-AS-JUDGE）是 LLM-as-Judge 评测方法的核心角色，其名称即该方法的简称……
weight: 18.0    combined_degree: 32    text_unit_ids: 2 个块

source: FLIP-RATE       target: JUDGE CONSISTENCY
description: flip-rate 是 judge consistency 的操作化定义
weight: 7.0     combined_degree: 7     text_unit_ids: 1 个块

这两条边的语义完全不同——一条说"是同义简称"，一条说"是操作化定义"——但这个差别只存在于那句话里，表里没有任何字段能区分它们。在 RDF 里，"把某类关系全查出来"是一条 SPARQL；在这里，你只能对描述文本做模糊匹配。✅ 实测：这一轮 120 条关系里，没有任何一对 (source, target) 出现两次——多块文本提到同一对实体就合并成一条、强度相加（有 14 条关系的证据块不止一个）。所以"同一对实体之间存在多种关系"这件事，在这个数据模型里表达不出来。

2 · 完整流水线：十个步骤，每一环在决定什么

官方 --method standard（标准索引链）就是下面这十步。其中真正写向量库的只有第十步（嵌入＝embedding，把文本变成向量，供查询时按语义找近似），它才是真实环境里必配的环节：

#步骤它在决定什么贵不贵 / 会不会静默出错
1load_input_documents读 input/ 下的文档 → documents 表（标题默认＝文件名）不花钱；多文件源只取第一个文件是已知限制 📄
2create_base_text_units切块 → text_units 表。chunk 是后续一切引用的落点（"事实源"）不花钱（纯本地）
3create_final_documents整理出对外版 documents 表不花钱
4extract_graph抽实体与关系——范围由实体类型表（靶子）＋提示词决定最贵（每块 1＋gleanings 次调用，默认 2 次）
5finalize_graph合并与裁剪：丢掉"引用了不存在实体"的边不花钱；会静默丢（只打 warning）
6extract_covariates抽 claim（关于某个实体的、可能带时间限定的断言）默认关闭 📄
7create_communities层次聚类成一片社区森林 → communities 表不花钱；use_lcc 会静默排除一部分实体（见 5.1）
8create_final_text_units给每个 chunk 挂上反向引用（这个块里出了哪些实体 / 关系 / claim），就地重写 text_units 表不花钱；与嵌入无关（见 2.2）
9create_community_reports为每个社区写一份报告（喂给 LLM 的材料）较贵（每社区一次）；失败静默（见第 4 节）
10generate_text_embeddings算向量并写向量库——唯一的嵌入步骤（详见 2.2）按 token 计费

补一句"树还是森林"：是森林。算法是层次 Leiden（hierarchical Leiden，📄 graphs/hierarchical_leiden.py），它在整张图上一次划出若干互不相交的顶层社区，每个顶层社区自己再往下分层成子社区——所以 communities 表里 level = 0 的行有好几个，它们是各棵树的根（parent 为 −1），而不是只有一个根。✅ 实测：判官篇那一轮 8 个根、Anthropic 篇 9 个、两篇混跑 14 个。顺带一个观察：这些根的"深浅"并不一样——判官篇 8 个根里有 4 个一个子社区都没有（它的最细粒度就是顶层），另 4 个往下分了 3–4 个子社区。这正是 0031 里"顶层社区天然大小不同 ⇒ 让用户指定层级不是个好设计"那条结论的数据来源。

2.1 官方三种套餐，以及全部 22 个可配环节

流水线不是一个写死的程序，而是一份"只跑我要的步骤"的清单（配置项 workflows，组合逻辑在 index/workflows/factory.py 📄）——这是所有小实验能成立的前提。官方内置三种组合：

套餐由哪些步骤组成什么时候用
--method standard上面那十步（LLM 抽图 ＋ 图上下文写报告）默认；质量优先
--method fast把"LLM 抽图"换成句法抽图（extract_graph_nlp ＋ prune_graph），报告也换成用"文本块原文"做上下文（create_community_reports_text）不调 LLM 抽图，便宜快；用质量换成本
--method standard-update / fast-update上面两种 ＋ 八个 update_* 步骤增量索引（见 0030）

自己拼的话，可选单步一共 22 个（📄 源码 index/workflows/，graphrag 3.2.0）：

环节它做什么
load_input_documents / load_update_documents读全量输入 / 读增量输入
create_base_text_units / create_final_text_units切块 / 整理对外版文本块
create_final_documents整理对外版文档表
extract_graph / extract_graph_nlpLLM 抽实体与关系 / 句法抽图（不调 LLM）
prune_graph / finalize_graph剪掉低频节点（fast 链）/ 合并与裁剪
extract_covariates抽 claim（关于实体的、可能带时间限定的断言）
create_communities层次聚类成社区森林
create_community_reports / create_community_reports_text写社区报告（图上下文 / 文本块原文上下文）
generate_text_embeddings算向量、写向量库
update_*（八个）增量链：文档 / 实体关系 / 文本块 / claim / 社区 / 报告 / 向量 / 状态清理

2.2 嵌入（embedding）不是可选项

十步里写向量库的只有第十步 generate_text_embeddings。容易看错的是第八步 create_final_text_units——它名字像"为嵌入做准备"，其实跟嵌入没关系：它只处理 chunk（流式读 text_units，给每块补上 entity_ids / relationship_ids / covariate_ids 三个反向引用列，就地重写同一张表；被嵌的 text 字段一个字符都没动 📄）。它的用途在查询与溯源：拿到一个块，能直接知道"这块里出了哪些实体、哪些关系"。顺带一句：它在报告生成之后才跑（排在第九步后面），所以也不可能成为报告的前置。

写向量库这一步嵌哪三样东西（配置项 embed_text.names，默认全开 📄）——注意它不只是嵌 chunk：

向量取自哪张表 / 哪个字段查询期谁在用它
text_unit_texttext_units.text——每个 chunk 的原文basic search 的"块向量 top-k"
entity_descriptionentities 的标题拼描述（title:description）local search 找入口实体
community_full_contentcommunity_reports.full_content——每份报告的全文查询时定位相关社区

同一行还有一条护栏：某个字段要嵌，但它的源表不在产出里（比如没跑报告那步），它就 warning 一句然后跳过，不会崩（📄）。

默认配置：嵌入模型 text-embedding-3-large（3072 维），向量库 LanceDB（vector_store.type 的默认值 📄）。成本注意：报告全文那一份通常最贵——报告本身就不短（我们测到的中位数在 2–3 千字符量级）。

所以"跳过嵌入"只在一种场景下成立：这次只看索引产出、不打算查。跳过之后产出里就没有向量库，将来想查还得把这一步补跑。

2.3 最小可跑集合：六个步骤，以及为什么少不了谁

从上面十步里摘掉四个（第十步嵌入、第八步补反向引用、第三步对外版文档、第六步 claim——后者默认本来就不跑），剩下的就是能一路跑出社区报告的最小链，六步：

load_input_documents → create_base_text_units → extract_graph
→ finalize_graph → create_communities → create_community_reports

为什么是这六步——不是随手删的，是按"下一环读什么"倒推出来的（📄 看每个 workflow 打开哪张表即可）：

步骤它读什么它写什么少了它会怎样
load_input_documentsinput/documents没有文档，切块没有原料
create_base_text_unitsdocumentstext_units抽图没有输入
extract_graphtext_unitsentities ＋ relationships没有图，聚类无从谈起
finalize_graphentities ＋ relationships清洗后的同一对表后面会拿到"指向不存在实体"的边
create_communitiesentities ＋ relationshipscommunities没有社区，报告无从谈起
create_community_reportscommunities ＋ entities ＋ relationshipscommunity_reports——（终点）

砍得掉的其实只有三类"收尾 / 服务端"的步骤，都不是主线：

  • 第十步 generate_text_embeddings——只服务查询期，本次只看索引产出，跳过能省一笔钱；
  • 第八步 create_final_text_units——只是给 chunk 补反向引用（嵌入不依赖它，见 2.2），跳过就等于放弃"块 → 实体/关系"的反查能力；
  • 第三步 create_final_documents——报告生成并不读 documents（create_community_reports 只开 communities / entities / relationships 三张表，📄）。

外加第六步 extract_covariates 默认就关。我们实跑时把第三步留着了，因为想让产出里也有一份整齐的 documents 表（不花钱）；第 3 节的最小配置为把"最小"讲干净，就按这六步写。

反过来讲：这六步里没有一步是"可选"的——每一环的输出，正好是下一环的输入。

动手 · 先跑起来，再谈调优

3 · 最快跑通

① 准备输入：把文档放进 input/（.txt 最省事；标题取文件名，想好看就把文件命名好）。

② 最小配置（settings.yaml）——注意这里故意不配 embedding_models，理由见 ③：

completion_models:
  default_completion_model:
    model_provider: <provider>        # LiteLLM 前缀，如 deepseek / openai
    model: <model>
    auth_method: api_key
    api_key: ${YOUR_API_KEY}          # 从环境变量注入
    call_args: { timeout: 180, num_retries: 2 }   # 不设超时会卡死（我们卡过 8 分钟）
concurrent_requests: 4                # 默认 25 容易把 API 打急
workflows: [ load_input_documents, create_base_text_units, extract_graph,
             finalize_graph, create_communities, create_community_reports ]
cache:     { type: json, storage: { type: file, base_dir: cache } }
reporting: { type: file, base_dir: logs }

③ 跑的命令，以及那条看起来自相矛盾的开关：

graphrag index --root . --skip-validation

--skip-validation 的意思是：跳过"预检"，不是跳过某个步骤（📄 它跳的是 validate_config_names）。预检做的事是——给配置里每一个模型发一条测试消息：每个对话模型试一次完成调用，每个嵌入模型试一次嵌入调用。于是：

  • 你没配 embedding_models、也没跑嵌入步骤 ⇒ 预检确实没得可试，安全；
  • 你配了 embedding_models 但填的是占位 key（我们早期就是这么干的）⇒ 预检会真去调它，直接 401 失败（✅ 实测）；
  • 所以口径是二选一：要么"不配嵌入 ＋ 加 --skip-validation"，要么"把嵌入配真 ＋ 不加这个开关"。上面那个配置示例属于第一种，配它自己的命令就是这个开关——两处并不矛盾。

④ 另一条必知坑：settings.yaml 里任何字面 $ 都会炸——它用 string.Template 做环境变量替换，连注释里的也算。我们踩了三次（给文件匹配规则写正则的结尾锚、在注释里写出占位符的完整写法……全是它）。

⑤ 先别动提示词和参数：先用默认跑一轮，拿到"默认长什么样"的基线，再改（不然没有对照）。

📄 源码：配置字段与默认值都没抄文档，直接读本地已安装的 graphrag 3.2.0（config/defaults.py 与 workflow 注册表）。

4 · 跑完先验收（因为它的失败大多是静默的）

先看四件事：① 实体 / 关系规模 ② 社区数 ③ 报告数 ④ 关系有没有被丢。核心动作是"对账"——拿集合相减，而不是看指标：

# 社区集合 − 报告集合 = 没写出报告的社区（本仓库脚本：data/tmp/graphrag-exp-juejin/_list_reports.py）
communities 的 community 集合  −  community_reports 的 community 集合
静默行为实测表现为什么指标看不见
社区报告没生成判官篇 prompt-tune 那版：64 个社区只出了 52 份（缺 12）；判官篇改完报告提示词那版：21 → 19（缺 2）；Anthropic 篇默认：23 → 20（缺 3）；两篇混跑：85 → 74（缺 11）失败发生在"LLM 返回 → 解析成 schema"这一步，HTTP 调用是成功的 ⇒ 不进 failed_response_count（✅ 实测：指标全绿与丢掉 19% 的报告同时存在）
关系被丢弃日志一行 Dropped N relationship(s) referencing non-existent entities只打 warning，不进任何计数字段
实体根本没进社区判官篇那一轮：抽出 101 个实体，最终只有 74 个能被任何社区报告覆盖不是失败、是 use_lcc 的设计行为，但没有任何提示（见 5.1）
方法：要判断"有没有丢"，拿集合对账，不看指标。指标的边界由埋点决定（这里埋的是"调用层"），而失败常发生在"产出层"。

调优 · 参数挂在哪一步、怎么挑

5 · 每一环可调的参数：先看角色 → 再定该测什么

按步骤挂（你要改东西时，先看它属于哪一步）：

属于哪一步参数它的角色因此该测什么
切块chunking.size（默认 1200 token）/ overlap（默认 100）决定"事实源"的粒度与块数抽取精度 × 成本。推荐值会随 LLM 代际过期，不必照搬（🤔）
抽图extract_graph.entity_types（默认 organization / person / geo / event）＋ 抽取提示词（含语言、示例）抽取范围的靶子；查询期根本不读 type范围与成本，不是分类正确率（✅ 实测：查询期零使用）
抽图max_gleanings（默认 1）召回开关：先断言"你漏了很多"，再让模型补一轮召回收益 vs 硬凑噪音（两者同源）
聚类cluster_graph.max_cluster_size（默认 10）/ use_lcc（默认 true）决定社区层级；use_lcc 决定哪些实体根本不进社区（见 5.1）覆盖面（✅ 实测：被判"串味"的实体，正是被 use_lcc 挡在社区外的）
写报告community_reports.graph_prompt / max_length（默认 2000）/ max_input_length（默认 8000）报告的语言与口径、输出长度、上下文预算可读性 / 信息量 vs token（✅ 实测：报告提示词译成中文后，报告长度中位从 2,749 字符降到 1,946）
嵌入embed_text.names / embedding_models / vector_store嵌哪三样、用哪个模型、存哪个库查询召回 vs 索引成本（见 2.2）
全流程workflows决定跑哪些步骤成本 / 耗时最直接的开关
为什么"角色"是这一节的核心：同一个字段，角色不同、要求就不同。entity_type 在 GraphRAG 里只是抽取提示词的参数（查询期零使用）⇒ 分类粗、偶尔归错都不算缺陷；但如果哪天它进了检索或路由，归错就变成漏召回，分类正确率立刻升级成硬要求。（已写进 AGENTS.md 的"判据纪律"第①条。）

5.1 use_lcc：决定"哪些实体根本不进社区"

名字是 largest connected component（最大连通片）。它的行为写在 graphs/stable_lcc.py 里，一共做三件事（📄）：

  1. 只保留最大连通片上的边——只在关系图上留下那个节点数最多的连通片（连通片＝在这个无向视角下能互相走到的节点集合），连不到它的节点与边全部丢掉；
  2. 归一化实体名（HTML 反转义、转大写、去空格），让"同一实体的不同写法"不至于把图撕开；
  3. 把每条边的方向按字典序摆平（名字小的当 source）——也就是说，社区划分实际上是在"无向图"上做的，边的方向只对最终那张关系表有意义。这一条其实在调 use_lcc 之前就已经做过一遍：cluster_graph 先把每条边两端按字典序排好并去重，源码注释直接写着 Normalize edge direction and deduplicate (undirected graph)（📄）。

一个容易混的细节：这三件里只有前两件归 use_lcc 管——把它关掉，连通片过滤和实体名归一就都不做了（后者不做，意味着大小写/空格不同的同一实体可能被当成两个，进而把图撕成更多小片）；第三件（方向摆平）无论开关都会发生，因为 cluster_graph 自己要先做一遍。

所以 use_lcc: true（默认）意味着：不在最大连通片上的实体，在聚类之前就被排除了，永远不会属于任何社区，也就永远不会被任何社区报告覆盖。实测后果（判官篇那一轮）：

抽取到实体            101 个
其中出现在关系里的      99 个   （另 2 个一条边都没有）
最大连通片上的节点      74 个   ⇒ 25 个节点在聚类前被丢掉
最终能被社区覆盖的实体   74 个   ⇒ 27 个实体一个社区都进不去

被挡在社区外的都是谁？看名字就知道它们为什么连不上主片：一串虚构地名和人名（白丘国、碧石监狱、苏小满、林柏舟、陈立诚、云溪……），加上仓库路径这类"语料里只出现过一次"的字符串——它们各自三两相连、自成小片。这些多半是语料里的噪声，被 use_lcc 顺手清掉了——这既是它的好处（自动去噪），也是它的代价（它不区分"噪声"和"稀但真实的旁支"）。

所以怎么决定：想要覆盖面、宁可多留噪声，就把 use_lcc 设成 false——代价是那些孤立小片会各自成社区，报告数量与成本一起上涨；想要干净、接受"稀有的东西看不见"，就保持默认。关键是知道这道闸门存在，并且它不打招呼。

6 · 要调优时：怎么挑值

  1. 固定其他旋钮，只扫一个——chunk 大小 / gleanings / 类型表，全都属于"最后都落到抽取范围"的那一类，一起动就说不清是谁的功劳；
  2. 用一份"抽取范围"小金标准对账：必须抽到的命中了几条、明显不该进来的进来了几条；
  3. 挑值。理由：这些参数与所用的 LLM 强绑定，纸面推荐值只说明方向（🤔）。

金标准只要"范围"这一级就够（不需要逐条完美），否则维护成本会失控。

7 · prompt-tune：调优的第一步，不是可选项

为什么把它放在调优里、而不是"可选工具"：官方默认提示词是给英文通用语料写的。换一篇别的语言 / 别的领域的语料，产出会明显变形（我们第一次跑判官篇，图与报告全变英文，实体类型也是英文通用那四类）。prompt-tune 做的事就是"用你自己的语料，反推一份适配的提示词"，一次跑几十美分，后面所有调参都建立在它给的基线上——所以它是调优的推荐起点。

一次跑产出六样（都落成文件）：领域推断 · 语言检测 · persona（角色设定）· 实体类型表 · few-shot 示例 · 评分标准（带锚点），写成三份提示词：

prompts-tuned/extract_graph.txt              # 抽图提示词（含实体类型表与示例）
prompts-tuned/summarize_descriptions.txt     # 实体描述摘要提示词
prompts-tuned/community_report_graph.txt     # 社区报告提示词（含评分口径）

采样：先全量切块（本地、零 token），再按选法抽块（📄 prompt_tune/loader/input.py）：

--selection-method实现性质
top取前 --limit 块（默认 15）系统性偏向文档开头 / 排在前面的那一篇（✅ 实测：两篇混跑时，示例全取自第一篇）
random（默认）随机抽 --limit 块无偏但样本小，且没有固定种子、不可复现
auto随机抽 ≤--n-subset-max（默认 300）块去嵌入 → 再取离质心最近的 --k（默认 15）块意图是"选最主流 / 最有代表性"；实现有缺陷（见下）；也是唯一会真调嵌入的选法
all全部块样本最大、也最贵

两处已知实现缺陷（📄 源码 prompt_tune/loader/input.py）：

  1. auto 的行号错位：抽样后的块存在另一个变量里，但最后取"离质心最近"时用的仍是原始顺序的整张表、拿位置索引去取 ⇒ 取到的不是"离质心最近"那些块，实际退化成文档开头那几块；
  2. 块数少于 15 会直接崩：越界时它先把 limit 回落成 15，再无条件 sample(15)。

产出的性质（✅ 实测）：

  • 类型与 persona 能跨领域融合：Anthropic 篇（英文·安全）＋判官篇（中文·评测）一起跑，得到一份 13 类、覆盖两边的类型表（organization / product / person / security_threat / security_defense_mechanism / evaluation_concept / benchmark / standard_or_framework / software_tool / academic_paper / code_repository / technical_publication / metric）；
  • 语言只能挑一个：检测到中文就把三份文件都写成 Chinese ⇒ 英文那一半的描述与报告会被译成中文。对"报告服务于分析者阅读"的定位来说可以接受，但换语料必须重跑；
  • 示例取自语料自身 ⇒ 它调的是"这一篇"的适配，不是"整个库"的适配；
  • 评分口径不保证有区分度：判官篇那一轮里，48/52 份报告的 rank 挤在 8–10 分（见第 8 节）。
能信到什么程度：把它当"给这一批语料、这一种语言"定制提示词的发生器，不要当通用提示词库。另外 limit / n-subset-max / k 都是命令行参数（没写死），缺的是"这是个成本 / 代表性的折中"这件事没在 --help 里表达出来（🤔）。

边界 · 它不擅长什么

8 · 已知边界与接口提醒

  • 实体类型不参与检索：entity.type 在查询期完全不被读取（✅ 实测：66 个 .py 文件里零命中）⇒ 别指望靠它做过滤或路由。
  • 社区报告可能缺：同一批语料里丢哪几个社区，每次都不一样（✅ 实测：判官篇第三版丢 #4；第四版丢 #9 / #18；prompt-tune 那版丢了 12 个）⇒ 是调用级的抖动，不是某个社区本身有问题。
  • 报告里的 rank 不保证有区分度：它的口径由报告提示词决定。prompt-tune 生成的那版在"与领域的相关性"口径下，判官篇 48/52 份挤在 8–10 分（✅ 实测）⇒ 想拿它排序或过滤，口径必须选一个"语料内部有方差"的维度。
  • 提示词换语料就得换：语言、领域、类型、示例全被烧进提示词文本里（✅ 实测：把判官篇调好的提示词套到 Anthropic 篇上，报告 100% 变中文，而且标题里出现"判官 / 金标准"这类另一篇的主题词——同时还会长出新的垃圾桶，比如 44% 的实体被归进 TECHNICAL TERM）。
  • 还有一条来自源码的限制：实验脚本读 input 时，多文件源只处理第一个文件（📄）——这是 graphrag 工作流的既有行为，不是配置问题。
  • 查询侧别按"层"的直觉去理解：默认模式的 community_level 实际是"level ≤ N 全给"（原本的"每个实体取最深社区"那套 roll-up 自 v2.0.0 起失效）⇒ 细节见 0031，问题单见 issue #2573。
