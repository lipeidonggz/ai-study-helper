第一部分 · 思路简要描述 ＋ 结论

0. 起因与结论先放

知识图谱是 WeKnora 里第三条检索面（KB capability 里的 graph）。0049 已经确认：我们实验的三条路线里只有 smart 挂了 query_knowledge_graph，而 KB 本身没开 graph indexing ⇒ 图谱在 0045／0046／0047／0048 的全部数据里从未被执行。这篇把这条链读清楚，回答"值不值得深入研究"。

结论：框架层面已经够清楚了，不值得现在投入逐行研究；理由三条（§6），以及三个更值得做的实验（§6）。最要命的一条是：它在数据层就把"跨源连接"切掉了（§3）。
后续两次复核又把结论推得更硬：① 实测（§12）——默认配置下它连关系都抽不出来（612 节点／0 边），而检索侧要求有边才当种子 ⇒ 图谱实际处于不可用状态；② 界面复核（§13）——界面上那个好看的「图谱」是 wiki 页面链接图，真正的实体-关系图没有任何可视化入口。合起来一句话："真知识图谱"在 WeKnora 里还没做起来。

2. 编译（抽取）过程

  1. 触发：知识 post-process 阶段，只有 IndexingStrategy 开了 graph indexing 才走；selectGraphChunks() 先滤掉纯图片占位的块，然后逐 chunk 入队一个 ChunkExtractTask（knowledge_post_process.go，注释里还留意了 "graph with NEO4J…" 的计数槽）。
  2. 粒度与成本：每个 chunk 一次 LLM 调用（chat.Chat(..., purpose=entity_extraction)）。源码注释原话："Each graph extract is per-chunk and runs one LLM call — the most expensive enrichment fan-out in the pipeline."
    对照我们那份语料：572 段 → 1,408 块（其中 text 836）⇒ 光抽取就是上千次调用量级（可对照 wiki 全量编译的 7,010 次调用）。
  3. 提示词：config/prompt_templates/graph_extraction.yaml 两个模板（实体／关系）＋ 每个 KB／文件可配的 ExtractConfig（Description／Tags／Examples／CustomInstructions，见 extract.go:328）。规则要点见 §7。
  4. 落库：Neo4j ＋ apoc：节点 apoc.merge.node(labels, {name, kg: knowledge_id})，并 SET node.chunks = union(node.chunks, row.chunks)；关系 apoc.merge.relationship(source, row.type, {}, attributes, target)。labels ＝ namespace ＝ [KB, Knowledge]（原文见 §9）。
  5. 两个"丢东西"的点：① 关系只剩类型——结构体 GraphRelation 只有 Node1/Node2/Type，提示词要求的 description 与 strength（5–10 分级）根本没被解析、也没进图；② 关系类型没有白名单——本该按 Tags 过滤的 RemoveUnknownRelation() 在调用点被注释掉了（extract_entity.go:200 附近）。
  6. 删除路径是接好的：DelGraph(namespace) 出现在删文档／重处理／克隆移动／删 KB 等多条路径（这点比 wiki 那侧完整）。

3. 最要命的限制：图是"按文件切成子图"的

节点 merge key 是 {name, kg: knowledge_id} ⇒ 同一个实体在不同文件里是两个不同节点，且文件之间没有边。于是：

  • "跨源连接"在数据层就不存在：按 KB 查询时能"撞见"多个同名节点，但看不到跨文件的关系；
  • 它能提供的实际是"实体 → 该实体所在 chunk"的额外召回通道。

这一条直接决定了我们对它的定位：它不是"关系查询/跨源连接"的载体，而是"实体维度的召回扩容器"。

4. 查询过程（两条用法）

  1. 检索流水线里的实体通道：search_parallel 并行触发 ENTITY_SEARCH → PluginSearchEntity 用 query 抽出的实体调 SearchNode（namespace 可整 KB、也可单文件）→ 拿回 nodes ＋ relations → 再映射回 chunk（用节点的 chunks 字段）。
  2. agent 工具 query_knowledge_graph：描述是"探索实体之间如何关联（例：Docker 与 Kubernetes 的关系），返回携带这些关系的 chunk（带 cN 句柄）"。
  3. Cypher 本身很"轻"（graphSearchCypher）：名字 子串匹配 ＋ 必须有边 → 排序是"精确名优先 → 名字短优先 → 字典序" → 取种子（≤200）→ 再取一跳邻域（≤2000 行）。⇒ 一跳、子串匹配、无谓词过滤、无权重排序（原文见 §8）。

5. 成本形状

逐 chunk 一次 LLM ⇒ 抽取成本大致是 O(chunk 数)；它跟 wiki 编译互不依赖（可以单独开），但同样属于"一次性重投入"。对照：wiki 全量编译 572 段 → 7,010 次调用／1,400 万 token（0045）；图谱这条量级相当甚至更高（每次都要吐 JSON 实体/关系，且没有 prompt 缓存友好的固定前缀设计）。

6. 判断：不值得现在深入；但有三件值得做

不值得深入的三条理由：

  1. 它先天拿不到我们最想要的那档能力——跨源连接在数据层被 per-file 切图掐掉；枚举靠"名字子串匹配 ＋ 一跳邻域"；关系没有谓词/权重可用。研究它，看到的是"它能做到什么"，不是"成熟范式长什么样"。
  2. 对我们已有数据的直接影响是 0：我们实验的 KB 没开 graph ⇒ 这条链一次都没跑（0049 §9.5）。
  3. Neo4j 适配层的细节只影响性能/运维（apoc 写法、索引、并发），不影响框架判断——逐行读性价比低。

值得做的三件事（按性价比）：

  1. 开一个 graph 小 KB，跑同一批题：看"实体通道"是加分还是噪声——正好接上已立项的"三档检索原语（块向量／主题标签／图谱）"待办。
  2. 专测跨文件同名实体：同一实体散在 3–5 篇文档时，per-file 切图会漏掉什么——这是"跨源连接"能不能兑现的直接检验。
  3. 把它丢掉的三样列成对照项（关系 description／strength、关系类型白名单）：若我们自己实现图谱，这三样是"便宜就能补"的差异点。

8. 查询 Cypher（neo4j/repository.go graphSearchCypher）

MATCH (n:` + labelExpr + `)
WHERE ANY(nodeText IN $nodes WHERE n.name CONTAINS nodeText)
  AND EXISTS { (n)--() }
WITH n, CASE WHEN n.name IN $nodes THEN 0 ELSE 1 END AS seed_rank, size(n.name) AS name_len, n.name AS name
ORDER BY seed_rank, name_len, name
LIMIT $maxSeedNodes          // 200
MATCH (n)-[r]-(m:` + labelExpr + `)
WITH n, r, m, seed_rank, name_len, name
ORDER BY seed_rank, name_len, name
LIMIT $maxRows               // 2000
RETURN n, r, m

注释还解释了排序的用意："Ordering by name alone lets an entity whose name is the query fall outside the cap once the substring matches exceed it." 以及"行数被截断时要显式告警，不要让人以为图里没有更多"。

9. 落库 Cypher（neo4j/repository.go addGraph）

-- 节点
UNWIND $data AS row
CALL apoc.merge.node(row.labels, {name: row.name, kg: row.knowledge_id}, row.props, {}) YIELD node
SET node.chunks = apoc.coll.union(node.chunks, row.chunks)

-- 关系
UNWIND $data AS row
CALL apoc.merge.node(row.source_labels, {name: row.source, kg: row.knowledge_id}, {}, {}) YIELD node as source
CALL apoc.merge.node(row.target_labels, {name: row.target, kg: row.knowledge_id}, {}, {}) YIELD node as target
CALL apoc.merge.relationship(source, row.type, {}, row.attributes, target) YIELD rel

merge key 里的 kg: knowledge_id 就是"按文件切图"的根源；row.attributes 在关系侧实际没赋 value。

读数二（比原判断更狠）：默认配置下这张图是"死的"。不配 ExtractConfig.Tags 时，一条关系都抽不出来（612 节点、0 边）；而检索侧的 Cypher 有一句 AND EXISTS { (n)--() } ⇒ 实体通道恒返回空。根因在提示词渲染（chat_pipeline/extract_entity.go QAPromptGenerator.System()）：模板字符串里的 "Allowed relationship types are: %s." 只在 Tags 非空时才做 %s 替换，Tags 为空时原样保留；同时 Examples 只要 len>0 就会渲染——从 API 建库时它是个空示例。⇒ 模型拿到的是"允许的关系类型 = %s"＋一个空例子，于是只吐实体、不吐关系。（另：config.yaml 里全局 extract_graph 自带的 tags: [Author, Alias] 与示例在这一路径上被 KB 的空 ExtractConfig 覆盖掉了。）

⇒ 对 §6 判断的加强：原来我们说"不值得深入"是因为跨源连接在数据层被切掉；现在实测又加一条——默认配置下连源内关系都不产出，图谱能力实际处于不可用状态（除非使用者自己配 tags 与示例）。这意味着：把它当"第三条检索通道"来评估时，必须先把 ExtractConfig 配对，否则测到的是"一个空通道"。

读数三（口径提醒）：同一篇 0042 在两次抽取里分别得到 184 与 250 个节点，差值来源未定——可能是 tags／示例改变了提示词，也可能只是 LLM 抽取自身的抖动（Temperature 0.3）。所以节点数这类量级指标只当参考、别当判据；本轮真正站得住的读数只有两条：跨文件边恒为 0（结构约束，与模型无关）与关系 0 → 24（方向性差异足够大）。第二次复核（同日，只读 Cypher 重跑）确认：全库 862 节点 ＝ 428 ＋ 250 ＋ 184，24 条边全部落在配了 tags 的那个库里，边类型只有 Alias(18)／Author(6)，跨文件边 0。

本轮核过的源码点（供复核）：① chat_pipeline/extract_entity.go:247-274 System()——len(Tags)==0 时不做 Sprintf，%s 原样留在提示词里；Examples 只要 len>0 就渲染。② service/extract.go:342-353——Examples 是写死的单元素切片（内容取 KB 的 ExtractConfig.Text/Nodes/Relations），默认配置下就必然是一个空示例；formatExtraction(nil,nil) 产出空 []、不报错。③ config/config.yaml:53-93——全局 extract_graph 自带 tags: [Author, Alias] 与 Romeo 示例，但在这条路径上被 KB 侧的空 ExtractConfig 覆盖。④ neo4j/repository.go:275 AND EXISTS { (n)--() }——没有边的实体连种子都当不上（这也解释了为什么"612 节点 / 0 边"等价于"实体通道恒空"）。⑤ extract_entity.go:170-180——抽取调用显式 Thinking: false（与 0049 §7.3 那张四格矩阵的"模型推理"一栏是一致的：抽取这层也没开推理）。

实测对账：exp-graph-tags／exp-graph-perfile 调 /wiki/graph → 400 error code: 1000, Wiki feature is not enabled for this knowledge base（两库 wiki_enabled=false，所以连那个 tab 都不渲染）；MuSiQue 库 /wiki/stats → total_pages: 4094（entity 2820／concept 701／summary 572／index 1）、total_links: 23393，/wiki/graph?mode=overview 默认只返回连接度最高的 500 个页面（前端注释明说是防止几万页把浏览器拖死）——界面上那个"全库 500"就是这个上限。图例里的 摘要／实体／概念／综合／对比 五种颜色＝wiki 页类型，与 0049 的页类型实测一致。

⇒ 结论（呼应 §6／§12）：① 界面上之前看到的"知识图谱很漂亮"，其实是 wiki 页面链接图，对 Neo4j 这条链没有任何证据意义；② 真正的实体-关系图在界面上没有任何可视化入口，只在检索期生效，而按 §12 的实测，默认配置下它还是空的 ⇒ "真知识图谱"在这套产品里还没做起来：没可视化、默认也没有可用产出，定位上更像"给检索加的一条弱通道"，而不是一个能独立交付价值的能力。

附：这也是为什么"把 WeKnora 当图谱范本来学"要谨慎——它展现给你的图谱能力（界面、演示）与实际实现的图谱能力（Neo4j 那条链）差着一截。
