Global Search · 基本模式（非自适应）

状态：✓ 已核（代码级；2026-09-22 起核，2026-09-26 重构定稿）· 一句话：把 level <= N 的全部社区报告当材料，用 map-reduce 生成一份"跨库综述"。

代码路径＝structured_search/global_search/{search.py, community_context.py}；提示词在 prompts/query/global_search_{map,reduce}_system_prompt.py。这里是机制正文；这条链上那段"roll-up 其实是空操作"的考古过程放在章末考古层，不看也不影响理解。

一屏流程（五步）

步骤做什么成本
第 0 步 · 选材料从 communities / community_reports 两张表里取出"报告集合"——当前版本 = level <= N 的全部报告纯本地

第 0 步 · 报告集合是怎么选出来的（这一步定死了后面拿什么当材料）

输入是两张表，输出是"报告列表"（read_indexer_reports）——"实体"只在中间露一次面：explode("entity_ids") 出来的那一列，而且那列是 entity id（哈希）、不带实体名。函数 docstring 用的是旧版的实体口径（"the max community level that an entity belongs to"），而代码早已换成社区口径——两套口径混在一段话里，读起来自然拧巴。这是上游的语义漂移被我们读出来了，不是我们没读懂。

表一行是什么关键列title 是什么
communities
社区表（层级结构）		一个社区community / level / parent / children / entity_ids / size"Community N"（create_communities.py 末尾直接拼字符串，N＝社区 id）
community_reports
报告表		一个社区一份 LM 报告community / level / summary / full_content / rank / findingsLM 生成的报告标题（如 "Paranormal Military Squad and Operation Dulce"）

默认模式（dynamic_community_selection=False）下，代码只有四件事：

  1. 社区表 explode 成"社区 × 成员实体 id"的长表：nodes_df = communities.explode("entity_ids")——这是"实体"唯一的出场（一行＝某社区带了它的某一个成员实体）。
  2. 两张表各按 level <= N 砍一刀：社区侧砍 nodes_df，报告侧砍 reports_df（报告表的 level 是索引期从社区表 merge 过来的，见 finalize_community_reports.py）。N ＝ 外部必填的 community_level。
  3. 按 title 分组、取 community 最大值：groupby(["title"]).agg({"community": "max"})——代码注释写着 # perform community level roll up，docstring 称它是"每个实体只留它所属的最深社区"。但这一步在当前版本是空操作（为什么，见考古层）。
  4. 用这组 community id 与报告表 inner merge ⇒ 输出＝报告集合（不是实体集合、也不是社区集合）。
于是 community_level 的实际语义（本节最重要的一段）：
· ＝ "报告集合 ＝ level <= N 的全体报告"，外加一条几乎恒真的约束（报告所属社区必须能在社区表里找到对应行）。
· community_level = None：不过滤 ⇒ 全部社区、所有层的报告。
· 它不是"选第 N 层"：API docstring 写 "the community level to search at"、notebook 注释写 "higher value means more fine-grained"——说法都是"那一层"，实现是"≤N 的所有层"，而且偏差方向是"给得比说的多"（把更粗的层全塞了进来）。
· 模型不知道自己在读哪一层：read_community_reports 只映射 id / title / community / summary / full_content / rank / attributes——level 没进对象，上下文表头里也没有 level 列。
· "max(community id) ≡ 最深"这条前提只在 roll-up 生效时才有意义；当前版本它不参与任何实际判断（留作历史理解）。
· 开 dynamic_community_selection 时整个 merge 被跳过，这个参数的语义变成"最多下探到哪一层"（见下文"可选第二条路径"）。

层从哪来：外部传参，不是自适应——但"默认值"各入口自己给，给的还不一样（2026-09-27 更正：此前写"外部指定，且必填"，不准确）：① Python API（api.query.global_search / ..._streaming）里 community_level 没有默认值（类型是 int | None）⇒ 不传直接报错，但传 None 合法、含义是"不过滤"；② CLI（graphrag query，默认 -m global）的 --community-level 默认值 = 2（cli/main.py 的 typer.Option(2, ...)）⇒ 命令行里不用填，但默认值是 2、不是"全层"；③ notebook 写常量 COMMUNITY_LEVEL = 2（与 CLI 同）；④ 配置 GlobalSearchDefaults 里没有这一项（只有 max_context_tokens = 12_000、dynamic_search_max_level = 2）⇒ 默认层由入口给、配置层不管。⇒ 准确说法：没有任何"自适应"，这个决定的承担者始终是调用方（要么接受入口默认值，要么自己选）；两端语义差别很大——None ＝ 不过滤 ＝ 全部社区所有层，数字 N ＝ level <= N。

层的高低意味着什么：C0 ＝ 根（社区最少、每个最大），越往下越细（社区更多、报告更多更短）。所以选高层 ⇒ 材料更细但更贵（每次要扫 level ≤ N 的全部报告）。选层是个裸超参——论文 §4 专门做实验比较"哪层最好"（结论：C0 明显差，C1–C3 在各数据集／指标上互有胜负，没有通用答案），这本身就说明没有默认答案。

第 1 步 · 装配上下文（GlobalCommunityContext.build_context）

  1. 算社区权重（仅当传了 entities 且报告尚无该属性）：遍历实体 → 取 community_ids → 把 text_unit_ids 累加到对应社区 ⇒ 权重 ＝ 该社区内所有实体关联的去重 text unit 数，再按最大权重归一化到 0–1，写进报告 attributes（默认名 occurrence weight）。⇒ 这就是 notebook 那句 "community weights for context ranking" 的实义：一个"社区里有多少独立文本块"的体量指标，不是相关性。作用：给"批内排序"提供第一关键字（体量大的社区在批内更靠前）；归一化让它变成相对量、便于跨数据集比较。
  2. 筛：report.rank >= min_community_rank（默认 0 ⇒ 全过）。此 rank 是报告自己的重要性分（记录 ㉓），不是查询相关度。作用：给使用者一个"直接砍掉低重要性报告"的阈值（省 token 的预过滤）；默认 0 等于不砍。
  3. 打乱（不是可选项）：random.seed(86) ＋ shuffle ⇒ 有固定种子的伪随机，同输入可复现（修正"随机分批"的笼统说法）。而且它关不掉（2026-09-27 核）：query/factory.py 构造 Global Search 时 context_builder_params 里 "shuffle_data": True 是硬编码；公共 API（api.query.global_search / ..._streaming）签名里没有这个参数、GlobalSearchDefaults 里也没有这一项 ⇒ 走 API／CLI／notebook 一律恒开，只有直接调底层 build_community_context 才谈得上关。关掉的后果（直接调底层时）：报告保留输入顺序 ≈ 社区 id 顺序 ⇒ 每批变成"连续一段 id"＝同层 ＋ 同子树扎堆，与设计意图相反。反证：local search 的上下文构造反而显式传 shuffle_data=False（local_search/mixed_context.py，它要的是局部上下文）——同一参数两条链取值相反，说明这是有意设计。作用：避免高价值信息集中在少数连续区域——即破坏"批次划分"与"任何使报告互相关联的维度"之间的对齐。不是特指"同主题"（相关还可能来自同父社区、同源文档、同一次入库批次）。两类真实的"顺序↔相关"对齐来源：① 社区表天然顺序（id 随深度递增、同父子社区相邻 ⇒ 同主题报告确实容易挨着，倾向、未完全核实）；② 增量入库分段（已证：旧报告在前、delta 报告整体偏移后拼接 ⇒ 同一批入库的报告连续排列，且同源性强）⇒ 增量之后"不打散"的危害比单次构建时更大。
    集中为什么有害（两条可核实的机制）：(a) map 单批输出有长度上限（max_length 默认 1000 词）⇒ 一批承载越多，压缩越狠、细节丢得越多；分散后每批只需覆盖一小块。(b) 批是失败的最小单元——JSON 解析失败/抛异常 ⇒ 整批归零（只打 warning，见第 2 步）⇒ 集中则一次失败全丢、分散则只丢一部分。⇒ 这才是"不要把所有鸡蛋放一个篮子"的可核实版本（它不是"防超窗"，也不是含糊的"防 LLM 抽风"，那两条已被否，见 0029 记录 ⑦「修正补记」）。固定种子则是"打散但可复现"的折中。
  4. 分批：逐条累加 token，超 max_context_tokens（类默认 8000；notebook 传 12000）即切批。GlobalCommunityContext 硬编码 single_batch=False（函数默认是 True，此处被覆盖）⇒ 走这条路一定是多批。作用：让每一批都装得进一次 LLM 调用（否则"没法 map"）；这一步不丢信息，只是切块——真正的丢弃发生在 reduce 的 max_data_tokens 截断。
  5. 批内排序 + 成表：切批时按 [occurrence weight, rank] 降序排，输出 | 分隔 CSV（表头≈id|title|…attributes…|summary 或 content|rank）⇒ 批间打散、批内有序，两个机制同时存在。作用：让体量/重要性更高的报告在批内靠前（影响模型阅读与注意力的先后）；成 CSV 是为了给模型一张带 id 的结构化表，好让它写出 [Data: Reports (…)] 这类引用。
  6. 有对话历史时（默认最多 5 轮、只用 user 轮）前置到每一批之前。作用：支持多轮指代（"那它的成本呢？"）；放在每一批之前，是为了让各批看到同样的上文、口径一致。

第 2 步 · Map（并行，一批一次调用）

  • 提示词：system = MAP_SYSTEM_PROMPT（带 {context_data} 与 {max_length}）、user = query；强制 JSON 输出。作用：这是"全量扫"的廉价实现——不做检索，让每一批自己摘出重要点并打分，把"筛选"推迟到 reduce；强制 JSON 是为了让分数与要点可程序化解析，而不是一段散文。
  • 产出解析成 points: [{description, score}] → 归一成 {answer, score}；并发由信号量控制（concurrent_coroutines=32）。作用：把"批"降级成"点集合"，让 reduce 能在一个列表上排序；并行＋信号量是为了让延迟与批数脱钩。
    但要更正一处（2026-09-22，沛东质疑）：本记录此前写"于是跨批可比（同一把分数尺）"，不成立——分数是每批独立自评的（模型只看本批那张表 + 一个没有细则的 0–100 要求），属"批内相对 ＋ 模型先验"，中间与高端跨批不可比；真正可比的只有"0 vs 非 0"这个二值门（0 的语义被明确定义：无可用信息）。而 reduce 提示词还断言"analysts' reports ... are ranked in the descending order of importance" ⇒ 系统把一个弱校准的排序当成可信输入，再据此降序截断 ⇒ 可能把最相关的点丢掉（排序不可靠 ＋ 硬截断）。这与我们项目里"分数区间重叠、无法定阈值"同源，只是发生在 LLM 自评而非嵌入相似度上。
    可复用判据：① 跨批/跨来源的分数要比较，必须先给评分标准 ＋ 锚点 ＋ 校准（或用成对比较）；② "统一了结构" ≠ "统一了刻度"。
  • 失败静默降级：JSON 解析失败 ⇒ 该批只产出 {answer:"", score:0}；抛异常 ⇒ 同样；只打 warning 日志。作用/代价：好处是不阻塞整条链（其余批照常出结果）；代价是答案会缺一块而没有显式提示——这正是我们最忌讳的"静默失败"形态。

map 提示词导读（prompts/query/global_search_map_system_prompt.py）

原文：global_search_map_system_prompt.py

  • 输入（两个模板变量）：{context_data} ＝ 一批社区报告拼成的 | 分隔表（表头 ≈ id|title|…attributes…|summary 或 content|rank）；{max_length} ＝ 要求的输出词数（默认 1000）。用户问题不在这里——它作为 user 消息单独传入（代码是 add_system_message(prompt).add_user_message(query)）。
  • 结构：---Role---（"helpful assistant"，只谈提供的表）→ ---Goal--- → ---Data tables---（注入上下文）→ 把 Goal 整段再重复一遍（与社区报告提示词同一手法："贴身重申"，代价是 prompt 变长）。
  • 输出：JSON —— {"points":[{"description":"… [Data: Reports (ids)]","score":0-100}]}；调用时强制 response_format_json_object=True；解析时只取 points 里的 description / score；解析失败 ⇒ 该批退回 {answer:"", score:0}（见第 2 步第 3 条）。
  • 约束（七条，逐条对应原文）：① 只用表里的数据做主要上下文；② 不知道就说不知道、不要编；③ 每条要点必须有 Description ＋ 0–100 的整数重要度分，且明确"'I don't know' 型回答必须 0 分"；④ 要点要带引用 [Data: Reports (report ids)]，单条最多 5 个 id、其余写 +more，id 取表格里的 id（不是行号）；⑤ 无证据不得写入；⑥ 保留原意与情态动词（shall / may / will）；⑦ 长度限制 {max_length} 词。
  • 三处值得注意：① 打分语义是"对回答用户问题的有用性"（query 相对）——与社区报告的 rank（社区自身重要性、query 无关）不是一回事，正好补上第 1 步"rank 不是相关度"的对照面；② 0 分有明确定义（"I don't know" ⇒ 0），与 reduce 的"丢 0 分"衔接；③ map 阶段永远禁止编造——allow_general_knowledge 的注入点在 reduce，不在 map（代码里只加在 reduce 提示词上）。
引用这一级到底给到什么：reduce 提示词（global_search_reduce_system_prompt.py）明确要求 "preserve all the data references previously included in the analysts' reports" ⇒ 引用有，但只到"报告"这一级、且没有校验；要回原文还得再走两跳（报告 → 实体／关系／claim → text unit），单条引用还有"最多 5 个 id ＋ +more"的抽样上限。

第 3 步 · Reduce（一次调用出最终答案）

  1. 汇总所有批的 points，每条标上"来自第几个 analyst（批次号）"；作用：保留"点 ← 哪个批次"的对应关系——这是最终答案里唯一残留的来源线索（批次本身还没到社区/原文那么细）。
  2. 丢掉 score = 0；作用：去噪——把"对这个问题没用"的点挡在最终窗口之外。
  3. 若一条不剩且 allow_general_knowledge=False ⇒ 直接返回固定的 NO_DATA_ANSWER（"我不知道"），零 LLM 调用；作用：宁可明确说"不知道"也不硬答（对应它"不要编造"的原则）；而且不调 LLM ⇒ 这种情况零成本。
  4. 其余按 score 降序，逐条格式化成 ----Analyst N---- / Importance Score: X / <answer>，累加到 max_data_tokens（默认 8000）为止、超了 break ⇒ 这里的截断会真的丢点；作用：在有限窗口里优先放最重要的点——这是整条链里真正"筛选"的一步；代价是低分点被直接丢弃，且丢多少取决于预算大小。
  5. 用 REDUCE_SYSTEM_PROMPT（带 {report_data} / {response_type} / {max_length}=reduce_max_length 默认 2000）流式生成；若 allow_general_knowledge=True，末尾追加"可引入通用知识"指令（官方警告会提高幻觉）。作用：把零散的"点"合成一篇连贯回答，并把它约束到 response_type 指定的形状；allow_general_knowledge 决定是否允许模型补充库里没有的外部知识（代价＝幻觉风险）。

第 4 步 · 返回

GlobalSearchResult 带 map_responses（每批原始产出）、reduce_context_data/text（reduce 实际用到的点）、分类的调用数与 token 数 ⇒ 中间产物全部可查（notebook 最后两个 cell 就是看这个）。作用：让"答案怎么来的"可复盘——这是调试与评测的抓手，也是我们做"验证成本"这类指标的基础（能直接看到 reduce 到底用了哪些点）。

追问一 · 跨批分数不可比，有没有解？

分成两半看：给详细评分标准能解决"档位语义"，解决不了"批内相对锚定"。更稳的思路是——别让跨批分数单独承担排序职责。

办法能解决不能解决 / 代价
① 评分细则 ＋ 锚点（如 90–100＝直接回答核心且不可替代；70–89＝重要支撑；40–69＝背景；1–39＝边缘；0＝无信息）＋ 少量 few-shot钉住档位语义，压缩区间重叠消不掉批内锚定（模型仍以本批为参照抬高"本批最相关"）；提示词变长，属基础件需人工过目 ＋ 回归
② 降精度使用：把 0–100 只当"三档"（无关/相关/核心），不当连续量承认它只能做粗分类，避免用噪声排序放弃细排序（本来也不可靠）
③ 批内归一化/校准（z-score、top-1 归一）抵消"整批偏高/偏低"的偏移危险：全无关的批会把噪声抬成高分 ⇒ 必须先过 0 分门；且放大低信息批的差异，收益不稳
④ 把排序交回同一次上下文（map 不打分，reduce 一次看全部候选再排）天然可比（同一把尺子的前提是真在同一上下文）受 reduce 窗口限制（max_data_tokens 8000），候选一多装不下 ⇒ 需要分级归并（先组内选优、再全局排序）
⑤ 只用"批内可信"的排序：每批取 top-k，再让 reduce 比这些"各批冠军"避免跨批直接比分数每批只贡献少数点，可能丢掉同批的次优但重要项
⑥ 把风险从"排序"转移到"截断"：扩预算 / 分级归并 / 遗漏声明排序不可靠也能接受，只要"丢了什么"可见需要额外的声明机制——而这正是我们的红线
一个反直觉的旁证（2026-09-22 查 LLM-as-judge 研究线）：这类"评分协议"问题被正面研究过（pairwise vs pointwise、judgment distribution、judge 一致性）。但 Pairwise or Pointwise?（2025-04）的结论反对"成对比较一定更好"：注入干扰特征时，成对比较更易被翻盘——翻盘率约 35%，绝对打分只有 9%。⇒ 换协议不是万能药：先分清病是"跨上下文刻度不一致"还是"抗干扰能力不足"。我们这里是前者，对症的是 ④ 与 ②；盲目改 pairwise 会在另一条轴上更脆。
务实推荐组合：① 0 分门当二值筛选（语义明确、可信）→ ② 分数只当粗分档 → ③ 排序尽量放回同一次上下文（reduce 自排，或每批 top-k 后二次排序）→ ④ 截断风险用"遗漏声明 ＋ 分级归并"兜住。

追问二 · 宏观问题 ＋ 细层，重要性判得准吗？

结论：判得出，但那不是"匹配"而是"归纳"——模型要把细节升维到主题（"这个 egress proxy 校验步骤属于防护体系"），这是 LLM 的强项；但它把一个局部观察转成了全局判断，于是有三个硬约束：

  1. 它在信息不足时做全局判断："这条细节在整个体系里重不重要"是相对性问题（取决于其他材料有没有覆盖它），而 map 只看到一批 ⇒ 用局部可见代理全局重要性。这正是 global search 的结构性破绽：筛选发生在局部，而"重要性"是全局属性；reduce 虽在同一次上下文里合成，但筛选已经在前一步发生（截断已经丢人）。
  2. 层级差越大越不可比，而且有个写在代码里的放大器：community_level 按文档是"选一层"、实现却是把 level ≤ N 的各层报告全塞进来（混深度是默认状态，见第 0 步更正）；更糟的是 read_community_reports 只映射 id / short_id / title / community / summary / full_content / rank / attributes——level 没被读进对象，于是 build_community_context 的表头（id|title|…attributes…|summary 或 content|rank）没有 level 列 ⇒ 模型连"这批是细节还是概览"都不知道，更谈不上按抽象层级校准重要性。这是个≈零成本可补的缺口。
  3. 宏观问题恰好是"局部最判不准"的那类：点状问题里相关材料自明；宏观问题的"重要性"取决于整体是否已有别的材料说了同一件事、甚至取决于"这些点加起来能不能答上" ⇒ map 的分数对宏观问题的信息量最低，而那正是最需要它的时候。（IR 里叫 granularity / abstraction mismatch。）
缓解办法（按性价比）说明
① 选层与问题形状匹配宏观问题本就该选粗层（层低＝粗且便宜，正好对上）；用细层答宏观问题是"自己制造的错配"
② 把 level 塞进上下文表让模型至少知道自己在看哪一层；成本≈0，最便宜的改进
③ 别让分数独自承担筛选0 分门当二值筛选 ＋ 粗分档 ＋ 多留点，把"谁更重要"的比较推到 reduce（同一次上下文里做全局比较）
④ 多层混给概览层 ＋ 细节层一起进上下文——DRIFT 大致就是这个思路
一个可检验的怀疑：论文没给出"哪层最好"的统一答案（Figure 2 里 C0 明显差，C1–C3 在不同数据集/指标上互有胜负），这与"抽象层级不匹配会劣化"一致。可做的实验：固定一批宏观问题扫 C0–C3，看答案质量与被丢弃点的比例；若选细层时被丢的多是宏观关键项，则坐实这条失真（也是我们"三档原语实验"之外的另一个小探针）。

追问三 · 社区权重为什么要"查询期重算"？

结论：索引期已经算好了，查询侧重算的是同一个量；重算的原因是"函数拿不到 communities"，不是"索引没设"。

  • 索引期（index/workflows/create_communities.py）：community.text_unit_ids ＝ 该社区成员实体 text_unit_ids 的去重并集（sorted(set(...))）。
  • 查询期（_compute_community_weights）：把每个实体的 text_unit_ids 按 community_ids 累加、再去重计数 ⇒ 与索引期是同一个集合，只是额外按最大值归一化到 0–1。
  • 为什么重算：build_community_context(community_reports, entities=None, ...) 的签名里没有 communities——GlobalCommunityContext 虽持有 self.communities，但只用于 dynamic selection，调用时不传 ⇒ 函数只能从 entities 反推。属接口历史遗留。
  • 代价：纯程序、零 LLM、一次 O(实体×社区) 遍历 ⇒ 很便宜，不是性能问题。
  • 真正的风险＝口径分叉："社区有多大"在系统里有三个来源：① communities.text_unit_ids（去重并集）；② community_reports.size（outputs 文档写 "entity count"，与①定义不一致；且 Community.size 的注释又写 "Amount of text units"，两处直接冲突，待核）；③ 查询期现算的 occurrence weight（反推 + 归一化）。⇒ 同一语义、三处定义、互不保证一致——与记录 ㉞ 的 degree（老值来自全量图、新值来自增量小图）是同一类病。
由此提炼一条我们的 schema 硬规矩：同一个语义值只允许一个权威来源；其余全部是派生值、且不落库。这样既不必在查询期偷偷重算，也不会出现"社区大小三处定义"的分叉。

这条链的边界：为什么"让用户指定层号"本身就不是好设计

前面说"选层是个裸超参"，这里把它的结构性问题说透——顺带给出三条替代路线。

沛东的论点：顶层社区天然大小不一、深度也不齐。设两个顶层社区，一个最深到 L2、一个只到 L1：用户指定 N=2 或 N=1 时，他想表达的粒度本该不同，可第二个顶层社区两次都只能给出它那个 L1 子社区（那就是它的最细粒度）——同一个旋钮、两棵子树、两套粒度。反过来"严格只取第 N 层"，浅分支又整个消失，照样丢信息。⇒ 用户表达不准、系统实现不准，问题不在实现，而在"用层号表达粒度"这个接口本身。

这条我认同，而且可以量化：拿仓库自己 issue #1650 里那位用户报的真实分布（社区数 / 平均规模）——L0 27 个 · ~120 节点、L1 61 · ~28、L2 90 · ~12、L3 35 · ~2。⇒ 同层内部规模方差本就大，而各分支能到达的层数还不同，于是"N=2"在一棵树上意味着"2~3 个节点的碎片"，在另一棵树上意味着"上百个节点的整块"。

分支N=0N=1N=2
深分支 T1（L0 40 个实体 → L1 四个各 10 → L2 十六个各 ~2.5）1 份（整块 40）4 份（各 10）16 份（各 ~2.5）
浅分支 T2（L0 8 个实体，没再细分）1 份（整块 8）1 份（同一份）1 份（同一份）
后果：N=1 → N=2 的"变细"只作用在深分支上，浅分支纹丝不动；而进到同一个上下文表里的报告，规模能从"2.5 个实体"跨到"40 个实体"——模型还看不到 level（见上面边界①）。

不过"按问题自己判断要哪些层"这条路，GraphRAG 里其实已经有了——就是前面写过的 Dynamic Community Selection：它自顶向下沿真实的树走，逐社区按 query 打相关度分，相关的留下并继续下探。它恰好绕开"层号 ≠ 粒度"这个坑：在哪一层找到相关就留哪一层，浅分支自然停在它自己的深度上，不需要谁去猜。

由此能提炼的判据：
· 静态层号：把"粒度"这个二维量（相关性 × 可得深度）硬压成一个一维标量 ⇒ 信息必然有损，用户表达不准、系统实现不准都是这个压缩的后果。
· 查询驱动的树遍历：让"能到多深"由数据回答，让"该不该要"由 query 回答 ⇒ 两个维度各归其位。
· 但静态旋钮并非一无是处：零额外 LLM 调用、成本可预测、可复现，做基线/调试/对照实验很合适 ⇒ 问题不是"该不该有它"，而是"别把它当表达粒度的正式接口"。

还有第三条路，对我们自己的产品最直接可用：把旋钮从"层号"换成"资源 / 覆盖口径"——目标报告数、token 预算、或"覆盖多少比例的 text unit"。这类量用户有直觉（"我要便宜一点 / 全一点"），系统也能自己做好（按预算在每棵子树上决定砍到第几层），且不需要额外 LLM 调用。⇒ 它把"用户做不好、系统也做不好"的那个维度，换成了两边都能对齐的维度。（与我们已定的方向一致：不让用户选层，而按问题形状——点 / 线 / 面、枚举 / 关系 / 连接——决定抓哪些社区，"层"只留作内部成本上限。）

一个必须承认的边界：粒度其实是问题与语料共同决定的，不只是问题决定的。就算 query 判得再准，如果某主题在库里只被粗层覆盖（那棵树没长下去），也拿不到细报告——此时正确行为是"给已有最细的 ＋ 明确声明这是最细可得"，而不是假装更细。动态选择在这一点上"天然诚实"（它只能从真实的树里挑）；静态层号则容易让人误以为"我选了细层就该有细节"。

先补一课：roll-up 本来在干什么？（2026-09-24 补，沛东追问）

一句话：roll-up ＝ "把同一实体的多行压成一行——只留它所属的最深社区"，目的是让每个实体恰好由一份报告代表。它解决的是"同一批内容被多层报告重复代表"这个问题。

为什么需要它：社区是层级结构，一个实体会同时出现在各个层的祖先社区里。以本页的合成语料为例，实体 A 同时属于 C5(L0)、C20(L1)、C77(L2)。若不处理，把 level ≤ 2 的报告一股脑塞进上下文，A 的内容就被 3 份报告各讲了一遍（C5 的报告里讲 A，C20 的报告里又讲 A，C77 的报告里还讲 A）——而这三份报告说的是同一批 text unit。代价：token 白烧；更麻烦的是 reduce 阶段按分数截断——重复代表会人为抬高同一批内容的"出现次数"，把别的材料挤出去。

数据形状：它的输入必须是一张 "实体 × 所属社区"的长表（一行＝一个实体在一个层里的归属）：

谁提供这张表长什么样分组键 title 是
旧版（v1）：final_nodes从图上解包出来的节点：label → title、cluster → community，一行＝(实体, 社区)实体名 ✅ 能区分实体
现在（v2/v3）：communities.explode("entity_ids")形状一模一样（也是"社区 × 成员实体"），只是实体列名叫 entity_ids（哈希）"Community N" ❌ 只能区分社区

它怎么干的（三步）：

  1. 按层砍一刀：长表里只留 level ≤ N 的行 ⇒ 相当于把"层太深"的那些归属先删掉，于是"最深"是在 N 这个上限内的最深。
  2. 按实体聚合，取 community 最大值：groupby(实体).agg({"community": "max"}) ⇒ 每个实体只剩一行。之所以 max 就等于"最深"，是因为社区 id 随深度递增（官方 outputs 文档原话："these increment with depth, so they are unique through all levels"）。
  3. 去重成社区集合，再 merge 报告：得到的 community id 去重 ⇒ "至少有一个实体把它当作最深社区"的那些社区 ⇒ 取它们的报告。

一条必须先记住的结构性约束（2026-09-24 补，沛东指出）：层级聚类里子社区完整划分父社区——一个社区要么是叶子（规模 ≤ max_cluster_size 或拆不动），要么被它的子社区不重不漏地分完。依据：hierarchical_leiden 是"对超限社区在其诱导子图内再聚类"，而 _compute_leiden_communities 收上来的是一张逐层的"节点 → 社区"映射（results[level][node] = cluster）⇒ 每个成员在每个更深的层里恰好落进一个子社区；官方样例也印证（社区 0 的 size 10 = 4+3+3）。因此"父社区只被拆走一部分、剩下的留在父社区"这种状态不存在。诚实边界：底层递归由第三方包 graspologic_native 实现，我没有逐行核它的递归逻辑；此约束由"graphrag 传入 max_cluster_size 的层级 Leiden 定义 ＋ 官方样例数据"双向印证。这条约束后面会用来否掉一个错误例子。

沛东的修正：roll-up 确实保证"实体不重复出现"（2026-09-24，我上一版写错了）

先认错：我上一版在这里写过一段"反例"，说"N=2 保留 {C77, C20, …}，而 C77={A}、C20={A,B}，所以 A 会同时出现在两份报告里 ⇒ 代言 ≠ 只出现一次"。沛东指出这个例子不可达：如果 C20 被继续拆分，B 也必然落在 C20 的另一个子社区里——C20 不可能"只拆走 A、把 B 留给自己"。而"子社区完整划分父社区"这条约束上面刚核实过（代码 ＋ 官方样例的 10 = 4+3+3）。所以那个反例是我凭空造的，结论要翻回来。

正确的结论：roll-up 保证保留集里的社区两两成员不相交 ⇒ 每个实体恰好出现在一份报告里。证明很短（两条合起来就够）：

  • 设实体 e 在层 ≤ N 内的最深社区为 C_e；保留集恰是全体 C_e 的集合。
  • 比 C_e 更浅的祖先社区，一个都留不下来：取 e 的任一祖先 A 且 level(A) < level(C_e)——A 必有子社区（e 在 A 的某个更深社区里）⇒ 由"完整划分"，A 的每个成员都落进 A 的某个子社区 ⇒ 没有任何成员的最深社区是 A ⇒ A 出局。唯一逃逸口是"层号刚好等于 N"，但那要求 level(A)=N，与 level(A) < level(C_e) ≤ N 矛盾。
  • ⇒ e 所属的社区里只有 C_e 留在保留集中 ⇒ 保留的社区成员互斥，每个实体恰好被一份报告代表。
两句话记住区别（修正版）：
· roll-up 生效：保留的是 level ≤ N 中还"拥有专属成员"的社区 ⇒ 保留集里成员互斥，每个实体恰好一份报告覆盖它；报告数 ≤ 实体数（上例 N=2：4 个实体 → 4 份报告）。"混层"照旧存在，那是分支提前到顶的兜底。
· roll-up 失效（现状）：level ≤ N 全给 ⇒ 实体与报告层层重复：上例 N=2 给 7 份，4 个实体形成 10 组（实体, 报告）对应（A 被 3 份、B 被 3 份、C 与 D 各 2 份）——正确行为是 4 组。
· 收益表述：不是含糊的"减重复"，而是"每个实体从最多 N+1 份报告回到恰好 1 份"。

等价刻画：它到底给了什么（2026-09-24，沛东把这一层说透了）

一句话：保留集 ＝ {level == N 的社区} ∪ {level < N 的叶子社区}。它同时等价于"每个实体的最深可得社区"。

为什么等价：对任一实体 e，它在层 ≤N 内只有两种处境——① 分支延伸到第 N 层 ⇒ C_e 是一个 level == N 的社区；② 分支在第 k < N 层就停了（那个社区不再细分＝叶子）⇒ C_e 是一个浅层叶子。两者合起来正是上面那个并集；反过来也成立：level == N 的每个社区至少有一名成员（其成员的最深就是它自己），浅层叶子同理 ⇒ 两边逐个对应。

用上例验一遍：N=2 → level 2 社区 {C77, C78} ∪ 浅层叶子 {C21, C22}（C20 有子社区、不是叶子；C5/C6 也不是）＝ {C77, C78, C21, C22} ✓；N=1 → {C20, C21, C22} ∪ ∅ ✓；N=0 → {C5, C6} ∪ ∅ ✓。（四个 N 值 0/1/2/None 已用脚本逐个比对：保留集与并集完全一致，不是只靠嘴上推。）

沛东的表述（我认为比 "roll-up" 这个名字更准确）：用户说"我要第 N 层"，想指定的其实是某种粒度；而数据里不见得每条分支都有第 N 层。那些没有第 N 层子社区的社区，它自己就已经是最细粒度了——直接丢掉就是丢信息。所以要把"这些社区里能拿到的最深子社区"取过来，从而在语义（粒度）上、而不是在层级（数据）上对上用户意图。
⇒ 换句话说：roll-up 是"粒度意图"与"层号数据"之间的翻译层——代码很少，但干的就是这件事。这也顺带解释了 docstring 为什么用"每个实体"而不是"第 N 层"来定义：因为意图本来就是 per-entity 的。

两个附带边界：① 这种翻译会让结果混层（上例 C21/C22 是 L1、C77/C78 是 L2），而上下文表里不带 level 列 ⇒ 模型看不出自己在读哪一层。② 当 N 超过语料实际深度时，正确行为是"给全部叶子"（没有 level-N 社区，只能给提前到顶的叶子），而现状是"给全部社区"（含所有非叶祖先）——官方 notebook 的 10 → 10 就是②的现场：社区 0 属于"被完整吸收的非叶祖先"，正确行为下它应当缺席，实得应 ≤9。

给自己的教训：举例子不能只让它在算术上自洽，还得让它在生成它的算法里可达。我那个 C20 的例子在"groupby-max 的结果"上看着没问题，却违反"子社区完整划分父社区"——验证一个例子，先问"这个状态是算法能产出的吗"。这也正是本页反复出现的同一个病：形状对、语义错。

    nodes_df = final_communities.explode("entity_ids")        # 一行 = (社区, 它的一个成员实体 id)；title 仍是 "Community N"

    if community_level is not None:
        nodes_df   = _filter_under_community_level(nodes_df, community_level)   # ← "≤N"
        reports_df = _filter_under_community_level(reports_df, community_level)

    if not dynamic_community_selection:                        # ← 默认模式才做
        # perform community level roll up
        nodes_df["community"] = nodes_df["community"].fillna(-1).astype(int)
        nodes_df = nodes_df.groupby(["title"]).agg({"community": "max"}).reset_index()   # ← 分组键＝communities.title
        filtered_community_df = nodes_df["community"].drop_duplicates()
        reports_df = reports_df.merge(filtered_community_df, on="community", how="inner")

    return read_community_reports(df=reports_df, id_col="id", short_id_col="community")


def _filter_under_community_level(df, community_level):
    return df[df.level <= community_level]                     # ← 只保留 level ≤ N

要害在分组键 title 上。"按实体取最深"要成立，title 必须能区分实体。旧版正是如此：当时入参叫 final_nodes，它就是一张 "实体 × 所属社区"的长表（create_final_nodes 里从图上解包出节点，把 label → title、cluster → community，再 drop_duplicates(["title","community"])，代码见 e5342236 版 create_final_nodes.py）——title 是实体名（图谱节点的 label）⇒ groupby("title") 真的在按实体分组，max(community) 才等于"这个实体所属的最深社区"。
而 communities.explode("entity_ids") 的形状跟它一模一样（也是"社区 × 成员实体"的长表）——这就是当年重构时看不出问题的原因：表形似换成等效的，但分组键的语义被换掉了（实体名 → "Community N"）。教训："两张表形状相同"不等于"这两个字段可互换"；重命名／改数据源时，第一件要核的是被当作语义键用的那一列。

现在入参换成了 communities 表，而它的 title 是 "Community N"：create_communities.py 末尾一行 final_communities["title"] = "Community " + community（官方 outputs 文档也把它描述为 "Friendly name of the community"）。本仓库下载的官方样例 docs/examples_notebooks/inputs/operation dulce/communities.parquet，其 title 列实测取值就是 Community 0 … Community 9。⇒ groupby("title") ＝ 按社区自己分组，每组只有它自己，max 还是它自己 ⇒ "实体"这一维被整个丢掉，只剩"每个社区一行"，等价于去重。

漂移的时点：2025-02-07 的 PR #1674 "Streamline workflows" 删掉了 create_final_nodes 工作流，把这里的入参从 final_nodes 改成 final_communities.explode("entity_ids")——但下面 groupby(["title"]) 一行没跟着改，docstring 也没改。此后这段 roll-up 就静默失效了：声明说"取最深"，实现是"全给"。

community_level = 1

旁证：官方 notebook 自己的数字。global_search.ipynb 里 COMMUNITY_LEVEL = 2，输出 Total report count: 10 → Report count after filtering by community level 2: 10。若 roll-up 生效，level 0 的祖先社区会被它的子社区吸收掉（它不可能是任何实体的"最深社区"），结果必然 < 10；等于 10 正说明它没生效。该 notebook 数据 period = 2026-01-13，晚于漂移时点，结论自洽。

于是：默认模式的实际语义与边界（2026-09-24 定）

  • 实际语义 ＝ "报告集合 = level <= N 的全体报告"，外加一条几乎恒真的约束（靠那个 inner merge 实现）：报告所属社区必须能在社区表里找到对应行。
  • community_level = None：不过滤 ⇒ 全部社区、所有层的报告，不是"每个实体最深社区"。
  • 不是"选第 N 层"：API docstring 写 "The community level to search at"、notebook 注释写 "higher value means more fine-grained"——说法都是"那一层"，实现是"≤N 的所有层"。⇒ 语义与实现不一致，且偏差方向是"给得比说的多"（把更粗的层全都塞进来）。
  • 报告集合确实"混深度"（C0…CN 全在里面），而 read_community_reports 只映射 id / short_id / title / community / summary / full_content / rank / attributes——level 没进对象，上下文表表头里也没有 level 列 ⇒ 模型完全不知道自己在读哪一层。⇒ 上面"宏观问题 ＋ 细层判不准"那个放大器依然成立，只是成因要改写成"混深度是默认状态"，而不是"层级不齐时的兜底"。
  • "max(community id) ≡ 最深"这条前提：官方文档说社区 id "increment with depth"，此条只在 roll-up 生效时才有意义；当前版本它不参与任何实际判断（留作历史理解）。
  • 默认模式 vs dynamic 的差别不在这一步：dynamic_community_selection=True 时整个 merge 被跳过，报告集合原本还是"level <= N 的报告"（只少了社区表对齐）；真正的差别在上下文装配阶段（动态模式按 query 逐社区打分剪枝，见下文）。⇒ 同一个参数名、两条路径两种含义这个结论不变。
这条更正对我们自己的意义（比 GraphRAG 本身更重要）：我们一直在追问"如何把用户 query 落到图的确定性入口"；而这里是一个反面教材——一个有效设计（"每个实体只留最深社区"）在重构中被静默降级成"全层都下发"，没有断言、没有日志、没有测试抓到它；连官方 notebook 打印出的 10 → 10 就是这个 bug 的现场证据，却没人当异常看。对我们的直接要求：编译／检索产物里那些充当"路由键"的东西（claim_type、概念归一、边的方向／极性），必须配可跑的语义探针，让"声明的语义"和"实现的语义"对不上时当场响。否则同类的静默漂移会以"结果看着还行、只是不太准"的形式长期潜伏。（这条与我们"基础件人工复核""根因修复闭环"两条纪律同源：语义也是基础件。）
