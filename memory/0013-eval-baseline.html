背景

按 0004 验收标准与 0012 明日起点，进入 golden set 评测基线。设计原则：一个用例文件 = 一次可复现的验收，runner 按契约执行，人工只标注需要判断力的维度。

Schema 定稿（backend/eval/schema.py，Pydantic 校验）

字段必填说明
id是唯一标识，小写连字符格式（tool-calc-001）
category是tool_call / boundary / combined / multi_turn / kb_qa
title / mode / input.messages是描述、会话模式、完整对话（单轮=1 条，天然支持多轮）
expected.behavior是预期行为要点（人工标注依据）
expected.criteria是验收维度受控词表（至少 1 个）
expected.tool_calls否预期工具调用（观察指标，不硬判）
expected.answer_contains否答案应包含关键词（模糊匹配）
expected.max_rounds否预期最大工具轮数（默认 4，对比实际值）——用户确认加入
timeout_sec否每条用例耗时预算（默认 30）——用户确认加入
tags / compare / notes否标签、是否参与豆包/千问对照、设计说明

criteria 受控词表（v1）

机器可自动判定：tool_used、tool_not_used、stream_complete、latency_budget；需人工/LLM 判定：answer_correct、refusal；阶段 2/3 启用：citation_correct、context_consistent。

首批 70 条用例（backend/eval/cases/，每用例一个 JSON 文件）

  • 工具调用 40：计算 15（基础/括号/幂/取模/大数）、日期时间 8、笔记保存 8、笔记读取 5、组合 4（计算+保存、先存再读、日期推算）
  • 边界 20：提示注入 5（索要系统提示/开发者模式/解锁咒语）、安全拒绝 5（危险/违法/隐私/自伤/医疗）、模糊与矛盾 4、知识库范围 3（阶段 2 启用）、诱导幻觉 3（不存在的人物/事件）
  • 综合 10：计算+解释、计算+比较、时间+推算、笔记+验证、工具链 3 步、多问题分步、错误纠正、任务分解等

多轮对话与知识库问答用例分别留待阶段 3（会话记忆）与阶段 2（RAG）就绪后补充。

设计决策（用户已确认）

  • criteria 分“机器可自动判定”与“需判断力”两类，不假装全自动
  • 答案用 answer_contains 模糊匹配，不用精确匹配
  • tool_calls 期望是观察指标不是硬性验收——模型可能合理选择不用工具（如 3+5 心算），该指标正好喂给“工具调用率”验证点
  • timeout_sec 与 expected.max_rounds 都是实际使用时值得关注的指标
