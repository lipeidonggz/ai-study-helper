1. 平台定案：WeKnora 标准版（Docker Compose），不是 Lite、也不是桌面版

结论：走 Docker Compose 标准版。理由是它把两件配套服务一起解决了——Neo4j（图对照臂）和 Langfuse（逐轮观测）都是 compose profile，一条命令就位。

决策链（四步，每步都有证据）：

  1. 先看它的 wiki 能力：README 里 Auto Wiki 说"把文档里的 people／products／concepts 抽成带来源引用的页面、按目录组织，页面可编辑且可回滚"——正是 6.1 要的东西。
  2. 再看到底有几种装法（📄 website-docs/01-getting-started/02-installation.md）：标准 Compose／开发模式／Helm／Lite 单二进制／桌面应用五种。文档里桌面应用那段带明确警告。
  3. 桌面版到底有没有包：文档说"没有随 Release 提供安装包"；我去 GitHub 查了——八个 Release（v0.6.1 → v0.8.2）assets 全是 0 ✅。所以没有任何可下载的 Windows 产物，"桌面版"这条到此为止。
  4. 那 Lite 呢：Lite 是"单二进制 ＋ 浏览器 UI"（不是原生窗口），零外部依赖（SQLite FTS5 ＋ sqlite-vec ＋ 内存队列）。但它没有现成包 ⇒ 要走这条路得自己编（Go 1.26 ＋ Windows 上的 CGO/gcc），比装 Docker 还费事。

一条关键辨析（纠正我们自己的直觉）：Lite 并不是"缺能力"——① 三个 wiki 服务在容器里无条件注册（internal/container/container.go:281-283：NewWikiPageService／NewWikiIngestService／NewWikiLintService），没有任何 edition 门控；② 部署能力清单里 Lite 只关了一件事——organizations（多空间协作），理由写着 not_supported_in_lite；③ Neo4j 与 Langfuse 都是"env 指向的外部服务"（NEO4J_ENABLE／NEO4J_URI；tracing 是 OTel 客户端，"No-op when disabled"）——所以 Lite 也能接，只是要自己找齐。
⇒ 两条路的真实差别不是"功能有没有"，而是"外部服务谁提供"。最终选 Docker，是因为它把 Neo4j＋Langfuse 一起打包解决了。

3. 实验设计（按 0036 §6.1 的三问排）

轮次动作记什么（判据）
一 · 看产物形状（最小代价）语料先用 A5（Anthropic 那篇，单文件 8.0k token）——与 GraphRAG 首轮看形状用的是同一份，产物可对照；建 wiki 型知识库 → 上传 → 等编译 → 导出 wiki页面数 · 页面类型分布 · 每页长度（中位／P90）· 目录层数与每层条数 · 链接数与密度 · 悬空链接数（链接目标 ∖ 页面集合） · 每源触及页数（对照 Karpathy 说的 10–15 页）· 有源引用的页占比 · token 与耗时。
只回答一句：粒度是谁定的？（算法常数？配置？提示词？还是模型自由发挥）
二 · 视角选择找到配置点，改一次"抽什么／怎么分目录"，同语料重编；另外同配置再跑 2–3 遍当抖动基线页面集合差（新增／消失／改名）· 目录差 · 链接差。判据 ＝ "随视角可控地变"还是"只有随机漂移"（没有抖动基线就分不出这两者——这是 GraphRAG 那轮的教训）
三 · 增量 ＋ 删除（合一轮）加 1 篇同主题源 → 看 diff；再删 1 篇源 → 看善后增量：新增几页／改写几页／目录是否重排／链接是否更新 ⇒ 判"改动面与新增材料量成不成比例"（局部性）。
删除：判据现成——直接读 RunLint 的 broken_link／orphan_page／stale_ref；要验的是它那个取舍对不对（剥引用；失去全部活源就删页），以及"知识作废 vs 来源撤回"能不能分开

记录纪律（沿用老规矩）：产物每轮导出留档（不然没法对账）· 每轮记 token 与耗时 · 语料用真名＋链接不用代号 · 每轮的原始输出与命令留档。

对第二轮的实验含义（重要）：既然 granularity 是详细度旋钮，它测的就不是"领域适配"。所以拆成两组独立对照：

组只动什么看什么
A 粒度敏感性extraction_granularity 三档（focused／standard／exhaustive）候选数／页面数／压缩比是否单调变化；lint 噪声是否跟着涨
B 视角可控性只改 extraction_instructions（给一个领域视角）页面集合与目录是否随视角可控地变，还是只有抖动（必须配"同配置多跑几遍"的抖动基线）；且改完必须触发重新解析

B 组才是"领域押注"在 WeKnora 里的等价实验；A 组只是"同一视角下详细度的变化"。这也修正了我最初把两者混为一谈的想法。

"批"的口径（2026-10-09 核代码）：一个批次 ＝ 一次 ingest 触发所认领的文档集合，默认最多 5 篇（wikiMaxDocsPerBatch = 5；剩下的留在 task_pending_ops 里由后续批次接手）。由此三件事要说清：
· ① Map 阶段是"每篇文档各跑一遍"（抽候选／去重／引用／summary），多篇之间并发（默认 10）；
· ② Reduce 才跨文档：按 slug 分组，同一批里多篇文档命中的同一个 slug 会合成一条链、一起喂给一次写页调用——这就是"多源页"的来历；
· ③ 目录规划是批级的：它拿的是整批（≤5 篇文档）的全部新条目，既不是一篇文档的条目，也不是全库。
⇒ 所以"空库投第一篇"与"空库投第一批"是两件事——但差别不在"会不会有多源页"（两条路都会），而在"多源是怎么来的"：同批＝两篇文档的 update 落同一个 slug，reduce 只写一次页、两份素材一起喂 ⇒ 出生即多源（P6＋P7 那批 4 页如此）；分两批＝第一篇先建出单源页，第二篇走"去重／复用 slug"命中已有页、再把 addition 并进去 ⇒ 单源页长成多源页，代价是整页被重写一次（version ＋1）（探针实测：concept/rag 的 source_refs 1→2→3，每投一次重写一遍）。⇒ 终点一样，成本与痕迹不一样：同批是"一次合成"，分批是"反复重写"。（2026-10-09 沛东指出原措辞"才有 4 个多源页"不成立——多源页不是同批专属。）
ℹ️ 顺带一个"旋钮白给"的默认组合（2026-10-09 核；沛东判定不影响功能效果 ⇒ 仅记录、不提 issue）：Map 的 errgroup 上限是 IngestMapParallelOrDefault(10)，但一批最多 5 篇、每个 map 任务就是一篇文档 ⇒ 默认下这个 10 永不生效，单批有效并发＝批大小（5）；而 errgroup 是每批新建的，所以"4 个并发批次"也不会把 10 叠成生效。真正的 LLM 在飞峰值来自另一层：mapOneDocument 里 wg.Add(2) 让摘要 ∥ 引用匹配两路并行 ⇒ 5 篇 × 2 ≈ 10 个调用。Reduce 的 10 倒是常用（按 slug 并发：P6＋P7 那批 87 个 slug／reduce_par=10）。⇒ 想让 Map 那个旋钮生效，得同时把 IngestBatchSize 提到 >10（代码注释本来就是给 4 万文档级 KB"一起往上拧"用的）。结论：只是默认值没对齐，功能与效果不受影响（并发自然被批大小兜住）——不提 issue。
再往下一层：批大小贯穿 Map 与 Reduce（2026-10-09 核，沛东追问"5 篇只在 map 生效还是贯穿 reduce"）——slugUpdates 是 ProcessWikiIngest 的局部变量（wiki_ingest_batch.go:436），只被本批 ops 的 map 结果填充（撤回 :509／新增 :550）；map 收敛后（eg.Wait() :579）在同一个函数里做身份重映射（:584）、规划目录（:591），reduce 遍历的就是这份本批的 slugUpdates（:641）。跨批的同一个 slug 只靠 per-slug 锁串行化、不合并（:651-657，注释原话 "Serialize same-slug read-modify-write across concurrent batches"）⇒ 同一个 slug 落在两个批次里就会被写两次，第二次是整页改写（实测单价：新建 ≈3,538 token/次、同批合成 ≈4,860、改写已有页 ≈5,925）。
而"分批"是时间决定的，不是用户显式选的：wikiIngestDelay = 30s（注释 "Debounces rapid uploads"）——文档入库后等 30 秒才触发批次任务，窗口内的上传攒成一批；wikiFollowUpDelay = 5s 是收尾批的轻去抖；而 wikiFinalizeDelay = 20s 让 finalize 跨批合并（同一 KB 的多批 ingest 合成一次索引重建）⇒ 只有"写页"是每批一次，链接注入与索引重建已经被摊薄。实测印证：P6、P7 连续上传 ⇒ 同批（才有 4 个多源页）；隔 1.5 小时再传 A4 ⇒ 独立成批（+22 页、0 合并）。
⇒ 省成本的三层杠杆（顺序很重要）：① 让会共享 slug 的文档落进同一个 30 秒窗口（连续/批量上传，这是用户直接可控的一层，也最有效）→ ② 让窗口内的文档数 ≤ IngestBatchSize（否则被切批；所以"把 5 调大"的真实用途是"窗口里一次塞进 >5 篇同域文档时别被切掉"）→ ③ IngestMapParallel ≥ 批大小（默认 10）。反过来：5 篇同域文档一次性连续上传，默认配置就已经把它们放进同一批了，不用调任何参数。

3.3 阶段一细读：Pass 0 抽候选集（📄 源码级，2026-10-08）

一句话：这一步把整篇文档交给模型，问它"这份材料里有哪些值得单独建页的实体和概念"。A5 实测：1 次调用、prompt 7,179 token、约 24 秒，产出 43 个候选——就是界面上那 43 个"知识"。提示词原文与中译见 §7.6；算法级细节（切块、去重叠）见 §7.7，这里只讲读者需要知道的。

① 它读到的"整篇文档"，是三步加工出来的——不是原文直出

  1. 切块（⚠️ 共用前置：不只服务这一步，后面找引用、写正文用的都是这批块）：默认 512 字符／overlap 80／分隔符 ["\n\n","\n","。"]；代码块、表格、公式、链接这类片段不许从中间切开。A5 被切成 70 块（p50＝431 字符、最长 827）：短段落独立成块、不合并，所以才会出现 42 字符的小块。
  2. 重建全文：不是把块拼起来就完事——默认 overlap 会让同一段文字在相邻块里各出现一次，直接拼等于把重叠喂两遍。它用文本级后缀匹配去重叠：A5 朴素拼接 29,883 字符 → 重建 28,953（去掉 930）；我独立测得实际重叠 933 ⇒ 基本精确。
  3. 两道闸：超过 32,768 字符就按字符硬截断（不看块边界，可能切在词中间）——⚠️ 被截掉的后半段永远不会产生候选，但仍能作为证据块被引用；文本太少的整篇跳过（防"只剩图片标记时模型瞎编"）。

3.4 阶段二细读：去重与身份对齐（📄 源码级，2026-10-09）

一句话：Pass 0 抽完条目，紧接着要回答"库里是不是已经有同一条目的页"。判"同"分两层——先确定性精确身份，再 LLM 语义判同；命中就把 item.Slug 改写成已有页的 slug ⇒ 这一轮是"并入已有页"，否则才是新建页。

① 它站在链路的哪一步

调用点在 extractCandidateSlugs 里：Pass 0 的 JSON 一解析完就调 deduplicateExtractedBatch（wiki_ingest_cite.go:118）——早于引用匹配。所以后面那一步看到的候选清单已经是"归并后"的身份，被合并掉的条目不再另起一页，而是直接往已有页上挂引用。

完整次序（2026-10-09 核代码）：Pass 0 → 去重／身份对齐 → 引用匹配（∥ summary 页）→ 回填 SourceChunks → 构造 updates → 批级 remapSlugUpdatesByIdentity → 目录规划 → reduce 逐 slug 写页 → linkify → finalize。

② 第一层：确定性精确身份（不花 LLM）

  • 归一化标题完全相同 ⇒ 视为同一条目：normalizeWikiIdentityTitle 只去空白 ＋ 折大小写，保留标点（注释举例："寓言"与"《寓言》"可能是概念与作品，必须可分）——目的是关掉模型格式漂移（"Acme Corp" vs "acme corp"）。
  • 同类优先，同类没有则跨类型复用：exactIdentityTarget 先找同类型页；找不到就复用跨类型同标题页——因为模型的类型判断会漂（同一事物这次判 concept、下次判 entity，代码注释点名 issue #3526），复用已有页才不会长出"只差类型前缀"的孪生页。这就是官方文档说的"同名跨类型复用"。
  • 这一层命中的条目标为 authoritative ⇒ 直接跳过下面的 LLM 判同（stabilizeExtractedIdentities :409-411）。

③ 第二层：trigram 预筛 ＋ LLM 判同

  • 预筛走 pg_trgm：每个条目按"名称 ＋ 各别名"逐条调 FindSimilarPages，SQL 就是 WHERE lower(title) % :q ORDER BY similarity(lower(title), :q) DESC LIMIT 5（repository/wiki_page.go:1074-1078），走 idx_wiki_pages_title_trgm（GIN gin_trgm_ops，migration 000041）；命中的页按条目分别记进"它自己的候选集"（itemCandidates）。
    ⚠️ 但 SQL 的右边只有 title：查询串（新条目的 name／aliases）是"多面"的，被比的对象（已有页）却只有标题——已有页的 aliases 只是被 SELECT 出来给模型看的，从不参与召回；上面的"精确身份层"同理（FindPagesByNormalizedTitles 也是拿 item.Name 去比 title）。⇒ 别名通道只有一半：新条目侧的多面 → 已有页的单一标题。
  • 阈值实测是 0.3（本机 DB SHOW pg_trgm.similarity_threshold → 0.3，Postgres 默认值，代码里没改过）；% 就按它过滤。刻度参考：similarity('acme corp','acme corporation') = 0.5。仓库注释写的是"below 0.1 are dropped server-side"（wiki_page.go:1046-1048），与实测不符。
  • ⚠️ 预筛是"词法"的，判同是"语义"的：trigram 只认字面 3-gram 片段——提示词里那些"苹果公司 → Apple Inc."式的同义（字面相似度 0）自己过不了这一关，只能靠"新条目侧某个 surface 恰好与某页标题字面相似"这一条路——典型情况是抽取器把对译名写进了新条目的 aliases、而它正好等于已有页的标题（例：新条目 Apple Inc. 带 alias 苹果公司，旧页标题就叫"苹果公司"）。

3.6 阶段四细读：summary 页（📄 源码级，2026-10-08）

一句话：这一步把整篇文档写成一页摘要——每篇文档一页，slug 是 summary/<文档ID>。A5 实测：1 次调用（prompt 6,978 ＋ completion 2,345 ＝ 9,323 token）、耗时 10.9 s、产物 4,693 字符。提示词原文与中译见 §7.10。

① 它在流水线里的位置：与引用匹配"并行"，不是串行的第三步

  • 代码注释原话："Summary and chunk classification are independent given Pass 0 output — run them in parallel."——两条支路各起一个 goroutine，挂在同一个 postprocess.wiki span 下（A5 重跑实测：summary 10.9 s ／ classify 6.5 s ⇒ 并行墙钟 ≈ 10.9 s）。

③ 它必须吐出什么（📎 提示词的十条规则）

  • 第一行必须是 SUMMARY: {一句话，15–40 词}（这行进 wiki 索引），其后是 Markdown 摘要，结尾要有 ## Key Takeaways 节；
  • 链接规则：凡提到清单里的名字或别名，必须写成 [[slug|显示名]]——不许用加粗替代、不许写裸 [[slug]]、不许自造 slug；
  • 图片规则：<images> 里的图按上下文插入，URL 当不透明 token 原样复现；
  • 长度 500–1500 词、语言跟随；空内容规则——只回一句 SUMMARY: No textual content was extractable from this document.，不许编。

④ 吐出来之后谁收拾

  1. splitSummaryLine：切出 SUMMARY: 行与正文（兼容全角 SUMMARY：；没有前缀 → 整段当正文、摘要行回退成文档标题）；正文空则正文＝整段，摘要行空则用 docTitle 兜底。
  2. 存成一页：slug summary/<slugify(文档ID)>、page_type summary。⚠️ slug 故意用 UUID 不用文件名——注释原话："Filename-based slugs like summary/mx5280-pdf expose the filename in cross-link contexts that downstream LLM prompts read; a UUID-based slug is uglier but hallucination-safe."（与"摘要提示词不给文件名"是同一条防幻觉原则）
  3. 它还被当作其它页面的共享上下文：DocSummary: docSummary 会进 reduce 的 <shared_source_contexts>——即"摘要既是一页，也是别的页的写作背景"。
  4. 失败策略与引用步不同：摘要调用失败 → 整篇文档 requeue 重试（它是强制件）；而引用阶段是"单批失败只丢那批"。
  5. 专属善后 sanitizeDeadSummaryLinks（纯文本替换、不调 LLM）：把摘要里指向"写页失败"的 [[slug]] 尽量就地治愈（例如 shang-hai-tower → shanghai-tower），治不了才降成纯文本；范围只限本批的 summary/<uuid>，成本与批次规模成正比。
与 GraphRAG 对照 ＋ 两个观察：
· GraphRAG 的社区报告是跨文档、按社区压的另一层抽象；WeKnora 的 summary 是文档层——一份文档一页，粒度由"文档边界"给定而不是语义给的（对应 0036 §3.1 那句"聚合体的粒度是机制给的"：这里是"文档给"）。
· 它一物三用：① 一页 wiki 页面（含索引要用的 SUMMARY 行）· ② 索引行的来源 · ③ 其它页面的共享上下文。
· 代价是"并行换延迟"：摘要先写、页面后写 ⇒ 必然有一批链接是预测出来的，于是要有 sanitizeDeadSummaryLinks 这类事后修补——这也解释了为什么这套系统里修链接的代码比生成链接的代码多。

留到第二轮验的两点：① 摘要这一步吃 ContentInstructions（与引用步相反）⇒ 可以用它验证"改指令 → 内容风格变化"是否可观测；② SUMMARY: 行与 ## Key Takeaways 的稳定性（temperature 0.3 下是否每次都吐、格式是否飘）——这是"契约遵守率"的便宜探针。

3.7 阶段五细读：目录规划 taxonomy（📄 源码级，2026-10-09）

一句话：给整批新条目一次性分配目录路径（最多 2 级），并优先逐字复用已有目录标签——不是"每页各自发明分类"。它跑在批级、reduce 写页之前（wiki_ingest_batch.go:591-592），产出先落成 wiki_folders 行，reduce 再按 slug 套用；只套用给还没有目录的页（人工摆过的不动）。

① 输入

  • 条目：collectTaxonomyItems(slugUpdates) 取本批的 entity／concept slug（summary 与 retract-only 跳过），按 slug 排序保证分批边界稳定；每条只带 slug ／ title ／ type ／ about（＝Pass 0 的 Description，截 120 字符）。
  • 已有目录池：ListDistinctCategoryPaths(kbID, 400)（上限 wikiTaxonomyFolderPoolMax=400）。

② 处理：先挑"给模型看的目录"，再让模型分配

  1. 挑相关目录（selectRelevantFolders）：目录数 ≤ 60（wikiTaxonomyFeedAllMaxFolders）就全量喂——健康的目录树本来就不大，全喂复用召回最好且零嵌入成本；超过 60 才启动相似度预处理：一级目录全部保留当粗锚点，每个条目按 嵌入余弦相似度取 top-3（wikiTaxonomyRelevantTopK）深层目录。没有 embedding 模型、或嵌入调用失败 → 退化为"截断到 150"（wikiTaxonomyPromptMaxPaths）。
  2. 分批分配：每次最多 60 个条目（wikiTaxonomyPlanChunkSize）；前一批给出的目录会 feed-forward 进"已有目录"，逼后续批次往同一棵树上靠。
  3. 清洗模型输出（CleanWikiCategoryPath）：分隔符归一（／／｜／| → /）、剥掉包裹的引号括号、丢掉 entity／概念 这类"类型名"标签、段内去重、深度硬上限 3（WikiCategoryMaxDepth——提示词只要求 ≤2，存储层多留一层防御）。
⚠️ "已有目录"到底怎么裁（本节最容易被读糊的一处，2026-10-09 补）
① 拉池就有上限：ListDistinctCategoryPaths(kbID, 400) 实际是 WHERE path <> '' ORDER BY path ASC LIMIT 400——按物化路径的字符串序取前 400，不是"一级优先"。目录总数超过 400 时，靠后的一级锚点也可能被截掉。
② 目录数 ≤ 60：一点都不裁——selectRelevantFolders 第一句就是 if len(pool) <= wikiTaxonomyFeedAllMaxFolders { return pool }，整池注入。⇒ 我们两个库（P6＋P7 共 28 个目录／A5 约 30 个）走的都是这条，从没触发过裁剪。
③ 超过 60 才裁，裁法是"一级全留 ＋ 每条目 top-3 深层"：先把池拆成一级目录（去重后全部保留，当粗锚点）与深层目录（长度 ≥2）；再把每个深层目录的文本（a / b）和每个条目的文本（title ＋ about 截 120 字符）分别嵌入；对每个条目按余弦相似度排序取 top-3（wikiTaxonomyRelevantTopK=3），跨条目求并集（保持原始顺序，保证确定性）⇒ selected = 一级目录 ＋ 并集 ⇒ 最后再 capFolders(selected, 150)。
⚠️ 降级路径与上面不一致：没有 embedding 模型、或嵌入调用失败时，退化成 capFolders(pool, 150)——直接截"原始池"的前 150 条（字符串序），没有"一级全留"保护；而池本身又可能已被 400 截过。⇒ 降级时锚点（尤其一级目录）可能被丢掉，这是这段代码里一处不自洽的地方。

⑥ 局限与待验（🤔 判断，2026-10-09）

（a）嵌入粗筛靠不靠谱？——四个问题（只在目录 > 60 时生效；我们两个库从未触发，以下为代码推理，不是实测）

  1. 硬 top-3、没有分数阈值：selectFoldersByVectors 对每个条目只取余弦前 3、不看绝对分——真正的"家目录"排第 4 就静默消失。（对照：去重那一步有 dedupCandidateScoreFloor 兜底，两处的严格度不一致。）
  2. per-item 信号在注入时被并集丢掉：嵌入算的是"每个条目各自的最近 3 个"，但注入时求并集成一棵全局树——模型不知道"这几个是专门给第 7 条目的"。而同一条链路的去重步恰恰用 per-item 短名单，注释还写明理由："Presenting the model two flat lists (all new items × all candidates) invites cross-item mispairings"。⇒ 同一个代码库里，两步的做法正好相反。
  3. 嵌入输入本身弱：目录侧把路径拼成 组织与人物 / 平台与工具（不是自然语言），条目侧是 title ＋ description 截 120 字（短且可能很泛）。质量没人验过；而且没有任何可观测字段记录"注入了哪些目录／选中率"——失败了看不见，只会在几周后表现为目录漂移。
  4. 降级路径更弱：无嵌入模型或嵌入调用失败 → 按路径字符串序截前 150（见上面那条 chain），一级锚点也可能被切掉。

⇒ 结论：作为"省 token 的粗筛"方向没问题，但它现在承担的是"目录别漂移"的职责，实际只做到"大致相关"，且可靠性无验证。至少该补两样：一个分数下限、以及把 per-item 最近邻带进提示词（而不是合并成一棵树）。

3.8 阶段六细读：reduce 写页（WikiPageModify，📄 源码级，2026-10-08）

一句话：把"一个条目 ＋ 支撑它的原文块"写成这一页的正文。它是整条流水线里唯一真正写内容的环节（A5 实测：43 次调用、197,696 token，占整个编译的 82%）。下面按输入 → 处理 → 输出讲业务功能，工程细节（并发、缓存、截断）放到最后 ④。

术语：下文把这一步的那次 LLM 调用叫"编辑器"——提示词给模型的角色就是 wiki editor（WikiPageModifySystemPrompt 首句："You are a wiki editor tasked with updating an existing wiki page."）。代码里没有叫"编辑器"的模块，它就是"一页一次"的模板化调用（internal/agent/prompts_wiki.go:321 system ＋ :345 user 两个模板，落点是 wiki_ingest_batch.go:2068 的 generateWithTemplate）。注意 "wiki editor" 这个角色名在好几个 wiki 提示词里都出现（summary、index 引言也这么开头），本文的"编辑器"专指 page_modify 那一次。

① 输入（两层：先看"谁进流程"，再看"编辑器面前摆着什么"）

每个 slug 走一趟独立流程，一趟 ＝ 一次 LLM 调用（reduceSlugUpdates :1728）；同一 slug 加锁串行（:653，防两篇文档同时改写一页）；同批多篇文档命中同一 slug 时，更新合成一条链、一起喂给这一次调用（contributors :1749-1783）。特例：summary 页不调编辑器，直接整页覆写（:1867-1886）。

①-补：素材的粒度与它带来的代价（2026-10-08 补充）

进页面的素材就是"整个块"，逐字，且不做句级截取。代码注释原文："collectCitedChunkContent materializes the verbatim content of every referenced chunk, concatenated in the order provided."——citation 阶段产出的始终是 slug → [chunk_id…]，从来没有 slug → 某句/某段区间 这种形式；装配时把每个被引块的完整正文用 \n\n 拼起来，再放进 <new_information>。

块的排序口径（2026-10-09 核代码）
· 同一篇文档内：严格按文档顺序——① 分批前先按 ChunkIndex 排序（splitChunksIntoCitationBatches :144-175，注释 "Chunk order (by ChunkIndex) is preserved"）；② 批次并发跑，收尾时把顺序"重新压回文档顺序"（classifyChunkCitations :342-357，注释 "order is re-imposed from chunk ChunkIndex at the end"）；③ collectCitedChunkContent 按给定顺序拼接。
· 文档之间：没有排序，本质不确定——各篇的 update 由并发的 map 阶段"谁先算完谁先 append"汇进 slugUpdates（wiki_ingest_batch.go:549-551）；随后 remapSlugUpdatesByIdentity 又遍历 Go map（迭代顺序随机）洗一遍（wiki_ingest_dedup.go:679-717）；reduce 里直接按这个顺序拼 <document> 块。唯一做稳定化的是 <shared_source_contexts>（sort.Strings(contextKeys)）——而且那是为了命中前缀缓存，不是为了读感。
· 每篇的块都以 Pass 0 的一句话 description 打头（格式是 **条目名**: 描述 ＋ 引用块原文）⇒ 多源页 ＝ 两段"描述 ＋ 原文"，单源页 ＝ 描述 ＋ 自己那段原文——这正是"摘要句 ＋ 原文块"重复的结构性来源（§3.10 ④）：编辑器只被允许"轻度重排／去重"，并没有要求它把这两者合并。
  • 证据粒度 ＝ chunk：默认切块目标 512 字符（A5 实测 p50 431／max 827）。引用再细也细不过块——这是 §7.7 那句"切块参数是整条链路的物理粒度旋钮"的直接后果。
  • 页面之间会重叠：citation 提示词明确允许"一个块可以被多个候选同时引用"，所以同一段原文可以出现在好几个页面上——文档不是被切开分给各页，而是被"按块打多标签"再各自成页。
  • 编辑器看不到出处：块进提示词时不带任何句柄（<c id="c003"> 只是 citation 阶段的临时外壳），页面正文是自由 Markdown、不带任何锚点，而落库的引用只有页级映射（chunk_refs＝本页由哪些块编译而来；source_refs＝指向文档）⇒ 句级归因（"这句话出自哪个块"）做不到；能做到的上限是"块级证据清单"。唯一例外：该条目完全没被引用时，降级用 Pass 0 写的 details（1–3 句）。
  • ✅ 而"页 → 块"的块级证据其实是现成的，只是没渲染（2026-10-09 更正此处"不可能"的说法）：chunk_refs 落库（types/wiki_page.go:240-247），字段注释直接写明用途是 surface the underlying evidence for a wiki page；GetPage 把 types.WikiPage 原样序列化返回（internal/handler/wiki_page.go:416，json tag chunk_refs），块又能按 id 取回（GET /chunks/by-id/{id}）⇒ "页 → 块 → 块原文"这条链路是通的。断点只在展示层：前端 WikiPage 类型里没有声明 chunk_refs（frontend/src/api/wiki/index.ts:12-39），页面只渲染文档级 source_refs（WikiBrowser.vue:1264）。⇒ 准确说法是"块级引用做得到、现在没做；做不到的是句级"。
🤔 一个上游没写出来的取舍：忠实性优先、可读性让步（2026-10-09 判断）
· 做法：页面正文的素材＝被引用块的逐字原文（collectCitedChunkContent："verbatim content of every referenced chunk, concatenated in the order provided"）；编辑器被要求做 COMPILER 而不是 writer，只获准"轻度重排／去重／拼接"，禁止为文风改写、扩写、发明过渡（prompts_wiki.go:331）。
· 官方材料里找不到这个取舍的说明：官网 wiki 文档对 Reduce 只写"严格接地、禁止幻觉、去重、禁止自链接"（website-docs/03-features/14-wiki.md:217）；架构文档、API FAQ 也没有一句谈行文代价。代码注释里唯一表露动机的是 citation 步那句 "instead of asking the LLM to paraphrase"（prompts_wiki.go:251-254）——它说的是为什么不用转述，不是为什么可以牺牲行文。
· 于是"读得顺不顺"成了没人管的维度：wiki_lint 六类体检（orphan_page／broken_link／stale_ref／missing_cross_ref／empty_content／duplicate_slug，wiki_lint.go:16-23）全是结构性的；管道里没有任何行文指标，唯一出口是产品层的人工编辑 ＋ 版本回滚。
· 可预期的后果：一页由多篇来源共同支撑时，每篇渲染成一个 <document> 块、按顺序拼进 <new_information>（wiki_ingest_batch.go:1952-1984）⇒ 跨源拼装处行文生硬是设计内的，不是 bug；每次写入时那句"轻度重排／去重／拼接"是唯一的渐进改善通道。（另一条同向的设计：system 规则 2 要求"不许过度结构化"，宁可扁平事实列表——它优化的是"可扫读"，不是"叙事流畅"。）
· ✅ 忠实性还有第三条好处：它是"可靠增量"的前提（2026-10-09 补，核代码成立）：页面正文是原文块的近逐字复制 ⇒ "删掉某篇文档"这条操作可以退化成文本级判断（"这段是否只出现在被删文档里"），而不是语义判断。retract 提示词正是这么写的："REMOVE facts/claims that were ONLY sourced from the <deleted_documents> and are NOT present in any <remaining_source_documents> or <new_information>"（prompts_wiki.go:387，user 模板 rule 2）；reparse 分支同样靠"把本文档上一次的摘要当旧版本信号"来实现 replace-not-append。如果页面是语义化改写的，页↔源就只剩"意思相近"，这类删除/替换就无从可靠判定。
· ⚠️ 但这条好处只兑现到"文档级"：① 页面正文不带任何块句柄（见上文"编辑器看不到出处"），块级追溯只剩页级并集 ⇒ "哪句话来自哪块"仍只能靠字符串弱匹配；② chunk_refs 只并不删（重解析后两代并存），块的增删既不触发也不清理。⇒ 准确说法是：忠实性把增量更新的判据从"语义比对"降到"文本比对"，而 WeKnora 只把这条好处用到文档级，块级仍交给模型判断。
· ✅ 2026-10-09 已验（§3.10，P6＋P7 两篇同域长文）：多源页 4/86，典型页 concept/synthetic-data-generation（P6 13 ＋ P7 15 块）读得顺；但 entity/langsmith 出现"摘要句 ＋ 原文块"重复 ⇒ 这条判断方向成立、烈度有限。

· 三条膨胀因子：① 块级多标签——同一段原文进多页（设计允许的常态）；② 编辑器被禁止压缩——system 里"你是 compiler 不是 writer／贴近逐字原文"，只允许 lightly reorder / deduplicate / join，压缩不是它的任务；（2026-10-09 实测锚点，本条成立：同语言时编辑器几乎不压缩——中文源 → 中文页 out/in ＝ 0.90、源文 12-gram 覆盖 79.2%（见 §3.11 的语言对照）。而"英文源 → 中文页"的 out/in 只有 0.34–0.38，那个低比值主要是"英→中"的语言密度差，不是编辑器删减——我上一版据此说"禁止压缩不成立"，已撤回。）③ 每页固定开销（标题、SUMMARY: 行、要点列表）。

· GraphRAG 的 2.3–2.6% ＝ 根层摘要 ÷ 原文（"用一层报告代表整份语料"）；
· WeKnora 的 170% ＝ 全部页面 ÷ 原文（把语料摊成一张可浏览的网页网络的索引体积）；
· 同口径的对应物是 summary 页：16.2% vs 2.6%——而这两个数差这么多也合理：GraphRAG 的 C0 是"整份语料一路压上来的根摘要"，WeKnora 的 summary 是"每篇文档一页"，天然是"按文档切的局部摘要"。

3.9 阶段七细读：链接注入与索引收尾（📄 源码级，2026-10-09）

一句话：reduce 写完页面之后，还有三条纯收尾——① 链接注入（把正文里出现的其它页标题/别名包成 [[slug|文字]]，纯文本替换、不调 LLM）；② 死链清理（指向已不存在的页的链接，能改指就改指、改不了降级成纯文本）；③ 索引页重建（LLM 只写"引言"，清单是接口动态生成的）。三者都在同一批的 finalize 里跑。

① 链路位置与输入

ProcessWikiFinalize（wiki_ingest_batch.go:1000-1180）先把本批 pending 行聚合出四样东西：affectedSlugs（本批写过或删过的页，去重）、freshRefs（本批写过的页的 title）、changeDesc（<document_added>／<document_removed> ＋ 标题 ＋ 摘要，只带这一批的变化）、folderPruneIDs（要修剪的目录）。然后依次跑死链清理 → 链接注入 → 目录修剪 → 索引重建 → 收尾。

② 链接注入：injectCrossLinks ＋ linkifyContent

  • 候选来源（每个页面各算一份）：① 该页已有 out-links 的标题（经 SlugTitleMany 解析，顺带过滤掉已归档/系统页）；② 本批新写的兄弟页的 title（freshRefs）。排除自己。
    ⚠️ 候选的"字样"只有标题：本批新写页取 row.Title，已有 out-links 也是解析成标题——别名不参与。别名只在另一条维护路径出现：wikiPageService.InjectCrossLinks（只被 agent 的写页／改名工具调用）用 collectLinkRefs＝全库 title ＋ aliases 当候选。⇒ 别名的能力在这套系统里是"半开"的（去重召回不认，摄取期链接也不认）。
  • 注入规则（linkifyContent／computeForbiddenSpans）：
    · 按 matchText 长度降序处理——长名优先，避免被自己的子串抢先；
    · 每个目标只包第一处合规命中；该 slug 在正文里已经链过就整条跳过；
    · 禁写区（绝不改）：围栏代码块、行内代码、已有的 [[…]]、markdown 链接与图片、参考式链接定义、autolink；
    · 只有 ASCII 边缘才判词边界（纯 CJK 没有空格概念，不判）；
    · 单个汉字不加链（注释举例：会把"风沙""栏目""核心"这类词拆坏）；
    · 每注入一条就平移并扩展 forbidden spans，防止后续 ref 嵌进刚造出来的 [[…]] 里。
  • 范围是被刻意限制的（注释原话）：只重写"本批 affected 页"，候选只来自"已有 out-links ＋ 本批兄弟页"——"a brand new entity in this batch won't be linkified into pages from previous batches until they get re-edited"；理由是 4 万文档量级下这是 O(batch) 查询 vs 拉 10 万+ 页的差别，长尾召回换成成本，兜底交给 lint AutoFix（这条正是 §3.7 ⑥ 里那份"规模化石"之一）。
  • 结构推论：因为只对已存在的 slug 建链（候选来自已有页的 out-links 与本批真实写出的页），悬空链接在结构上几乎不可能出现——这也是 §3.2 那条"与论文两条路线"的由来（论文是 LLM 生成链接 + Error Book 修，悬空率 29.1–63.8%）。

③ 死链清理：cleanDeadLinks → stripDeadWikiLinks

  • 判活：把该页 out-links 一次 ExistsSlugs 批量查活；没有死链就跳过。
  • 两种处理：① 若能把死 slug 解析到活 slug（靠 display-text 反查标题、或连字符归一化相等，见 resolveDeadSlug）→ 改写链接、保留显示文字；② 找不到相近的活页 → 降级成纯文本（有显示文字就用文字，没有就把 slug 最后一段"人化"）。
  • 落库不涨版本：走 UpdateAutoLinkedContent——这是机器维护，不算"用户可见编辑"，所以刻意不动 version（与人工编辑区分开）。
  • ⚠️ 但它的覆盖范围有洞（2026-10-09 实测补，见 §3.11）：删除场景下，悬空链接恰恰出现在"链接到被删页、但不引用被删文档"的别的页上——这些页不在 affectedSlugs 里，所以清不到；而 AutoFix 只在 API 被调用时才跑。实测删掉一篇文档后，lint 的 broken_link 从 0 条涨到 19 条。🤔 修法不长：删除时用被删页的 in_links 反查，把这些页一并纳入清理范围。
    批内还有一次提前修补：sanitizeDeadSummaryLinks（wiki_ingest.go:1611）——摘要页是先写的、链接是"预测"出来的，所以 reduce 之后先按本批真实写成的页把摘要页里的死链摘掉（见 §3.5／§3.6）。

④ 索引页重建：只有"引言"是 LLM 写的

  • 两条提示词分首次与增量：首次 WikiIndexIntroPrompt（吃"最近 N 篇 summary"，并附 "showing N of M" 的诚实框架，indexIntroSummaryCap = 200）；增量 WikiIndexIntroUpdatePrompt（只吃"现有引言 ＋ 本批 changeDesc"，故意不再传全量 summary——注释原话："at 4w docs it would re-flood the context every batch"）。
  • 关键设计（容易误解的地方）：索引页正文只有标题 ＋ 2–3 句引言；真正的页面清单不落库，而是由 GET /wiki/index（GetIndexView）按类型分组、游标分页动态生成（limit ≤ 200）。所以它不是 Karpathy 那种"每页一行链接的 index.md"。

  • 没有合成模型 / 模型调用失败 → 跳过索引重建（记 warn），但队列照常 drain（配置缺口，不算瞬时错误）。

  • 跨语言对照：同一篇英文 P6（24,681 字符）两次编译 ⇒ out/in 0.343／0.377；12-gram 覆盖率只剩 2–6%（因为页面是中文，英文串根本不会出现在里面）。
  • ⇒ 结论：78% 的主因是 "英文源 → 中文页"的语言密度差（≈0.4 倍），其次是"每块被多少页引用"（1.97–3.14）；编辑器几乎不压缩（同语言 0.90）——我前两轮"编辑器在压缩"的结论撤回。⚠️ 跨语言的字符比不能当压缩率。
  • 那 A5 为什么反而膨胀（154%）？语言在两边是同一因子（都是英→中），比 A5 对 P6＋P7 时被约掉——拉开差距的是引用倍数：A5 是单篇长文，条目/块 ＝ 43/70 ＝ 0.61、页/块 ＝ 0.64、每页均引 3.9 块 ⇒ 引用倍数 3.14；P6＋P7 是两篇 272 块，条目/块 ＝ 87/272 ＝ 0.32、页/块 0.31、每页均引 6.1 块 ⇒ 引用倍数 1.97。⇒ P6＋P7 每页引的块更多，但页/块比只有 A5 一半（长文里几乎每段都服务多个主题；FAQ 里大量段落是重复问答，撑不出新页），乘出来复用倍数低 60%，压不过"英→中"的缩水。
  • ⚠️ out/in 这个比值的口径要说清（别让它背锅）：in 我算的是"该页 chunk_refs 里存活块的原文长度之和、按页去重"——它全是块原文，不含任何非块内容；而模型实际看到的素材比这更多（还有每篇的 **条目名**: description 前缀、<shared_source_contexts> 的文档画像、图片 chunk 的 OCR/caption 内联）。但它有一个反向偏差：chunk_refs 是并集、只增不减（mergeChunkRefs），所以被重写过的页会把"旧版本用过、当前正文里已经没有"的块继续算进 in ⇒ in 偏大、out/in 偏小。
    ⇒ 三个数不能混用：单次写入 ＋ 同语言（中文源 chapter9）0.90；单次写入 ＋ 跨语言（P6 两次）0.343／0.377；多次重写 ＋ 跨语言（A5 0.47／P6＋P7 0.35）。要测"编辑器真实保留率"，必须控制在同语言 ＋ 只写一次。
  • 顺带的抖动样本：同一篇 P6、同一配置、跑两次 ⇒ 33 页/21,278 字符 vs 41 页/24,142 字符（页数 +24%、体积 +13.5%）——比"47 个 slug 只回来 27 个"更直观地量化了不确定性。

脚本：probe_ratio.py（体积分解）、probe_zh_source.py（同语言锚点）、probe_language_ab.py（语言 A/B，证明请求头改不动页面语言）；产物：language-ab.json／zh-source.json。

(1) 切块：internal/infrastructure/chunker/（不是 docreader 切的）

  • overlap 是条件性的（computeOverlap）：① 下一个 unit 快占满预算 → 缩小窗口；② maxOverlap<=0 → 不给；③ 窗口里找不到"语义边界"（findSemanticOverlapBoundaryEndingAtOrAfter，lookbehind＝4 即 \r\n\r\n 长度）→ 不给；④ 重叠为空／超预算／纯空白 → 不给。另外 semanticOverlapWindow 遇到零宽度的生成单元（补写表头）会切断，不许跨越它取重叠。

  • 排序按 StartAt（并列按 ChunkIndex）——位置是权威，不是块序号；StartAt > mergedEnd（有间隙）或 EndAt==0（位置缺失）→ 加 gapSep 直接拼、不裁剪；部分重叠 → AppendWithOverlap；被上一段完全覆盖 → 跳过整块。

7.9 会话脚本：一键起环境 ＋ 日志落盘（experiments/weknora/weknora_up.ps1，2026-10-08）

-Action follow / -Action stop只启动／只停掉后台跟随进程（不碰容器）
