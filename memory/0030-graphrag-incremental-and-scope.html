决策层（一分钟摘要）

一句话：GraphRAG 的"增量索引"实为 append-only 的"增量追加"——新内容独立跑一遍小流水线，再把实体/关系/社区/报告几张表拼接进旧索引；不重算社区、不重算度数、删除只检测不落地。

四条结论

  • 对 global search（跨库综述）是实质削弱：跨批主题永不出现、同主题重复计入（把"全面性"指标虚高）、层级粒度不可比、成本随更新单调上涨而覆盖不涨、已删内容继续参与回答。
  • 对 basic / local search 基本无害、部分有益：向量库 upsert 即可查；实体按 title 合并会并集 text_unit_ids、并列 description ⇒ 旧实体被新证据补全。
  • "社区不能增量重算"不是工程懒，而是算法性质：Leiden 是全局模块度优化（慢变量），局部重算会卡在接缝上、质量不可验证；保质量就退化成全量重算（还要连带重写报告、失效引用与基线）。这条线学术上研究了近十年仍未成为默认做法。
  • 它不是"不适合知识库"，而是"不适合高频更新的知识库"；判据＝索引刷新周期要与语料演化速度同量级，且要区分"全局结构"（慢变量）与"局部检索"。

适用范围（速查）

语料更新频率全局结构（global search）局部检索（basic / local）
基本不动（书 / 法规 / 制度集 / 研究集）合适合适
每月补充几次可行（离线全量重建）合适
每日新增需分域 / 分档刷新合适（追加即可）
分钟级流式不适用（任何"全局结构"都不适用）可用，但已超出该范式

对我们的三条落点

  • 我们的语料（精选文章 / 论文 / 书）更新频率天然低 ⇒ 落在适用带；
  • 我们的方向是扁平受控类别表 ＋ 逐条挂标（而非全局聚类）⇒ 新内容是局部判定，天然可增量；
  • 真要做跨库综述，走按需渲染而非预生成摘要（不预生成 ⇒ 没有"预生成过期"）。

适合谁读：要评估"要不要上某种全局索引 / 结构"的人；要设计增量更新机制的人；以及以后想复用"成熟度判断法"的人。

补充与更正（2026-09-26，为写对外文章重核一遍 3.2.0 源码时发现，四处）：
① 边表的 combined_degree 其实是重算的——主体层表格里"度数不重算"要收窄为"实体 degree 不重算"：更新流程会按合并后的边表重算 source_degree / target_degree / combined_degree（index/update/relationships.py）。两点残留瑕疵：重算发生在 filter_orphan_relationships 之前（被丢掉的悬空边已计入度数）；且实体 degree 被查询侧当作实体排序键（query/indexer_adapters.py 的 rank_col="degree"），所以那份脏账不是纯摆设。
② 合并后会再调一次 LLM（此前漏记）：合并把同一实体的多条描述收成列表，随后 get_summarized_entities_relationships 会调用摘要步骤，而 SummarizeExtractor 对"描述条数 ≥ 2"的条目真的会调模型（0 条返回空 / 1 条原样 / >1 条才调）⇒ 所有跨批出现过的实体与关系都要再付一次摘要钱。原笔记"省掉存量抽取"的说法成立，但"增量很便宜"的印象要修正。
③ 每次增量都会把整个 output/ 全表复制一份到 update_output/<时间戳>/previous/（index/run/run_pipeline.py 的 _copy_previous_output，逐表读写）⇒ 磁盘按"每次一份完整索引"的量级增长，且没有任何清理。
④ 关系合并的分组键是 (source, target)、weight 取平均（原笔记写作"按 title 分组去重"）；communities 合并会把所有社区 title 统一改写成 Community N（原笔记已记）。另补一条部署坑：config.workflows 会覆盖 --method（PipelineFactory.create_pipeline 里是 config.workflows or pipelines[method]）⇒ 若 settings 里显式列了 workflows，graphrag update 跑的是你列的那条链，而不是 18 步的更新链。

主体层 · 一、增量索引的流程

入口是 CLI 命令 graphrag update --root <dir>（cli/main.py 的 @app.command("update")，内部 is_update_run=True，输出到 update_output/）。它把方法名变成 <method>-update，由 PipelineFactory 选出 8 个 workflow：

update_final_documents → update_entities_relationships → update_text_units → update_covariates → update_communities → update_community_reports → update_text_embeddings → update_clean_state
  1. 算差异：get_delta_docs 把当前输入与上一轮 documents 表按 title 比对，得到 InputDelta(new_inputs, deleted_inputs)；但调用方 load_update_documents 只返回 new_inputs，deleted_inputs 被丢弃。
  2. 跑一遍 delta 小流水线：仅对新文档做抽取/摘要，产出这个批次的实体、关系、社区、报告（所以 delta 的 degree 是在"只有新文档的小图"里算的）。
  3. 合并实体：按 title 精确匹配建 {delta_id: old_id} 映射；text_unit_ids 取并集、description 并列成列表、frequency 重算；degree 保留旧值（代码里是 "degree": "first" 并留了 TODO）。
  4. 合并关系：编号偏移后拼接、按 title 分组去重，并调用 filter_orphan_relationships 丢弃悬空边。
  5. 合并社区：delta 的社区编号整体偏移（v + old_max + 1）后 直接 concat；-1（无社区）不变；社区 title 被覆盖成通用的 "Community N"。
  6. 合并报告：用同一套编号映射把 delta 报告拼到旧报告后面（size / period 就是为这类合并留的记账字段）。
  7. 嵌入与收尾：为新内容补向量；清掉 incremental_update_* 状态。

一句话概括：新内容独立成图 ＋ 表级拼接；只有"实体/关系的记录级合并"是真合并，结构级（社区划分、度数）不做重算。

主体层 · 二、这个设计带来的效果

效果说明
不用全量重跑省掉对存量语料的重复抽取（LLM 调用是最贵的部分），这是它存在的唯一理由。
旧实体被新证据补全text_unit_ids 并集 ＋ description 并列 ⇒ 实体/关系的证据集合随更新增长，local search 反而更全。
记录级去重是有效的按 title 合并确实阻止了"同一实体在表里出现两份"，实体 id 映射也把新关系正确接到了旧实体上。
基础检索不受损向量库 upsert 即可支撑 basic search；局部检索也不需要全局结构。

主体层 · 三、它解决不了的问题

#问题机制后果
1跨批主题永不出现社区是"旧树 ＋ 新批次树"并置，无跨批重聚global search 的立身之本（跨整个语料综合）被削弱；同主题被分批表述
2重复计入，指标虚高同一主题两批各有报告，map 各出答案、reduce 汇总comprehensiveness / diversity 看起来更好（冗余污染指标）
3层级粒度不可比旧树可能深到 C3，新批次或许只有 C0–C1"选同一层"时两边粒度不同，却在一起打 helpfulness 分
4度数口径被污染degree 不重算（老＝全量图、新＝小图）社区报告挑"哪些元素进窗口"时按度数排序 ⇒ 新批次可能按错的重要性取材
5删除不落地、陈旧内容留着deleted_inputs 被丢弃；向量库只增不删已删内容仍可被召回、仍参与全局综述 ⇒ 不是"覆盖不足"，是把不存在的东西当当前知识
6成本单调涨、覆盖不涨global search 每次扫该层全部报告token/延迟随每次更新上升，新增部分常是"另一批对旧主题的复述"
7查询侧不消费"批次"period 只做记账；查询配置无 period 过滤、上下文构建不读 period新旧产物被当同质语料混用，用户无从知道哪部分来自哪次更新

注：问题 4 的落点在"社区报告取材"，不在 local search 选取——local search 按 rank（不是 degree）排序。

主体层 · 四、根因：为什么"社区不能增量重算"不是工程问题

  1. Leiden 是全局优化：它最大化整张图的模块度（全局求和）。加几条边，最优划分可能在任意位置变化，不只在新节点周围。
  2. 解空间有大量近似最优划分（near-degenerate）：分数差极小、成员差很多；算法本身还带随机性——GraphRAG 为此专门固定 seed（"to guarantee clustering stability"）。"必须锁种子"就是"输出对细节敏感"的自证。
  3. "只重算受影响的社区"会卡在接缝上：重算区与冻结区的边界不对应任何一致划分 ⇒ 得到"既非旧最优、也非新最优"的混合体，没有目标函数能判它合不合格。要做只能用"局部模块度 ＋ 边界冻结"，质量不可验证。
  4. 保质量就退化成全量重算：不只要重跑划分，还要重写所有受影响的社区报告（LLM 生成，成本与社区数成正比）；而报告 id ＝ full_content 的 sha512 ⇒ 重算后 id 全变，缓存、引用、评测基线一起失效。增量省下的抽取钱，可能不够付重算报告的钱。

层级会放大影响：层级是递归切出来的（"递归到 ≤10 或切不动"）⇒ 一次小插入可能改变分支深度（主题落 C2 还是 C3 都变），而 global search 是"选一层扫全量"⇒ 用户看到的是"一次增量让全局问答的取材范围整体变动"。

这不是没人想到：动态社区检测是一条活跃研究线——DynaMo（2017，"增量最大化模块度"）、DyPerm（2018）、Constrained Spectral Clustering（2019）、Flow stability（2021）、ComNetX: Local Hierarchical Adaptation for Dynamic Community Detection（2026-07）。研究了近十年仍未成为默认做法，原因是"增量带来的结构漂移"必须与"结构可比性 / 稳定性"做交换，而 GraphRAG 的价值正建在"结构是全局的"之上。

主体层 · 五、适用范围与提炼

判断顺序（两问，先问再选型）

  1. 语料变化速度 vs 索引刷新周期，差几个数量级？（全局结构是慢变量：需要时间窗收敛；语料若变得比刷新快，"全局主题"还没形成就过时了）
  2. 我要的是"全局结构"还是"局部检索"？（前者只配低频刷新；后者可随写随更）

持续更新场景的四种对策

对策做法代价
分层刷新率高频只做 chunk ＋ embedding；低频做结构重算（Lambda 思路）两套路径要维护；新鲜度不均
分域建图按主题/来源/时间窗切稳定子域，各自建图各自重算跨域连接丢失（正是立项三件事之一）
滑动窗口图新内容建小图、老图冻结，查询跨多图等于默认接受"结构分批"，需查询侧配合
接受滞后并声明索引当快照，标明"数据截至某时间"，定期重建用户看到的最新的内容可能不在索引里

三条可复用的方法论提炼

① 成熟度三看法（读任何开源能力都适用）：看文档覆盖（没文档的能力多半在施工）→ 看 CHANGELOG 有无后续推进（只有"引入"那次、之后全是外围修补＝搁置）→ 看引入与最后相关改动的跨度。本例：增量索引 0.4.0（2024 初）引入、之后近两年只有存储重构/ID 修复/async 这类外围改动，而"Calculate new inputs and deleted inputs"从第一天就算出来、至今没用。
② 索引刷新周期要与语料演化速度同量级：这条能提前挡掉一大类"建的时候爽、维护起来废"的全局索引方案。配套要区分"全局结构"（慢变量，只配低频刷新）与"局部检索"（可随写随更）。
③ "约束哪一端"的第三次回本：我们选择"约束边、放开点"（38 条受控谓词）带来的红利是一条链——可过滤（能当检索键）→ 可归一（一致性靠机制而非指令）→ 可增量（逐条挂标是局部操作）。对比 GraphRAG 的全局聚类，它天生不具备增量性。
但有条硬约束：若把"类别维度"做成多层级上位概念体系，同样会撞上全局重算（层级越高越需要全局视图）⇒ 只有"扁平受控表 ＋ 逐条挂标"才保得住增量性。这条应在讨论"类别维度怎么建"时摆上台面。

对我们的落点（与既有决策的接口）

  • 语料更新频率低 ⇒ 我们落在它的适用带；真正的风险不在"更新太快"，而在"结构设计得依赖全局重算"。
  • 我们的编译产物天然可增量（逐篇编译 ＋ 扁平类别表 ＋ 逐条挂标）；一旦要做增量，先列三档：必须精确 / 可近似 / 必须重算，其中过滤键属"必须精确"——GraphRAG 的 degree 脏账可以容忍（只影响排序），我们的过滤键脏了检索直接错。
  • 删除必须落地：GraphRAG 把它算了两年没用；我们若做增量，删除要按"标脏 ＋ 局部重算"处理，不能当纯减法。
  • 跨库综述走按需渲染：不预生成摘要 ⇒ 没有"预生成过期"；这也再次支持"事实层结构化 ＋ 呈现层按需渲染"的路线。
  • 与既有待办的接口：本条与"编译层只编译第一个文件（S0 未完成，需分批＋断点续跑）"是配套关系，可一起设计。

实测（2026-09-26，第一次真跑增量）

为写对外文章 0034，第一次真跑了 graphrag update。设置：上一轮索引＝一篇中文技术文章（8138 token / 7 块，用完整标准链跑出 100 实体 / 120 关系 / 14 社区 / 8 报告）；增量＝新加一篇同系列文章（2290 token / 2 块）；模型 DeepSeek deepseek-chat；本轮不碰 embedding（embed_text.names: []）。产物在 data/tmp/graphrag-exp-update/。

七条实测结论

  1. 18 步被日志证实：load_update_documents + 9 个标准链 + 8 个 update_*，一字不差（此前只是从 factory 读出来的推断）。
  2. "删除被忽略"比"删除不落地"更准确：把一份文档从 input/ 删掉再跑 update ⇒ 只执行第一步就结束（后 17 步一步没跑）、退出码 0、6 秒、documents 表里那份文档还在。同名改文件内容同样只跑第一步。⇒ 删除这件事连"处理得不完整"都算不上，是完全不处理。
  3. 实体 degree 实测偏差 3 处（判据＝源码口径"无向去重度数"）：基线 0 处不符、delta 0 处、合并后 3 处，全是"跨批出现且拿到新边"的实体——AI-STUDY-HELPER 停在 4（应为 11）、RAG 评测工程 停在 1（应为 5）、FORMAT 停在 1（应为 2）。只在新批次的实体度数是对的（它们本来只有新边）；边表的 combined_degree 确实重算，脏的只有实体这一侧。
  4. 重汇总开销比"看起来"小得多：进度条刻度 309（=136 实体+173 关系）看着吓人，但按"描述条数 ≥ 2 才调模型"的规则，实际只有 4 次调用（4 个跨批同 title 实体；跨批关系对 0）。
  5. 成本量级：这次增量 24 次 LLM 调用（抽图 4 / 描述汇总 14 / 社区报告 6），墙钟 42 秒；该语料的完整重建是 62 次调用、64 秒。⇒ 约 40%。另：报告的 6 次调用只产出 4 份报告（静默丢报告在增量里同样存在）。调用数由缓存文件计数得到（缓存一条调用一个文件）。
  6. 规模对账：documents 1+1=2、text_units 7+2=9、entities 100+40→136（唯一"不=相加"的表，4 个按 title 合并掉）、relationships 120+53=173（两批无重合边）、communities 14+6=20（新批次编号 0–5 偏移为 14–19）、reports 8+4=12（旧 8 份报告 id 与标题 8/8 全保留）。证据块并集也确认了（1 块+1 块→2 块）。
  7. workflows 盖掉 --method，且是静默的：把一份"六步裁剪清单"写回 settings.yaml 再跑 graphrag update ⇒ 日志第一行就显示用的是那六步（8 个合并步骤一个没跑），它把 input/ 里的文档全部重新索引（那一刻 input/ 下是 2 篇＝原始那篇＋上次新增那篇；该轮 delta 的 documents=2 行、text_units=9 块＝7+2，可对账），产出 126 实体/166 关系/29 社区/26 报告写进 delta/；索引本体一个字节没变（仍 136/173/20/12），退出码 0，耗时 92 秒＝一次完整索引的钱白花。⇒ 想用更新链：要么别写 workflows，要么把它写成完整的 18 步。（口径澄清：说"2 篇"是指 input/ 里的文档数；另有 previous/ 快照目录也含这些文档，但它不参与下一轮的输入判断。）

两处"读代码的判断"被实测推翻（保留过程）

  • 社区标题没丢：读合并代码看到"把所有社区 title 统一改写成 Community N"，判断是"旧索引里有意义的社区标题会被抹掉"。实测：communities.title 在完整链产出的索引里本来就是 Community N，有意义的标题在另一张表 community_reports.title 里、且被完整保留 ⇒ 那行重写在实际数据上是 no-op。（教训：读代码看得出"做了什么动作"，看不出"这个动作在当前数据上有没有效果"。）
  • 度数不符的面没有想象中大：第一版我用"有向边条数"当判据，量出基线索引自己就有 14 处不符、合并后 17 处，差点写成"增量让 17 个实体度数失真"。改用源码口径（无向去重）后真相是基线 0 处、合并后 3 处——原来那 14 处是我换了定义（有向计数 vs 无向去重）。判据口径写不清，结论就会整体跑偏。

一条实操前提

更新链要求上一轮索引"长得齐全"：第一次实验拿六步精简链（跳过 create_final_text_units）的索引当上一轮，跑到 update_text_units 直接 Pipeline error: 'human_readable_id'——那张 text_units 表缺列。⇒ 自己裁剪过流水线的，要先补齐缺列再谈增量。

脚本：_run_update.py（跑增量）/ _analyze_update.py（三份产物逐表对账）/ _check_degree2.py（按源码口径量度数）/ _analyze_calls.py（算真实调用面）/ _levels.py（层级分布）。
