会话元信息

日期：2026-08-02 参与：用户 + Codex（AI 协作开发助手） 类型：规划 / 决策

背景

用户已熟悉单 Agent / 多 Agent 架构模式，理解 prompt 工程、context 工程、harness 工程、loop 工程的演化路径，并具备一定的 LLM 底层原理知识。目标是通过一个由浅入深的项目，实践并印证这些知识，最终覆盖当前 Agent 设计开发的主要知识体系。本记录是后续工作的路线图基线。

总体设计原则

  1. 一个产品、多阶段演化：同一产品从简到繁持续重构，让架构演进的成本与收益可见、可记录。
  2. 先手写、后框架：Agent loop、工具调用、上下文管理各手写一遍再引入框架，避免抽象掩盖要印证的知识点。
  3. 每阶段 = 知识主题 + 验证点 + 对比测试：学习闭环为“提出假设 → 实现 → 对比 → 下结论 → 记录”。
  4. 评测从第一天有，深度随复杂度递增：评测习惯（golden set、验收标准）从阶段 0 建立；评测建制化程度随产品稳定性与系统复杂度同步上升。

产品载体（定稿：以 0003 为准）

使用自有知识库、自有工具集增强的通用 AI 助手（与目录名一致）。三大支柱：通用底座（对话与常用能力）、自有知识库（用户文档形成个性化知识源）、自有工具集（用户自定义工具集合）；核心命题是范围控制：看得见 / 控得住 / 说得清。完整需求定义见 0003（阶段 0 已定稿）。各阶段能力落点如下：

阶段产品能力落点
1通用对话 + 工具调用（内置工具）
2知识库问答 + 引用 + 兜底策略验证
3记忆用户偏好（默认知识库/工具优先级）+ 多步任务规划
4工具执行沙箱、观测台、人工介入
5检索 / 工具 / 回答多 Agent 分工
6指标回归与产品化（任务完成率等）

六阶段蓝图

阶段 0 · 需求与产品定义

知识模块：需求分析、成功指标定义、边界定义

交付物：产品定义文档（用户、核心场景、最小闭环、成功指标、不做什么）

验证点：

  • 最小闭环是否足够窄，能支撑第一版上线
  • 每个后续阶段的验收标准是否可量化（杜绝“效果变好”这类不可测表述）
  • 成功指标能否覆盖“对用户有价值”，而非仅“系统能跑”

对比测试：需求文档评审

评测：定义 golden set 的取材来源与首批用例

框架：无

阶段 1 · 最小单 Agent（手写 MVP）

知识模块：Prompt 工程、function calling、基础 Agent Loop（思考→行动→观察）、结构化输出、流式

交付物：手写 loop 的单 Agent，跑通阶段 1 产品落点：通用对话 + 内置工具调用（范围见 0003）

验证点：

  • loop 各步骤是否都必要（消融：去掉某步结果如何）
  • 有/无 CoT、不同系统提示结构、few-shot，对准确率与稳定性的影响
  • 结构化输出的可靠性：schema 校验失败率、JSON 解析鲁棒性
  • 温度等采样参数对任务质量与一致性的影响

对比测试：prompt 策略矩阵、采样参数扫描

评测：golden set + 人工标注，记录基线

框架：纯手写（仅 LLM SDK）

阶段 2 · Context 工程（RAG）

知识模块：分块、嵌入、向量检索、重排、上下文预算、压缩、引用溯源

交付物：带引用的资料库问答

验证点：

  • 分块策略（大小/重叠/语义切分）对检索质量的影响
  • 检索质量与答案质量的相关性——检索差是否必然导致答案差
  • Top-k、重排、上下文预算分配（检索内容 vs 系统提示 vs 历史）的取舍
  • 上下文打满 vs 压缩后的信息损失如何量化

对比测试：分块 × 嵌入 × Top-k 检索质量矩阵；有/无重排；有/无压缩

评测：recall@k、MRR 自动化 + 答案质量抽样

框架：只引入嵌入/向量库，检索管线自拼

阶段 3 · 单 Agent 深化（记忆、规划、反思）

知识模块：长期记忆（语义/情节）、记忆写入与检索策略、Plan-and-Execute、反思与自纠错

交付物：Agent 记住用户偏好（如默认知识库/工具优先级），能做多步任务规划并自我修正

验证点：

  • 记忆的增量价值：冷启动 vs 多轮后，有/无记忆的差异
  • 记忆污染：错误记忆如何影响输出；哪些该记、哪些该丢、如何修正
  • 规划 vs 反应式：任务复杂到什么程度，plan-and-execute 才真正更优
  • 反思是否真的提升结果，额外 token/延迟是否值得

对比测试：消融对比（有/无记忆、有/无规划、有/无反思）；多轮一致性

评测：可复现任务集上的消融实验成为主线

框架：纯手写

阶段 4 · Harness 工程

知识模块：工具沙箱与安全、MCP、错误处理/重试/超时、可观测性、人工介入、状态持久化与断点

交付物：生产级 harness——沙箱化工具执行、失败恢复、观测、人工审批点

验证点：

  • 沙箱是否真正隔离；prompt 注入等攻击能否得逞（红队测试）
  • 故障注入（工具超时/报错/返回异常）下的恢复率
  • 哪些环节必须人工介入，介入的成本与收益
  • 观测数据能否定位一次失败的根本原因

对比测试：故障注入、安全用例集；阶段末的手写 vs 框架试点（spike）

评测：恢复率、安全用例通过率、spike 对比数据

框架：手写最小 harness → 阶段末限时框架 spike，用数据决定阶段 5

阶段 5 · 多 Agent 架构

知识模块：编排模式（Supervisor/流水线/辩论）、通信协议、共享状态、任务分解

交付物：多 Agent 版产品（如检索 / 工具 / 回答 Agent 分工）

验证点：

  • 单 vs 多：质量、成本、延迟的量化对比——什么任务值得拆
  • 编排模式横向对比：Supervisor、流水线、辩论各自的适用场景
  • 共享状态设计：黑板 vs 消息传递；状态一致性如何保证
  • 错误传播：一个 Agent 失败的影响，以及降级回单 Agent 的路径

对比测试：单 vs 多三元组（质量/成本/延迟）、模式间对比、失败降级

评测：阶段 3/4 任务集回归 + 成本/延迟指标

框架：依据 spike 数据正式决定

阶段 6 · 评测体系化与产品化

知识模块：eval 套件、LLM-as-judge、回归测试、成本/延迟优化、缓存、部署、产品指标闭环

交付物：统一评测与观测体系、可部署版本、任务完成率等产品指标闭环

验证点：

  • LLM-as-judge 与人工评分的一致性有多高，偏差模式是什么
  • 回归套件能否捕捉到此前各阶段引入的回归
  • 缓存/模型选择/并行等手段对成本与延迟的真实收益
  • 产品指标（任务完成率等）与系统改动的因果关系

对比测试：judge vs 人工一致性、版本回归、A/B、成本优化前后

评测：统一回归 + 线上指标

框架：评测与观测体系保持与框架解耦

关键决策记录

决策一：评测分级原则

评测习惯从阶段 0 建立（golden set、可量化验收标准）；评测建制化深度随产品稳定性与系统复杂度递增，而非一开始就建全套。理由：早期产品表面不稳定，重基建等于持续返工；输出复杂度低时人工/轻量评测 ROI 更高；过早引入 LLM-as-judge 容易变成“调裁判而非调产品”。各阶段评测对象：

  • 阶段 1：答案准确率与稳定性 → golden set + 人工标注
  • 阶段 2：检索质量 → recall@k、MRR
  • 阶段 3：记忆/规划/反思增量价值 → 消融对比、任务完成率
  • 阶段 4：鲁棒性与安全 → 故障注入、恢复率、安全用例
  • 阶段 5：多 Agent 性价比 → 质量/成本/延迟三元组
  • 阶段 6：统一回归套件 + LLM-as-judge + 产品指标

决策二：框架引入策略

引入信号（满足一两条即认真考虑）：

  • 手写胶水代码（持久化、断点、重试、流式、人工介入）开始超过 Agent 业务逻辑体量
  • 状态机出现多入口与异常恢复路径，手写状态转移开始出 bug
  • 需要大量官方维护的集成（工具生态、MCP、向量库），自维护 adapter 成本上升
  • 需要多人协作的公共语言

不引入信号：说不出具体痛点；核心 loop 尚未被自己的评测验证；框架版本剧烈变动。

执行方式：阶段 1–3 纯手写；阶段 4 手写最小 harness 后做限时 spike（1–2 天，同功能手写版 vs 框架版），对比维度固定为开发工时、代码量、调试难度、功能覆盖（断点续跑/人工介入/流式）、可维护性；用数据决定阶段 5 是否正式引入。业务层只依赖自有 Agent 接口，框架实现藏在后面；选型标准为“状态机 + 持久化 + 人工介入 + 多 Agent 编排”能力，而非名气。
