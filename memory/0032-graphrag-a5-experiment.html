第一部分 · 思路简要描述 + 结论（复习先读这里）

当时为什么做

0031 里把 GraphRAG 的查询侧（global/local/DRIFT 的选层、roll-up、map-reduce）核得比较细了，但一直是读代码。0029 的阅读清单第 ③ 步本来就写着"拿 A5/O2 跑一遍"。沛东明确目标不是做对比，而是——看看 GraphRAG 默认模式吐出来的"社区报告"到底长什么样（字段、长度、语气、findings 结构、能不能回锚）。于是设计了一个最小实验：只跑到社区报告为止，跳过一切 embedding 相关步骤。

结论（七条）

  1. 跑通了，报告形状拿到手。A5（＝我们语料里的 Anthropic《How we contain Claude across products》，8.0k token）→ 6 个 text unit → 128 实体 / 185 关系 / 23 社区（L0=9、L1=14） → 20 份报告。报告是"# 标题 ＋ 每个发现一个小节"的长文，中位 5,882 字符，findings 中位 7 条。
  2. 报告正文里本身就带实体/关系级引用：段落末尾形如 [Data: Entities (41); Relationships (47, 48, 46, 53, 54)]——即生成报告时就把引用写进了正文。（口径说明：0029 在 2026-09-22 已把引用分层改准确了——claim 级一跳、实体/关系级回到"该实体出现过的 text_unit 集合"（粒度粗）、最终答案只到报告级。本轮新增的事实是"报告正文自带这层引用"，所以"报告 → 实体/关系 → text_unit 集合"是条可实测的路径，只是粒度粗；不是推翻 0029。）
  3. DeepSeek 不支持 GraphRAG 要用的 JSON schema 结构化输出 —— 这是硬卡点（真实数据坐实了计划里标的风险①）。23 个报告调用全部 400，报告表为空，最终以 KeyError: 'community' 的形式暴露出来。加了一个本地 shim（只剥掉 API 层 schema 强制）才跑通。
  4. 提示词示例串味（确证 12 个）：128 个实体里有 12 个直接来自 GraphRAG 自己 extract_graph.py 的 few-shot 示例文本（Aurelia / Firuzabad / Quintara / Krohaara / Tiruzia / Cashion / Samuel Namara / Durke Bataglani / Meggie Tazbah / Hostage Exchange / Alhamia Prison / Aurelian Officials）——模型把示例当正文抽了。这跟 AGENTS.md 里"Pass 1 提示词含本语料示例"是同一类病、方向相反（这次是通用示例污染我们的图）。
    2026-09-25 当天更正：我先前按"名字不在原文里"的严格字面匹配报了"22/128（17%）"，偏高了——把 28 个严格不匹配的实体逐个看过之后，只有 12 个是串味，其余多是概念短语的规范形式（如 EGRESS ALLOWLIST PROXY、TRUST DIALOG VULNERABILITY）或轻度推断（MICROSOFT 由 HCS 推出），属检测器假阳性。而且那 12 个自成一个小连通片，被默认 use_lcc=True（只对最大连通分量划分社区）挡在社区之外 ⇒ 本轮没有进入任何报告正文（全文 grep 0 次）。⇒ 危害面是"污染了图（实体/关系表），没污染报告"，比我当时说的轻。
  5. 还有一次静默部分失败：23 个社区里有 3 个报告生成失败（模型返回空内容 → JSONDecodeError），但流水线报成功、退出码 0，只在日志里留下 No report found for community: 9.0 这样的 WARNING。
  6. 报告语言是"无约束下的默认回落"，不是干净的继承（第二篇掘金中文文章上实测，见第 九 节）。v2 数据上曾看起来是"实体语言决定报告语言"（全中文实体 → 10/10 份中文报告；全英文实体 → 0/11），但 v3 出现反例：社区 #8 的实体名／实体描述／关系描述全中文（1.00／1.00／1.0），报告正文却只有 0.61% 中文（几乎全英文），模型还把中文实体名翻成英文再括号回注；#3 亦然（实体名 75% 中文／描述 100% 中文 → 报告正文 2.5% 中文）。⇒ 真实机制是：报告提示词一句语言要求都没有 ⇒ 模型回落到自己的默认语言（英文），且不稳定（同一批 20 份里 12 份中文、8 份英文）。本节先前"100% 继承"的说法已撤回。抽取侧的三版提示词对比依然有效（实体描述中文率 11%→91%、关系描述 3%→98%、报告正文 40%→80%）；v4 把报告提示词原样翻译成中文 ⇒ 报告标题 19/19、正文 19/19 全部中文（语言问题解决）。（另有两条当天更正：① 我先前报的"串味 12–16→0–1"是比错文件造成的假象——v4 图里其实有 15 个实体来自我写的中文示例、并形成 24/120 条关系，只是被 use_lcc 挡在社区外、未进报告；② 报告层本身干净：真幻觉候选 0 个、19/19 报告都带引用。详见第 九 节。）
  7. prompt-tune 实测（v5）：GraphRAG 自带的"提示词自动生成"工具，一次产出 domain / language / persona / 实体类型 / few-shot 示例 / 评分标准。换掉默认四类之后，EVENT 垃圾桶占比 61% → 最大桶 14%；那批我先前叫"结构垃圾"的实体（EVIDENCE／0号输出／RUNNER.PY…）各自落进了合适的类型（output schema field／dataset artifact）⇒ "垃圾"其实是"没有合适的桶"。它也自动生成了我们手改三轮才得到的语言设定（Return output in Chinese）。但有个反直觉副作用：它把评分口径改成"与领域的相关性"，而整篇语料本身就是那个领域 ⇒ rank 中位 6.0→9.0、48/52 份挤在 8–10 分，排序能力被口径吃掉。

成本与耗时（实测）

整轮实验累计：87 次请求、16.8 万 token、$0.0546（其中 72% 命中缓存）；冷启动那一轮约 $0.024 / 116 秒。⇒ 这个体量上，成本完全可以忽略，以后想反复试配置，随便试。

第二部分 · 现场细节

一、实验设计（为什么这么切）

  • 目标：看一个社区报告的形状，不评估检索效果。
  • 范围：不跑检索（global/local/DRIFT）、不接我们自己的 KB、不与我们的编译器对比、不改默认提示词与实体类型（先看默认形态）。
  • 关键在于 workflows 这个开关（官方文档原话："run exactly and only what you want"）：只列 7 步 ⇒ 两个 embedding 工作流（create_final_text_units、generate_text_embeddings）被跳过 ⇒ 我们不需要 embedding 端点（DeepSeek 没有 embedding，本地又没起服务）。这是整个实验能成立的前提。
  • 输入：用我们自己的 app.kb.chunker.extract_sections_html_auto 把 A5 的 HTML 洗成纯文本（去 nav/footer/订阅噪声、保留小节标题）⇒ 15 个小节、28,951 字符 ≈ 8.0k token。没有把 228KB 原始 HTML 丢给 GraphRAG 的 markitdown，是为了少一个变量。
  • 只放 A5 一篇，不放 O2，减少变量。

六、四个发现

① DeepSeek 不支持 JSON schema 结构化输出（硬卡点）

社区报告这一步显式传 pydantic 模型当 response_format（community_reports_extractor.py:84），graphrag_llm 原样透传给 litellm → 转成 json_schema → DeepSeek 返回 400："This response_format type is unavailable now"。drop_params=True 兜不住（litellm 的模型表没把 response_format 标为 DeepSeek 不支持）。

处置：写了本地 shim sitecustomize.py——只把"pydantic 类的 response_format"在调 API 前剥掉；GraphRAG 拿到文本后仍会在本地用 structure_completion_response() 解析成同一个模型。不改提示词、不改 schema 定义。但代价见发现④。

② 报告内部带实体/关系级引用（对我们价值最高的一条）

正文段落末尾形如 [Data: Entities (41); Relationships (47, 48, 46, 53, 54)]。⇒ 报告不是"黑盒摘要"，它自带回锚线索：报告 → 实体/关系 → text_unit_ids。但粒度要如实说：实体/关系级引用回到的是"该实体出现过的那些 text unit"的集合（可能几十上百），不是一句话级证据——这与 0029（2026-09-22 那次修正）的分层口径一致。本轮新增的只是"这层引用确实写在报告正文里"，让这条路径可实测而非仅理论存在。

③ 提示词示例串味：确证 12 个实体来自示例文本

把 128 个实体名逐个回 A5 原文做匹配：严格字面匹配有 28 个一次都没出现；逐个看过之后，确证 12 个来自 GraphRAG extract_graph.py 的 Example 3——那段虚构新闻原文：

Example 3:
Entity_types: ORGANIZATION,GEO,PERSON
Text:
Five Aurelians jailed for 8 years in Firuzabad and widely regarded as hostages are on their way
home to Aurelia.
The swap orchestrated by Quintara was finalized when $8bn of Firuzi funds were transferred to
financial institutions in Krohaara, the capital of Quintara.

⇒ 我们的图里因此出现了 AURELIA / FIRUZABAD / QUINTARA / KROHAARA / TIRUZIA / CASHION / HOSTAGE EXCHANGE / ALHAMIA PRISON / SAMUEL NAMARA / DURKE BATAGLANI / MEGGIE TAZBAH / AURELIAN OFFICIALS，它们之间还有 8 条关系（185 条里的 8 条）。

危害面的实测边界（2026-09-25 当天补测）：这 12 个串味实体自成一个小连通片，被默认 use_lcc=True 排除在社区划分之外（28 个"字面不匹配"实体里只有 15 个落进了社区，且都是概念短语那批）⇒ 它们没有进入任何一份报告（对 reports.md 全文 grep：Aurelia/Firuzabad/Quintara/Krohaara/Tiruzia/Cashion/Namara/Tazbah/Alhamia 各 0 次）。⇒ 准确说法是"污染了图，没污染报告"；我先前"22/128 污染了语料"的说法偏高，已更正。

与我们自己的关系：AGENTS.md 开放待办里有一条"Pass 1 提示词含本语料（A5）示例 → A5 数字偏乐观"——那是我们的示例污染我们的语料；这里是反方向，GraphRAG 的通用示例污染了我们的语料。同一个病：few-shot 示例一旦与正文同处一个上下文，弱指令跟随的模型就会把示例当内容。

④ 静默部分失败：3 份报告没生成，流水线却报成功

社区 1 / 9 / 20 没有报告。日志里是 error generating community report → Community Report Extraction Error → No report found for community: 9.0，根因是模型返回空内容触发 json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)。但整个 workflow 打印 completed successfully、进程退出码 0。

诚实归因：这 3 例很可能是 shim 去掉 API 层 schema 强制的代价（模型少了约束，偶尔返回空）。要区分"模型的锅"还是"shim 的锅"，需要换一个支持 json_schema 的模型重跑——本轮没做。

七、实践与经验教训

  1. 掩码必须按"值的内容"判敏感，不能只按列名。我为查 key 写了个探针，只按列名（key/value）判敏感，于是 settings 表里那列 JSON（{"provider":…,"api_key":"sk-…"}）被原样打印，泄露了一把真实 DeepSeek key。事后查证：该 db 未被 git 跟踪且在 .gitignore 里 ⇒ 没进仓库，泄露面＝会话记录。探针已改为按值内容脱敏（含 JSON 敏感键），并把这个教训写进文件头。建议吊销重发。
  2. settings.yaml 里任何字面 $ 都会炸——GraphRAG 用 string.Template 做环境变量替换，连注释里的也算。给 file_pattern 写正则结尾锚 ⇒ Invalid placeholder in string；在注释里写出占位符的完整写法 ⇒ Environment variable not found。踩了三次才干净。
  3. 不要把子进程输出转发到本进程 stdout。两次"卡在 132/317"根本不是模型/限流问题，而是管道死锁（本进程 stdout 未被实时消费 → 停止读取子进程 → 子进程写满管道 → 僵死）。长跑任务的输出应当直接落盘，再另行 tail。
  4. "卡住"要先用日志时间戳判定，再动手改参数。我先怀疑限流、降并发加超时，白折腾一轮；真正有效的动作是"看日志最后写入时间 + 进程状态"。
  5. 比"看效果"更值钱的是看到失败模式：这一轮真正有信息量的不是报告长什么样，而是串味、静默失败、provider 兼容性这三类"看报告看不出来的东西"。

③ 经验教训：判定器自身连错四次（都属于"想当然"）

  1. 跨语言下"实体名回原文匹配"整体失效：我用它把 JOHNS HOPKINS UNIVERSITY 判成幻觉，可原文写的是"约翰霍普金斯大学"——错的是我。⇒ 中文语料＋英文图时，必须改用语言无关判据（如"是否命中提示词示例专名"）。判据先要问：它在目标语言下成立吗。
  2. all([]) == True 陷阱：判据写成"实体名的每个词都能在提示词里找到"，中文名切不出拉丁词 ⇒ 词表为空 ⇒ 恒为真 ⇒ 把所有中文实体误判成串味。

十、prompt-tune 实测（v5）：换掉类型表，垃圾桶就没了

起因：v4 的类型分布是 EVENT 62/101（61%）——默认四类（organization/person/geo/event）是给叙事语料设计的，技术文章里的概念/方法/指标/字段全挤进 EVENT。GraphRAG 自带 prompt-tune（用 LLM 从语料推断 domain / language / persona / 实体类型 / few-shot 示例 / 评分标准），于是拿它跑了一遍。

① 要四处准备，不止"加一个参数"

  1. --limit 7：默认 limit=15，而越界回落的实现是 limit = LIMIT(=15) 之后无条件 sample(n=15) ⇒ 块数 < 15 直接崩（我们这篇正好 7 块）。
  2. 必须补 embedding_models 占位块：prompt-tune 无条件构造嵌入客户端（get_embedding_model_config("default_embedding_model")），缺 key 直接 ValueError——哪怕 top/random 选法根本不用嵌入。
  3. 要带 shim：generate_entity_types 在 API 里写死 json_mode=True ⇒ 传 pydantic schema ⇒ DeepSeek 400（同 #2573 那个坑）。
  4. 输出目录必须换：默认 -o prompts 会写 extract_graph.txt——正好覆盖我们手改的那份；改用 -o prompts-tuned。
  5. 连带发现：补了占位 key 之后，索引的预检会真的去调嵌入端点（拿占位 key 打了 OpenAI，401），尽管 workflows 里没有任何 embedding 步骤 ⇒ 索引得加 --skip-validation。又一个"配置要求与实际使用脱钩"。

运行结果：退出码 0 · 33 秒 · 11 次调用 · $0.0367，产出三份提示词（extract_graph.txt 25KB/499 行、summarize_descriptions.txt、community_report_graph.txt）。

② 它自己生成了什么

  • 14 个领域类型：evaluation metric / evaluation methodology / failure mode / root cause / fix strategy / gold standard / judge prompt / output schema field / model / technical term / experiment / paper / dataset artifact / design principle。
  • 语言＝中文：它先跑 detect_language，再把 language 填进所有提示词模板 —— Return output in Chinese、If you have to translate into Chinese, just translate the descriptions, nothing else!、Your answers should be in Chinese。我们手改三轮才得到的东西，它一次给全了，而且"只翻译描述、别动实体名"那句比手写的更狠。
  • 领域 persona：「expert in LLM evaluation methodology and algorithmic analysis… diagnosing instability through metrics like flip-rate and judge consistency」。
  • 评分标准带锚点：把默认的 "impact severity" 换成 "relevance to LLM evaluation methodology… 1 = trivial or irrelevant，10 = highly significant"。
  • 2 个 few-shot 示例，取自本文档原文 ⇒ 对"这一篇"是自污染，对"给整库调提示词"则合理——与我们 AGENTS.md 记的"Pass 1 含 A5 示例"同类。

⑤ 反直觉的副作用：评分标准"领域化"之后，rank 失去区分度

v4:  中位 6.0 · 范围 1.0–8.5
v5:  中位 9.0 · 范围 5.5–9.8 · 标准差 0.78 · 48/52 份落在 (8, 10]

原因是 prompt-tune 把评分口径从"影响严重程度"换成了"与 LLM 评测方法学的相关性"——而整篇文章本身就是讲这个的 ⇒ 每个社区都高度相关 ⇒ 全部 8–10 分。

可复用判据："评分标准领域化" ≠ "评分有信息量"。判据必须与用途对齐：rank 在 GraphRAG 里是用于排序与过滤的（min_community_rank、批内排序、reduce 降序截断），那就必须选一个在语料内部有方差的维度；选"与领域的相关性"这种全库同质的维度，等于把排序能力杀掉。v5 的锚点比 v4 清楚（1=trivial / 10=highly significant），但方差被口径吃掉了——"有锚点"和"有信息量"是两件事。

⑥ 两处小的

  • 类型越界：v5 出现第 15 个类型 PROJECT（实体 RAG 评测工程系列），不在配置的 14 类里、提示词里也没有 ⇒ 模型自造类型。内容合理，但说明类型约束不是硬约束。
  • "串味"判据在中文语料上不可用：v5 上报了 39 个，逐个核下来基本都是跨语言误报——字段顺序（原文 4 次）、反例（7 次）、探针（12 次）、合并（2 次）都在原文里，只是被译成了英文。这类误报本 session 已犯三次 ⇒ 中文语料上不要用它判串味。

⑦ 当天更正：v5 的静默失败比我说的更严重，而且指标看不见

我在 ③ 那张表里先写的是"调用失败数 0 ⇒ 静默失败消失"，依据是运行日志末尾的 LLM 指标（failed_response_count: 0）。那是把读数当成了结果。查缺失清单才发现：v5 有 12/64 个社区（19%）没生成报告，日志里 No report found 也是 12 条，与缺失清单（6、16、17、19、24、26、27、32、34、44、49、60）逐一对得上。

为什么指标是"全绿"的：那 12 次失败发生在 "LLM 返回内容 → 解析/校验成 pydantic schema" 这一步（community_reports_extractor 自己的 try/except 里），而 HTTP 调用本身是成功的 ⇒ 不进 failed_response_count。⇒ 指标的统计边界是"调用层"，不是"产出层"；于是"指标全绿"与"19% 社区没报告"可以同时成立。这与 #2573（roll-up）同一性质：失败被静默吞掉，且汇总层看不到。
顺带修正另一处：v4 是 2/21（10%），v5 是 12/64（19%）——tuned 提示词并没有减少静默失败，丢失率反而升了（可能因为社区数多了 3 倍、每个社区的上下文更碎）。所以 ③ 表里"静默失败消失"的结论撤回。
