0.2 Karpathy 的 llm-wiki.md（gist）

它是什么：不是论文，是一份"idea file"——原话："This is an idea file, it is designed to be copy pasted to your own LLM Agent (e.g. OpenAI Codex, Claude Code, OpenCode / Pi, or etc.). Its goal is to communicate the high level idea, but your agent will build out the specifics in collaboration with you."

地址：gist.github.com/karpathy/442a6bf555914893e9891c11519de94f　本地：data/tmp/karpathy_llm_wiki.md（76 行）

核心主张（三句原文）：
① "Instead of just retrieving from raw documents at query time, the LLM incrementally builds and maintains a persistent wiki — a structured, interlinked collection of markdown files that sits between you and the raw sources."
② "the wiki is a persistent, compounding artifact. The cross-references are already there. The contradictions have already been flagged. The synthesis already reflects everything you've read."
③ "You never (or rarely) write the wiki yourself — the LLM writes and maintains all of it. … Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."
结构内容（原文要点）
三层架构Raw sources（不可变，"your source of truth"）／The wiki（LLM 全权拥有的 markdown 页：摘要、实体页、概念页、对比、概述、综合）／The schema（决定 wiki 怎么组织、有什么约定、按什么流程工作）
三个操作Ingest（读源 → 与你讨论要点 → 写摘要页 → 更新索引 → 更新相关实体/概念页 → 追加日志；一个源可能触及 10–15 个页）／Query（检索页 → 读 → 带引用综合；好答案可以归档回 wiki，让探索也复利）／Lint（定期体检：页间矛盾、被新源取代的过期断言、无入链的孤儿页、被提到却没有自己页面的重要概念、缺失的交叉引用、可由联网补上的数据缺口）
两个特殊文件index.md：内容目录（每页一条链接 ＋ 一行摘要），每次 ingest 更新，回答时先读索引；原话："works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure"。／log.md：时间序、append-only，条目带固定前缀即可用 grep 取最近几条
可选工具规模大了要有搜索：推荐 qmd（本地 markdown 搜索引擎，BM25＋向量混合＋LLM 重排，带 CLI 与 MCP server）
为什么有效原话："The tedious part of maintaining a knowledge base is not the reading or the thinking — it's the bookkeeping. … Humans abandon wikis because the maintenance burden grows faster than the value. LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass."　人的职责："curate sources, direct the analysis, ask good questions"
精神祖上"related in spirit to Vannevar Bush's Memex (1945) — a personal, curated knowledge store with associative trails between documents… The part he couldn't solve was who does the maintenance. The LLM handles that."
边界声明原话："This document is intentionally abstract. It describes the idea, not a specific implementation. The exact directory structure, the schema conventions, the page formats, the tooling — all of that will depend on your domain, your preferences, and your LLM of choice. Everything mentioned above is optional and modular… The document's only job is to communicate the pattern. Your LLM can figure out the rest."　⇒ 它给的是模式，不是实现；论文＝把这个模式操作化，nashsu/llm_wiki＝把这个模式工程化。

两点值得单独记：① "缺口可见性"在 Karpathy 这里是显式的 Lint 项（孤儿页、缺页、缺交叉引用、数据缺口）——比论文更正面（论文只在 Layer 2 的修复清单里出现"missing pages"，没有面向使用者的缺口视图）；但它是人触发的定期体检，不是自动机制。② 规模前提不同：Karpathy 说 index.md 在"~100 源 / 数百页"这个量级够用；而论文的 2WikiMHQA Wiki 是 5,825 知识页 ＋ 6,840 源页——已经远超"够用"区间，这大概正是论文必须补 Error Book 与两层校验的原因。

本文的展开顺序是一条因果链，不是对照表：① 为什么要把检索自主权交给 LLM → ② 为什么先编译 → ③ 编译的三个要求如何推出"Wiki"这个形态 → ④ 为什么 Error Book 是必选；与 GraphRAG 的对照集中放在 §5，作为这条推理的下游结论。一句话概括两者关系：语义层同构、机制层不同构。

1. 为什么要把检索自主权交给 LLM

驱动力来自一个观察：知识库上的问题五花八门，统一流程应付不了。固定 top-k 检索 ＋ 一次生成，擅长"局部事实"（答案就在少数几段里）；但问题一旦是全局的（整份语料在讲什么）、多跳的（A → B → 答案）、枚举的（都有哪些）、比较的（两者异同），"先取固定几段、再一次性回答"就失灵——因为在读之前，系统根本不知道该看哪几段。

而 LLM 有推理能力，可以承担"先看什么、下一步看什么、够了没有"这些判断。于是把自主权交给它：检索不再是一次性的取数动作，而是一段由推理驱动的过程——论文称之 retrieval-as-reasoning，并给了两条典型路线：search-first（从实体出发锚定）与 browse-first（开放式与枚举型：先看全景，再逐级下钻）。

论文自己的两句话，正好是这条推理的两端：
· 该做——"The bottleneck lies in how knowledge is organized and exposed to the agent, not merely in the retrieval algorithm."（瓶颈在"知识怎么被组织、怎么暴露给 agent"）
· 能做——agent 已具备 ReAct 式的"推理 ＋ 行动"工具调用循环，可以把"搜索／阅读／跟随链接／判断够了没有"拆成原子动作再组合起来。

反例就在旁边：GraphRAG 的 Global Search 默认检索行为仍是确定性流程——取哪些社区报告由调用方交给它的 community_level 决定（CLI 默认 2，语义是 level ≤ N；只有传 None 才是全层不过滤），然后把这批报告扫一遍、map-reduce 出答案。也就是说，"该看多细"这个判断被外包给了调用方（这个参数是它唯一的出口），而不是交给 LLM。另三种模式里，Basic／Local 同样是"先定死取数、再生成"；DRIFT 与 Dynamic 才释放了少量 LLM 判断（前者迭代生成后续查询，后者只判"某个社区要不要"）——完整对照见 §5。

2. 为什么先编译：原始文本也能给自主权，编译只是更好

先把话说实：不编译也能做自主检索。把原文直接交给 agent、给它搜索与阅读的工具，它照样能多轮探索——已有的 agentic RAG 就是这么干的。所以编译不是"能不能自主检索"的必要条件，它换来的是三件增量：

  1. 省掉"每次重新发现"：原始文本是平的，每一次提问都要从头把散落的信息找出来、临时拼起来；编译把这些工作一次性提前做完。
  2. 提供原文里不存在的指针：原文只有顺序，没有"这两段在讲同一件事"的显式提示；编译把关系与指针物化出来，遍历才有依托。
  3. 把成本前移、摊薄查询期：论文的说法是 "Front-loading organization to compile time"；Karpathy 的说法是 "the LLM is rediscovering knowledge from scratch on every question. There's no accumulation."——编译之后，知识是累积（compounding）的，而不是每次重算。

3. 编译的三个要求 ⇒ 为什么落到"Wiki"这个形态

3.1 要求一：得能承载知识 —— 借 KG 的核心概念，不背它的形式包袱

承载知识，目前已知较好的框架就是 KG 那一套：实体 ＋ 关系。但它很重——本体、类型系统、推导规则、一致性约束都要人定义和维护。所以只借它的核心概念，不借它的形式约束。它列举的那些页面（摘要、实体、概念、对比分析、概述、综合介绍），大体可归成三类：

语义类LLM-Wiki 里的形态GraphRAG 里的形态
实体（名词单位）实体页（标题 ＋ aliases）实体表（name ＋ type ＋ description）
关系（谓词，含被 reify 的）链接 ＋ 其后的关系说明（-- father of John V）＋ 对比分析页 ＋ 实体页里的结构化陈述（Key Facts）关系表（source → target ＋ description）
聚合体（把一组内容压成一个单位）摘要页、概述页、主题/综合介绍页社区报告（层级摘要）

链接与关系不是两回事：wikilink 是可跟随的指针，而页面 schema 要求它后面跟一句关系说明——附录 E 的原例就是 - [[people/Ernest-I-Prince-of-Anhalt-Dessau]] 紧跟 -- father of John V。所以关系这一类在 wiki 里的承载 ＝"链接 ＋ 那句说明"（＋ 对比分析页）。差别在关系的"类型"以什么形式存在：这里是自然语言的自由说明（没有受控词表、没有固定字段）——人读得懂、机器能查出"悬空链接"，但不能按关系类型机检／过滤（对照 GraphRAG：端点在关系表里可机读、可筛选，而 description 同样是自由文本）。

关键修正："摘要/概述"不是"被 reify 的谓词"，而是一元聚合——它把一组内容压成一个可读单位，不对应任何具体关系。这个区分很要紧：聚合体的粒度是"机制给的"，不是"语义给的"（GraphRAG 侧实测：L2 社区 100% ≤10 实体，粒度来自 max_cluster_size=10 这个算法常数）。

这个选择有一个前提：推断这一步已经由 LLM 承担了。本体、类型系统、推导规则在传统 KG 里是承重结构——它们管的是"两个概念能不能这么连""能不能从已知事实推出新事实""数据里有没有自相矛盾"，没有它们，机器既推不动、也检不出。而在这里，这些判断由 LLM 直接在自然语言上完成（与 §1 的"LLM 有推理能力"是同一条）。形式层于是不再是承重的，可以省。所以"只借概念"不是图省事的简化，而是把这一层的职责换了个承担者：从形式系统换成了模型本身。

"只借概念"的代价要认：没有本体与类型系统、没有推导规则、也没有全局一致性保证——一致性得靠"编译期校验 ＋ 纠错机制"来兜（这正引出 §4）。这条也是它与正统 KG（KAG 那一极）的分界线。

3.2 要求二：得能支撑自主检索 —— 尤其"遍历"

自主检索要能边走边看，就需要三样东西：可寻址的单位（能指名某个东西去看）、显式的指针（能从一个走到另一个）、全景入口（不知道从哪下手时先看目录）。这三样正好落在"页面（标题即地址）＋ 双向链接（带关系说明）＋ 目录索引"上：

检索期需要什么组织上就得提供什么出处
已知实体的局部事实可寻址的实体页（标题唯一 ＋ aliases 兜别名）论文 §6（source-localized 问题 "may favor methods that retrieve the original article directly"）；Karpathy 的 entity pages
关系跟随 / 多跳桥接显式链接（页与页的双向 wikilink，成为可跟随的指针）论文 §6 "relation following"；附录 E "bidirectional wikilinks expose explicit traversal paths"
证据枚举 / 跨文档聚合主题页与聚合页（把一组内容压成一个可列举、可综览的单位）论文 §6 "evidence enumeration / cross-document aggregation"
开放式探索（不知道从哪下手）目录层（index.md／_index.md：先看全景，再逐级下钻）Karpathy："When answering a query, the LLM reads the index first to find relevant pages, then drills into them."
结构上真正的区别：链接提供"任意关联"——跨目录、跨层级、任意两页都能连，所以桥接／跨文档聚合这类需求靠链接走，而不是靠翻层级。两条限定：① 链接是 LLM 生成 ＋ 校验出来的，完备性与正确性都没有保证——dangling link 是它第一大错误类，占检测到的错误 29.1–63.8%；② wikilink 本身不带类型参数，关系靠紧跟其后的自由文本说明（-- father of John V）——所以可读、可跟随，但不能按关系类型机检／过滤（对照 GraphRAG 的边：端点在关系表里可机读、可筛选，description 同样是自由文本）。
层级的出处与形态（📎 论文附录 E ＋ Karpathy）：wiki/ 下 6 个主题目录（concepts／geography／history／media／organizations／people）＋ 根 index.md；每个目录各有 _index.md 并在内部按语义分组（如 people/_index.md 把 3,241 条分在 "German Nobility"、"Chinese Film Directors" 下），即"全局索引 → 主题目录 → 目录内分组 → 页面"；但深度不受机制限制（目录可继续嵌套、schema 由使用者定），论文这一实例是两三层。

3.3 要求三：大规模编译必然用 LLM ⇒ 产物必须"人可读"（纠错所需 ＋ 知识库自身的定位）

语料一大，"靠人写编译产物（分类、摘要、关联）"成本不可承受，用 LLM 编译是必然选择；而 LLM 会出错（§4 详述），所以必须有人在环中检查；要让人能检查，产物就得是人能直接读的——这是"人可读"的第一条理由（为了纠错）。

还有第二条理由，而它跟问答没关系：知识库的定位本身就包含"给人读"。人会直接翻阅、检索、核对这份编译产物（wiki 这种形态存在的意义正在于此），而不是只把它当成问答管线里的一段中间数据——对组织级／个人知识库来说，"能被人直接读懂、直接查"本身就是交付物的一部分。所以"人可读"不只是为了让纠错流程跑得通而做的被动妥协，它是一个独立的产品需求；两条理由合起来，才说明它为什么是硬要求。

三个要求合起来是个交集：机器可寻址、可遍历（要求二）∩ 人可以直接阅读（要求三）＝ 以页面 ＋ 链接为载体的文本——也就是 Wiki。论文自己的措辞正是这个交集："human-readable and machine-traversable substrate"。

但"人必须在环"≠"人逐条读"——否则这个要求在大语料上立刻自相矛盾。它能成立，靠的是把错误分流：错误的第一大类是结构类（悬空链接、引用格式、索引不一致——占比见 §4），这一层由程序确定性查出，也能自动修；留给人的是内容类（无据断言、跨页矛盾），而内容类本就只能抽检。所以"人可读"这个要求，实际买到的是可审查性（inspectability）——人能随时打开任一页核对、能看懂程序报出的结构错误——而不是"人工逐条验收"。

为什么不是别的形态：
· 只有"遍历"这一条，会推出图／三元组（机器友好，人不好读）；
· 只有"人可读 ＋ 人检查"这一条，会推出普通文档（人友好，但没有指针、不能遍历）；
· 两条的交集才唯一指向"页面 ＋ 链接"。（Karpathy 的说法很直白："Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."——wiki 是给人读、给机器跑的同一份东西。）

4. 因为用 LLM 编译，错误是必然的 ⇒ 纠错机制是必选

LLM 写出来的页面不会天然自洽。论文实测的错误分布，是这条推理最硬的证据：七类系统性错误里，悬空链接占检测到错误的 29.1–63.8%、malformed references 占 18.9–28.5%——结构类错误是第一大类；此外还有内容类的：无据断言（unsupported facts）、跨页矛盾（cross-page contradictions）。

错误类别典型形态谁来查
结构类悬空链接、页面不完整、引用格式错、未见覆盖（unseen overwrites）、索引不一致确定性校验（代码）
内容类无据断言、跨页矛盾与源对齐的 LLM 校验 ＋ 跨页一致性检查

它的解法是 Error Book：把"反复出现的错误"沉淀成约束规则，注入后续编译提示词，并驱动修复。五个阶段——发现 → 归因 → 写成规则 → 注入编译提示词 → 定期复验并关闭；落盘为 error_book.yaml，每条含现象／根因／约束规则／验证方式／状态（open／closed）。

修复分两层：代码层——每个编译批次之后跑确定性修复（悬空链接、格式、索引不一致）；LLM 层——每若干篇触发一次，处理需要推理的问题（缺页、摘要不完整、无据断言、跨页矛盾）。定稿时再跑三轮"代码修复 ↔ LLM 修复"回环收敛。

5. 与 GraphRAG 的对照（上面那条推理的下游结论）

一句话：两者语义层同构、机制层不同构——它用 KG 的"实体—关系"骨架来组织知识，但组织形态的依据是"检索期需要什么"，而不是"KG 的形式完备性"；机制上最要紧的差别则是"可读的那一层，和可遍历的那一层，是不是同一层"。而这条差别不是偶然：根源是两者锚定的目标不同（本节末尾展开）。

语义层（同构）：两边都用"实体／关系／聚合"来装知识，区别只在形态（表见 §3.1）。机制层（不同构）：把两条线放到两个轴上——人读与机器遍历（这两个轴对应论文那句判据，📎 "…whether the resulting knowledge base exposes explicit, traversable structure that an agent can search, read, and traverse"）

线产物人读机器遍历
GraphRAG图（实体 ＋ 关系）＋ 社区报告（层级摘要）△ 可读与可遍历不在同一层：报告是文本、可读；图那一层不天然给人读（要另建可视化／导出）△ 能但受限：可沿社区上下级行走，也可沿实体的关系邻域寻址（local search 的"入口实体 → 邻域"就是这种遍历）；但缺"页面级稳定寻址单位"，跨社区／跨源也没有任意关联的边
LLM-Wiki页面 ＋ 链接 ＋ 索引✅ 能（markdown 页天然可读）✅ 能（页面可寻址 ＋ 链接可跟随 ＋ 索引可下钻）
所以分野不是"能不能遍历"，而是"可读的层与可遍历的层是不是同一层"：GraphRAG 两层分离——报告可读但不可遍历，图可遍历（沿隶属与关系）但不天然给人读；LLM-Wiki 合在同一层：页面既是给人看的文本，又是可寻址、可跟随的单位。论文的措辞正是这个交集："human-readable and machine-traversable substrate"。
这条差别的根源：两者锚定的目标不同。
· GraphRAG 锚定的是"把一份语料上的全局性问题答好"——所以它要的产物天然是跨文档的多粒度抽象：社区层级就是给"把该层报告扫一遍、map-reduce 出答案"准备的。至于"哪些内容该算一个主题"，它交给了图的结构——层次 Leiden 在实体图上按边划分社区（无向划分，📄 源码核过），而不是让 LLM 去判主题。这个目标在索引期就被押注进去了：实体类型表、报告模板那一组提示词，正是"目标已知"这个前提的产物。
· LLM-Wiki 锚定的是"把检索主动权交给 LLM、面向事先不知道的问题"——所以它要的产物必须是可寻址、可跟随的单位：页面 ＋ 链接是从这个目标直接推出来的；而目标本身以可编辑的 schema 形式留在外面，由人和 LLM 一起演化。
回到 §1：这正好解释了为什么 GraphRAG 会把"该看多细"交给调用方——它的目标把粒度押在索引期的全局结构上，查询期只需选层；而 LLM-Wiki 把判断交给 LLM，因为它的前提就是"问题事先不知道"。
一句话收口：GraphRAG 把"该看多细"交给用户、把知识压成一批跨文档的分层报告；LLM-Wiki 把"该看多细"交给LLM、把知识摆成可读又可遍历的页面。可以说，前者回答"目标已知时怎么省"，后者回答"目标未知时怎么找"。

6. 待验证清单（回归主线：对着 LLM-Wiki 的三个机制看）

§1–§5 是把它读通；§6 是读通之后还不知道的部分。三个机制的信息密度差得很远：知识编译是落地时最基础的一环，却也是论文与 Karpathy 讲得最含糊的一环；错误处理（Error Book）机制清楚，要验的相对少；检索给的数据最详细、机制也好理解，但有一处数字反直觉。下面按这个顺序排。

6.0 实验平台：WeKnora（2026-09-30 定 · 📄 README ＋ 源码核过 · 决策链与代码盘点见 0037）

之所以选它：三种模式共用同一套知识管线——RAG 问答／Agent／Auto Wiki（Tencent/WeKnora，Go，31.2k★，越 4.1k，v0.8.2 发布于 2026-09-24）——正好一条腿踩住下面三节要验的东西：

待验WeKnora 里对应的能力（README 原文口径）
6.1 知识编译Auto Wiki：把知识库文档里的 people／products／concepts 抽成带来源引用的页面、按目录组织；知识图展示页面之间的关系；页面可直接编辑，每次改动都能回滚（revision diff）
6.1 增量／删除同上的编辑＋diff＋回滚，加上知识库的目录树（folder tree）、chunk 编辑与修订、文档解析的分阶段时间线
6.2 错误处理有两条通路：① 确定性体检 ＋ 自动修复——wiki_lint.go 查 6 类（broken_link／stale_ref／empty_content／orphan_page／missing_cross_ref／duplicate_slug），带严重度、能否自动修与 HealthScore（0–100）；② Agent 问题台账——flag_issue 记 4 类内容问题（mixed_entities／contradictory_facts／out_of_date／other），状态 pending → resolved/ignored。缺的是论文 Error Book 的签名动作：把反复犯的错沉淀成规则、回灌下一轮编译
6.3 检索Agent 模式＝ReAct agent 在知识库与工具上跑多步（可选 steer／fork／rewind）；另有 hybrid search（关键词＋向量）＋ rerank ＋ parent-child chunking ＋ GraphRAG（Neo4j），后者正好当对照臂
6.3 计时口径Langfuse 追踪每个 agent step 的推理、工具调用与 token 用量——论文时延表缺的四样里，"每方法输入输出 token 数"与"步骤构成"这两样在这里能自己补上

📄 源码核过的两处关键（2026-09-30，D:\lida-data\vscode\WeKnora，tag v0.8.2 @ 3e8b0bf）：
· 纠错不是"只有人工兜底"——RunLint 的六类检查里，有三类可自动修（AutoFix）：破链把 [[slug]] 降级成纯文本（保留文字、拆掉链接，不补页）、空页归档（不删）、失效引用剥掉 source_ref——若该页再无活源就直接删页，注释写明理由："留下孤儿摘要页更糟，模型还会链它、wiki_read_source_doc 的下钻永远失败"。
· 目录／视角是"批次级一次规划"（wiki_ingest_taxonomy.go）：整批一次性规划分类，锚在已有目录上复用，更深的候选目录用嵌入相似度 topK 挑，且只补空缺（已有分类的页不再改）。代码注释直言这是在替换旧做法——"per-page, parallel CATEGORY invention — which couldn't converge, worst of all on the founding batch when the KB has no folders to anchor on."（每页各自发明分类，收敛不了；首次批次没有目录可锚时最惨）⇒ 这是继"算法常数"（GraphRAG）、"人写的 schema"（Karpathy）之后的第三种视角形态。

三条要认的限制：① 它不是论文的实现（论文无代码），所以跑出来的结论属于"WeKnora 的 wiki 模式"，不是"论文方法"；② 错误处理缺的是"规则回灌"那一环——自动体检与问题台账都有，但没有论文那套"把反复犯的错写成约束、注入下一轮编译"；③ 项目迭代很快（v0.8.0／v0.8.2 都在 2026-09），实验必须锁版本号，README 承诺的能力要按"📄 核过"抽查过再用。部署是 Docker Compose（PostgreSQL ＋ Redis，上 GraphRAG 另需 Neo4j），有完整 Web UI，模型侧支持 DeepSeek——成本口径能和 GraphRAG 那条线对齐。
备选记一笔：nashsu/llm_wiki（20.1k★，TypeScript，桌面应用）更贴 Karpathy 的描述——两步 CoT ingest ＋ 增量缓存 ＋ Louvain 社区发现 ＋ **知识缺口**视图 ＋ rebuild index；但检索侧没有 agent 工具循环、也没有 Langfuse 这类可观测性 ⇒ 留作 6.1 的"编译实现对照"，不做主台子。

6.1 知识编译 —— 最不清楚、也最基础

为什么排第一：这是把原始语料变成 wiki 的那一步，后面检索全靠它的产物；而两篇材料恰恰在这里最含糊——论文没给编译提示词原文、没写 SelectPages 的选择机制、没有命名／合并规则（这三条也是"论文对应的实现不存在"的直接原因）；Karpathy 那边则把这一层整个交给 schema，只说"和 LLM 一起演化"。要验的三件事，正好对应编译面临的三种输入变化：

  • 全量怎么编——从 schema／目标出发的三步：视角选择（schema 定下什么该进 wiki）、抽取（页面与陈述从哪些源、以什么粒度产出）、合并（同一实体的别名、同一主题的多页：归并还是并存）。
    两条概念判断挂在这里一起测：① §3.1 归纳的"实体／关系／聚合体"三类是否真的承载得住（＝"语义层同构"能不能用实验体现）；② 聚合体的粒度到底是机制给的还是语义给的——图侧量社区规模分布、wiki 侧量页面粒度分布，各量一次即可对照。
  • 增量怎么处理——追加新源后页面级更新是否真局部？目录／索引／命名冲突这些全局结构谁维护？改一次 schema 再追加，先量新旧页面混存的比例与跨代链接的完整性，再对同一批问题各问一次，看答案会不会自相矛盾。（论文 Limitations 自认 indices 会失控、stale-fact 是 future work）
  • 删除怎么处理——删掉一个源，量悬空链接数、孤儿页数，并检查答案里是否还在引用被删内容；同时要区分"知识作废"与"来源撤回"两种语义。判据现成：RunLint 直接给 broken_link／orphan_page／stale_ref 三类，而且 stale_ref 的自动修法已经内含一个取舍（剥引用；失去全部活源就删页）——我们要验的正是这个取舍对不对。

已知对照（📄 论文 Limitations ＋ ✅ GraphRAG 侧实测）：GraphRAG 的增量是追加式（社区不重划、度数不重算）⇒ 结构分代，同一份语料追加两轮后根节点数 9 → ＋6 → 15；删除则是"删除被忽略"（退出码 0、索引与删除前完全一致）⇒ 只剩全量重编译一条路。这两条正是"LLM-Wiki 逻辑上更好"的依据，但也仅止于逻辑上——它没有这些问题，是因为它没有全局算法，不是因为有谁验证过删除协议。

6.2 错误处理（Error Book）—— 机制清楚，要验的少

论文给了错误分布（悬空链接占检测错误的 29.1–63.8%、malformed refs 18.9–28.5%）与五阶段流程（发现 → 归因 → 写成规则 → 注入编译提示词 → 定期复验并关闭），做法直白：把反复犯的错写成约束，喂回下一轮编译。所以它更像"要不要照做"，而不是"怎么做"。要留意的只有两点：错误率是否随迭代收敛，以及这套规则换一份语料还管不管用——规则是从本语料的错误里长出来的，跨域迁移没有先验理由。另外，§6.0 那台子上只有这套机制的前两段——自动发现（体检）与问题记录（issue 台账）都有，"写成约束、回灌编译"这一段没有；所以这一节能验的是"发现与记录够不够用"，不是"规则回灌灵不灵"。

6.3 检索 —— 机制好懂，但有一处数据反直觉

机制层面不难理解：检索权交给 LLM，靠两个工具（wiki_search ／ wiki_read）加遍历，"下一步看什么"由模型自己决定；它依赖的就是 LLM 的推理能力——所以"效果好不好"与"模型强不强"是同一件事。论文在这一块的实验也最细（三个多跳基准各 500 例 ＋ 按跳数分层）。

但耗时这一项，按结构算它一定是慢的。稠密向量检索是"一次检索（毫秒级）＋ 一次生成"；而 LLM-Wiki 走的是串行推理循环——工具调用预算 T_max=15（连续 3 次空搜索即停，且回答前至少得读一次页），而每次工具调用前后都要过一次 LLM，所以是十几轮串行推理。多出来的全是实打实的开销，而且轮与轮之间有依赖，并行摊不掉。所以看到附录 G Table 10 里它在 HotpotQA 上是 14.9s、快过稠密检索的 16.3s（MuSiQue 27.1 vs 26.9、2WikiMHQA 15.9 vs 15.6 反而略慢）时，要解释的不是"它为什么慢"，而是"它凭什么能快到这个程度"。

只有三种可能，而且都能验：① 每轮调用极短——一轮只读一页、只输出几十个 token，轮数多但每轮便宜；② 最后那次生成比稠密检索短得多——生成是自回归的，稠密检索要塞 5–10 个 chunk 原文，模型容易写得长；③ 测量条件本来就不同——同一个表里 GraphRAG 是更强的旁证：它是 map 上百份报告再 reduce，结构上比谁都贵，却在三个基准上都最快（14.0／13.9／10.8）⇒ "同等条件"这个前提本身就值得怀疑。这张表口径缺四样（端点定义／测量条件／每方法输入输出 token 数／失败样本处理，详见 §7.5），所以它现在的身份是"待解释的数据"，不是证据。要验：

  • 逐轮记账：固定模型与并发，把轮数 ＋ 每轮的输入／输出 token ＋ 各段耗时都记下来——这是唯一能回答"时间到底花在哪"的口径（§7.5 已列三个候选驱动：输出长度、并行度、方法内部额外计算）。
  • "优势随跳数增长"（附录 G 的 fine-grained analysis）换一份语料能否复现出同样的趋势（不求复现绝对分数）。
  • 多路径 vs 单一路由键：wiki 允许多条链接路径到达同一实体，推断是"召回更鲁棒、但枚举更难穷尽"，这条怎么测。

另有一项事务性核查：论文发表状态——arXiv 元信息（journal_ref／comment）、Semantic Scholar（venue／publicationTypes）、DBLP 三处对一遍。

第二部分 · 现场细节（2026-09-29 / 09-30）

7.1 沛东的七条初步想法（原话要点）

  1. 两者都是"先编译后使用"，只从这点看与 GraphRAG 相同；在此框架下有相同点与不同点。
  2. LLM-Wiki 没规定严格语义结构，但它列举的"摘要、实体、概念、对比分析、概述、综合介绍"大体可归为实体、关系、主题三类，即 GraphRAG 建模的三类；甚至可认为 GraphRAG 的编译过程（暂不考虑存储结构与细化定义）是 LLM-Wiki 的一种具体实现；KG 的实体、关系仍是很好的基础，所谓主题/对比分析/摘要/概述/综合介绍，本质上是预先把一部分谓词 reify 并实体化。
  3. 编译阶段的核心区别是承载方式：GraphRAG 是"图 ＋ 社区报告"（图承载实体＋关系，社区报告在层级上类似主题或综合介绍）；LLM-Wiki 是 Wiki 这种方式。
  4. 检索阶段是关键区别：LLM-Wiki 把自主权完全交给 LLM（只留极少 harness，如最大迭代次数）；GraphRAG 自主权主要仍在确定性代码，只在某些策略里释放局部决策权（如 DCS 判断某社区是否有利于检索）。
  5. 增加内容：GraphRAG 受制于 Leiden，基本无法低成本增量；LLM-Wiki 因为底层语义仍是 KG 那套、且不依赖 Leiden 这类全局算法，逻辑上要好很多，不存在难以逾越的障碍。
  6. 减少内容：GraphRAG 基本只有全量重编译一条路；LLM-Wiki 同样因为没有全局算法，逻辑上可以较好支撑——虽然 Karpathy 与那篇论文都没提到这一点。
  7. 编译必然带应用目标视角：LLM-Wiki 解决得更好——它有一个主层级目录结构，但通过链接实现了"语义不那么严格的图的关联关系"；在假设 LLM 足够智能的前提下，可以靠链接与"边推理边检索"召回足够信息。

4 检索自主权同意补"决策对象不同"：一方释放的是"选材取舍"、另一方是"下一步做什么"（§1 反例 ＋ §5 根源段）。

7.5 时延表（附录 G Table 10）为什么"看着不合理"（2026-09-30）

沛东在论文 §5 附近的效率分析里看到这张表，第一反应是"不合逻辑"：稠密向量检索不是最快的，连完全不做外部检索的 None（闭卷）也不是最快的。原文数据（秒/题）：

方法HotpotQAMuSiQue2WikiMHQA
None（闭卷）24.730.021.6
BM25 RAG18.130.216.7
Dense RAG16.326.915.6
RAPTOR19.940.228.0
GraphRAG14.013.910.8
LightRAG41.451.339.7
HippoRAG 233.538.232.4
LLM-Wiki14.927.115.9

我的判断：不是"不合逻辑"，而是"这张表没给能判断它的口径"。端到端延迟在这种系统里通常由三件事主导，而不是"有没有外部检索"：

  1. 输出 token 数——生成本身是自回归的。闭卷没有证据约束，模型倾向写得更长更泛；只要它多写几十个 token 就会慢过检索版。GraphRAG 最快也能这么解释（它的最终输出是短汇总）。
  2. 并行度——GraphRAG 的 map 阶段是并行的（concurrent_requests，默认 32），而 BM25／Dense 是"一次检索 ＋ 一次串行生成"。"调用次数多"不等于"墙钟长"。
  3. 方法内部的额外计算——HippoRAG 2 那 33.5s 里大头很可能是 PPR／图运算，RAPTOR 的 28–40s 很可能是树检索里的多次 LLM 调用，LightRAG 41–51s 同理；这些都跟"有没有外检索"无关。
真正的问题在于它没给什么：全文关于这张表只有一句 "Table 10: Query latency in seconds per question on three benchmarks."＋ §4.4 的 "we report latency in Table 10"。缺 ① 端点定义（TTFT 还是总时长）② 测量条件（并发／顺序／重试／硬件或服务）③ 每方法输入与输出 token 数 ④ 失败样本怎么算——全文 A100／GPU／throughput／concurrency／output tokens／prompt tokens／answer length 出现次数全是 0。没有这四样，这张表既不能被解释、也不能被复现。
而且它在这篇论文里是加分项（用来说明"LLM-Wiki 不比检索慢"），口径不严的方向恰好对它有利 ⇒ 不该当证据用。
还有一处措辞比数据宽：正文写 LLM-Wiki "comparable to or faster than BM25 and Dense RAG"，但按表看，MuSiQue（27.1 vs 26.9）与 2Wiki（15.9 vs 15.6）上它其实略慢于 Dense RAG。
可落地的检验（成本极低）：固定同一模型与并发，同时记录 输入 token ／ 输出 token ／ TTFT ／ 总时长。若闭卷的输出 token 明显更多，"闭卷更慢"立刻被解释；若不成立，问题在测量条件（排队、顺序、重试）。
