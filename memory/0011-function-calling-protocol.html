会话元信息

日期：2026-08-03 参与：用户 + Codex（AI 协作开发助手） 类型：调试记录 / 协议学习

现象

用户询问“3+5等于几？”时，DeepSeek 返回 400 Bad Request。从处理过程面板看，第一轮消息只有 system + user（2 条），工具定义看似“没发出去”。

排查过程：用已配置 Key 直接探测——第一轮载荷（4 个工具 + 同款消息）返回 200；deepseek-reasoner 同样 200。最终用模拟第二轮请求复现 400，错误体给出准确原因：messages[2]: missing field 'name'。

根因（两个协议细节）

  1. 流式 tool_calls 片段不能原样回显

    流式响应里一个工具调用被拆成多片：第一片带 id/type/name，后续片只有 arguments 增量。原实现把原始片段列表直接回显，第二片缺 name（更早版本还缺 id/type），API 反序列化失败 → 400。

    修复：按 index 合并成完整对象再回显：{"id": ..., "type": "function", "function": {"name": ..., "arguments": ...}}。

  2. tool 消息必须带 tool_call_id

    第一处修复后第二轮报 messages[3]: missing field 'tool_call_id'：OpenAI 兼容协议要求每条 role="tool" 的消息通过 tool_call_id 关联到对应的工具调用。

    修复：ToolCall 与 LLMMessage 增加 id 字段，回填工具结果时带上 tool_call_id。

验证

  • 真实 API 端到端：询问当前时间（强制触发工具）→ 模型调用 current_datetime → 执行成功（0.1ms）→ 第二轮消息数变为 4（含回显与结果）→ 生成最终回答；rounds: 2, tool_calls: 1
  • 后端 14 个测试全绿（新增断言：回显必须是完整结构、id 保留）
  • 附带改进：API 错误信息现在会带上响应体原文，前端/日志直接可见失败原因；trace 的 llm_call 展示模型名与发送的工具定义

附带观察（prompt 工程素材）

“3+5等于几”这类简单算术，模型即使看到工具定义也可能直接心算而不调用工具（本次复测即如此）。这提示：工具增强模式的系统提示需要更明确的任务要求，否则模型是否用工具是“看心情”的——这是 golden set 阶段值得做对比测试的点（不同 prompt 下工具调用率）。

教训

手写 function calling 时，OpenAI 兼容协议有两个硬性要求：tool_calls 回显必须完整合并（不能回显流式原始片段），tool 消息必须关联 tool_call_id。排查 API 400 时，先看错误响应体，别猜。

补充：usage 解析教训（2026-08-03 追加）

实现流式 token 用量采集时发现：DeepSeek 开启 include_usage 后，每个流式 chunk 都带 usage 键（内容 chunk 里为 null）。判断“是否用量 chunk”不能看 usage 键是否存在，否则所有内容 chunk 都会被误跳过。且响应有两种变体：用量可能出现在 choices 为空的 chunk，也可能带在最后一个有 finish_reason 的 chunk 里——稳妥做法是“只要 usage 非空就采集”。
