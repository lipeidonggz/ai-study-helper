为什么提前做（背景与动机）

0002 原计划把"评测体系化"放在阶段 6，但那是"完整体系化"（LLM-as-judge、统一回归、成本/延迟优化）。本次提前做的不是那一整套，而是评测的使用门槛——理由有四：

  1. 阶段 2–5 的验证点全部依赖评测：检索指标（recall@k/MRR）、消融对比、故障注入、多 Agent 三元组，都建在"用例 + 跑批 + 结果追踪"这套地基上。评测不是阶段 6 的锦上添花，而是后面每个阶段的必备工具。
  2. 当前结果闭环断在人工标注：Excel 标注表填了也无法合并回报告统计，质量维度（答案正确/拒答合理）的结论一直出不来——阶段 1 的验收也因此悬着。评测台把标注 UI 化，是把闭环合上的关键一步。
  3. 评测价值已被验证：0015 的 70 条用例跑批抓到了两个真 bug（多工具并行 400、工具失败崩 turn）。这套体系值得加码投入，而不是停在"能跑"。
  4. 提前但不越界：只做 P1 内部工具（够用、可追踪），用例仍以 JSON 文件为真源（git 可 diff、可评审、可回滚），不做产品级后台，避免"基建返工"。

定位

评测台是项目的"内部工具"：让用例管理、跑批触发、结果跟踪、人工标注都在一个界面里完成，支撑阶段 1 验收与阶段 2–5 的对比测试。不是产品后台，不追求通用性与美观。

P1 范围（本次实现）

一、用例管理（Case Management）

  • 列表：按 category / criteria / tags / 状态 / 关键词（id、title、input）筛选与排序
  • CRUD：新建 / 查看 / 编辑 / 删除；保存走现有 Pydantic schema 校验，错误逐字段提示
  • 状态字段：新增 enabled（默认 true），停用的用例不参与跑批
  • 备注拆分：notes（设计说明，已有）+ 新增 admin_note（管理备注：停用原因 / TODO / 标注判断依据）
  • 轻量变更记录：updated_at + updated_by（单用户本地，不做完整审计）
  • 导入 / 导出：导出当前筛选结果为 JSON；支持从目录导入（现有 70 条零成本迁移）

二、测试管理（Test Run Management）

  • 触发跑批：选择用例范围（全部 / 分类 / 标签 / 手选 id 子集）+ 参数（llm real|fake、concurrency、retries、超时）；真实模型前有确认提示（会花钱 + 限流经验：并发 2 + 重试）
  • 运行状态机：queued → running → done / canceled / error；进度 = 已完成/总数；v1 轮询刷新（1–2s），SSE 为可选增强
  • 结果查看：汇总指标（通过/错误/待标注、工具调用率、平均耗时、总 token、分类统计）+ 用例结果表（状态、耗时、轮数、工具调用、自动判定），可展开看输出、trace 关键事件、错误信息
  • 历史与对比：runs 列表 + 两个 run 的汇总级对比（同指标并列）
  • 人工标注 UI 化：run 详情内联标注（答案正确 对/错/存疑；拒答 合理/不合理/不适用 + 备注），保存进 run 数据，实时计算人工判定通过率；Excel 降级为导出格式
  • 导出：JSON 全量 + Excel 保留

五个决策点（用户已确认）

决策点结论理由
备注字段 notes（设计）+ admin_note（管理）分开 设计说明面向读者与用例意图，管理备注面向维护过程（停用原因/待办/标注依据），混在一起语义不清
用例存储 JSON 文件为唯一真源 git 可 diff、可评审、可回滚，符合项目"一切可追踪"的风格；UI 直接读写文件，SQLite 只存跑批结果
人工标注 本轮 UI 化，替代 Excel 为主途径 Excel 标注无法合并回统计，结果闭环断在此处；UI 内联标注才能实时算出质量维度结论
run 对比 P1 只做汇总级对比 汇总对比已能支撑"改动是否变好"的日常判断；case 级 diff 是增强，后置
断点恢复 不需要；取消跑批要 单用户本地跑批分钟级完成，续跑收益低；取消是操作体验必需（跑错参数/想停就停）

数据与存储设计

  • 用例：继续 backend/eval/cases/*.json；schema 新增 enabled、admin_note、updated_at、updated_by
  • 新增 SQLite 表 eval_runs：id、创建时间、名称、配置（JSON）、状态、进度、汇总（JSON）、错误信息
  • 新增 SQLite 表 eval_run_cases：run_id、case_id、状态、输出、elapsed_ms、rounds、tool_calls、tokens、自动判定、pending_human、人工判定（answer_correct / refusal / 备注）

技术落点（大致方案）

  • 后端：新增 app/api/eval.py router（/api/eval/cases、/api/eval/runs 等）；跑批复用 runner 核心函数，从 CLI + asyncio.run 重构为可取消的异步任务（asyncio task 承载，支持 cancel）
  • 前端：新增"评测"入口 + 两个页面（用例管理、测试管理），复用现有 Vue/TS 结构与样式体系
  • 注意：跑批进程内直连 loop 会占用 uvicorn 事件循环，跑批期间其他请求响应受影响——单用户本地可接受，但 --reload / 多 worker 场景要小心
