第二部分 · 现场细节（按阶段分界，复原现场用）

阶段 A · 全量入库体检（2026-09-04，主战场第一仗）

  1. 全量入库完成：27 源 3333 块（此前 260 块）——T1 书 928、T2/T3 教程、A/O/P/B/D 系列业界文章；D4/D5/PAPER 未采集不在范围。
  2. embed 内存失控与修复：fastembed embed 默认 batch 256，e5-large 在 CPU 上单批峰值可达十几 GB（T1 入库跑到 17.7GB 失控）；修复 = FastEmbedEmbedder 固定 batch=32，实测内存稳定约 3.7GB。吞吐 ~1 块/s 是本机 CPU（12 逻辑核）跑 5.3 亿参数 fp32 的物理上限（豆包给的 INT8 速度数字自相矛盾、与物理账不符，未采信；性能优化非主线，不做）。
  3. index-all 重入浪费：全量入库不跳过已 ready 源（T1 白跑两遍约 34 分钟）→ 待改：index-all 语义 = 补齐未入库，跳过 ready（重入库走单源接口）。
  4. D6（阿里云 developer）失败根因与 lake 适配：正文以 JS 字面量（GLOBAL_CONFIG.larkContent）藏在 script 里（静态 DOM 只有导航 + "关注卡"，且关注卡被包在 <article> 里误导根容器选择）→ 新增 lake 富文本抽取（extract_lake_content 反转义 + extract_sections_html_auto 自动分流 + 回归测试）；D6 重入库 12 块、节标题归位、检索命中正常。
  5. 意义：全量入库是抽取适配的体检场——素材类型每扩一批，管线适配要跟着补（与 0025"先做对适配再放开范围"的经验一致）；这三条是质量评估报告的第一批发现。
