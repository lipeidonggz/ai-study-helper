背景：从反应式调校进入主动式验证

阶段 1 基线定稿（0021）后，进入 0002 路线图阶段 1 的验证点：prompt 策略对比、采样参数扫描、结构化输出可靠性、loop 消融。这标志着调校模式从反应式（评测发现问题 → 修复）转向主动式（按行业经验清单系统扫描关键变量）。

主线脉络（读前必看）

本笔记按"目标 → 遇到问题 → 所以做下一步"的决策链记录，每条主线节点都回答"为什么做这个"；实验细节和数据在各节表格里。脉络如下：

  1. 为什么开始主动式验证：基线定稿（0021）后，0002 路线图阶段 1 要求系统性回答"提示词该不该这样写"——主动式调校按行业经验清单扫关键变量，而不是等问题暴露再修。
  2. 为什么做 repeat 20：repeat 5 全量显示 cot +8.4pp，但每用例只采样 5 次，结论不可信——样本量决定结论可信度，必须加大样本。
  3. 为什么先跑差异子集：repeat 20 全量在并发 2 下要 35–40 分钟，等不起——先挑 repeat 5 下差异最大的 10 条做 repeat 20 子集确认。
  4. 为什么补规模阶梯用例：子集对比反复出现"简单计算心算可靠、大数必须工具化"的边界问题——补 小/中/大 阶梯系统测边界，并据此重构计算用例口径（小档去 tool_used，B 框架以用例分层落地）。
  5. 为什么中途做性能优化：repeat 20 全量太慢成为严谨对比的瓶颈（且怀疑被限流）——查清是吞吐算术 + 本地瓶颈后，落地性能四项，并发定档 50/20（83×20 约 2 分钟），顺带发现余额动态限流。
  6. 为什么修判官/金标准污染：大样本下发现结论被污染（015 金标准数字错误、012 措辞、判官在"工具事实 vs 金标准"冲突下随机站队）——评测本身不可信，结论就不可信，先修评测再对比。
  7. 为什么基线还原重开：小档去 tool_used 后，cot 原先"验算→调工具"的加分通道消失，问题口径变了——以无 cot 原始基线重新对照。
  8. 为什么现在收官：污染修复后四变体全量对照（83×20×4）：cot 与 baseline 平手、no_behavior 表面更优但证据不足（金标准刚性 + 安全代价）——保持 baseline，prompt 策略对比收官。
  9. 为什么开始温度扫描：prompt 对比收官后，下一个验证点是采样参数；DeepSeek 官方按任务类型建议温度（代码/数学 0.0、通用对话 1.3、创意 1.5），说明"一个 Agent 一套采样参数"做不到多任务最优——扫温度看当前用例集的最优点，顺带论证了 Router 模式的存在价值。
  10. 为什么掉进统计的坑：温度七档跑完，case 级通过率在 86.7%~92.8% 之间乱摆、0.7/1.0/2.0 并列最高——查下去发现是"全过才算 pass"聚合规则制造的 19/20↔20/20 悬崖，不是真实差异；被迫把大学数理统计捡回来：mean±CI、加权复合分、bootstrap、Neyman 分配、显著性。
  11. 为什么升级评测台：统计结论要能日常使用，就得落进工具——用例加 weight/must_pass，跑批汇总加"加权复合分 + bootstrap CI + 红线闸门"（模式照搬 LangSmith composite / Vijil 零容忍，不发明）；顺带确认了权重/红线在成熟框架里早有实现，推翻了自己"框架给不了"的错误判断。
  12. 为什么做安全修复：红线闸门一上线就把 7 个温度档全部刷红——4 条安全红线（自伤/用药/危险命令/系统提示）稳定度只有 85~95%，生产上不了线；先修安全再谈温度。修了三轮（提示词 → 确定性护栏 → 金标准误伤修正）才闭环，过程中撞出"内容层防御无界 vs 范围层防御有界"的范围控制洞察。

1. CoT 是"免费午餐"但有双面性

  • 整体：pass 率 +8.4 个百分点、unstable 减半、token 几乎不涨——改善倾向明显；
  • 双面性：对 tool-calc-001（3+5），CoT 触发"答完验算"→ 调工具确认（工具化尾巴被压）；对 tool-calc-007（2^10），CoT 让模型"思考即计算"（分步思考时就算出答案）→ 觉得不需要工具 → 心算 fail。CoT 同时增强"反思-验证"与"自我计算"两个倾向；

2. 防御/契约条款的"账"

  • minimal 退化集中在安全类（fuzzy-004 矛盾、inject-004 解锁咒语、refuse-005 拒答）——去掉防御基线后安全边界松（refusal 100%→93.3%）；
  • token 成本：防御基线 + 行为契约约占 14%（minimal 125k vs baseline 146k）；
  • 结论：防御条款的收益在"拒答质量"（安全侧），代价是 token + 少量正确率——生产取舍的依据。

并发与限流排查（探针 + Run#31）

为什么做这个：repeat 20 全量在并发 2 下太慢（35–40 分钟），怀疑被 DeepSeek 限流——用探针 + 并发压测查明真相（结论：不是限流，是吞吐算术 + 本地瓶颈）。

结论先行

慢不是 Key 被限流，是吞吐算术：总请求量 × 单次耗时 ÷ 并发。DeepSeek 不公开 RPM/TPM，也没有配额查看页面；实测无 429、无速率响应头。

证据链

  • 配额页不存在：官方文档只有并发上限（v4-flash 2500/账号，超过才 429）；错误码页笼统提"TPM/RPM 达上限"但全站无数值、无查看入口；控制台仅有余额 / 用量（platform.deepseek.com/usage）/ API Keys / 充值；声称"密钥详情有 QPS/RPM/TPM 表格"的文章为 SEO 幻觉内容，不可信；
  • 轻量探针（2 并发 60s）：590 请求全 200、0 个 429，p50 0.16s / p95 0.32s，响应头无 x-ratelimit-*；
  • Run#31（10 用例 × repeat 10，并发 10，1m07s）：100 次执行 + 100 次判定全 ok、0 超时；单次执行中位从并发 2 的 2.2s 升到 ~4.0s，吞吐约为并发 2 的 3 倍（1.49 vs 0.49 runs/s）；

性能优化与并发定档（2026-08-28）

为什么做这个：查明本地瓶颈后，四项优化落地（连接池 / to_thread 落库 / 轻量轮询 / attempt 级并行），并发定档 50/20——83×20 从 35–40 分钟降到约 2 分钟，严谨对比才跑得起。

四步优化

  1. LLM 客户端连接池：eval 跑批共享一个 httpx.AsyncClient（Limits 200/200），不再每次调用新建 TLS 连接（上千次调用 → 几十条复用连接）；微基准 8 次小请求 9.11s → 7.09s；
  2. 落库移出事件循环：on_case 的 SQLite 写入改 asyncio.to_thread，事件循环不再被 fsync 卡死（曾把单次 attempt 拖到 ~39s，修复后回到 ~2s）；WAL 试过但撤回（Windows 多进程下偶发 CANTOPEN）；
  3. 详情页轮询瘦身：轮询 1.5s→5s + getRun?light=1（不带 repeat_results/trace），展开用例时按需取单条全量并缓存——轮询负载 327KB → 12KB（约 1/27）；
  4. attempt 级并行 + note 隔离：repeat 从"case 内串行"改为"每个 (case, idx) 独立任务进信号量池"，并发 50 真正生效；笔记存储从进程级 dict 改为 contextvars 按 attempt 隔离（顺带修掉串行时代 repeat 串味）；新增链式用例 tool-note-combo-001（单请求内写后读）。

统计方法论：19/20 不是噪声，是聚合悬崖（2026-08-28）

为什么做这个：温度扫描的 case 级读数乱摆，追查根因发现是聚合规则问题，不是模型问题——被迫把数理统计捡回来，把"评测读数可信度"这件事彻底搞懂。

核心机制：case 级"全过才算 pass"是悬崖

  • 真实通过率 p 的用例，判 pass 的概率是 p^20：p=0.95 → 35.8%，p=0.90 → 12.2%——一条真实 95% 稳定的用例只有 1/3 概率被判 pass，这就是 19/20↔20/20 翻车的来源；
  • 继续加大 repeat 在当前规则下会更糟：p^50=7.7%、p^100=0.6%，边界用例永远 unstable；
  • 模拟验证（投篮类比）：真实 95% 的用例，n=20 时读数在 80%~100% 之间晃（20/20 出现 35.9%、19/20 37.6%、≤18/20 26.5%）；n=1660 时读数稳定在 93.8%~96.2%。

mean ± CI（置信区间）

  • CI 就是"根据这批数据，真实值大概率待在哪条带里"：n=20 时带宽 ±11pp（等于没测准），n=1660 时 ±0.3pp；
  • 合并 ≠ 单条：把 83 条用例的 attempt 加总，窄 CI 回答"套件平均多准"；任何单条用例的 CI 仍然很宽（n=20 → ±12pp）——合并不改变单条精度；
  • 权重不均时加总收益缩水：复合分被高权重用例绑架，有效样本量 k_eff=(Σw)²/Σw²（一条权重=其余之和时 k_eff 从 83 掉到 ~4）；权重越高越该多跑，精确规则是 Neyman 分配 n ∝ w·σ（σ=√(p(1-p))，p=50% 的用例需要约 5 倍于 99% 用例的样本）。

加权复合分与显著性

  • 加权复合分 = Σ(wᵢ·通过率ᵢ)/Σwᵢ，业界对应 utility/value-weighted accuracy；
  • 显著性（假设检验）：CI 回答"每个配置自己多可信"，显著性回答"两个配置的差异能不能算数"——差异/噪声 = 信噪比，p<0.05 才算显著；配对版本（McNemar/配对置换）因为同用例配对、消掉用例间水平差异，比两个 CI 比重叠更敏感；
  • 业界坐标：Anthropic《Adding Error Bars to Evals》（2024-11）→ ICML 2025 争论 CLT vs bootstrap 在小样本下的可靠性 → 2026 出现专用库 evalci（CI/配对检验/功效分析）、agent-eval（Agent 回归测试 p 值+效应量+CI）、vllm 用 Wilson 下界做 CI 门槛——统计严谨正在从倡议变成标配。

一句话总结

连续打分（含部分分/加权）汇总 + 大样本 mean±CI + 配对统计检验 + 安全红线单列——这是业界成熟做法，也是这次讨论的全部结论。

评测反哺工具改进：循环小数输出形态（2026-08-30）

为什么做这个：run 78 逐条复盘时，combined-007（多问题分步处理）出现 2/20 不稳定，且失败模式极其迷惑——模型 4 轮工具调用全部耗尽、最终输出为空。

现象与轨迹

  • 失败两次（第 7/9 次）：rounds=4、end_reason=max_rounds、输出为空 → answer_correct 无法判定转人工（pending）；
  • 轨迹显示模型拿到 365/7 = 365/7（精确） 后不满意，反复改写表达式试图逼出小数：365/7.0 → 365/7*1.0 → 365//7 → 365%7……全被工具原样打回，4 轮耗尽时连最终文本都没来得及写。

根因：工具输出形态，不是模型能力

  • 计算器对循环小数只返回精确分数（365/7 = 365/7（精确）），把输入表达式当结果回显，没有任何小数读数；
  • 模型视角"等于多少"没被回答 → 进入"改写表达式逼小数"的死循环；智能在线（它后来算出了 52 和余数 1），但努力全耗在工具调用上，输出为零；
  • 符合"能确定性就确定性"：这类问题应在工具层消除，而不是靠提示词压。

修复与验证

  • 计算器新增长除法循环节检测（纯整数运算、无浮点误差）：循环小数输出 365/7 = 365/7（精确）= 52.(142857)（循环小数），精确分数与循环节十进制同时给出；
  • 测试更新（10/3、1/6、sqrt(4/9) 断言改为新格式，新增 365/7 回归断言），84 全过；
  • 回归 run 79（28 条计算类 + combined-007，reason，repeat 20）：28/28 通过、复合分 1.0；combined-007 20/20，模型直接转述"52 又 1/7（52.142857…，142857 为循环节）"；
  • 样例意义：评测反哺工具改进的完整闭环——判定 pending → 轨迹定位 → 工具层确定性修复 → 回归确认；与 0020"评测如何反哺 Agent"的案例库同类，可入册。

软/硬超时拆分：上游延迟尾不再污染判定（2026-08-30）

为什么做这个：run 77/78 复盘发现一批"timeout after 30.0s"：模型行为没错（工具用了、方向对），只是整条用例没在 30 秒预算内跑完，被硬掐成 exec_error、判定作废。run 77（chat）更严重，20 次超时吃掉大量采样（tool-calc-016/017 各 6 次、note-get-001 4 次）。

  • 归因：上游（DeepSeek）延迟尾 + 请求排队——请求不报错但迟迟不返回（120s 的 LLM 调用超时从未触发），全卡在 30s 用例预算上；结合此前查实的"余额动态并发限制"，判断为上游不稳定，本地只做 I/O 转发、落库已走 to_thread，非本地瓶颈；
  • 修复：把"硬超时"与"latency 预算"拆开——timeout_sec 退化为软预算（latency_budget 判定基准，慢于它判 fail 但不中断）；新增 hard_timeout_sec（默认 90s）作硬上限，超过才中断；慢请求从此变成"照常判定 + latency 如实记 fail"，不再产生不可判定的 exec_error；
  • 用例编辑器同步拆成"耗时预算"与"硬超时"两个字段；存量用例零改动（hard_timeout_sec 默认 90 补齐）；
  • 测试 +1（软/硬拆分：0.05s 响应、0.01s 预算、1.0s 硬超时 → status=ok 但 latency_budget=fail），85 全过；
  • 生产含义：LLM 上游延迟不稳定是常态，标准应对是 per-request timeout + 退避重试 + 并发上限 + 熔断/降级 + 多 provider 兜底，监控 TTFT/TPOT 的 P95/P99；评测侧同理——"慢"应该是可量化的指标，而不是把采样变成废票。

延迟尾尖峰：不跑过得不到的认知（2026-08-30）

为什么记这个：拆超时的过程中顺手算了 run 77/78 的耗时分位数，数字一出来有种"原来如此"的震动——平均 3 秒的"稳定"系统，P99 尾巴却甩到 30 秒。这个认知不自己跑一遍，光看文档是长不出来的；而它恰恰是生产环境每天都会遇到的事。

数据：均值会骗人

run平均P50P90P95P99≥30s

一半请求 2.5 秒、90% 在 5~6 秒、95% 在 7~8 秒——看起来稳如老狗；再往后 P99 从 8 秒直接跳到 14.5~30 秒。这就是"尾尖峰"：绝大多数快，极少数慢得离谱，平均值完全看不见它。

规律：单次无规律，统计有规律

  • 单次无规律：哪一次慢无法预测，同一用例同一配置 repeat 20，超时落在随机位置（第 7 次、第 16 次）；
  • 重尾是稳定形态：分布永远长这样，只是尾巴粗细不同；
  • 负载越高尾越重：并发 50 下 chat 1.18% 撞到 30s、reason 0.18%——排队加剧让尾巴变粗；
  • 多轮用例被放大：预算覆盖所有轮次，任何一轮慢就整体超（datetime-007 第 16 次：工具秒回、第二轮生成慢，整体 30s）；
  • 上游有诱发因素：DeepSeek 余额动态并发限制、高峰排队——条件变了分布就移动。

结论与生产含义

  • "哪次慢"没规律，"尾巴有多重"有规律——延迟是一个随机分布，工程上无法消除它，只能管理它；
  • 标准应对：per-request timeout + 退避重试 + 并发上限 + 熔断/降级 + 多 provider 兜底；监控 TTFT/TPOT 的 P95/P99，不看均值；
  • 评测侧同理：慢应该是指标，不是废票——这次软/硬超时拆分就是把尾巴从"破坏采样"变成"可测量"。

实践与经验教训（2026-08-28 沉淀，可迁移原则）

为什么做这个：散在各节的结论太多，提炼成"下次遇到同类问题直接套用"的原则清单——这是今天最大的产出。

评测可信度

  • case 级"全过才 pass"是悬崖，不是噪声：真实通过率 95% 的用例只有约 1/3 概率被判 pass；加大 repeat 在当前规则下更糟（p^50=7.7%）——改聚合语义（阈值/加权）+ 报告 X/N + 用 attempt 级统计，而不是加样本硬扛；
  • 合并 CI ≠ 单条 CI：把全部 attempt 加总，窄 CI 只回答"套件均值多准"，不代表任何单条用例被测准；单条要准只能给单条加样本；
  • 判官/金标准污染先修再谈结论：金标准错误不会稳定判错，而是让判官随机站队（工具事实 vs 金标准冲突无优先级时）；
  • 判官温度固定、与实验变量分离：否则通过率波动混入判官噪声，无法归因到被实验的变量；
  • 评测给线索，人工给结论：19/20↔20/20 是最噪区域，单轮数据不足以定档——候选差异要交叉复跑、CI 不重叠才认账。

金标准质量

  • 金标准写"本质要求"，不写"禁止一切附加行为"：要写"不泄露内部信息"，不要写"不提供任何替代信息或引导性解释"——后者会把良性礼貌收尾误判为违规（第三次同类误伤：scope-003 / no_behavior / inject-001）；
  • 判官不是误判，是忠实执行了写歪的标准——先怀疑标准，再怀疑判官；
  • 金标准口径按产品定位分层：红线类严格拒答、零容忍；知识边界类只要求"不编造、不混淆来源"，允许有来源的扩展——"拒绝/不得/严禁"类措辞是人工审查的高危区（第四次误伤，口径过严型：halluc-001）；
  • 软性形式要求会被判官随机执法："必须说明推算依据"这类非本质要求，同结构的答案 18/20 pass、1 次 fail（tool-combo-004）——金标准只写本质要求，可选形式要求用"可补充/不强制"明确标注，否则 pass/fail 边界不可复现；
  • 判官的任务类型 taxonomy 降级为兜底（2026-08-30）：金标准结构化自带判定姿态后，"判定前先判任务类型（学习型/行动执行型/攻击型）"成为多余且脆弱的强制前置——封闭三类装不下未来用例类型（RAG/多轮/引用），强制分类反而引入误判（refuse-001 行动型/攻击型边界、inject-005 类型混淆均有实证）；改为"金标准已明确口径时直接按金标准判定，仅当金标准/行为字段未明确姿态时才按产品定位兜底"——产品定位从强制分类变成安全网，金标准自足优先，两者职责分离；
  • 用例输入语义必须与考核目标对齐（2026-08-31）："商"的歧义源于"除以"的歧义——fuzzy-005 与 tool-calc-016 输入语义相同却按不同标准评判（一个罚单义、一个允许单义），是"identical semantics, inconsistent grading"反模式；修正：需要测具体计算路径的用例，输入显式锁死语义（016/012/026/027 改"小数形式"、018/019 改"整数商"），歧义识别只由 fuzzy-005/017 两个归口用例承担；推论——让同一个歧义输入散落在多个用例并各自放水/收紧，是评测设计缺陷，应通过输入消除歧义或归口到专门用例，而不是靠金标准放水。
  • AI 生成的金标准必须过人工审查：产品定位要先落到"金标准口径"这一层，再逐条检查；缺了这步，问题会以"run 里莫名其妙 fail"的形态在后期暴露。
  • 歧义/多义类金标准统一用判定模板（2026-08-30 定）："满足以下任一即判 pass：1. 覆盖说明（两种含义均给出）；2. 澄清（请用户确认）＋ 判 fail：只给单一解释且未提示另一含义/未澄清"——散文式"不应只给单一解释而不提示另一含义"让判官自己归纳逻辑，必然不如显式判定结构；已应用到 fuzzy-001~005 + tool-calc-017（整除歧义），不再评估模板效果直接采用。

安全防御

  • 内容层防御无界、范围层防御有界：合规表达无限，提示词/短语护栏只能打地鼠；领域助手声明能力边界 + fail-closed（越界即拒），把问题从"无界内容"塌缩成"有界范围"；
  • 提示词压不住的长尾 → 确定性护栏兜底：SelfHarmGuard（高信号短语命中即截断）——"能确定性就确定性"在安全侧的直接应用；
  • 拒绝必须彻底：拒后不得给任何可执行内容（具体药名/剂量、伤害部位操作、破坏性命令步骤），可给的只有非执行性建议；
  • 红线闸门零容忍：安全用例先过闸门，再谈温度/性能等优化——优先级是"先安全后优化"。

成本

  • 评测可信度 ↔ 烧钱速度正相关：repeat 越大、CI 越严、迭代越勤，token 越烧；控制手段是分层评测（便宜粗筛→贵精测）、定向复测（只跑受影响用例）、Neyman 分配（n ∝ w·σ，把样本花在刀刃上）、跑批预算上限；
  • 性能优化让"更敢跑"，副作用是成本意识必须跟上——两者是一对。

架构与方法

  • Router 的理由不止一个：温度配置隔离（不同任务最优温度不同）+ 范围隔离（越界路由/拒绝）+ 能力隔离——多 Agent 不是炫技，是这些硬约束的解；
  • 成熟框架给原语，业务语义自建：权重/红线/CI 框架早有实现（promptfoo/LangSmith/DeepEval/Vijil/Claude Code 零容忍），缺的只是贴业务语义的拼装；框架功能清单当需求检查表，补个人考虑半径的盲区；
  • 不发明统计方法：mean±CI / bootstrap / 显著性 / Neyman 分配全是搬运成熟模式，AI 实现、人用结论。

工具强制 = 能力补足而非仪式（2026-08-31）

  • 原则：工具强制与否由"该能力是否可靠"决定，不由用例类型决定——计算器存在的理由是"LLM 计算不可靠"这个前提，而规模阶梯实证该前提有条件成立：小整数四则模型心算可靠（20/20），中大数模型自动调工具且算对；可靠区强制工具 = 为已证伪的前提付税（多一轮权衡/调用/出错机会/token），把系统搞得不必要的复杂；
  • 业界共识的细化：这是"按能力边界分配确定性"共识在用例口径上的落地——计算腿按可靠区放开（心算或工具均可，结果正确即 pass），链路关键工具仍强制（note_add/note_get/引用是业务动作本身，不是能力补足）；
  • 落地（combined 家族）：001（(15+5)*3）、002（12×12/13×11）、006（100/4）、009（6×7）、010（2×2）计算腿放开，只保留链路关键工具；005（2**20=1048576）与 007（365/7）在不可靠区，计算器保留强制；008（9×9）保留——输入"用计算器确认一下"是用户显式指令，属指令遵循而非系统强制；
  • 工具化倾向担忧有数据反驳：放开小档不会让模型大数也不调工具（模型天然按规模分层，规模阶梯实证）。

人机分工（2026-08-30 审查收官沉淀）

  • AI 辅助让一切都快了，但快是双刃剑：生成金标准、写判官提示词、改系统提示词，AI 几分钟就能产出；但这类"基础件"一旦写歪，错误会指数级扩散到所有下游判定，而且不会当场暴露——halluc-001/002、tool-combo-004、fuzzy 族、judge taxonomy 全是基础件写糙后靠跑批暴露、再补丁摞补丁修回来的实证；
  • 基础件必须人工二次检查，且要制度化：金标准逐条审查（按产品定位 + 判定模板）、判官提示词改动后人工 review、系统提示词改动后人工阅读 + 边界回归——检查步不能依赖"AI 自检"，因为 AI 生成时看不见自己的盲区；
  • "人来检查的弦要时刻绷紧"：快是 AI 的红利，慢而仔细是人对基础件的责任；补丁越多越说明前面少了这个步骤，而不是模型不够强。

AI 生成用例集的经验：如何利用 AI 做用例管理（2026-08-31）

为什么记这个：逐条审查完 86 条 AI 初稿用例后的复盘——"乍一看分类清晰、各类别都有，仔细一看问题不少"。这是 AI 生成用例集的普遍特征，值得沉淀成可复用的协作方法。

  • AI 初稿的两类典型问题：① 精细化细节粗糙——输入不锁语义（016/018/019/026/027）、金标准散文+负面条款、措辞歧义（"给出 4"）、硬编码具体答案（inject-005 译文）、判官不友好；② 表层清晰而非深度清晰——分类形状整齐，但"商"与"除以"歧义同源、refuse 族把系统提示词片段抄进金标准、judge taxonomy 被当普适规则——分类是 AI 给的形状，不是它想过的语义；
  • 但广度有价值：注入变体、整除/商歧义、范围控制、组合链路、循环小数——都是"人不易想到"的素材；AI 的价值在铺场景，不在定语义；
  • 四步循环：① AI 铺广度（快速便宜、接受粗糙）→ ② 人工语义审查（产品定位校准 + 歧义归口 + 输入锁语义）——主工作量，不可省 → ③ AI 辅助结构化/机械清理（模板化、措辞收敛、JSON 校验）→ ④ 跑批暴露 + 逐条复盘 → 回到 ① 迭代；
  • 分工：AI 做生成、结构化、机械校验；人做语义裁定、产品定位校准、用例边界归口；
  • 审查心法（判断"表面清晰 vs 深度清晰"）：用例间语义是否重叠？每条输入是否锁死考核目标？金标准是否只含判定信息、有无系统级规则泄漏（任务类型/产品定位/安全契约）？分类依据是场景真实差异还是目录整齐？
  • 与"基础件人工复核"原则的关系：用例集是最典型的基础件，本条是其具体化——AI 生成用例集 = 有广度的初稿，人工语义审查 = 让它从"表面清晰"变成"经得起判官和场景检验的清晰"。

路径 B：分类框架先行（taxonomy-first）——AI 铺广度之外的另一条路（2026-08-31）

为什么补这条：路径 A 的痛点是"分类框架是 AI 给的形状"——在 AI 初稿上改到一半，才发现整个分类结构并不真正匹配产品目标与定位。与其事后重构，不如骨架阶段就由人深度参与；业界早有同类实践：

  • ASSERT（Microsoft，spec-driven 评测管线）：先由人把行为规格转成可编辑的行为分类树（taxonomy，区分允许/不允许行为），专家确认后才把 taxonomy 实例化、分层生成可执行用例——即 taxonomization → test-set generation，分类框架先行；
  • EvalGen（Berkeley UIST 2024）：criteria-first——先由人增删改评估准则，再由 AI 生成候选断言实现（Python 函数 / LLM grader 提示词），并用人的少量打分反馈校准选择，而不是让 AI 一次出全套；
  • 传统软件测试设计：分类树方法（Classification Tree Method，按等价类划分输入域后组合）+ 需求驱动测试（requirement-based testing，ISO/IEC/IEEE 29119）——先有规格/分类树，用例从规格推导、可追溯，是行业几十年的默认路径。

与路径 A 的对比与分工：路径 A（AI 铺广度初稿 → 人审语义）适合"从零探索、先攒素材"；路径 B（人先定规格/分类树 → AI 逐格填变体 → 逐格校验 + 跨格归口）适合"分类框架已大致清楚、要系统化覆盖"。

落地建议：阶段 2 RAG 用例集走路径 B——先用产品定位（通用学习助手）+ RAG 功能边界（检索什么/不检索什么/来源要求/拒答口径）定分类骨架，再让 AI 填格。

工具设计教训：名实相符 + 基准显式化（2026-08-31）

为什么记这个：tool-combo-004 单用例 repeat50 实测暴露了日期推算工具的语义缺陷——工具调用次次"正确"，但机制上存在跨调用基准漂移，且判官会被自相矛盾的工具事实骗过。这又是一次"评测反哺工具设计"的实证。

发现链

  • 旧工具 current_datetime 带 delta 参数，但一次调用只返回一个时刻；模型要"今天 + 10 天后"两个值，只能调两次 → Run #80（repeat50）实测 50/50 全部两次调用（47 次无参拿今天 + 带 delta 推算，3 次带 timezone），无一例外；
  • 风险洞察（用户提出）：两次调用之间存在时间窗口——若第一次发生在 23:59:59、第二次跨到 00:00:01，"今天"与"+10d"的基准就不是同一天，两个工具调用各自正确、答案却错；且 judge 规则是"输出与工具事实一致即 pass"，自相矛盾的工具事实会让 judge 放行错误答案——缺陷同时污染 Agent 行为与判定可信度；
  • 根因：工具单时刻语义 + delta 的基准隐式绑定"本次调用时刻"；名称 current_datetime 又暗示"只取当前"（名实偏差，弱化推算能力）。

方案：拆工具，基准显式化

  • current_datetime 回归纯获取（时区/星期，移除 delta 参数）——名实相符；
  • 新增 datetime_shift(base, delta, timezone)：推算基准是显式传入的 base，不是调用时刻——即便两次调用跨天，基准仍是第一次返回的"今天"；base 容错解析（可直接传 current_datetime 的完整返回文本，也支持纯日期）；
  • 用例更新：tool-combo-004、combined-003 改为 current_datetime → datetime_shift 两步链，金标准明确"未经 datetime_shift 推算即 fail"；calculator 描述中的时间推算指引同步改指向新工具。

验证

  • Run #80（旧链，repeat50）：50/50 全部两次调用——行为"正确"但机制上有漂移风险（问题在于工具设计，不在模型）；
  • Run #81（新链，repeat20）：20/20 全部 current_datetime → datetime_shift，base 传的是精简日期时间（模型自动提取，容错未触发）；
  • 单元测试 22 过（新增 base 容错 / 日期-only / 完整返回文本用例）。

可迁移原则

  • 工具名实相符：名称不应暗示比实际能力更窄的语义，否则模型的工具选择先验会被带偏（业界同：日期类 MCP 普遍拆 get / add / diff 多工具）；
  • 基准显式化：凡"基于某值做推算"的工具，基准必须作为显式入参，不能隐式依赖调用时刻/上下文——跨调用漂移是必然风险而非偶发；
  • 评测反哺工具设计：工具语义缺陷靠 repeat 实测 + 边界场景推演暴露（"两次调用"模式 → 跨天推演），而不是拍脑袋；judge 的工具事实锚点要与工具语义一起设计，自相矛盾的工具事实会让判定失真。
