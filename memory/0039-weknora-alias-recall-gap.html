0039 · WeKnora 缺陷实录：去重召回只看标题，别名那一侧没接上

一分钟摘要：WeKnora 判"新抽出的条目是不是已有页面"时，召回只看已有页的 title——提示词要求 name／alias 四向比对、官方文档也写"名称与别名双向比对"、连被它取代的旧实现都两侧带别名，但迁到 pg_trgm 之后页侧别名这一半丢了。后果是"只靠别名相连"的同义（跨语言名、缩写↔全称、译名）永远进不了候选，只能长出孪生页。属召回缺口（该合没合），不会错合并。

第一部分 · 问题、证据与修复建议

1. 问题（一句话）

去重的候选召回只查已有页的 title，不查 aliases。于是"新条目／新条目的别名"与"已有页的别名"之间的同义关系在召回阶段不可见——模型连这对候选都看不到，后面的判同规则再准也没用。

3. 证据 B：真实数据直接证伪（✅ 可复现）

在跑完 P6＋P7 的真实库里，concept/rag 这一页的别名里一字不差地写着这串英文；而 live 谓词一行都召不回：

-- 1) 别名里确实有
SELECT slug, title, aliases::text,
       round(similarity(lower(title),'retrieval-augmented generation')::numeric,3) AS sim_title
FROM wiki_pages
WHERE knowledge_base_id='7c601025-5bc2-42b9-9cee-6b07c49cbadd' AND slug='concept/rag';
    slug     |    title     |                  aliases                  | sim_title
-------------+--------------+-------------------------------------------+-----------
 concept/rag | 检索增强生成 | ["RAG", "Retrieval-Augmented Generation"] |     0.000

-- 2) live 谓词（等价于 FindSimilarPages 的 WHERE）
SELECT count(*) FROM wiki_pages
WHERE knowledge_base_id='7c601025-5bc2-42b9-9cee-6b07c49cbadd'
  AND lower(title) % 'retrieval-augmented generation';
 count
-------
     0
结论：这条别名在召回阶段"等于不存在"。阈值：pg_trgm.similarity_threshold 实测 0.3（Postgres 默认值，代码里没改过；仓库注释写"below 0.1 are dropped"与实测不符）。
另有一条数据卫生问题：162 行里 29 行的 aliases 是 JSON null 而不是数组（jsonb_typeof(aliases::jsonb) = null）——将来若按别名召回，必须先规范化。

4. 证据 C：端到端探针（✅ 跑了两次，但被"命名一致"掩盖）

往该库投两篇小文（Z1 带 (RAG)；Z2 只写全称、绝不出现 RAG），两次都没有长出孪生页——新内容全并进了 concept/rag：source_refs 1→2→3、version 1→3。

原因（这本身是个更有意思的发现）：该库输出语言是中文，模型把英文文档里的概念也命名成"检索增强生成" ⇒ 与旧页标题完全相同，于是走精确身份层就地更新，压根没轮到别名出场。⇒ 缺口的暴露面被"命名一致 ＋ 精确身份层"掩盖了；本例因此只能证明代码问题，不能作为现象级证据。

5. 影响面与定性（🤔）

  • 定性：召回缺口 / 功能回退（recall-only）——症状是"该合没合"，产出孪生页（同一事物两页）；不会错合并（判同那一步有 per-item 校验兜底）。
  • 触发条件（三条同时满足才会咬人）：① 新条目的名字与旧页标题既不相同、字面也不相似（trigram < 0.3）；② 旧页的别名与新条目（名或别名）相同/相近；③ 新条目自己的 slug 不等于旧页 slug（否则 slug 同名会就地更新，见下）。
  • 典型受害场景：跨语言名（中文页 vs 英文条目）、缩写↔全称、译名——正是提示词里那几条"正确合并"的示例。
  • 为什么现在没炸：模型的命名通常稳定（同一语言环境下同一事物会得到同一个名字），而"名字相同"由精确身份层兜住；另外 slug 同名（concept/rag 这种情况）也会就地更新——这两条都在掩盖缺口。

6. 修复建议（三选一）

  • A（推荐）扩召回谓词：把 WHERE lower(title) % :q 扩成"标题或任一等价别名命中"，例如 
    WHERE lower(title) % :q
   OR EXISTS (SELECT 1 FROM jsonb_array_elements_text(
                CASE WHEN jsonb_typeof(aliases::jsonb)='array' THEN aliases::jsonb ELSE '[]'::jsonb END) a
              WHERE lower(a) % :q)
    并给别名侧补一个可索引的表达（现在只有 lower(title) 的 GIN trgm 索引；直接 OR 会退化成顺序扫）：推荐维护一个 alias_text 生成列（lower ＋ 空格拼接）＋ gin_trgm_ops，或单开 wiki_page_aliases(page_id, alias) 表加索引。
  • B（改动最小）：保留 trigram 主路，另外用现成的 List query 通道（它已经支持 aliases::text ILIKE）按新条目的 name／alias 精确回捞一次，把命中的页补进 candidatePages 与 itemCandidates。代价是全表 ILIKE，需限流或加前缀索引。
  • C（最省）：不改实现，改文档与提示词——把"别名对别名"的承诺收回来。代价是明确放弃这类召回能力。

无论走哪条，都建议补 live 路径的测试（现在只有那个已绕开的老函数有测试），最小用例＝"页 title=中文、页 alias=英文全称；新条目 name=英文全称" ⇒ 应命中候选。

8. 可直接提的 issue 草稿（英文）

Title: Wiki dedup candidate recall ignores page aliases (only `lower(title)` is matched)

## Summary
The wiki ingest dedup pre-filter (`FindSimilarPages` -> `idx_wiki_pages_title_trgm`)
matches new items against existing pages by **title only**. Page `aliases` are
selected into the result payload (and are used by the LLM later), but they are
never used as a search key. So a merge is only ever *offered* to the model when
the item's name/aliases are trigram-similar to the existing page's **title**.

This contradicts:
* `WikiDeduplicationPrompt` — "Compare name-to-name, name-to-alias, alias-to-name, and alias-to-alias."
* `website-docs/03-features/14-wiki.md` — "名称与别名双向比对（名称对别名、别名对别名）".
* the implementation this path replaced: `selectDedupCandidatePages` scored
  `[Title] + Aliases` on BOTH sides (Go-side bigram Jaccard).

## Impact (recall only)
Same-entity pairs whose surfaces only meet through an alias (translations,
acronyms, full forms) can never become candidates, so they keep growing as
duplicate ("twin") pages. No wrong merges are introduced — the per-item guard
`dedupMergeRejectReason` still rejects cross-item targets.

## Evidence
Real KB (86 pages) contains:
  slug=concept/rag  title=检索增强生成  aliases=["RAG","Retrieval-Augmented Generation"]
but:
  SELECT count(*) FROM wiki_pages
   WHERE lower(title) % 'retrieval-augmented generation';   -- 0
  similarity(lower('检索增强生成'), 'retrieval-augmented generation') = 0.000
(pg_trgm.similarity_threshold = 0.3, the PostgreSQL default; the code comment in
repository/wiki_page.go:1046-1048 says "below 0.1", which does not match.)

## Repro
1. Have a page whose title differs from a new document's surface, with the bridge
   stored only in the page's `aliases` (e.g. title="检索增强生成",
   aliases=["RAG","Retrieval-Augmented Generation"]).
2. Ingest a document that only ever says "Retrieval-Augmented Generation".
3. The dedup pre-filter returns no candidate for that page; if the extracted item's
   deterministic slug also differs, a duplicate page is created instead of merging.

## Suggested fix
Extend the predicate to cover aliases, e.g.
  WHERE lower(title) % :q
     OR EXISTS (SELECT 1 FROM jsonb_array_elements_text(
                  CASE WHEN jsonb_typeof(aliases::jsonb)='array' THEN aliases::jsonb ELSE '[]'::jsonb END) a
                WHERE lower(a) % :q)
and back it with an index (a generated `alias_text` column with `gin_trgm_ops`, or a
`wiki_page_aliases` table). Also add a test for the live path — today only the
retired in-Go helper is covered, and it is exercised by tests but no longer called
by production code.

## Notes
* `aliases` is JSON `null` (not an array) on 29 of 162 rows in our KB — normalize
  before querying.
* Our end-to-end probe did not reproduce a twin page, because the KB's output
  language is Chinese and the model re-named the English item to the existing
  Chinese title, which is caught by the exact-identity path
  (`FindPagesByNormalizedTitles`). The bug is real at the code level; whether it
  bites depends on naming stability.

8.2 方法学教训（我这两次探针为什么"没炸"）

  • confound 1：输出语言。库的语言解析结果是中文，模型把英文文档里的概念也命名成中文 ⇒ 与旧页标题完全相同 ⇒ 走精确身份层。想验别名通道，得让两侧命名不可比（跨语言 KB，或人为构造"标题与条目名都不同、只有别名相同"的语料）。
  • confound 2：slug 同名。当新条目 slug 恰好等于旧页 slug（concept/rag 这种情况），reduce 会把它当"同一页的更新"，与去重无关——代码里也明确把"自身 slug"排除出候选（wiki_ingest.go:2524-2528："an identically-slugged existing page is a re-ingest/update, not a merge target"）。
  • confound 3：脚本的自动判读不可靠。初版脚本把 slug 里含 retrieval 的新页当成"RAG 孪生页"，其实那是"检索失败模式／检索质量"两个不同概念——已改成只报事实、结论人工下。又是一次"判据必须覆盖要断言的边界"。
