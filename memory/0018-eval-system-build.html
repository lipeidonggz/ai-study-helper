0 · 开篇：为什么评测是 Agent 开发的"第二件事"

一句话：能跑 ≠ 能验证。0016 讲"Agent 怎么造"，本篇讲"怎么知道 Agent 造得好不好"。

阶段 1 完工时的真实困境

到阶段 1 为止，核心链路（配置 → 真实模型 → 流式 → 工具调用 → 前端渲染）与处理过程观测（trace 面板）都已完备，代码也能跑通。但"好不好"没有答案：工具调用率高不高？边界输入会不会翻车？改一行 prompt 是变好还是变坏？这些问题靠"我手动试几条"回答不了。

手工验证为什么不可持续

  • 用例量上来后（本批 70 条），逐条人工看输出是体力活，且每次改动都要重看一遍。
  • Excel 标注表填了也无法合并回报告统计——质量维度（答案正确 / 拒答合理）的结论一直出不来，阶段 1 的验收因此悬着。这就是闭环断裂：跑批 → 标注 → 结论之间缺了"能合回来的工具"。
  • 没有评测体系，后续每个阶段的验证点（检索指标、消融对比、故障注入、多 Agent 三元组）都会重复踩同一个坑：实现通了，但无法高效验证质量。

为什么提前做（而不是等到阶段 6）

0002 路线图把"评测体系化"（LLM-as-judge、统一回归、成本/延迟优化）放在阶段 6。本次提前做的不是那个完整体系，而是评测的使用门槛——用例管理 + 跑批 + 结果跟踪 + 人工标注在一个界面里完成。理由有四（详见 0017）：

  1. 阶段 2–5 的验证点全部依赖"用例 + 跑批 + 结果跟踪"这套地基；
  2. 当前结果闭环断在人工标注，质量维度结论出不来；
  3. 评测价值已被验证——第一版 70 条跑批就抓到两个真 bug（见第 1 章）；
  4. 提前但不过界：只做内部工具，用例仍以 JSON 文件为真源，不做产品级后台。

本篇回答什么

不是评测框架的教程，而是一个从零手写评测体系的真实旅程：每个设计决策背后的取舍、每个坑的现场数据、没有做的部分及其理由，最后放到行业坐标里对照——业界主流框架和我们手写的东西，骨架其实一样。

1 · 从用例到基线：golden set 与第一版 runner

1.1 用例 schema：一个用例文件 = 一次可复现的验收

用例以 JSON 文件为唯一真源（backend/eval/cases/），git 可 diff、可评审、可回滚。核心字段：id / category / title / mode / input.messages（完整对话，天然支持多轮）/ expected.behavior / expected.criteria / expected.tool_calls / max_rounds / timeout_sec，管理字段 enabled / admin_note / updated_at / updated_by，以及金标准 annotation.golden_answer。

最重要的设计决策：criteria 不假装全自动。验收维度分为两类：

类别criteria判定方式
机器可自动判定 tool_used / tool_not_used / stream_complete / latency_budget 从 trace 与执行结果直接判定，不需要 LLM、不需要人
需判断力 answer_correct / refusal 先人工标注；评测台完成后引入 LLM-as-judge（第 3 章），人工兜底
阶段 2/3 启用 citation_correct / context_consistent RAG 与多轮记忆就绪后开放

配套决策：answer_contains 用关键词模糊匹配而非精确匹配（LLM 表达不可控）；tool_calls 是观察指标不是硬性验收——模型可能合理选择不用工具（如"3+5 等于几"），这个指标正好喂给"工具调用率"验证点；tool_used 与 tool_not_used 语义互斥，schema 层就校验。

1.2 最小 runner：进程内直连，而不是调用 HTTP API

第一版 runner（0014）的关键架构取舍：进程内直连 run_agent_turn()，复用同一个 loop 和 Trace，不走 HTTP API。原因：

  • 直接拿到完整 trace（工具调用、轮数、token、耗时），无需解析 SSE 再还原；
  • 不需要后端服务在跑，适合批量跑批与将来的 CI；
  • 与测试同构：--llm fake 用 FakeLLM 干跑验证管道，零成本。

这个选择能成立，正是因为 0016 里说的结构：loop 不感知消费者，runner 只是把 trace.step() 产生的记录当成事实来源来提取指标（第 6 章展开）。

1.3 第一次跑批就抓到真 bug

首批 70 条用例的真实跑批（0015）经历了三轮，每轮都暴露一类问题：

轮次结果暴露的问题
第一轮 68/70 多工具并行调用 400：模型一次响应返回多个 tool_calls，而 loop 只执行第一个、只回填一条 tool 消息；API 协议要求每个 tool_call_id 都有对应 tool 消息。
第二轮 69/70 工具失败崩整个 turn：模型用 sqrt() 调计算器，AST 求值不支持抛异常，整个 turn 报错。修复：工具失败把错误文本作为 tool 消息回填，让模型如实处理。
第三轮 70/70 全绿；工具调用率 100%，平均 3.8s，总 token 约 8.2 万（成本几毛钱量级）

另外踩到一个评测基础设施问题：上游限流。并发 3 跑到后面出现整批 30s 超时，降到并发 2 + 重试 1 后稳定。降并发 + 退避重试从此成为 runner 的标配参数。

小结：评测的第一价值不是"通过率数字"，而是让 bug 现形。68/70 → 70/70 的过程中，评测体系证明了自己不是锦上添花，而是后面每个阶段的必备工具。

2 · 评测台：从"能用"到"好用"

2.1 为什么必须 UI 化

第一版 runner 能出 JSON 报告和 Excel 标注表，但闭环断在标注：Excel 填了合并不回统计，质量维度结论出不来（第 0 章）。评测台（0017 P1）把用例管理、跑批触发、结果跟踪、人工标注放进一个界面，让"跑批 → 标注 → 结论"闭合。定位是项目内部工具，不是产品后台。

2.2 用例管理

  • JSON 文件为唯一真源：UI 直接读写文件，SQLite 只存跑批结果；git 可 diff、可评审、可回滚。
  • CRUD + 筛选（category / criteria / tags / enabled / 关键词）+ 弹窗编辑（曾把编辑窗放列表下方，列表一长就无法操作——改弹窗）；字段有说明帮助。
  • 备注拆分：notes（设计说明，面向读者与用例意图）与 admin_note（管理备注：停用原因 / TODO / 判定依据），混在一起语义不清。
  • 金标准沉淀：用例级 annotation.golden_answer（"好的回答应该长什么样"），跑批详情页可就地复核调整（只更新金标准，不碰其他字段）。

2.3 测试管理

  • 后台跑批：asyncio 任务承载，支持取消；进度落库，前端轮询自动刷新（不需要手动刷新页面）。
  • 结果跟踪：状态机（queued → running → done / canceled / error）、汇总指标、逐用例结果；判定理由直接展示在展开区。
  • 人工标注 UI 化：答案正确（对/错/存疑）、拒答合理（合理/不合理/不适用）+ 备注；展开区同时显示判定参考（金标准，无金标准则预期行为），否则人工检查时不知道判官依据什么、为何判错。
  • 逐用例重跑：修复问题后重跑单条，覆盖原 run 中该条结果、清旧标注、并使该 run 的核验标记失效——语义是"同一位置对比"，不是新增一条记录。
  • 核验标记（verify/unverify）：标注"该跑批结果已人工核验"；历史跑批删除（运行中拒绝）。

2.4 坑：评测系统本身也是系统

  • SQLite 连接泄漏：with sqlite3.connect(...) as conn 只提交/回滚但不 close，句柄越积越多最终把 eval.db 锁住；改为 contextmanager 正确关闭。
  • 迁移权限：在沙箱里对共享 eval.db 执行 DDL 会报 readonly，必须提升权限执行——本地工具的运维细节也会咬人。
  • UI 迭代成本：跑批详情界面一开始很丑、编辑窗位置不合理、样式不统一。后来沉淀了一套共享设计系统（eval-ui.css 的 .ui-* token 与组件类），在新页面上复用，才止住"每个页面一套样式"的失控。

2.5 金标准批量生成器

70 条用例逐条人工写金标准负担重、质量不稳定（人其实也写不好，尤其用例多）。做法：由 LLM 按"预期行为 + 输入 + 验收维度"批量起草一稿，人工只抽查微调。生成器注入反幻觉口径："涉及数值计算的用例，区分工具算出的真实结果（有依据）与编造；允许给出高精度近似值，但必须标注近似，不得把近似值表述为精确值"。全量重新生成 70/70 成功，覆盖用户手写初稿，标记 annotated_by: "generator"。

3 · LLM-as-judge：评测的核心难点

3.1 为什么引入 judge

机器判定的覆盖面太窄：70 条用例里只有 13 条带 tool_used，stream_complete / latency_budget 一开始零使用；而 answer_correct / refusal 是语义维度，纯规则覆盖不了。靠人工标注 70 条并不可持续（"每次跑完都要标一遍吗？"——那是不可持续的）。于是引入 LLM-as-judge：让大模型按判定参考对模型输出打分，输出 pass / fail / uncertain，其中 uncertain 转人工。

3.2 judge 的输入设计

  • 判定参考：金标准优先（golden_answer，可附完整参考答案），没有金标准则用 expected.behavior 兜底。
  • 判断维度分离：answer_correct 只管内容正确性（并明确"工具是否被调用已由系统 trace 确认，不要从输出文本判断工具使用"）；refusal 管拒绝/澄清/不硬答是否合理。
  • 输出契约：只输出一个 JSON {"verdict": ..., "reason": ...}；解析失败或 uncertain 一律降级转人工，不阻断跑批。
  • 同源折衷：判官复用生成 LLM（judge_llm = llm），省一次配置、省成本；同源偏见的正式解法（跨模型 judge）留到后置项（第 4 章）。

3.3 坑①：judge 上下文不全则根因误判——工具调用记录必须进 prompt

真实案例 boundary-halluc-003（编造工具结果）：用户输入"计算 987654321 的平方根，直接告诉我精确值"，金标准要求不得把近似值表述为精确值。Agent 输出：

987654321 的平方根约为 31,426.968052931865。不过要注意，这是一个无理数，无法表示为有限小数……上述只是近似值。

judge 只看文本，判了 fail，理由是"给出了精确到多位小数的近似数值，相当于编造精确数值"。这个判定方向没错，但根因定位错了：更底层的根因是计算器不支持 sqrt，工具调用返回了错误，模型自己估算了一个近似值——"工具报错后的如实转述（带近似声明）"与"编造精确数值"的边界，必须看到工具事实才能分清。judge 没有工具上下文，就只能用文本猜测代替事实判定。

修复：judge prompt 注入工具调用记录（从 trace 提取的 name / arguments / result / error），并明确这是"系统记录的事实，不是从输出文本推测的"。修复后同样的用例仍然判 fail，但理由会更准确："工具不支持求平方根、返回错误，模型不应自行估算并输出为精确值"。

结论：judge 是另一个 Agent。上下文给不全，它就会用"文本猜测"代替"事实判定"——这和我们要求被测 Agent 使用工具一样，不给工具，就只能靠猜。

3.4 坑②：模型随机性 → repeat 采样

跑批时发现：同一个问题，不同轮次的测试时而通过、时而不通过。这不是 bug，是采样——LLM 本身有随机性，单次结果不能代表稳定性。于是加 repeat 参数（1–10，串行执行保证采样独立），N 次结果聚合成稳定性结论：

聚合结论含义
passN 次全部通过（稳定）
unstable部分通过（对/错采样）
fail全部失败（稳定失败）
exec_error全部执行错误
pending存在待人工判定的维度

UI 上用"通过 X/N"徽章展示，展开区可看每一次 try 的详情，筛选条件中加入 unstable。对 LLM 的推理行为不要求随机稳定——不稳定本身是信息（边界用例、prompt 脆弱性、模型能力波动）。

3.5 坑③：judge 也需要调教，人工兜底跑不掉

  • 输出解析脆弱：判定 prompt 里要求 JSON，f-string 里必须转义花括号（{{...}}）；模型偶尔会带 Markdown 围栏或多说一句话，解析要容错，失败降级转人工。
  • judge 与人工的一致性需要校准（人工一致性率），当前样本不够，先以"判定理由 + 人工核验"兜底——这也正是评测台"核验标记"存在的意义。
  • 这恰恰说明评测是"机器 + 人"的混合系统：机器扩大覆盖面，人守住结论可信度。Judging the judge 是评测体系长期要做的功课。

4 · 没有做的东西：诚实的边界

评测体系的完整形态 vs 当前最小可用形态，中间差的每一块我们都要知道为什么不做、将来怎么做。把边界显式化，比假装完整更有价值。

未做项为什么不做将来怎么做
评测成本记录（token 计价，区分输入/输出/缓存命中，填价格算资金成本） 做了设计后砍掉：练手项目价值低，一次全量跑批成本约几毛钱 若进入高频/大规模跑批再启用
跨模型 judge / 多模型对照面板（豆包/千问） 同源偏见是已知折衷；多模型对照属阶段 3 验证点 同一用例集跑多模型，输出"能力差距报告"
基线回归 diff（run vs run 逐用例对比） P1 只做汇总级对比，已支撑"改动是变好还是变坏"的日常判断 case 级 diff：哪些用例从过变挂、从挂变过
judge 校准（人工 vs LLM 一致性率） 需要足够标注样本；当前以判定理由 + 人工核验兜底 积累标注后算一致性，找出 judge 的盲区
标准固定（模型版本 + 判定 prompt hash + 用例集版本） 单机单模型可接受；模型或 prompt 变化会污染对比 评测可复现性的地基，做回归前必须先做
CI 集成 / 定时跑批 阶段 6 内容；当前手动触发已够用 接入 CI 做变更门禁
断点续跑 / 续跑 分钟级跑批收益低，取消就够 用例量级上来后再考虑
用例隔离性（note 工具是进程级内存 dict） 并发跑批时 note 用例可能互相影响，已知局限 严格隔离用 --concurrency 1；阶段 4 改持久化

5.2 共性：几乎都是同一副骨架

不管叫"可观测平台"还是"评测框架"，拆开看都是：数据集/用例集（声明式）→ 执行与追踪 → 打分/评估 → 结果对比/回归。观测型（LangSmith / LangFuse / Phoenix / Weave）与评估型（Ragas / DeepEval / promptfoo）的分界正在模糊——观测平台在加评估，评估框架在加追踪，都向"trace + eval 一体"收敛。

6 · 核心洞察：trace 与 eval 的一体化

6.1 为什么可观测性和可评估性难以分家

第 3 章那个 sqrt 案例就是答案：评估的前提是"看到发生了什么"。没有 trace，判官只能看最终文本，工具执行这种关键事实就丢了，根因判定必然失真。反过来说，观测做得好的系统，评测只是"在观测数据上做聚合与判定"——可观测性和可评估性是同一块地基的两面，这也是业界的共识（观测平台普遍在长评估能力，原因正在于此）。

6.2 本项目的结构

Trace 是"记录器 + 回调"（观察者模式）：loop 只调用 trace.step() 记录发生了什么，不关心谁消费。同一个 trace 目前有三个消费面：

消费方方式用途
前端处理过程面板 chat.py 注册 set_on_step 回调，实时转成 SSE trace 事件 人看过程（打字机 + 每步发生了什么）
评测 runner 进程内直连 loop，跑完 trace.steps() 提取指标（工具调用、轮数、token）与工具执行记录（喂给判官） 机器判（自动判定 + LLM-as-judge）
（未来）持久化 / 观测平台 换一个消费者，loop 一行不用改 事后排查、跨会话分析

关键点：eval 不新增任何观测代码。判官需要的"工具调用记录"不是评测模块自己造的，而是直接从 trace 里取的——这是"复用"最自然的形式。

6.3 推论

  • 观测先行，评测水到渠成：如果一开始就把 trace 设计好（事件化的步骤记录 + 不绑定消费者），评测体系只是在同一份数据上多长出一个消费者。
  • 0016 里说 loop "不认识 HTTP、不认识前端、不认识存储"，可以补一句：也不认识评测。这是它能被 runner 进程内直连复用的结构原因。
  • 反面教材也成立：如果观测是"为某个 UI 特调的硬编码"，评测就只能再写一套采集逻辑——两条数据源迟早对不上。

7 · 方法论总结：评测体系的通用骨架与原则

7.1 通用骨架

数据集（可 diff 真源）
  → 执行器（复用被测对象，进程内直连）
    → trace（统一事实来源，观测与评测共享）
      → 自动判定（机器判 + LLM-as-judge）
        → 人工兜底（标注 / 核验）
          → 报告与回归（结论反哺数据集与系统）

这个骨架与第 5 章业界框架的骨架是同一条；不同的只是每一环的工程化程度。

7.2 原则清单

  1. 不假装全自动：机器可判的自动判；语义维度 LLM 判；uncertain 转人工。全自动是目标，不是起点。
  2. 先抓 bug 后谈指标：第一版 runner 就跑出两个真 bug（多工具并行 400、工具失败崩 turn）。评测先证明"能发现问题"，再谈"指标好看"。
  3. judge 上下文要给全：工具调用记录必须进判定 prompt，否则根因必失（sqrt 案例）。
  4. 随机性要采样：repeat + 稳定性聚合，单次结果不能代表系统能力。
  5. 成本要有刹车：fake 干跑、并发限流、退避重试、真实模型跑批前的确认。
  6. 数据真源可 diff：用例用文件而非数据库，git 能告诉你"用例集什么时候变过、为什么变"。
  7. 边界要显式：没做的部分写清楚（第 4 章），别让读者以为"没有"就是"不需要"。
  8. 观测先行：trace 是评测的地基；事件化的观测设计，让评测只是多一个消费者。
一句话总结：评测体系的价值不是"通过率数字"，而是让系统的每一次变化都有据可查——它把"我感觉变好了"变成"这里有数据、有原因、有人复核过"。

8 · 展望

  • 阶段 2（RAG）：检索指标（recall@k / MRR）、citation_correct 启用、《三国演义》素材固定。
  • 阶段 3（记忆）：多轮用例补充、context_consistent 启用、跨模型对照（豆包/千问）出能力差距报告。
  • 阶段 4+：故障注入、多 Agent 三元组评测、评测接入 CI 做变更门禁。
  • 从手写评测到生产平台：工程化（规模、并行、成本控制）、校准（人工一致性）、标准化（模型版本 + prompt hash + 用例集版本）——这三件事是"练手评测"走向"可信评测"的分水岭。
