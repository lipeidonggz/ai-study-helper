记录 ① · 两家各约束了哪一端 待复核

记录 2026-09-22 17:07 · 由沛东的观察引出（"我们确定谓词列表，GraphRAG 给定了实体类型"）

事实（仓库 packages/graphrag/graphrag/prompts/index/extract_graph.py）：抽实体时字段是 entity_name / entity_type: One of the following types: [{entity_types}] / entity_description；抽关系时字段是 source_entity / target_entity / relationship_description（自由文本）/ relationship_strength（数值）——边没有受控谓词表。默认 DEFAULT_ENTITY_TYPES = ["organization", "person", "geo", "event"]（config 里 entity_types 是可调旋钮）。

事实（同类核对）：实体类型基本只活在抽取那一步——社区报告提示词的示例输入里，给 LLM 的实体表只有 human_readable_id,title,description（没有 type 列）；local_search 的配置只有 top_k_entities / top_k_relationships / text_unit_prop / community_prop，没有"按类型过滤"。

结论：两家正好是镜像——我们约束边（38 条受控谓词）、放开点（概念无类型）；它约束点（4 个通用类）、放开边（自由文本 + 强度）。

代价对照：我们约束边的代价＝归类磨损（acts_on 收容桶 A5 44 条混 apply/describe/automates、is/is_a 混用、S5 串味错案、方向极性反了）；它放开边的代价＝边不可枚举、不可按类型查（问不了"库里所有 blocks 的关系"）。我们放开点的代价＝概念 399 起、无类型、碎片化（"防护手段"碎成 52 片）。它约束点买到的是抽取稳定 + 跨领域可移植（换 4 个类型词即可）。

为什么各自这么选（用目标反推）：它要的是材料（描述 + 社区报告）喂 LLM 写综述，边的可枚举性对它无用，自由文本信息量更大；我们要的是可过滤、可枚举的检索结构，所以边必须受控。一句话：它约束的那端是"抽取先验"，我们约束的那端是"查询维度"。

候选（未动手）：受控谓词 + 自由描述可以并存——我们已有 predicate（受控归一）与 predicate_surface（原文表面形式）并存；可考虑补一条"关系解释"（对应 relationship_description）与"权重"（对应 relationship_strength，用途与我们已登记的 object_surface 一致：审计 + 弱排序）。属编译层 schema ＋ 基础件 → 先方案后实现 ＋ 人工复核。

记录 ② · 复杂度不是"多步 vs 一步"，是"要的东西多不多" 待复核

记录 2026-09-22 17:07 · 由沛东的观察引出（"我们拆了很多步骤，它一个提示词搞定"）

先把它的说法修正一半：它的抽取确实是一个提示词同时出实体与关系，但整条索引链不止一步——官方 docs/index/methods 列的是：实体抽取 → 关系抽取（同一次）→ 实体描述归并（每个实体一次 LLM 调用） → 关系描述归并（每个关系一次） → claim 抽取（可选）→ 社区报告生成（每个社区一次）；且官方说图抽取约占索引成本 75%。所以它的复杂度是搬到了后面（按记录、按社区铺开，随规模放大）。

真正的差别：我们那条链上几乎每个环节都在给一条能力或红线付费，而那些东西它全都不需要——体检/S4.5 指代消解/S5 端点规范化与组图/S6 归并/S7 reify/S8 引文锚定，对应的分别是"可对账 / 可点名 / 可回锚 / 可过滤 / 可枚举 / 遗漏透明"。它没有受控谓词（省掉谓词清洗与归一）、没有方向极性角色的显式建模（省掉校验）、没有逐字证据要求（省掉锚定与护栏）、没有全量对账（省掉台账）；实体身份靠 title 字符串相等这一招。

它的代价：漏抽不可度量——没有体检、没有"每条 claim 必须落在建边 / 丢弃 / 待定三者之一"的口径，所以它连"这篇有多少内容没进图"这个数都不存在（我们当年是这个数炸出来的：旧形态 42–45% 的 claim 无声无息没建边）。

判据（比步数重要）：每个环节背后有没有一条产品要求；把"枚举 / 跨源连接 / 关系查询 / 遗漏透明"这四条里砍掉任何一条，对应环节就该消失——这正是三档原语对比实验（已立项）要验的东西。诚实注：我们链里相当一部分是踩坑长出来的（谓词表来自"结构判同指失败"、S5 大改来自"为何会有孤立实体"、S4.5 来自 O2 第一次泛化撞线），既是价值也是成本。

记录 ③ · 窗口大小与 gleaning（本轮最"可执行"的一条） 待复核

记录 2026-09-22 17:07 · 由沛东读到"精度–chunkSize 权衡、推荐 600 token"引出

它那边的原文（修正版）：600 不是"推荐输入"，是语料切片尺寸（播客 1669 × 600-token 块、块间 100 token 重叠；新闻 3197 × 600）。真正的对比是——"the LLM tends to extract few entities from chunks of larger size. For example, in a sample dataset (HotPotQA), GPT-4 extracted almost twice as many entity references when the chunk size was 600 tokens than when it was 2400."应对不是"必须 600"，而是 self-reflection / gleaning：把已抽实体回喂，用 logit bias=100 强制 yes/no 判断"有没有漏"，若答漏则用"MANY entities were missed in the last extraction"催它再抽一轮，最多迭代 N 次（Fig.3 显示迭代能把 2400 那档补上来）。结论：块小抽得全但调用多；用补抽让大块不掉质量。

我们这边的实测数字（代码）：Pass 1 窗口＝_window_text(clean_t, 5000)，而函数签名是 max_chars（字符，不是 token）→ A5 这类英文语料 ≈ 1000–1300 token（比它 600 大、比 2400 小）；中文语料 ≈ 3300–5000 token（已超过它那个"抽得少"的 2400 档）。检索块＝MAX_TOKENS = 450（实际 320–450），比它的 600 还小；内容单元上限＝12k token。

顺势发现的隐患：我们的窗口口径是字符、它是 token，于是同一份配置在不同语料上的实际窗口差 3–4 倍，而抽取质量从没按语言标定过——这与"论文类语料验证 ＋ 语料依赖风险清单"那条待办同源。

两个候选动作：① 窗口 A/B——用 A5 召回金标准，把窗口从 5000 字符降到 2500 / 1500，量 claim 召回率的变化（便宜、可测、直服务"遗漏透明"）；② 移植 gleaning 做"补抽断言"——我们已有"补引文"的先例（只补引文、不重抽断言、同样过逐字护栏、同样记账），照着做一版即可。

边界（别当结论）：它的对比是 HotPotQA ＋ GPT-4 ＋ 短段落语料，且量的是实体引用数而非 claim 召回率；我们只能把它当假设，用我们自己的金标准去证伪。

记录 ④ · 可追溯性：不是"没有映射"，是"粗、两跳、不逐句校验" 待复核

记录 2026-09-22 17:07 · 修正沛东当时的第 3 条印象（"天然没法做社区摘要到 chunk 的引用映射"）

事实：它维护了实体↔文本单元的多对多映射——entities.text_unit_ids（"包含该实体的 text units"）、relationships.text_unit_ids、反向的 text_units.entity_ids，社区报告自己也带 text_unit_ids / entity_ids。社区报告提示词还明确要求引用，但引用的是记录 id：[Data: Reports (1), Entities (5, 7); Relationships (23); Claims (7, 2, 34, 64, 46, +more)]，规则规定单条最多列 5 个 id、其余写 +more。

于是准确的分层是：claim 级引用可以一跳回到具体 text unit（claim 记录自带 text_unit_id）；实体/关系级引用回到的是"该实体出现过的那些 text unit"的集合（可能几十上百，粒度极粗）；而最终答案带引用、但只到"报告"这一级（[Data: Reports (id)]，reduce 提示词明确要求 "preserve all the data references"）——不是"没引用"，是"引到的是 LLM 写的报告、不是原文块，且无任何校验"（单条引用还有"最多 5 个 id ＋ +more"的抽样上限）。（口径已更正，2026-09-22 写 0031 时核出。）缺的不是"映射"，是句级/断言级的逐字回锚 ＋ 可审计——正是我们红线的要求。

两个更影响我们的劣势（比可追溯性更硬）：① 抹平跨源差异——global search 的目标就是综合成一个整体看法（QFS），"A5 与 O2 在这一点上不同"这类对比会被合成掉，而"跨源连接/对比"是我们立项的三大理由之一；② 静态冻结——报告是索引期预生成的，语料一变就得重跑（论文自己把 just-in-time community report generation 列为 future work）。

值得偷的一点：粒度旋钮——社区层级（C0–C3，越往下社区越多越细），token 与详略可在查询时选；我们的粒度固定在 chunk 与断言两级，没有这个旋钮。这与"类别维度建起来后，枚举可以按层级选粒度"是同一个思路。

记录 ⑤ · 社区层级怎么停：叶子的判定标准 待复核

记录 2026-09-22 17:07 · 由沛东提问引出（"怎么判断无法划分、也就是叶子社区"）

事实（两个停分条件，满足任一即停）：① 规模条件——社区节点数 ≤ max_cluster_size；② 拓扑条件——在该社区的诱导子图上再跑 Leiden，切不出多个社区。来源：graspologic hierarchical_leiden 源码 docstring 原文——"Every community whose membership is greater than max_cluster_size will then also have entries where level == 1, and so on until no communities are greater in population than max_cluster_size OR we are unable to break them down any further"；并把"归属不再变化"的节点标 is_final_cluster = True。

事实（GraphRAG 的具体取值）：它用的就是 graspologic（论文原话 "We implemented Leiden community detection using the graspologic library (Chung et al., 2019)"）；`ClusterGraphDefaults.max_cluster_size = 10`（配置文档：这组是"settings used for Leiden hierarchical clustering of the graph to create communities"，字段说明 "the maximum cluster size to export"），而 graspologic 自身默认是 1000——即 GraphRAG 把阈值压到了 10。另两个参数：use_lcc = True（只对最大连通分量聚类）、seed（固定种子，"to guarantee clustering stability"）。

实践含义（这条比定义重要）：因为阈值是 10，实际运行中绝大多数"叶子"是被"节点数 ≤ 10"截出来的，而不是"模块度真的到头了"——所以"叶子 = 拓扑上不可再分"一半是算法事实、一半是配置选择。层级 = 递归深度（level 0 根划分；level 1 在人数超阈值的社区里再切），C0–C3 就是这么来的：层级不是自然长出来的，是"递归 + 阈值"共同切出来的。

顺带三条：① use_lcc: True ⇒ 只有最大连通分量参与聚类，不在 LCC 的实体拿不到社区归属——与我们 S5 处理过的"孤立实体"是同一现象的镜像（已核：get_levels 里 lvl != -1 被显式排除，即 level == -1 的节点不参与社区报告生成、也就没有社区报告）；② 固定 seed ⇒ 把聚类随机性锁住换可复现，与我们"确定性操作不交给 LLM"的纪律同向；③ 没有 min_cluster_size（配置只有 max）⇒ 出现大小 1–2 的社区是可能的，而它们同样各生成一份社区报告，报告质量参差有一部分来自这里。

机制补正（同日补）· max_cluster_size 到底是"下拆触发器"而不是"输出上限"：graspologic 参数文档原文——"Any partition or cluster with membership >= max_cluster_size will be isolated into a subnetwork. This subnetwork will be used for a new leiden global partition mapping... Once all clusters with membership >= max_cluster_size have been completed, the level increases and the partition scheme is scanned again... and the process continues until every cluster's membership is < max_cluster_size or if they cannot be broken into more than one new community." 即：① 先在全图跑一次 Leiden（level 0）→ ② 挑出"仍然超阈值"的社区，把它们的节点单独切出来各跑一次 Leiden（得到 level 1）→ ③ 层级 +1，重复 ②，直到每个社区都 < 阈值、或拆不动为止。层级＝下拆轮次（level 0 的社区最大最少；层级越高社区越多越小）；每一轮只对上一轮仍超阈值的子图重跑，其余节点不动，所以 level 1 的社区是 level 0 某些社区的细分（不是另起一套）。
于是关键推论：max_cluster_size 不是"输出的尺寸上限"，叶子社区可能仍然大于阈值——只要那个子图"拆不出多于一个社区"（文档里两个条件用 OR 连接）。文件内部还自相矛盾一处：类 docstring 说 "greater than"，参数文档说 ">="——实现以代码为准，重写时要自己核。
举个例（假设图 400 个实体、阈值 10）：level 0 切出 200/120/80 三个社区 → 三个都超阈值，各自再跑：200 里切出 4 个、120 里切出 2 个（成 level 1），而那个 80 的再跑也只能得到 1 个社区 → 它停在 80 就不再细分，成为一个"大于阈值的叶子"。所以"叶子 = 小社区"是错的，叶子 = 小社区 或 拆不动的大社区。

对我们最值钱的一条对照：这套设计给"层级"提供了确定性、可复现、零 LLM 的来源——归属是算法算的（连接密度），不是模型判的。但代价是：它的可解释是"结构性的"（它和这些节点连得密），不是"语义性的"（它属于这一类），所以给不出"这一类都有哪些"的成员判据（回到记录 ①）。推论：将来若建类别维度，这套"递归到 ≤N 或切不动"可以原样抄来做层级（零 LLM、可复现、可对账），但类别名与归属判定仍需另想办法（注册表 or 人工受控表）——一句话：层级可以从拓扑长出来，类别不能。

记录 ⑥ · 父级摘要为什么"优先用元素、而不是用下一层摘要" 待复核

记录 2026-09-22 17:07 · 由沛东的观察引出（"叶子级顺理成章，有意思的是高层级也优先用元素摘要"）

事实（代码原文）：index/operations/summarize_communities/build_mixed_context.py 的 docstring 写着——"Build parent context by concatenating all sub-communities' contexts. If the context exceeds the limit, we use sub-community reports instead." 代码里的替代是从最大的子社区开始（大的最占地方），注释还写了一句"this sub-community has no report, so we will use its local context"（叶子子社区没有报告，直接用它的局部上下文）。兜底：若连"全用子报告"都超预算，就按顺序塞报告直到塞满。所以准确说法是：父级报告默认把子社区的"局部上下文"（实体 / 关系 / claim 表）拼起来 → 超预算时才降级用子社区报告；元素是正文，摘要是"省 token 的备选"。

事实（生成顺序）：summarize_communities.py 把已生成的 reports 逐层传给上下文构建器，而 utils.get_levels() 返回 sorted(levels, reverse=True)——即由深到浅、叶子先写，父级要用子报告时它已经存在。这条顺序是被实现强制的。

论文里的精确规则（§3.1.5，2026-09-22 晚补核）：论文原文分两条写——
· Leaf-level communities：leaf 的元素摘要先被排序，再逐条加入 LLM 上下文直到塞满 token 上限；排序规则＝按社区内每条边的 "source 节点度数 ＋ target 节点度数" 降序（即显著度 prominence），每条边加入 source 节点描述、target 节点描述、边本身、相关 claim。注意：叶子也不是"元素全进"，而是按图拓扑显著度挑前 N 个。
· Higher-level communities：如果全部元素摘要装得下窗口，就照 leaf 的做法——直接总结元素摘要；装不下时，才按"子社区的元素摘要 token 数降序"，用子社区摘要（更短）替换对应的元素摘要（更长），直到装得下。
——这精确印证了沛东那条观察（高层优先用元素），并给出了两条我们此前没有的规则：叶子的取舍靠"度数显著度"，高层的降级靠"子社区 token 体量降序"。

为什么这么设计（判断，待复核）：① 避免"摘要的摘要"逐层累积误差——每层都回到元素重写，高层报告不会因为低层摘要漏了东西而继续丢；摘要只是在预算不足时用来"降级覆盖率"。② 元素表里带的是记录 id（实体 / 关系 / claim），所以从元素出发的报告能带可解析引用；用子报告时数据集名变成 Reports——这正好解释 grounding rules 示例里为什么会出现 [Data: Reports (1), Entities (5, 7); Relationships (23); Claims (...)]。③ 它给了层级一个显式的父子结构（sub_community 字段 ＋ 逐层生成），我们图里没有这个东西。④ 用"度数"当取舍依据很值得注意：它没有用文本相关度，而是用图上的连接显著度决定"哪些元素进摘要"——一个纯结构信号。

对我们的意义（这条最能学）：GraphRAG 在这里其实站在我们这边——把"结构/元素"当真相，把"摘要"当预算不足时的压缩品，这与我们"事实层要有结构、呈现层按需渲染"是同一个立场。反过来推：如果我们做"主题页 / 概念页"，正确做法也是从 statement ＋ 出处重新渲染，而不是让 LLM 拿上一层摘要再摘一遍——否则每一层都在丢信息，最后没人知道丢了什么。将来若建类别维度，"父社区 → 子社区"这个骨架可以照抄，但父子关系解决的是"层级"，不解决"类名与成员判据"（回到记录 ①⑤）。

记录 2026-09-22 17:07 · 由沛东提问引出（"Map / Reduce 看懂了，Prepare 这步没明白"）

先纠一个误解：这一步不生成摘要——摘要在索引期就写好了（每层每社区一份，带 title / summary / rating / findings）。Prepare community summaries 是查询期的"分批打包"：给 Map 决定"一批多大、装哪些"。原文（§3.1.6）："Community summaries are randomly shuffled and divided into chunks of pre-specified token size. 它干三件事：① 选定层级——"for a given community level"，即用 C0/C1/C2/C3 哪一层的摘要（层级是查询期选的，不是索引期定的）；② 随机打散该层全部摘要；③ 按预设 token 大小切块→ K 个批次，每批＝一次 Map 调用（一批通常装好几份摘要）。

更正（2026-09-24，读代码后发现）：上面"用某一层的摘要"是论文口径；当前代码实现是"level <= N 的各层全给"——原本用于"每个实体只留它所属最深社区"的 roll-up，因 2025-02-07 PR #1674 把入参从 final_nodes（title＝实体名）换成 final_communities（title＝"Community N"）而静默失效，groupby(["title"]) 退化成按社区去重。证据（源码／官方样例 parquet／官方 notebook 的 10→10／本仓库探针）与全部影响见 0031 第 0 步。

为什么必须分批：每份摘要本身有长度上限（max_report_length），而一层的摘要总量远超单窗口预算 → 只能切成 K 批。至于为什么随机而不按顺序——见下方"修正补记"，我第一版给的两个理由（防超窗、防答坏）都站不住。

修正补记（同日，由沛东两问更正）：
① "防超窗"不是随机的理由——按 token 预算切块本身就是确定性操作，顺序打包同样保证每批不超窗；把原文 "concentrated (and potentially lost) in a single context window" 读成"超窗截断"是误读。
② "答坏"不作论据——一批里若有对问题有价值的内容，模型至少能抽出其中的点；以"LLM 抽风"论证设计不成立。而且新版实现的打分对象是"点"而不是"整批"：官方 docs/query/global_search.md 里 map 产出的是"a list of points, each of which is accompanied by a numerical rating indicating the importance of the point"，reduce 汇总的是"a filtered set of the most important points"——所以一批里只要有点重要，它就能活下来，不存在"整批全灭"。
③ 我认为站得住的解释（判断）：随机化防的是"最终窗口在语料上的分布"，不是"装不下"——reduce 只取排在前面的一小撮点/批次；若按语料顺序打包，同主题社区挨在一起 ⇒ 高分点集中在少数连续区域 ⇒ 最终窗口偏向语料一小块、覆盖面窄；随机打散 ⇒ 每批都是全语料抽样 ⇒ 高分点天然来自不同区域 ⇒ 覆盖面广。这正好对上它自己选的评测指标 comprehensiveness ＋ diversity（"多样性"只有在批次被打散时才谈得上）。
④ 附带解释（判断）：顺序打包暗含"相邻社区＝相关"这个未经证实的假设（社区 id 是算法输出顺序，本身无语义）；随机化是不做该假设的保守选择——这也解释了后来为什么能做 dynamic selection：那是用真的相关度评分替掉"相邻即相关"的猜测。
⑤ 官方文档的旁证：数据流里那三批的标注就是 "Shuffled Community Report Batch 1/2/N"。

三步合起来的链路：索引期各层摘要已就绪 → ① Prepare：选层 ＋ 洗牌 ＋ 按 token 打包成 K 批；② Map：每批独立生成"中间答案 ＋ 0–100 helpfulness 分"（0 分直接丢）；③ Reduce：按分降序、一批批塞进新窗口直到塞满 → 生成最终答案。

两个对我们有用的观察：① 它是"全量扫 ＋ 打分筛"，不是"先检索再总结"——这正是 global search 与 local search 的分界（只有 local search 做实体匹配），也解释了它为什么不需要实体锚定。② 随机分批有副作用：批次边界与语料结构无关，所以中间答案无法自然追溯回"哪个社区、哪段原文"，链路到"批次"就断了——与记录 ④ 的可追溯性问题同源。

记录 ⑧ · 随机分批 vs 按相关度分批：沛东的反例与 GraphRAG 的升级版 待复核

记录 2026-09-22 17:07 · 由沛东质疑引出（"相关度更高的社区放一个窗口应该答得更好；无关的批次自然 0 分被过滤，岂不是更好"）

结论：这个直觉是对的，而且 GraphRAG 后来就是这么做的。仓库里有 query/context_builder/dynamic_community_selection.py（配 notebook global_search_with_dynamic_community_selection.ipynb），docstring 即"Algorithm to dynamically select relevant communities with respect to a query"。机制：从根社区（level 0）自顶向下遍历社区树 → 对每个社区用 LLM 打对 query 的相关度分（rate_relevancy，可用 summary 或 full_content）→ ≥ 阈值则保留并把子社区入队，低于阈值则整枝剪掉 → global search 只在留下来的社区上跑。参数含 threshold（默认 1，偏低 ⇒ 偏向"宁滥勿缺"）、use_summary、keep_parent、num_repeats、max_level、并发 8。

为什么初版（随机）仍然成立：它的前提是"全局问题没有相关度信号"——若系统能算出哪些社区相关，它就是在做检索；而全局问题之所以需要图，正因为跨了太多社区、单条 query 与任何具体内容都不像。所以随机不是"顺序的对立面"，而是"没有任何排序依据时的默认处理"；有依据时（dynamic selection）就按依据来。

无信号前提下，"随机"优于"按原始顺序"（口径已按记录 ⑦ 的"修正补记"更正）：理由不是"防超窗"（按预算切块是确定性的，顺序打包也不会超），也不是"防答坏"（新版按"点"打分，一批里有点重要就能活）；真正的理由是最终窗口的分布——reduce 只取排在前面的一小撮点，若按语料顺序打包，同主题社区挨在一起 ⇒ 高分点集中在少数连续区域 ⇒ 最终窗口覆盖面窄；随机打散 ⇒ 每批都是全语料抽样 ⇒ 高分点来自不同区域 ⇒ 覆盖面广（对上它的 comprehensiveness ＋ diversity 指标）。同时随机化不做"相邻社区＝相关"这个未经证实的假设——这正是后来 dynamic selection 要替换掉的东西。一句话：顺序打包赌"相关的东西是相邻的"，随机打包赌"抽样能代表整体"——是代表性选择，不是容量或容错选择。

两边的代价都不白拿：随机分批牺牲单批信息密度（中间答案更碎片化），并让批次边界与语料结构无关 ⇒ 中间答案追溯不到社区/原文（与记录 ④⑦ 同源）；dynamic selection 的代价是多一轮 LLM 评分，以及"评分错 → 整枝被剪"的漏召回风险——剪枝天然伤覆盖，而覆盖恰是全局问题最在意的。归纳：初版＝全量 + 随机 + 打分过滤（保覆盖，牺牲密度与可追溯）；升级版＝相关度剪枝 + map-reduce（保密度，牺牲覆盖与成本）——与我们自己在"枚举完备"与"入口精确"之间的取舍同构。

事实（§4.1.3 Configuration）：① 8k token 是"生成阶段的固定上下文窗口"——统一用于"生成社区摘要 / 社区答案 / 全局答案"三处（细节在 Appendix C）；② 600 token 是索引抽取的窗口（§A.2）；③ 建图成本：播客语料（1669 块 ≈1M token）耗时 281 分钟，环境＝16GB RAM、Intel Xeon Platinum 8171M @2.60GHz、公开 OpenAI gpt-4-turbo 端点（2M TPM / 10k RPM）；④ Leiden 用 graspologic 实现；⑤ 提示词在 Appendix E、评测提示词在 Appendix F、统计细节在 Appendix G。

两条口径别混（这条是本记录最实用的部分）：600 是"喂给抽取的窗口"，8k 是"生成阶段的窗口"——两者相差 13 倍，分属索引与生成两个阶段。沛东最初问的"我们的窗口是不是比它大不少"，现在有了更准的答法：比抽取窗口（600）我们大（英文 ≈1000–1300 token）；比生成窗口（8k）我们小得多（我们 Pass 1 单窗 ≈1–5k token；检索注入上限我们设的是 32k 但那是检索侧预算）。

量级对照（粗算，仅作参考）：它 1M token 语料 281 分钟 ⇒ 每 8k token ≈ 2.2 分钟；我们 A5（≈8256 token）全链大约 2 分钟（记录里"白跑 2 分钟"是实测）。也就是说：我们那条"多步链"虽然步骤比它多，但单篇成本与它处在同一量级（约 2 分钟/8k token）。注意可比性有限：模型端点、硬件、语料语言、每一步的提示词长度都不同，这里只主张"量级不差一个数量级"，不做精确比较。这条对"三档原语实验"的成本预算有直接参考价值。

记录 ⑪ · directness 是"控制项（简洁度）"，不是质量指标；而 empowerment 暴露了它的真短板 待复核

记录 2026-09-22 17:07 · 由沛东的疑问引出（"全局问题上 SS 怎么会更'具体清晰'？具体事实对全局题不该是次级指标吗"）

论文的四条标准（原文）：Comprehensiveness＝"How much detail does the answer provide to cover all aspects and details of the question?"；Diversity＝"How varied and rich is the answer in providing different perspectives and insights..."；Empowerment＝"How well does the answer help the reader understand and make informed judgments about the topic?"；Directness＝"How specifically and clearly does the answer address the question?"，且明确标注为 "control criterion"（控制项）。

关键澄清（原文）："In plain terms, directness evaluates the concision of an answer in a generic sense that applies to any generated LLM summarization. We include it to behave as a reference against which we can judge the soundness of results for the other criteria. Since directness is effectively in opposition to comprehensiveness and diversity, we would not expect any method to win across all four criteria." ⇒ SS 赢 directness 是设计预期，不是异常：它赢的其实是"短、聚焦、给具体事实"——这套评测里 directness ≈ 简洁（concision）；而 SS 只看到约 13 块原文，答案天然更简洁。目的＝验证判官没有无脑偏好又长又全的答案。

但更有价值的是 Empowerment 那段的自我诊断（原文）："Using an LLM to analyze LLM reasoning for this measure indicated that the ability to provide specific examples, quotes, and citations was judged to be key to helping users reach an informed understanding. Tuning element extraction prompts may help to retain more of these details in the GraphRAG index." ⇒ 论文自己承认"具体细节"是它的短板，并把病因指向"索引端把细节磨掉了"。这印证沛东的判断：对"帮用户形成理解"来说，具体事实不是次级指标，而是关键；抽象摘要在这一项上吃亏。

对我们的直接意义：我们这条设计恰好是对着干的——保留 evidence_texts（逐字证据句）＋ evidence_chunks（可回锚块）、引用红线要求可回锚、注入下游 LLM 的是 chunk / 逐字证据而非"社区摘要"（图只做索引、不承载事实）。所以 GraphRAG 在 directness / empowerment 上付的代价（抽象化、丢引文），在我们架构里本就不该发生——不是我们更聪明，而是目标不同：它是"答案生成器"（必须综合成一个整体看法 ⇒ 必然抽象），我们是"检索结构"（把证据交回去，让下游 LLM 说具体话）。反向推论：将来若真做"主题页 / 聚合页"这类预写摘要，就会把它的短板搬进来 ⇒ "页面必须从 statement ＋ 出处渲染、不能自由写"这条纪律又多了一个理由（保住具体度与引文）。

方法论提醒：它把 directness 当控制项、用它验证"判官是否被长度带跑"——值得抄。我们自己的评测（金标准 ＋ 判官）目前有"引用红线 ＋ 遗漏透明 ＋ 覆盖性"，但没有一个明确标为"效度检验"的对照维度 ⇒ 可以进评测侧待办。

记录 2026-09-22 17:07 · 由沛东提问引出（"它发表的刊物或会议是个啥水平？"）

先定义两个词（本项目规矩：代号/新词首现必须定义）：预印本（preprint）＝作者把稿件先放到公开服务器（arXiv / bioRxiv / SSRN 等）上，公开、有稳定编号、可正式引用，但未经同行评审，因此不算学术口径的"正式发表"；若后续被会议/期刊接收，arXiv 页面会补上 journal_ref / comment。"工业预印本"不是学术上的正式分类，是本记录为描述一类东西用的说法——指由公司/工业研究机构（微软研究院、Google、Meta、OpenAI 等）产出、通常从设计上就不打算投会议/期刊的技术报告或预印本，典型形态＝arXiv 一篇 ＋ 同步博客 ＋ 开源代码（GraphRAG 即标准样本：MSR 博客 ＋ microsoft/graphrag ＋ 这篇 arXiv）。"算不算发表"分语境：学术评价口径不计入；引用口径可正式引用；工程/产品口径常被当权威参考。

事实（三处口径一致）：没有正式发表。① arXiv 元信息——没有 journal_ref、没有 comment（作者从未登记期刊/会议）；② Semantic Scholar——venue = arXiv.org，publicationTypes 标为 JournalArticle（S2 对预印本的默认归类，不代表期刊）；③ DBLP——条目号 journals/corr/abs-2404-16130，而 journals/corr 是 DBLP 给 CoRR（arXiv 预印本集合）的编号。⇒ 微软研究院技术报告 / 工业预印本，未经同行评审。这也解释了它的画像为何是"高引 ＋ 方法论松"：传播渠道是博客与仓库而非评审台，没人逼它补对照实验、对齐口径——没经过那道关是身份决定的，不是偶然。

换尺子看"水平"：引用量 2,170 次（Semantic Scholar，2026-09-22）；作者/机构＝Microsoft Research ＋ Office of the CTO（Darren Edge 等）；工程落地＝microsoft/graphrag 开源、36k stars、持续 push。同族对照：HippoRAG 在 OpenAlex 有 conference-paper 记录（2024）；LightRAG 仓库自述 EMNLP 2025；RAPTOR 本次只查到预印本条目（印象中是 ICLR 2024，未核到会议条目，待核）。
一句话：它的影响力来自工程与产品化，不来自学术评审——工业预印本的典型画像：引用量极高、方法论把关较弱。

对我们的三条意义：① 引用时必须标明身份（工业预印本 ≠ 同行评审证据），以后在本项目文档里写它要带这个限定；② 这解释了本轮挑出的问题为什么没人挡过——缺同类预摘要对照（RAPTOR / Kim 那类只进相关工作、没跑实验）、正文与图表在 diversity 上口径不一致、把"预摘要 vs 向量"的差距归因成 GraphRAG 的优势 ⇒ 这些在正式评审里大概率会被要求补实验；我们不是挑刺，是补它缺的那道关；③ 引用量 ≠ 评审等级，两个信号分开看：当工程参考用它（能读、能跑、有生态），当证据用得先过我们自己的金标准。

记录 ⑮ · 官方"适用性声明"分析：它把 verify / augment 外包给领域专家，而我们不能 待复核

记录 2026-09-22 17:07 · 由沛东给出的一句 RAI 声明引出

出处（已核）：仓库根目录 RAI_TRANSPARENCY.md——《GraphRAG: Responsible AI FAQ》，README 里专门列了它的五个入口（能做什么 / intended uses / 怎么评测 / 局限 / 运营条件）。性质＝官方"适用性声明"，不是技术规格，所以它是使用边界而非修辞。

逐句抠字：「designed for settings where users are trained in responsible analytic approaches and expected to apply critical reasoning」——关键词全是前置责任（settings / trained / expected），把"用对"的前提押在场景与用户素质上，功能上＝缩小适用面；「can provide deep insight」——承诺的是洞察而非"答案/事实"（用词刻意克制，从不说 accurate answers）；「however, a domain expert should analyze its answers to verify and augment」——verify＝可能错、augment＝可能缺、domain expert＝需专业知识才能判断对错与缺口 ⇒ 把验证与补全外包给领域专家。同一文件运营条件段更直白：「the system is designed for trusted users. Human analysis of responses is important ... and information provenance should be traced to verify the inferences made during answer generation」。

这不是客套话，与架构自洽（三条已核证据）：① 最终答案由 map-reduce 汇总，引用只保留到"报告"这一级、且无校验（记录 ④；原文写"不带引用"，2026-09-22 更正）；② 社区是拓扑近似、报告为索引期预生成（记录 ⑤⑥）；③ 论文自认"帮人理解的关键是具体例子/引文"并建议调抽取提示词保留细节（记录 ⑪）⇒ 细节确实会被磨掉。

同一文件里另外三条信息量更大的：① intended use 第一条把场景定义为"跨多文档、嘈杂、混着 misinformation、问题比底层数据能直接回答的更抽象"——这就是"学习型问答"的画像；② Limitations 只列两条——(a) "依赖构造良好的索引提示词…独特数据集上有效索引取决于能否正确识别领域概念"＝我们卡点①②的官方承认，(b) "索引相对昂贵"＋建议"先在目标域做小数据集试点评估 indexer"＝我们"先跑 A5"做法的官方背书；③ 它评测关注点含 transparency and groundedness，手段是 coverage ＋ 人工检查返回的上下文——在意可追溯，但靠人工看而非结构化引用。

与我们定位的对照（本轮最值钱的一层）：它用户画像＝受训分析者 ＋ 领域专家兜底 ＋ trusted users ⇒ 可以把 verify / augment 外包；我们用户画像＝学习者，不具备也不该被要求具备专业判断力 ⇒ 不能照抄它的免责策略。我们那套"引用红线 ＋ 遗漏透明 ＋ 判官 ＋ 金标准"，本质是把它的"需要专家 verify / augment"变成产品功能：让 verify 变廉价（点开即回原文）、让 augment 变可见（显式声明不完整）。但要诚实：我们同样免除不了最终判断——红线保证的是"可核查"而非"保证正确"，目标是"让验证便宜、让缺失可见"，不是假装不需要验证。
反向收获：它那句 "information provenance should be traced to verify the inferences" 恰好是我们已做到、而它默认流程做不到的（我们有逐字证据句 ＋ chunk 映射，它的最终答案无引用）⇒ 在"可信度/可核查"这个维度上我们可以明确宣称强于它，尽管我们的图更小更浅。
安全边界提示：它明说 "designed for trusted users"——即不能直接拿来服务公开/不受信用户；我们若面向不受信输入要另做设计。

引用纪律：以后引用 GraphRAG 的结论必须带这条 intended use（"答案需领域专家核实与补充"）——它与"它是工业预印本"是两条互补限定：一条限方法可信度，一条限适用场景。

给它一个公平的钢人（为什么逻辑上不矛盾）：① "专家要验证" ≠ "专家不如它"——专家的价值是"审一份对全量语料的粗加工"，覆盖率是人力做不到的那部分；类比资深分析师审初级分析师初稿，省的是"从零写"的时间，不是判断的责任。② 其 intended use 第一条（跨多文档、嘈杂、混 misinformation、更抽象）指向的真场景是"跨域快速定位"——有专业判断力但没时间读完语料的人。这个岗位成立。

真正的矛盾（两条证据）：① 没做到——最终答案的引用停在"报告"这一级（不是原文块）且无校验（记录 ④⑮；原文写"不带引用"，2026-09-22 更正），验证仍得自己回去翻语料；RAI 还得专门叮嘱 "information provenance should be traced"，等于把负担推回用户。② 没量化——它的评测只测答案质量（comprehensiveness / diversity / empowerment / directness），从没测"验证成本"（确认或推翻一段答案要花多少时间），而这是"专家在环"模式成立与否的分母。
⇒ 准确答法：要它来当"粗加工器"；但验证成本压不下来，它连这个岗位都站不住——质疑戳的是它未验证的那个假设。

附带一层：体裁错位。这类文档一半是能力宣传（What can GraphRAG do?）、一半是责任避风港（intended use / limitations / operational factors），连着读就像自我否定 ⇒ 别把 RAI 段落当产品定位读，但别忽略它——它暴露的是产品的未验证假设，不是文风问题。

对我们的意义（最值钱）：我们的用户是学习者，本来没有专业判断力 ⇒ 不能复制"依赖用户会验证"这个模式（会掉进同一个坑且更糟：专家至少能验证，学习者连验证能力都没有）。三条红线的产品语言：引用可回锚＝把 verify 成本压到接近零（点开即回原文）；遗漏透明＝把 augment 缺口替用户说出来；判官 ＋ 金标准＝把"看起来对"与"确实对"分开。
一句话对照：GraphRAG 的价值主张依赖"用户的验证能力"；我们的价值主张必须依赖"系统的可核查性"——可直接用作定位陈述："把 GraphRAG 推给用户的那部分责任，做成系统能力"。

顺带得到一个可测的新指标：既然判据是"验证路径够不够短"，那就能量——拿 A5 做小实验：从答案出发，要几步、多久才能确认/推翻每一句（我们 vs 它 vs 纯向量）。这个数它没有、我们可以有，且能接到现有评测体系（引用真实性那套已有一半基础）。属评测侧新增维度 ⇒ 按纪律先方案后评审。

记录 ⑰ · 它怎么测"透明性与有据性"：能自动化的只有覆盖，groundedness 交给人工审计 待复核

记录 2026-09-22 17:07 · 由沛东给出的 RAI 评测段一句引出

原文："Transparency and groundedness of responses are tested through automated answer coverage evaluation and human inspection of the returned context."
翻译：回答的透明性与有据性（groundedness），通过自动化的答案覆盖度评估＋对返回上下文的人工检查来测试。
抠词：groundedness＝答案是否有据（扎根于给定材料、非模型自带知识）；returned context＝为本次回答拼装的那批材料（GraphRAG 里主要是社区报告），不是答案本身；answer coverage＝覆盖度（recall 类）。

先定义三件常混的术语（本记录用到"透明性"，按规矩首现即定义）：Attribution（归因/引用）＝答案带出处，判据是"有没有引用"；Groundedness（有据性）＝答案确实被出处支持，判据是"引用是否真的支撑结论"；Transparency（透明）＝系统的依据/行为可见，判据是"你看得到它用了什么"。关键：有引用 ≠ 有据——引用可能挂着却不支持结论，所以要"要求引用 ＋ 验引用"两步（我们项目里就是引用真实性判官）。
"transparency"在本句里的具体所指：指 responses 的来源可见——系统不只给答案，还把"为这次回答拼装了哪些材料（returned context）"暴露出来；所以它的测法才是"人工检查返回的上下文"（检查上下文＝检查透明这件事）。
另一层含义：这份文件本身叫 RAI_TRANSPARENCY.md，在微软 RAI 体系里"transparency"还指一类披露文档（说明能力 / 适用面 / 局限 / 评测 / 运营条件）——即"响应级透明"＋"文档级透明"同名。
它的透明是弱版本：returned context 主要是社区报告（LLM 写的摘要） ⇒ 透明到一个 LLM 产物 ≠ 透明到源头；配合"引用只到报告级、且无校验"（2026-09-22 更正；原文写"最终答案不带引用"），它做到"可查"（能看到给了什么材料）但没做到"可核"（能验证材料支撑结论），后一步它写进 RAI 让用户自己 trace。我们的对应：引用可回锚＝把"可查"升级为"可核"；遗漏透明＝把透明从"材料可见"扩展到"覆盖状态可见" ⇒ 业界常说的 transparency / attribution / coverage 三件，我们合成了两条可测的量。

解读（关键在分工）：① 能自动化的只有"覆盖"；"有据"那半交给人工 ⇒ 它的 groundedness 没有被自动化，退化成"让人去看材料对不对"——这是审计流程，不是评测指标。② 人检查的对象是上下文而非答案 ⇒ 判定的是"材料里有没有相关内容"，不是"答案每一句是否真被材料支持"（后者要逐句对齐 ＋ 引用真实性判定；它没做——虽有 [Data: Reports (id)] 标注，但停在报告级且无校验，记录 ④，2026-09-22 更正）。③ 隐含漏洞：returned context 里含 LLM 写的社区报告，人若要检查"摘要是否忠实于原文"，得顺 [Data: ...] 往下钻两跳（报告 → 实体/关系/claim → text unit，记录 ④），成本很高 ⇒ 实操上多半只确认"有相关内容"，难确认"这份上下文忠实于原文"。④ 附带：它把"透明性"与"有据性"并列写，但实测手段里没有对应"透明"的量——"透明"没有独立指标（这也是"验证成本"空缺的一部分）。

与我们评测体系的对照（最值钱的部分）：它＝自动化覆盖 ＋ 人工看上下文；我们＝自动化覆盖（判官）＋ 逐字回锚的引用真实性（判官 ＋ 确定性提取）＋ 遗漏透明声明。差别在谁判 groundedness：它靠"人 ＋ 抽象上下文"，我们靠"判官 ＋ 逐字证据句"——我们强一档，代价是编译期必须保留证据句与映射（我们做了：记录 ④ 那张多对多表）。
更值得记的分工差异：它把人工放进"每次评测的流程"（人看上下文），我们把人工放在"基础件"上（金标准 / 判官口径 / 提示词），让自动化部分可回归——"可回归"才是评测的意义，人工审计每次重来、不产生累积。

一句总结：这句话表面在说"我们测了透明与有据"，实际暴露的是"有据性无法自动验证，所以交给人工审计"；而我们的设计相反——把"有据"操作化成"能否逐字回到原文"，一个可测、可回归的量。

记录 ㉒ · 产品层面的拷问：学习助手到底要多"准确"？——分层准确性 ＋ 可发现性 ＋ 低纠错成本 待复核

记录 2026-09-22 17:07 · 由沛东的一个想法引出（"十分准确有多重要？学习是渐进过程、智能本身有不完备性，是不是该追求'靠谱的搭子'而不是单次十分准确"）

我的结论：对了一半。把"单次回答十分准确"当目标是偏的（既不可达、也不是学习者真正需要的）；但不能由此推出"准确性可以降级"。正确重构＝分层准确性 ＋ 错误的可发现性 ＋ 低纠错成本。

一、错误不是均匀的，代价取决于落在哪一层：细节（"83% 还是 80%"、"Seatbelt 在 macOS 上"）⇒ 后续材料能对上，代价低；骨架（因果搞反、"这两条路线是一回事"）⇒ 学习者正是靠它理解别的东西，不能自纠，代价高；归属/极性（把 A 的观点记成 B 的、把被明确否定的说法当主张）⇒ 完全不能自纠，代价最高。要点：学习是建构性的，错的心智模型比"不知道"更糟（教育心理学的"错误概念难以纠正"：它不是空缺，而会主动干扰后续学习）。⇒ "准确"不能当标量整体放松，必须分层：骨架/归属/极性不可松，细节/措辞/程度可容忍。注意这与我们图里那条"正确性分层"（方向/极性/范围不可错，字面量/程度可容忍）是同一条原则，只是从索引层搬到回答层。

二、"学习是渐进的"这条论据隐含一个不成立的前提：它成立的前提是"学习者有能力在后续迭代中识别并纠正错误"——而我们的用户画像恰不具备（这正是我们与 GraphRAG 的定位分叉，记录 ⑮）。这句话 disclaim 了纠错的必要性，却没提供纠错的能力；对初学者说"你以后会自己发现我错了"，等于把风险转嫁给最没有能力承担的人。

三、"持续交流的搭子"方向对，但替代不了结构性正确：对话能澄清/追问/逐轮补充（学习本就该是对话式），但三个硬限制——① 用户不知道自己不知道什么，不会针对性追问从未怀疑过的错误；② 多轮会累积偏差，第一轮的错误结论被后续当作前提（错误被上下文固化，比单次错误更难发现）；③ 它把指代消解变成必需，也因此引入错误传播。⇒ 它的真正价值不是"可放松准确性"，而是把准确性从"单次答案"转移到"可核查的交互结构"上：允许单次不完美，但每个结论都能被追问到依据。

四、把"十分准确"重构成三个可交付属性：① 不正确率（分层）——骨架/归属接近零，细节/程度可容忍但要有标注；② 错误的可发现性——引用可回锚 ＋ 不确定标注 ＋ 遗漏声明（这是护城河，不是妥协）；③ 纠错成本——发现后改起来多贵（一句话能否定位到依据）。⇒ 合起来才叫"靠谱的搭子"：不是不出错，而是"错得起、看得出来、改得动"。

五、反向风险（必须说清）：若把目标定成"靠谱的搭子"而放松准确性，很容易滑成聊天机器人——那用户凭什么不用通用大模型？我们的差异化恰恰是"有材料、可回溯、能核对" ⇒ "搭子"必须站在材料上：一个能带你去原文的搭子，不是更会聊的搭子。

六、可操作判据：纠结某处要不要做准时，问一句——"如果用户拿着这句去写论文，我敢让他引哪一句？"敢让他引的＝骨架层，必须准；不敢的，必须显式标注"这层是综合推断/可能不完整"，而不是混在一起让他分不出来。

七、与现有设计的对接：我们的评测三件套（覆盖性 / 引用真实性 / 遗漏透明）已覆盖上述第 1、2 条属性，缺的正是第 3 条"纠错成本"——与记录 ⑯ 的"验证成本"是同一族（待办候选 2）。⇒ 这个想法不是推翻现有口径，而是给它补上第三根柱子。

记录 ㉚ · claim_type 要求"跨文本可重复"，但每次只看一个块——指令 ≠ 机制 待复核

记录 2026-09-22 17:07 · 由沛东追问引出（"一次调用只给一个 TextUnit，却要求 claim_type 跨多个 TextUnit 重复，岂不是看 LLM 心情"）

结构硬伤（成立）：提示词写 "Name it in a way that can be repeated across multiple text inputs, so that similar claims share the same claim type"，但每次调用只看到一个 text unit，模型看不到别的块产出了什么类型 ⇒ "可重复"既不是查表（无闭集）、也不是全局对齐（无全局视图），只是"同一提示词 → 同一命名习惯"的先验赌注。

为什么还部分能用（四条）：① 同一提示词 ＋ 同一模型，命名先验较稳（相似内容易收敛到相似粗类）；② claim_description 是全局共享配置，所有调用被同一句话锚住；③ 大写 ＋ "overall category" 的措辞把输出推向粗粒度名词、抑制长短语；④ 最关键：下游不靠它做过滤——local search 配置里没有"按 claim type 过滤"（只有 top_k_entities / top_k_relationships / text_unit_prop 等）⇒ claim_type 是描述性元数据、不是查询键，近似重复可容忍。

什么时候崩：① 类型空间一大就崩——欺诈场景类型少而显著，开放领域（如技术文章）类型空间无界，漂移立刻显形；② 抽象层级不一致——同一件事可能一块写成 BID RIGGING、另一块写成 ANTI-COMPETITIVE PRACTICES（兄弟类并存，而非同义合并）；③ 不可复现——同输入两遍类型名可能不同 ⇒ 基于 claim_type 的计数/筛选都不稳定。
⇒ 准确说法：不是"看心情"，而是"一个有先验约束的随机变量"——主分布集中（少数大类为主），长尾不稳定且不可复现。

我们的第一手证据：我们早期就是这么干的——自由谓词 → 长尾碎片 ＋ 收容桶（acts_on 44 条混着 apply/describe/automates/倾向判断）→ 因"结构判同指失败"才收敛成 38 条受控表（记录 ①）；中间还踩过"一致率口径只覆盖 27% 样本"的坑。⇒ 它在我们的早期阶段、我们是被数据逼出来的；它不往前走是因为不需要（claim_type 不当过滤键，碎片化对它只是不好看，不是错）。

想真一致有四条路（它一条都没走）：① 给闭集（把类型表写进提示词）；② 两趟归一（自由抽 → 归一到受控表 ＋ 表外词台账）；③ 事后聚类合并（类型名向量聚类/近义合并，便宜的中间路线）；④ 让一次调用看到一批 text unit，使"跨文本重复命名"有执行基础（它没这么做，claim 抽取是逐块的——而这条是最直接的结构性修法）。
结论一句话：它把"一致性"写成了要求，我们把"一致性"做成了机制（受控表 ＋ 归一步 ＋ 台账）——这也解释了两家的成本结构差异（记录 ㉘）：它省掉归一，代价是类型不可用；我们多花那一步，换来类型能当过滤键。

记录 ㉛ · "既然 LLM 是续写，为什么不写 I am 而写 You are"——直觉对在基座层，落点其实在结构 待复核

记录 2026-09-22 17:07 · 由沛东看提示词时的想法引出

直觉在基座模型层面成立：裸模型的训练目标是续写，把提示词写成"文稿的延续"确实更贴合目标。其正统实现是"预填充（prefill）"——在 assistant 回合开头写 "I am a careful analyst. …" 让模型从那里续；而 "I am" 放到 user 消息里会被理解成"用户自称"（模型以第三方回应），放到 system 里则语义错位（那是"系统在设定"，不是"我在说话"），最容易导致角色混淆。

为什么 "You are" 在 chat 模型上照样有效：① 指令微调把"system＝指令、assistant＝回答者"的映射训进了模型 ⇒ "You are …" 落在 system 位置**本来就在训练分布内**；② chat 模板是结构化的（system / user / assistant 分段），续写只发生在 assistant 段落内部，改称呼没法把整段 prompt 变成文稿；③ 所以人称差异更多体现在口吻与自我一致性，不在"能否理解任务"。

真正的收益点在结构，不在人称（本轮最值钱的判断）：续写范式最有效的用法是"把答案的开头与格式摆好让模型接着写"——而 GraphRAG 的提示词其实已经这么干了：extract_claims 与 community_report 结尾都是 Output:"（留下答案的开头等它续写），结构是"示例输入 → 示例输出 → 真实数据 → Output:"；人称写 "You are"，结构却是续写式的。对照 basic_search 的系统提示词是纯命令式（"Generate a response ..."），同一项目里两种范式并存。⇒ 人称的作用（若有）远小于结构，力气应花在"给格式、给半成品、给 Output 钩子"。

公开研究证据现状（已查 arXiv）：有 role-play prompting 这条线——"Better Zero-Shot Reasoning with Role-Play Prompting"（2023-08-15）、"Role-playing Prompt Framework: Generation and Evaluation"（2024-06-02）、ORPP（2025-06-03），以及一条反面证据："Persona is a Double-edged Sword: Mitigating the Negative Impact of Role-playing Prompts in Zero-shot Reasoning Tasks"（2024-08-16）⇒ 角色提示不是免费收益。没找到专门比较"第一人称 vs 第二人称"的研究 ⇒ 该假设目前无现成结论，是开放问题。

它最好的地方是可证伪，且我们具备测它的条件。建议实验（一次只动一个变量）：任务＝现成的 L3 形状判定（19 条标注、判官与台账都在）；三版提示词——A＝现状（system "You are …"）／B＝预填充（assistant 开头 "I am …"）／C＝纯结构版（去掉人称，只留格式示例 ＋ Output: 钩子）；指标＝判定准确率 / 格式合规率 / 理由质量，同重复次数。关键：人称与结构分开测（A vs C 测结构、A vs B 测人称）。⇒ 无论结果如何都得到一手结论，且可复用到后续所有提示词。涉及提示词属基础件 ⇒ 先在方案层确认再动手。

对 global search 的影响（四条，均较硬）：① 跨批主题永远不会出现——输入＝"旧树各层 ＋ 新批次各层"两套报告并置 ⇒ 同一主题被分批表述，跨批的对比/连接/趋势没有对应报告，直接打在其"跨整个语料综合"的立身之本上。② 主题重复把"全面性"虚高——同一主题两批各有报告 → map 各出部分答案 → reduce 汇总时同事实计两次 ⇒ comprehensiveness / diversity 这两个指标被冗余污染。③ 层级粒度不可比——旧树可能深到 C3、新批次或许只有 C0–C1 ⇒ 同层选择下两边粒度不同，却在同一批不可比对象上打 helpfulness 分。④ 成本线性涨、覆盖不涨——global search 每次扫该层全部报告（记录 ⑦）⇒ 报告数随更新单调增长，token/延迟持续上升，新增部分常是"另一批对旧主题的复述"。⑤ 叠加删除不落地 ⇒ 已删内容继续参与全局问答（不是覆盖不足，而是把不存在的东西当当前知识）。

· local search：影响较小且部分为正向（旧实体被新证据补全——text_unit_ids 并集、description 并列）；已核 mixed_context.py 不按 degree 排序（degree 出现 0 次），用 rank（rank_description 默认 "number of relationships"）、社区按 (matches, rank) ⇒ degree 那笔脏账主要落在社区报告生成（㉞），不在 local search 选取。
· basic search：向量库只增不删 ⇒ 已删文档的块仍可被召回（最直接的一种"错"）。
· 所有查询：period 虽在数据模型里（"used for incremental update merges"），但 local search 无 period 过滤、mixed_context.py 里 period 出现 0 次 ⇒ 查询侧完全不消费批次信息，新旧产物被当同质语料混用。

记录 ㊳ · 为什么"增量 + 社区划分"不该做：它是全局优化，不是工程偷懒 待复核

记录 2026-09-22 17:07 · 由沛东追问引出（"有全量流水线了，增量应该不难啊？不对，是不是要重跑一半社区划分？少量增量会不会引起划分大变化"）

一、Leiden 是全局优化，不存在"局部增量"：它最大化**整张图的模块度**（全局求和），加几条边，最优划分**可能在任意位置变化**。三个机制叠加：① 目标函数全局；② 解空间有大量"近似最优"划分（near-degenerate，分数差极小但成员差很多）；③ 算法带随机性——GraphRAG 为此专门固定 seed（"to guarantee clustering stability"，记录 ⑤）⇒ "必须锁种子"本身就是"输出对细节敏感"的自证。

二、"只重算受影响的社区"会卡在接缝上：重算区与冻结区的边界不对应任何一致的划分 ⇒ 得到"既非旧最优、也非新最优"的混合体，且没有目标函数能判它合不合格。真要做得用"局部模块度优化 ＋ 边界冻结"，代价是质量不可验证。

三、一旦要保质量，就退化成"全量重跑聚类"——而且不只是重跑划分，还要重写所有受影响的社区报告（LLM 生成，成本与社区数成正比）⇒ 增量省下的抽取钱很可能不够付重算报告的钱。两个连带影响：① 层级放大影响——层级是递归切出的（"递归到 ≤10 或切不动"，记录 ⑤），一次小插入可能改变分支**深度**（主题落 C2 还是 C3 都变），而 global search 是"选一层扫全量"（记录 ⑦）⇒ 用户看到的是"一次增量让全局问答取材范围整体变动"；② 引用与基线连带失效——报告 id＝full_content 的 sha512（记录 ㉓），重算后全变 ⇒ 缓存/引用/评测基线一起失效，重算把"稳定性成本"从算法层推到工程层。

四、这条线在学术界是活跃题目（已核 arXiv）：DynaMo: Dynamic Community Detection by Incrementally Maximizing Modularity（2017-09-25）、DyPerm（2018-02-13）、Constrained Spectral Clustering for Dynamic Community Detection（2019-11-04）、Flow stability for dynamic community detection（2021-01-15），以及最新 ComNetX: Local Hierarchical Adaptation for Dynamic Community Detection（2026-07-10）——最后这篇的标题几乎就是"局部层次自适应"。⇒ 这个想法学术上研究了近十年，没成为默认做法，原因是"增量带来的结构漂移"要和"结构可比性/稳定性"做交换，而 GraphRAG 的价值正建在"结构是全局的"之上。

五、它为什么不做的三条：① 目标场景是"静态语料、建一次、查很多次"（记录 ㊱）⇒ 无高频更新压力；② 真做增量要么引入不可验证的近似、要么退化成全量重算，两头不划算；③ 没有产品需求逼它做对——免责声明（记录 ⑮）已把"结构可能不准"兜住。

六、对我们的启示（"约束哪一端"的第三次回本）：我们的路线在增量上天然占优——要的是受控类别表 ＋ 逐条归属，给新断言挂类别标签是局部判定，不需要重跑全局聚类。同一个选择第三次给红利：受控词表 → 可过滤（记录 ①）→ 可归一（记录 ㉚）→ 可增量（本条）。
反面的诚实话：若"概念结构层"将来做成多层级上位概念体系，同样会撞上全局重算（层级越高越需全局视图）；只有"扁平受控表 ＋ 逐条挂标"才是天然可增量的形态 ⇒ 这对"类别维度要不要做层级"是实质约束。

记录 ㊴ · 推论："GraphRAG 不适合持续更新的知识库"——对一半，受影响的是"全局结构"而非整个系统 待复核

记录 2026-09-22 17:07 · 由沛东的领悟引出（"知识库长期稳定的不多，大多是持续更新的，那 GraphRAG 岂不是不适合很多知识库场景"）

一、受影响的只有"全局结构"能力：四种查询模式里，只有 global search 依赖全语料社区结构（DRIFT 依赖一半，它也吃社区信息）。另两种在持续更新下基本可用：basic search（纯向量 ⇒ 新内容 upsert 即可查）、local search（靠实体图 ＋ text unit，而实体合并按 title 并 text_unit_ids 是真合并 ⇒ 旧实体被新证据补全，越更新越全，记录 ㊲ 已给此条）。⇒ 准确说法："全局综合"与"持续更新"不兼容；"局部检索"与持续更新兼容。

二、更深的理由：全局结构本质是"慢变量"——"跨全库主题聚类"需要一段时间窗才能收敛；语料若变得比索引刷新快，那个"全局主题"还没形成就过时，概念本身不成立。由此得一条可复用判据：索引刷新周期要与语料演化速度匹配在同一量级（差得太多就白做）。分档：每月补充几次 ⇒ 完全可行（离线全量重建，几小时机器时间）；每日新增 ⇒ 需调度 ＋ 分域/分档刷新；分钟级流式 ⇒ 不适用——不是它不行，是任何"全局结构"都不行。
公平话：静态语料（书 / 法规 / 制度集 / 研究集）它很合适，企业知识库里"基本不动、偶尔补"的也不少 ⇒ "不适合很多知识库"应限定为"不适合高频更新的知识库"。

三、业界对"持续更新"的四种对策（非 GraphRAG 独有难题）：① 分层刷新率（Lambda 思路：高频只做 chunk ＋ embedding，低频做全量结构重算）；② 分域建图（按主题/来源/时间窗切稳定子域，各自重算，避免全局重算随语料无限增长）；③ 滑动窗口图（新内容建小图、老图冻结，查询跨多图）；④ 接受滞后并声明（把索引当快照，标明"数据截至某时间"、定期重建——最常见也最诚实，正是我们"遗漏透明"的精神）。

四、对我们的实际结论：我们的语料是精选文章 / 论文 / 书，更新频率天然低（用户传一篇、隔几天再传），正好落在它的适用带。而且我们有个结构上的便宜：逐篇编译 ＋ 扁平受控类别表 ＋ 逐条挂标（记录 ㊳）⇒ 新内容是局部判定、天然可增量，不依赖全局重算。真要做"跨全库全局综述"，路线也已明确：按需渲染而非预生成摘要（记录 ⑯㉒）——不预生成，就没有"预生成过期"。这是"事实层结构化 ＋ 呈现层按需渲染"这条路线又一次替我们挡掉了别人踩的坑。

五、最值得留档的判断顺序：以后讨论"要不要上某种索引/结构"，先问两句——① 语料变化速度 vs 索引刷新周期，差几个数量级？② 我要的是"全局结构"还是"局部检索"？（全局结构＝慢变量，只配低频刷新）。这两句能提前挡掉一大类"建的时候爽、维护起来废"的方案。
