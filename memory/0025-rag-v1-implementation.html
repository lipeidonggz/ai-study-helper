实践与经验教训（2026-09-02 实现阶段沉淀）

  1. 本地 embedding 选型三约束：①fastembed 0.8 已移除 BGE-M3，计划会落空——选型前先查当前版本支持的模型清单；②"本地"不等于效果差，决定质量的是模型选型（中英混合素材 → multilingual-e5-large）；③字符数 ≠ token 数（1766 字符的 ASCII 代码块 = 447 tokens），切块与界面要显示真实 token，不能按字符猜。
  2. Qdrant 本地模式单进程锁：两个进程共享同一数据目录直接冲突（8000/8899 双实例翻车现场）；解法 = 同路径客户端单例（进程内）+ 懒加载（不用 KB 的流程不占锁）+ 测试独立目录（conftest 设 ASH_QDRANT_PATH）。嵌入式存储类选型的通用运维坑。
  3. 向量库 scroll ≠ 入库序：scroll 返回内部存储序，业务顺序（chunk 在原文中的先后）要显式写入 payload（seq），展示按它排序，不能依赖存储序。
  4. 入库文件规则放代码而非 MANIFEST：data/ 整体 gitignore，规则放代码（ingest_rules.py）才能随提交沉淀；MANIFEST 管"有什么素材"，代码管"哪些文件进库"。
  5. 全量入库按钮要按阶段放开：适配器未做对前，全量会把不适配素材（PDF / 教程目录 / 老编码 HTML）拉进来 → 先做对格式适配，再放开范围；v1 首轮切片本就是 O2/A5/自有。
  6. 项目特点（非通用洞察，勿外推）：本项目的复杂度来自格式本身而非内容组织——内容组织干净（标题层级），复杂度全在格式适配（HTML 站点差异 / PDF / 编码 / 多语言目录）。这是本项目素材特征，不是行业通用规律。
  7. PDF 抽取选型：要还原结构先拿到版式信息：纯文本流（pypdf）没有"标题"概念，visitor 字号恒为 1.0 不可用；换 pdfplumber 逐字符字号/位置后，标题（字号 ≥ 正文 1.5×）、页脚带（底部固定区域）、段落（行距）都可判。另发现一个真 bug：句子切分正则漏了 ASCII 句号 .，英文 PDF 因此断在行尾。
  8. 版式噪声无害，代码块截断才是真风险：行号/页码/零星断词对向量召回与 LLM 理解基本无害（实测限定 O1 检索"WebSearchTool 代码示例"命中带行号的代码块）；真正的风险是超长代码块被 token 上限拦腰截断——将来出现"使用/复刻代码"类用例时，需要"代码块整体不拆"的切块规则。
  9. 模糊指代文档的检索：先给 chunk 注入文档身份，router 别做单点锁定：用户"那本/那篇/0022 笔记"这类输入是设计内场景（0024 规范禁止用编号）；最便宜的解法是来源行把作者/平台·标题拼进每块文本（实测"OpenAI 指南"前 6 条全命中 O1、"harness 那篇"全命中 O2，此前会被 OW1 淹没）。文档目录预路由只在"查询含可对齐的区分信号"时有效；无信号（纯记忆指代）谁都救不了，信号说错时单点锁定会放大错误——若探针证明需要，router 应输出候选列表供下游澄清，而非锁死一篇。
  10. 生产级入库质量保障框架（业界通行做法，落地待做）：KB 变大后逐篇检查不可行，行业做法是"抽样检查 + 出问题定位"，内核四件套：①质量信号自动化（空文本/字数异常、噪声词频率、乱码率、chunk/token 分布，超阈值才人工）；②分层抽样 + 金样张回归（每类站点/格式抽代表固化为金样张，抽取器改动跑回归防"修 A 坏 B"）；③归因链（入库记录来源 + 抽取器/规则版本 + 质量信号，问题反查到"哪一层哪一版"）；④人工审"类"不审"篇"（新格式类别人工建基线一次，存量靠信号监控）+ 坏答案回流（faithfulness/检索失败率异常高的来源反查入库质量）。落地形态 = "入库质量报告"功能（见下一步 ④）。
    盲区与三层补强（2026-09-02，A5 lede 归位教训）：信号层只覆盖"格式/噪声"，抓不到"内容完整但归位错误"——A5 开场 lede 被排到文档流后、仅靠一处重复兜住，信号全绿。该类问题由三层补：①人工内容层抽查（对照原文读开头/结构，样本级，不逐篇）；②每次发现固化成"金样张 + 结构断言"（如"首块以 X 开头"）防复发——金样张只免疫已知问题，不发现新问题；③坏答案回流兜底（评测/真实问题触及该内容时失败反查，属被动哨兵）。工程化补强 = 结构指纹（每篇输出"首段文本 + 节路径序列 + 各节长度"，新类别首建由人确认一次，之后同源 diff 自动抓归位变化）。启发：问题不在"逐篇 vs 抽查"，而在"内容层是否有断言机制"——抽查发现新问题类，断言防复发，回流兜漏网。
  11. 协作分工教训（2026-09-02，沛东批评"不问就不说"）：Codex 的默认认知（资深工程经验里的"道道"）不会自动讲出来——沛东不问入库质量保障，Codex 就没主动提。改进 = 在换阶段 / 上规模 / 加新素材类型等关键节点，主动给一份"你可能还没问但值得知道"的风险与做法清单，不等追问；这也呼应 0022"人做二次检查"的反面——AI 的增值不止是执行快，还包括主动把视野里的坑摆上桌。
  12. 引用编号 [n] 是给判官/系统的，不是给用户的：注入块编号对模型是格式约束、对判官是证据映射，但裸 [6] 对用户无意义。修法 = 编号行自带来源名（从 chunk 首行"来源：…"提取，正文去重不增 token）+ 提示词要求首次引用带名称；实测 rag-a5-001 回答开头变为"根据 Anthropic《How we contain Claude》…[3]"。判官证据编号必须与注入编号同序（已如此）。
  13. 用户点名素材 = 期待"仅根据该素材回答"——点名检测 → 定向过滤（2026-09-02，a5-002 教训）：这是一类明确且高频的场景：用户已经尽其所能给出指向信息（点名文章/文档/书名），其期待就是"只根据他指定的素材回答"。完整记录如下：
    • 场景与失败现场：rag-a5-002 问 A5《How we contain Claude》里 83% 拦截率的含义。纯全库稠密检索 top6 混入了 OW1（自有笔记），模型在回答尾部顺带引用了一条自有笔记（"100% 是危险信号"）且没有规范来源标注——内容无害但违背了"用户点名 A5、就该以 A5 为准"的预期。
    • 机制根因（两个叠加）：①检索是"全库无差别 top-k"，不知道用户点名了哪篇、也没利用这个强信号（payload source 过滤能力早已具备但没接）；②语料量不均（OW1 183 块 vs A5 23 块）+ 自有笔记本身就是这些话题的二手总结 → 语义相近的 OW1 chunk 挤进 top6。不是检索坏了，是"点名"这个意图没被识别。
    • 修法（确定性规则，非模型判断）：文档点名检测 = 人工精选"能唯一定位一篇"的短语词典（小写子串匹配，太泛的词不收）；规则 = 仅当点名唯一一篇时才过滤（payload source_id 过滤后在该源内取 top6）；点名 ≥2 篇（跨文档对比如 cmp-001）不过滤，避免砍掉对比类查询；纯语义指代（无标题词）不进这层。挂在 RagBackend，chat 与评测 runner 共用。
    • 效果验证：a5-002 定向后 6 条命中全为 A5（trace reason 记录"点名文档 A5 → 定向检索"），回答尾部的自有笔记旁白消失，verdict pass；rag-a5-001 rerun 同样干净。新增点名词典 + RagBackend 过滤单测 6 个。
    • 认知提炼：点名类交互的产品语义 = "范围锁定"——用户说"XX 文章/文档/书上怎么说的"，他要的是该素材的说法，而不是语料库里语义更近的二手内容代替。这把"用户意图"变成了确定性规则（骨架硬化），且与 0024"禁止用编号、必须自然表达"的用例规范互补：自然表达里点名（标题/书名的自然写法）恰好是过滤器能识别的强信号。
    • 边界与后续：语义指代（无标题词，如"A社讲怎么限制 Claude 的文章"）实测大部分已被"来源行 + 稠密检索"覆盖（4 条实测中 2 条直接命中原文）；剩余"原文 vs 二手竞争"（描述与 OW1 语义更近的场景）与双点名对比的覆盖问题，留步骤 6（source 配额 / 检索质量节点）与步骤 7（原文 vs 二手竞争探针）处理。

  15. 用例设计的主轴在问题域：场景亚类拆解优先于解决域质检工具（2026-09-03，cmp-001 深究）：cmp-001 的两个问题（锋利度不足 / 固定 top-6）讨论后收敛出的方法论：

  6. v1 落点（定案）：12 用例任务空间设计期可枚举 → workflow + 相关性门控；agentic 作为受控 A/B 排队（评测链路稳定后补多跳用例对比）。

调校结论（2026-09-03：稳定性基线 + 类级根因）

  1. 现象：Run#103（repeat 20）cmp-001 15/20、a5-005 19/20 不稳；Run#104 每源配额定向后 18/20 仍不稳——加配额只是把问题搬进每个源。
  2. 根因（一句话）：证据充分性由"排序位置 / 固定 top-k"决定，而排序位置不携带"够不够"信息 → 语料、源规模、问题类型一变即失效（打地鼠的机制性来源）。
  3. 类级方向（定案）：决策路径移除排序位置常量，充分性改由问题类型覆盖模型判定：细节/定义 = 连贯单节；对比 = 每源代表立场齐；聚合 = 跨源分布；多跳 = 前提链证据齐。块数是判定结果，不是输入。
  4. 预算语义：预算 = 资源约束而非策略；顶住时输出一等公民"证据不足"，与拒答校准衔接。
  5. 方法论：评测失败 = 不变式被违反；当前状态只用于发现问题，不进入设计输入；探针池按不变式族组织（详见经验教训第 17 条与现场细节）。
  6. 用例完备性补充来源（2026-09-03 定案）：除问题域亚类拆解（静态、需求驱动）外，根因驱动扩展（动态、缺陷驱动回归）是第二来源；每个根因修复交付 = 机制改动 + 该类不变式探针 + 全量回归（详见经验教训第 18 条）。
  7. 证据收集信号修正（2026-09-03）：核心 + 邻近窗口被 o2-001 证伪（位置连续性假设不成立）；证据组改为"宽召回候选的高分证据块集合"，选择信号依赖向量语义相似而非位置邻近（详见经验教训第 19 条）。
  8. 量化证伪优先于纯逻辑推演（2026-09-03，沛东认可）：RAG 检索是不确定性场景，纯逻辑推演不够用——机制/参数假设必须用数据定界；12 条证据定位实测推翻"纯 e5 排序够用"（own-002 rank23、cmp-001 分数平带）并给出 C/B 量级（详见经验教训第 20 条）。

阶段 B · 问答侧（2026-09-02）

  1. 沛东提出两种解法的理解：①先查 chunk（可融合多种方式）+ 预处理（如重排序），再与用户 query 一起给 LLM；②Agentic RAG——检索封装为工具、模型自主决策、天然支持多轮查询。请 Codex 确认理解 + 补充其他方式。

  8. 生产形态观察（Voltage Park 引语解读，2026-09-02）："生产里大多数 agentic RAG 系统，最后长得不像一个聪明的提示词包着向量库，而像一个管线"——开放循环被延迟 / 成本 / 可靠性 / 可观测性四力压回"管线 + 少量有界决策点"的形态；纯开放的 agent 只是 demo 里的理想形态。
  9. 【决策点】骨架硬化原则（沛东洞察，2026-09-02）：既然生产 agentic RAG 的骨架是确定的，就没有必要用提示词规定模型行为——应把骨架硬化进 Agent 代码，LLM 只在某些节点做判断；否则落入"指令遵循性到不了 100%"的陷阱。Codex 精确化：硬化 ≠ 不用提示词，LLM 判断节点要窄输出 + schema 约束 + 兜底分支；这是 0022 护栏/harness 原则（确定性兜底不确定性）在 RAG 编排上的延伸。
  10. 泛化（沛东，2026-09-02）：这种方式本质是"支持 LLM 节点的工作流"；只有当任务复杂、天然需要多次迭代摸索、或后序检索依赖前序检索结果时，才应把决策权完全交给 LLM——而那时已接近 ReAct，检索只是其中一个工具。问题因此归位为通用选型：何时用 ReAct，何时用支持 LLM 节点的工作流。
  11. 查证（Codex，2026-09-02）：泛化不是自嗨——Anthropic《Building Effective Agents》的 Workflow/Agent 二分（workflow = 预定义代码路径编排 LLM 步骤，适合确定性可分解任务；agent = 模型动态主导过程，适合路径无法硬编码的开放任务），判据原话精神即"任务歧义度允许预映射决策树 → workflow"；RAG 2025 taxonomy 直接按 agentic depth 分类；多篇文献明示"Agentic RAG 与 ReAct 高度一致"。但需带三个标注：①Agent 是家族不是单点（Self-RAG 反射 token / Plan-and-Execute / multi-agent / Reflexion 均非 ReAct），"agentic RAG ≈ ReAct"是工程近似；②二分在实践里本来就融合（OpenAI SDK 支持代码编排与策略驱动混合；LangChain：生产大多是组合；Anthropic：agent 的工具可以是 workflow），更准确是"骨架硬化程度"旋钮；③该框架只回答"谁决定检索编排"，检索质量是独立轴（CRAG 纠错式），可被 workflow 的验证/纠错节点吸收但框架本身未显式包含。
  12. 【决策点】v1 落点（2026-09-02）：12 用例任务空间设计期可枚举 → workflow（支持 LLM 节点）+ 相关性门控；agentic（ReAct + 检索工具）作为受控 A/B 排队——评测链路稳定后，用同一批用例 + 补多跳用例做对比，有质量缺口再切换或混合。
