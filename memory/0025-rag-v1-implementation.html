决策层 · 30 秒判断：要不要读、怎么读

本文讲的是"如何构建一个最匹配产品定位的 RAG 增强单轮检索系统"——交付系统形态（workflow + 门控 + 证据组检索机制）与构建方法（评测驱动的最小系统演进）。评测不是主角，是方向盘。

  • 本文解决什么问题：RAG 的技术方案很多很杂且远未成熟（向量 / BM25 / rerank / 图检索 / agentic……），直接堆叠全套是灾难。本文回答：①系统的目标形态是什么——为什么是"固定检索 + 门控 + 证据组"，而不是一开始就 agentic；②怎么从最基础起步并演进——先做纯稠密 top-k 跑通，每次技术叠加都由评测证据驱动（稳定性基线暴露问题 → 根因 → 机制修复 → 再评测），BM25、rerank 的引入与降级都是这条链的产物；③评测自身怎么保证可信——金标准时间线污染、判官执行一致性、用户视角缺失三类坑。
  • 一分钟摘要：系统形态——评测驱动不是"什么都上"：v1 = 骨架硬化 workflow + 相关性门控 + 证据组检索机制（每源宽候选高分块集合 + 预算约束，取代"排序位置决定取多少"）；输入侧节标题进文本是最大单点修复（自有笔记问答用例里，答案块从检索第 23 名升到前 4）。构建方法——稳定性基线（每条用例重复执行 20 次）是驱动力：某轮跑批暴露跨文档对比用例与一条细节用例不稳 → 根因"排序位置常量病" → 覆盖模型；own-002 先归因输入侧（标题丢失）再归因检索机制；工具侧临时笔记空库覆盖注入也在评测中现形。技术叠加守纪律：BM25 曾被误引入（实测无贡献 → 降级对照）、本地 rerank 被成本否决（CPU 约 3 pairs/s）、两阶段检索与 agentic 排队到下一篇。评测可信度——金标准三大坑（时间线污染 / 用户完整性导向 / 判官自由裁决不一致→结构化裁决方向）。

主体层 · 构建 RAG 单轮检索系统（读完即可用）

一句话主线：先做最基础的检索系统（纯稠密 top-k），让它跑通产品要的最小场景；然后用评测这把尺子反复量，量出问题 → 根因归类（输入侧 / 检索机制 / 生成 / 工具 / 评测自身）→ 类级修复 → 再量；只有当评测证据表明"某个技术方案能解决被量出的问题"时才叠加它，否则不叠——这就是把"多而杂、未成熟的 RAG 技术方案"收敛成"最匹配产品定位的系统"的方法。

名词约定（读前扫一眼）：本项目用代号称呼素材与用例——素材：O1 = OpenAI《A Practical Guide to Building Agents》、O2 = OpenAI《Harness engineering》、A5 = Anthropic《How we contain Claude》、OW1 = 项目自有文档合集；用例：own-002（自有笔记问答）、cmp-001（O2 vs A5 跨文档对比）、a5-005、o2-001（隐含定义探针）等 12 条 RAG 评测用例（设计见 0024）；跑批 = 评测系统批量执行真实模型，Run#103 这类编号是跑批序号；repeat20 = 每条用例重复执行 20 次测稳定性；dense 检索 = 稠密向量相似度检索（v1 默认的唯一召回方式）。

0 · 前置约束：产品定位与素材的时间性

产品定位：学习助手，不是"知识库问答机"（0023/0024 定稿）：允许内化直答（答对即可，不强制来自检索）→ 引用真实性只能是条件触发红线；表达合适性 = 教学形态匹配；拒答按任务类型。目标范围 = 单轮 RAG 增强问答。素材 = Agent 学习资料（教程 / 业界文章 / 自有笔记），大量是 2025-2026 最新前沿——素材带时间戳、概念在演化，这是评测自身会踩坑的土壤。

贯穿性警告（时间线污染）：写金标准/下结论时，别把"素材发布日期之后才成立的知识"（如 harness 后来成为统一话语）当成素材自身的前提。检查：每个前提问"素材发布那一刻，作者知道/认同吗"。

1 · 系统形态：四个关键决策

  1. 问答侧形态：固定检索 + 相关性门控的 workflow（骨架硬化：流程写死在代码、LLM 只在窄判断节点）；agentic RAG 归位为 ReAct 实例、受控排队。为什么：v1 的任务空间设计期可枚举，不需要一开始就把检索决策权交给模型（决策权留给真正需要它的场景）。
  2. 检索机制（核心交付）：点名单源/多源 → 每源宽候选（稠密检索取前 25）→ 相关度门控 → 注入预算（总约 3600 token，按证据组均分）取证据块集。三个设计要点：①覆盖模型——"取多少块"由问题类型决定（对比题每个点名源都必须有代表），不由排序位置决定；②证据组 = 每源宽候选里的高分块集合（组内多块、无单核心、无位置窗口）；③预算只是资源约束，不是充分性判据，顶住时输出"证据不足"而非静默砍。配套职责分层：结构覆盖（每组非空）由确定性规则断言，内容覆盖（答案证据是否真齐）交给判官/诊断层。
  3. 知识输入形态（每块的"文本 + 元数据"双层结构）：入库文本块 ≤450 token，由三层文本组成——①素材标题行（"来源：作者/平台 · 标题"，多文件源再拼文件级标题，如"项目自有笔记 › 0022 · 主动式验证…"；这是模糊指代"那篇/那本"的检索锚点）；②叶子节标题行（节标题往往是答案高密度区——自有笔记常把结论直接写进节标题，标题不参与检索 = 系统性漏检）；③正文。除文本外，每块还携带结构化元数据（payload）：source_id（素材标识）、document_id、section_path（节路径，引用定位与判官核对用）、knowledge_date / decay_class（时间维度）、seq（原文顺序）、tokens、kb_id / chunk_id。为什么元数据必要：点名检索的支持基础——用户点名某篇时，系统检测出素材标识，靠 source_id 做 payload 过滤、只在指定素材内检索；其余字段分别支撑引用定位、展示排序、判官证据核对与时间管理。
  4. 工具面形态：RAG 问答模式只向模型暴露与知识问答兼容的工具集，排除系统自带的临时笔记工具（note_add/note_get/note_search）。为什么：模型手里若同时有"检索注入"和"笔记工具"两条路，可能走工具路——而笔记工具指向另一套空库，其结果会覆盖已注入的检索资料。

2 · 构建路径：评测驱动的最小演进

  1. 最小基础先跑通：纯稠密向量 top-k + 门控 + 注入，先不叠 BM25 / rerank / 图 / agentic——把链路（入库 → 检索 → 注入 → 生成 → 判定）跑通、12 条用例首跑逐条审阅修复（Run#101-102）。
  2. 上稳定性基线（repeat20）：这是评测驱动的核心动作——单次 pass 会掩盖不稳；repeat20 暴露 cmp-001 15/20、a5-005 19/20（Run#103）。
  3. 失败 → 根因归类 → 类级修复：每次失败先归因到"哪一层"（输入侧 / 检索机制 / 生成 / 工具 / 金标准 / 判官），再决定修哪一层；修复必须类级（评测失败 = 不变式被违反，交付 = 机制改动 + 该类探针 + 全量回归）。本轮的归因样本：own-002 是输入侧（HTML 清洗删掉了文档一级标题，标题链断在"节标题不进检索"）；cmp-001 是检索机制（排序位置常量病 → 覆盖模型）；生成侧温度尾分支与判官口径是另一层。
  4. 技术叠加由评测证据驱动，且守成本现实：BM25 曾因 own-002 的 rank23 被误引入，量化后确认根因是输入侧 → 降级为实验对照（不为想象中的问题付复杂度）；本地 rerank 实现后被 CPU 成本否决（3 pairs/s）；RRF 融合排序在有 rerank 时冗余（候选并集直进 rerank）。每一条叠加/不叠加都能指到具体评测证据——各技术的初测与结论详表见下一节。
  5. 量化证伪优先于纯逻辑推演：机制与参数假设（如"本地稠密模型排序够用"、候选上限 C 与注入预算 B 取多少）用 12 条用例的证据定位表定界（把每条金标准的要点反查到它在检索里的实际排名），不用拍脑袋。

3 · 技术候选的初步检验：哪些值得叠、哪些先不叠

RAG 技术栈多而杂，逐个说明我们审视了什么、初测了什么、结论是什么、什么条件下会再评估。检验原则两条：①一次只动一个变量（机制与分数质量层分开验证，避免两个变量同时动无法归因）；②"蓝图里有 / 业界标配"不是引入理由——只有当评测证据表明"它解决的问题真实出现"且成本前提满足时才叠。

4 · 评测可信度：定义对、执行稳、用例不腐

系统靠评测驱动，所以评测自身必须有可信度——方向盘不能骗人。可信度由三件事撑起来：定义对（金标准不能错）、执行稳（判官不能时松时严）、用例不腐（用例集要持续有效）。

4.1 定义对：金标准是尺子的刻度，刻度刻错了量什么都错

  1. 时间线污染：跨文档对比用例的旧金标准把"两家对 harness 的理解异同"当前提，而两文处于术语未收敛窗口期（Anthropic《How we contain Claude》通篇用 containment、不用 harness 这个词）——把"素材发布之后才成立的知识"写成了文本前提，模型正确指出"概念不同层"反被判 fail。修复 = 演进感知金标准（先厘清概念状态，再做可确证对比）。
  2. 用户完整性导向：锋利版阈值"4+4 vs 全覆盖"是工程视角的错误二分（数主题）；用户要的是"完整可信、不误判、遗漏透明"，不要目录复述。原则：产品/用户视角第一性，工程权衡刻意降权（入 AGENTS.md）。

4.2 执行稳：判官是读尺子的人，不能时松时严

自由文本 LLM 判官做"逐主题识别 + 综合裁决"二合一时，长清单金标准下同一份缺失 20 次里 15 次判 pass、5 次判 fail（pass 时把"渐进式披露"当成 AGENTS.md 地图的覆盖、把"三种隔离模式"混作"三类风险三组件"），温度 0 也压不住。过渡修法 = 判官必须输出结构化核对表 + 从严覆盖判定；方向 = 判官只做逐主题识别（covered / not_covered / equivocal + 支撑原句），综合裁决交给确定性规则聚合（下迭代待办）。

4.3 用例不腐：用例集要持续有效，且组织上有分工

三层分工：基础用例集（冒烟，验证跑通）→ 基准用例集（主战场：锋利、守不变式，驱动系统进化）→ 探针池（边界探索，验证后升基准）。12 条全稳后第一条基准用例（rag-cmp-002，O2 与 A5 的全景主题对比）已开张——目前是红的，等着检索升级来翻绿。

防污染：公开素材会被模型训练内化，用例随时间失效。当前模型未内化 2026 年后素材 → 现在测的是"检索补知识缺口"的纯价值（零污染窗口），但窗口会随模型更新关闭；把污染监控制度化 = faithfulness 抽样审计（低吻合 + 答案正确 = 用例被内化污染的强信号）+ 0024 的污染半衰期管理（快速衰减素材到期进 review / 换锚）。

阶段 B · 问答侧（2026-09-02）

  1. 沛东提出两种解法的理解：①先查 chunk（可融合多种方式）+ 预处理（如重排序），再与用户 query 一起给 LLM；②Agentic RAG——检索封装为工具、模型自主决策、天然支持多轮查询。请 Codex 确认理解 + 补充其他方式。

  3. 中间态（"还有其他方式"的核心）：路由型（Adaptive-RAG 按复杂度路由 / query router 按类型路由）、自适应检索（Self-RAG 判要不要检索 + 批判 chunk；FLARE 生成中按需检索）、纠正式（CRAG 检索后评估、差则换路）；Modular RAG = 工程上组件可组合。共同点：LLM 有部分决策权，但没有完整工具循环。
  4. 正交轴（索引范式）：GraphRAG（图+社区摘要，擅长聚合类/全局类问题）；长上下文 / context engineering（RAG 的替代思路，大窗口下越来越可行，可作为 v1 兜底）；我们已定的 Qdrant+BM25 混合属于检索侧组件组合，与问答侧选型正交。

  7. 待定方向（下一轮）：检索触发/注入方式、回答形态与引用格式、判官检索信号、UI 引用展示、多路检索/rerank。
  8. 生产形态观察（Voltage Park 引语解读，2026-09-02）："生产里大多数 agentic RAG 系统，最后长得不像一个聪明的提示词包着向量库，而像一个管线"——开放循环被延迟 / 成本 / 可靠性 / 可观测性四力压回"管线 + 少量有界决策点"的形态；纯开放的 agent 只是 demo 里的理想形态。
  9. 【决策点】骨架硬化原则（沛东洞察，2026-09-02）：既然生产 agentic RAG 的骨架是确定的，就没有必要用提示词规定模型行为——应把骨架硬化进 Agent 代码，LLM 只在某些节点做判断；否则落入"指令遵循性到不了 100%"的陷阱。Codex 精确化：硬化 ≠ 不用提示词，LLM 判断节点要窄输出 + schema 约束 + 兜底分支；这是 0022 护栏/harness 原则（确定性兜底不确定性）在 RAG 编排上的延伸。
  10. 泛化（沛东，2026-09-02）：这种方式本质是"支持 LLM 节点的工作流"；只有当任务复杂、天然需要多次迭代摸索、或后序检索依赖前序检索结果时，才应把决策权完全交给 LLM——而那时已接近 ReAct，检索只是其中一个工具。问题因此归位为通用选型：何时用 ReAct，何时用支持 LLM 节点的工作流。
  11. 查证（Codex，2026-09-02）：泛化不是自嗨——Anthropic《Building Effective Agents》的 Workflow/Agent 二分（workflow = 预定义代码路径编排 LLM 步骤，适合确定性可分解任务；agent = 模型动态主导过程，适合路径无法硬编码的开放任务），判据原话精神即"任务歧义度允许预映射决策树 → workflow"；RAG 2025 taxonomy 直接按 agentic depth 分类；多篇文献明示"Agentic RAG 与 ReAct 高度一致"。但需带三个标注：①Agent 是家族不是单点（Self-RAG 反射 token / Plan-and-Execute / multi-agent / Reflexion 均非 ReAct），"agentic RAG ≈ ReAct"是工程近似；②二分在实践里本来就融合（OpenAI SDK 支持代码编排与策略驱动混合；LangChain：生产大多是组合；Anthropic：agent 的工具可以是 workflow），更准确是"骨架硬化程度"旋钮；③该框架只回答"谁决定检索编排"，检索质量是独立轴（CRAG 纠错式），可被 workflow 的验证/纠错节点吸收但框架本身未显式包含。
  12. 【决策点】v1 落点（2026-09-02）：12 用例任务空间设计期可枚举 → workflow（支持 LLM 节点）+ 相关性门控；agentic（ReAct + 检索工具）作为受控 A/B 排队——评测链路稳定后，用同一批用例 + 补多跳用例做对比，有质量缺口再切换或混合。

经验教训档案（24 条完整案例，折叠）

展开：实践与经验教训（每条一个可复用的坑与解法）
  1. 本地 embedding 选型三约束：①fastembed 0.8 已移除 BGE-M3，计划会落空——选型前先查当前版本支持的模型清单；②"本地"不等于效果差，决定质量的是模型选型（中英混合素材 → multilingual-e5-large）；③字符数 ≠ token 数（1766 字符的 ASCII 代码块 = 447 tokens），切块与界面要显示真实 token，不能按字符猜。
  2. Qdrant 本地模式单进程锁：两个进程共享同一数据目录直接冲突（8000/8899 双实例翻车现场）；解法 = 同路径客户端单例（进程内）+ 懒加载（不用 KB 的流程不占锁）+ 测试独立目录（conftest 设 ASH_QDRANT_PATH）。嵌入式存储类选型的通用运维坑。
  3. 向量库 scroll ≠ 入库序：scroll 返回内部存储序，业务顺序（chunk 在原文中的先后）要显式写入 payload（seq），展示按它排序，不能依赖存储序。
  4. 入库文件规则放代码而非 MANIFEST：data/ 整体 gitignore，规则放代码（ingest_rules.py）才能随提交沉淀；MANIFEST 管"有什么素材"，代码管"哪些文件进库"。
  5. 全量入库按钮要按阶段放开：适配器未做对前，全量会把不适配素材（PDF / 教程目录 / 老编码 HTML）拉进来 → 先做对格式适配，再放开范围；v1 首轮切片本就是 O2/A5/自有。
