在 0003 需求定义基础上，把成功指标落地为可量化的验收标准，并确定 golden set 的取材来源与首批用例结构。本记录与 0003 共同构成阶段 0 的完成物。

测量原则：v1 全部指标用 golden set + 人工标注 + 脚本统计测量；LLM-as-judge 留到阶段 6。所有数值为初始建议值，首轮基线跑完后校准再冻结。

三、golden set 取材与首批用例结构

总结构：建议首批 120 条。

类别数量取材来源验收维度
多轮对话20日常对话 + 学习/工作场景自造一致性、指代、记忆
知识库问答30《三国演义》txt（详见下）正确率、引用、拒答
工具调用40计算/日期时间/笔记场景自造选择、schema、执行、回填
边界与拒答20自造（未覆盖、模糊、诱导性问题）兜底行为
综合场景10组合场景（对话中同时用知识库和工具）端到端

知识库取材：《三国演义》txt（用户指定）

选用理由：事实可验证（公开可查，标注无争议）；内容复杂（120 回、数百人物、跨章节事件线）；公版无版权问题；半文言长文本能检验分块与检索质量。

关键设计点：三国演义知名度高，模型可能凭参数记忆直接答对而不检索知识库——因此用例必须包含“只有检索才能答对”的类型，且引用校验为硬指标。30 条知识库用例细分：

子类型数量示例方向验证目的
直接命中8人名、字号、事件、地点等单回明确事实基础检索 + 回答正确
跨章综合6人物完整事迹线、某集团成员构成多文档综合、证据组织
细节与原文引用6某句原话出自哪一回、生僻小人物确认真的检索了 + 引用精度
关系与推理5人物关系、事件因果基于检索到的证据推理
陷阱与拒答5书中不存在的内容、与其他演义易混淆点兜底行为、不硬答

素材管理：固定一份干净可靠的 txt 来源（建议维基文库版或用户手头版本），记录版本/来源/哈希作为标注依据；预处理按 120 回切分，回目作为检索锚点。txt 文件在进入实现阶段时落到项目内。

范围控制顺带验证：边界用例加入“三国以外的问题”（如问红楼梦），验证助手不会拿三国知识库硬答，而是走通用模式或明确拒答。

四、与豆包/千问的对照测试方式

同一用例集分别跑本助手与豆包/千问，按能力维度记录差距，产出“能力差距报告”：达标项、差距项、差距原因归类（模型底座 / 检索 / 工具 / 编排）。v1 阶段不设“必须追平”的门槛——工程上可优化的是检索、工具、编排层，模型底座差距属于记录项而非达标项。

五、校准机制

首轮基线跑完后：指标远高于门槛 → 用例太简单，补充更难用例；远低于门槛 → 判断是能力未达标还是门槛不合理，分析后调整。校准后冻结，作为后续阶段的回归基准。
