产品定义

一句话功能定义（用户原话）：使用自有知识库、自有工具集增强的通用 AI 助手。

讨论提炼建议稿：在豆包/千问级别的通用对话能力之上，让用户自己定义助手能“看到什么知识、调用什么工具”的 AI 助手。

三大支柱：通用底座（对话与常用能力）、自有知识库（用户文档形成个性化知识源）、自有工具集（用户自定义工具集合）。

核心命题（已确认）：范围控制

产品灵魂是解决通用助手“不易圈定优先使用的知识库范围、工具范围”的痛点，提炼为九个字：

  • 看得见：用户随时能看到当前启用了哪些知识库、哪些工具
  • 控得住：能启停、调优先级，甚至按会话切换范围
  • 说得清：回答引用知识库来源，展示工具调用过程

定位说明：知识库 + 工具组合在 Coze/Dify 等产品中已是标配，本项目不追求商业差异化，而是将范围控制作为设计透镜，使每个设计点可映射到学习路线图中的知识模块。

目标用户与部署（已确认）

  • 先服务个人用户：单用户、本地优先部署
  • 多用户、云端、账号体系后置，架构上预留扩展接口

核心场景与最小闭环

核心场景：用户上传文档形成个人知识库，与助手对话获取带引用的回答；用户通过表单注册工具，在对话中触发工具调用并看到调用过程。

最小闭环 v1：多轮对话 + 知识库问答（带引用）+ 2–3 个内置工具 + 工具表单注册（L2）+ 管理界面。

v1 功能范围（已确认）

v1 包含

  • 多轮对话（上下文记忆）
  • 流式输出
  • 知识库问答（带引用）
  • 工具调用（先 2–3 个内置工具：计算、日期/时间、笔记）
  • 管理界面：文档上传与管理、知识库启停与优先级、工具注册（L2）与启停、对话日志

v1 明确不做（后置）

  • 多模态输入、图像生成、语音
  • 实时网页检索（依赖外部搜索 API）
  • 复杂多步工作流

取舍依据：不支撑前几阶段要验证的知识点，且工程量不可控。

工具自定义深度（已确认）

MVP 做到 L2 表单注册：名称、描述、参数 schema、执行方式（本地命令或 HTTP）。

  • L1 内置工具，用户只能启停——作为基础层
  • L2 表单注册——MVP 目标，足够练习 function calling 与 harness 工程
  • L3 上传代码脚本——后置到阶段 4，配合代码沙箱能力

范围控制机制（需求草案）

  • 全局设置：知识库/工具的默认启停与优先级
  • 会话级模式：通用模式 / 知识库优先 / 工具增强，每会话可选
  • 可解释性：回答展示引用来源，工具调用过程在对话流中可见
  • 兜底策略：知识库未覆盖的问题不硬答——可配置为拒答或退化为通用回答（阶段 2 核心验证点）

成功指标草案

  • 能力达标：每个 v1 能力对应一组基准用例（多轮一致性、引用正确率、工具调用成功率），与豆包/千问做对照测试
  • 范围控制：知识库命中率、工具误用率（该用没用/不该用乱用）、拒答准确性
  • 产品指标：v1 阶段以任务完成率为主

与六阶段路线图的映射

阶段产品能力落点
1通用对话 + 工具调用（内置工具）
2知识库问答 + 引用 + 兜底策略验证
3记忆用户偏好（默认知识库优先级）+ 多步任务规划
4工具执行沙箱、观测台、人工介入
5检索 / 工具 / 回答多 Agent 分工
6指标回归与产品化（任务完成率等）

  2. 定义 golden set 的取材来源与首批用例
  3. 进入架构设计讨论（技术栈、系统结构）
