这篇笔记回答什么问题

用 LangChain / LangGraph 这类框架时，最大的困惑往往是：循环到底在哪？框架把"思考 → 行动 → 观察"藏在 AgentExecutor、StateGraph、Node/Edge 这些抽象后面，初学者读框架源码很容易被概念淹没。本笔记以本项目手写的极简实现为标本，直接剖开封装，展示一个最典型的 LLM 应用——带自定义工具的单轮对话——的完整全貌。

目标读者：对 Agent 已有认知、但缺乏实践经验的架构师或高级研发；对技术本身有较高兴趣、不满足于"会用框架"的初级工程师同样适合。

与 0008 的区别：0008 是"按什么顺序读代码"的路线图；本篇是"整个应用长什么样、为什么长这样、框架在封装什么"的静态解剖。

一句话总结：这是一台"裸机 Agent"——一个 for 循环 + 一张消息列表 + 一个工具注册表。看懂它，LangGraph 就只是一层皮。

一次请求的完整调用链

用户在界面发一条消息，后端发生的事（忽略前端渲染细节）：

用户消息
  → POST /api/chat（chat.py 校验请求体）
  → 从 app.state 取依赖、构建 LLM 客户端（没配 Key 则发 error 事件）
  → 返回 StreamingResponse(gen())：返回的不是结果，而是一个"生成器"
  → gen() 内部进入 run_agent_turn()：Agent 核心循环
      ├─ 组装上下文（system + history + 当前消息）
      ├─ 流式调用 llm.stream()，文本增量 yield 给 SSE
      ├─ 若模型要调用工具 → 执行 → 结果回填上下文 → 再来一轮
      └─ 模型不再调用工具（或达到 4 轮上限）→ 结束
  → gen() 把 trace 步骤与文本增量包装成 SSE 事件推给前端
  → 前端解析 event: start / trace / delta / error / done

注意两个"返回的是生成器"的层次：chat() 返回 StreamingResponse（内部持有 gen()），run_agent_turn() 本身是异步生成器（async for 消费）。流式是"拉模式"——下游每取一段，上游才继续生产，这一条链一直通到 DeepSeek 的 TCP 连接。

五个文件，五层职责

整个 Agent 核心只有五个文件，每个文件只回答一个问题。这就是"最小分工"的样板：

文件职责（回答什么问题）关键接口
agent/loop.py 循环本身：什么时候调模型、什么时候执行工具、什么时候结束 run_agent_turn()（异步生成器）
agent/context.py 模型"能看到什么"：系统提示 + 历史 + 当前消息的组装 assemble() / system_prompt()
agent/llm.py "调用大模型"这件事：协议、流式解析、消息模型、事件模型 LLMClient 接口：chat() / stream()
agent/trace.py 可观测性：每步发生了什么，按时间顺序记录并回调通知 Trace.step()（观察者模式）
tools/（registry + executor + builtin） 工具的声明、注册与执行：模型看到 schema，代码执行 handler ToolRegistry.schemas()/execute() → ToolExecutor

依赖方向是单向的：API 层（chat.py）→ loop →（llm / context / trace / tools）。loop 不认识 HTTP、不认识前端、不认识存储，它只操作"消息列表 + 工具执行器 + 可选的记录器"。这是它能在评测 runner 里被进程内直连复用的原因。

核心循环：一轮的解剖

run_agent_turn() 的骨架（语义等价，非逐字）：

messages = assemble(mode, history, user_message)
for round_no in range(1, _MAX_TOOL_ROUNDS + 1):   # 上限 4 轮
    tool_events = []
    async for event in llm.stream(messages, tools=schemas):
        # text → yield 给前端（打字机效果）
        # tool_call → 先攒着，流结束后统一处理
        # usage → 累计 token；raw → 只进 trace
    if not tool_events:            # 模型决定不调工具 → 本轮就是最终回答
        return
    # —— 行动 + 观察 ——
    messages.append(assistant(tool_calls=合并后的原始调用))   # 协议回显
    for call in all_calls:                                    # 支持并行
        result = await tools.execute(call.name, call.arguments)
        messages.append(tool(content=result, tool_call_id=call.id))
    # 回到循环顶部，模型带着"自己调过什么 + 工具返回什么"继续思考

要点拆解：

  • 流式事件是唯一的"语言"：llm.stream() 把零散的 SSE chunk 统一成五种事件——raw（原始 chunk）、text（文本增量）、tool_call（工具调用请求）、usage（token 用量）、done（本轮结束）。上层只认识这五种，不认识 SSE 格式。
  • 工具调用要"攒"到流结束：流式响应里一个 tool_calls 会被拆成很多片（名字可能两片、参数 JSON 可能十几片），必须等流结束按 index 拼出完整对象才能执行。
  • 终止只有两种原因：no_tool_call（模型不再调用工具，正常结束）或 max_rounds（达到 4 轮上限，静默结束）。没有"强制完成动作"——这由模型的"不再调工具"隐式表达。
  • 并行工具是天然支持的：一次响应可带多个 tool_calls，循环逐个执行、每条各回填一条 tool 消息。
  • 工具失败不崩整个 turn：异常被捕获，错误文本作为观察回填，让模型自己解释或换路。

三个"协议硬规则"

手写 function calling 时，OpenAI 兼容协议有三个必须遵守的硬性规则，本项目的踩坑记录都在 0011：

  1. 回显必须用合并后的完整结构：流式原始片段不能原样回传（缺 name/id/type 会 400）。llm.py 负责合并成 {"id", "type", "function": {"name", "arguments"}}。
  2. tool 消息必须带 tool_call_id：每条 role="tool" 的消息通过它关联到对应调用，否则 400。
  3. assistant 回显与 tool 消息必须一一对应：回显侧如果只取第一个事件的 tool_calls，而执行侧遍历了全部事件，一旦某 LLM 实现产出多个 tool_call 事件就会破坏配对（本次会话已修复：现在合并全部事件的 raw_tool_calls）。

这三条是"框架替你做的事情"的最小集合——手写一次，就知道框架的 add_tool / 消息规范化在背后帮你挡了什么。

剖开 LangGraph：映射表

用 LangGraph 写同样的东西，代码结构是"定义状态 → 定义节点 → 定义边 → 编译"。把两者并排看：

LangGraph 概念本项目对应说明
StateGraph 的 state messages 列表（loop 内局部变量） 状态就是上下文；LangGraph 把它显式化并加了 reducer 规则
llm_call 节点 循环内一次 llm.stream(messages, tools) 节点 = 一次完整的 LLM 调用（含流式消费）
tools 节点 for call in all_calls: await tools.execute(...) 执行全部并行调用并回填结果
条件边（conditional edge） if not tool_events or tools is None: return 决定"继续循环"还是"结束"
节点写回 state messages.append(assistant/tool) LangGraph 用 reducer（如 add_messages）做同样的追加
checkpointer / 持久化 （无） LangGraph 额外提供断点续跑、人工介入、时间旅行

所以 LangGraph 并没有发明新机制，它把这段循环 显式化为可检查的图 + 状态机，再叠上持久化与调度能力。看懂了本项目的循环，LangGraph 文档里的 create_react_agent 就只是一层熟悉的外衣。

LangChain 侧则是更宽的"工具带"：消息抽象、memory、callback/追踪、retriever 包装、output parser（文本协议时代的遗留物）、海量第三方集成。这些是生态价值，不是循环本质。

手写 vs 框架：诚实的取舍

  • 手写值得的理由：零依赖、完全可控、调试路径最短（trace 自己写，每个字节都认识）；是理解 Agent 本质不可替代的"裸机训练"。
  • 框架值得的理由：边界情况（重试、并发、持久化、断点、观测）被大量团队踩过坑；生态接入即用；代码量省一个数量级。
  • 判断标准：循环一旦超过"一个 loop + 几张工具"（需要多 Agent、人工审批、复杂状态流转），框架收益开始显现；但框架的抽象也会把"为什么"藏起来——这正是本笔记存在的原因。

延伸思考

  • 与 ReAct 的关系：本循环是"ReAct 的骨架 + 原生 function calling 的血肉"。行动层用结构化 tool_calls 替代文本解析是合理进步；但"思考"被折叠进模型内部——reasoning_content 只适合当观测数据，不宜直接当系统可控的状态（专题讨论待后续记录）。
  • 背压传导：流式是拉模式，慢客户端 → 上游停拉 → TCP 反压 → DeepSeek 超时掐断。整条链路无需任何缓存层就能天然限速，但也意味着用户侧网络问题会中断生成。
  • 下一步自然演化：历史接通（把多轮消息传进 history）→ 上下文预算 → 记忆/检索 → 显式规划。每一步都在这同一个循环上加，而不是推翻它。
