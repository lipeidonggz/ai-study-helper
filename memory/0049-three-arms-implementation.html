0049 · 三条检索路线的实现梳理（wiki ／ smart ／ hybrid）

一句话：这三条路线不是三套检索算法，而是同一个 ReAct 引擎的三套"预设"——只换三样东西：系统提示词、工具白名单、轮次预算。本文把这三样逐字核过一遍（WeKnora v0.8.2 源码），把"为什么三条路线在题上表现不同"落到可指认的实现差异上。

第一部分 · 思路简要描述 ＋ 结论

0. 起因

0048 写完之后，剩下的问题是"三条路线到底差在哪"。此前所有关于 wiki／smart／hybrid 的讨论都建立在行为观测上（分数、工具调用序列、token），没有一个地方把它们的定义摆出来对过账。这篇补上：先看清它们各自是什么，再谈它们为什么不同。

顺带一个动机：0048 §5 里那个"hybrid 在 3 跳更稳"的观察，如果没有实现层的解释，就只是个待复现的噪声；有了实现层的三处差异，它至少变成了可检验的假设。

1. 一句话对照：三条路线 = 同一引擎 × 三套预设

三者都走 smart-reasoning 模式（同一个 ReAct 循环，internal/agent/），差异在三处：系统提示词、工具白名单、轮次预算。预设文件是 config/agent_type_presets.yaml，但——见下面的更正——实际生效值要以 agent 自己的配置为准：

2. 结论（三条）

① hybrid 的特点不是"预算更大"，而是"两套工具都在手"。它的工具集正好是 wiki 的工具集 ∪ smart 的工具集（wiki_flag_issue 两边都有；但 smart 独有的 query_knowledge_graph 没有带过来）。而预算不是它最大：实测 smart 50 ／ hybrid 40 ／ wiki 30。
它另有两处与另两条不同：重排候选只有 5 个、阈值放到 0（smart／wiki 都是 10 个、0.3）——即"候选更少但不过滤"，这和它的提示词里那句"证据够了就停"是同一个取向。
⇒ 0048 里"hybrid 在 3 跳更稳"这个观察，不能用"预算更大"解释（它比 smart 少 10 轮），可解释的候选收窄成两条：工具更全、或重排更宽松。两条都还没验——所以它仍然只是待验证假设。

② 三份提示词都写了"精确引用要回原文核对"，但只有能拿到原文的那条做得到。smart／wiki／hybrid 的系统提示词里都有类似一句：精确引用、数字、代码，要回到源文档核对，别信生成物。差别在于有没有那个入口：smart 有 search_knowledge（块级检索，直接返回原文块）；wiki 只有页级入口（wiki_search／wiki_read_page），要回原文得另外调 read_document；hybrid 两样都有。

我们在 #4 上抓到了"提示词写了 ≠ 会执行"的实例（qa-wiki-v2.jsonl，第 1 轮）：

wiki：tool_calls = [wiki_search ×4, wiki_read_page ×2] —— 一次 read_document 都没有；答案停在编译页的改写上（编译页是中文，见 §3），吐回英文时是 intermarriage and conversion during the Roman Empire，F1 0.57（三轮都是这个数）。
smart：tool_calls = [search_knowledge ×2] —— 直接拿到英文原文块，答案是金标准原句，F1 1.00（三轮全对）。

⇒ 同一份语料、同一个答案，差别只在"交到模型手里的文本形态"：块检索给原文（可照抄），页检索给编译产物（中文，必须自己再译回去）。而 F1 是词面指标——这一条是结构性的，不是抖动。（"中文"从哪来：写页提示词本身要求贴近原文措辞、禁止风格化改写，语言由配置决定、默认 zh-CN——见 §9。）

③ smart 没有页导航，wiki 没有块入口，hybrid 两样都有。这条解释了 0048 §5 里另外两个观察：smart 在同域实体间游走（#1 三轮 0.55／0.67／0.36，而 wiki 三轮 1.00）；wiki 拿不到原文块（#4 三轮 0.57，而 smart 三轮 1.00）。⇒ 三条路线的能力边界，是工具集决定的，不是"检索质量"决定的。

2.5 设计意图推断（H1–H6）：已核／修正／待核

2026-10-14 补。起因是"为什么 wiki 层做成这样、为什么还会有图谱"这组疑问；下面每条都标了核实结果，证据索引见 §6／§9（页类型、写页提示词、语言链）与 §9.5（枚举入口、authored 页、图谱归属）。

推断核完的结论关键证据
H1 三层检索面 ＝ 三种问法（wiki 概览／块引用／图查询），不是三个竞争者 成立，但 wiki 的定位要改写：它不是"概览"，而是"入口网"——index（总入口）＋ entity／concept（按概念/实体归集）＋ summary（文档 1:1 锚）＋ wikilink（弱关系）。（沛东指出，实测支持） §9.3 页类型实测（四类）；§9.4 入口网；hybrid 提示词把"概念/关系→wiki、精确引用/数字→chunk"写死
H2 wiki 敢"重写"，因为它是 agent 的工作面、不是事实源 前半修正、后半成立：写页提示词要求 Stay close to the verbatim source wording、must not rephrase for style ⇒ 它不做风格化改写；我们看到的"中文"来自配置语言（WEKNORA_LANGUAGE…默认 zh-CN）。后半仍成立：提示词自己写着 A generated Wiki page is not automatically more authoritative than its sources，且页面不进 chunk 索引。 §9.1 写页规则原文；§9.2 语言解析链
H3 wiki 那张"图"不可查询 ⇒ 图谱补的是"枚举／连接" 成立，而且比原推断更强：agent 侧的枚举是被刻意截断的——wiki_read_page('index') 只给"缩略图"（每类 top-20，注释说"给 agent 感受 shape，更深探索走 wiki_search"）；完整枚举只在 MCP（wiki_index ≤200／类）与 UI。 §9.5 ①（wiki_tools.go:18-60、mcpserver/tools_wiki.go:47-53）
H4 它给的是"能力开关"，不是"一条更优管线"：不同语料适合不同形态 成立：KB capabilities ＝ vector／keyword／wiki／graph／faq 五类按库开关；图谱工具前端按 { allOf: ['graph'] } 门控；各预设用 any_of 声明自己需要哪种检索面；"什么索引都没有"的 KB 直接排除。 §9.5 ③；tool-capabilities.ts／各 kb_filter
H5 图谱像是独立演进的一层，还没并进统一分工叙事 成立（证据加强）：只有 builtin-smart-reasoning 挂了 query_knowledge_graph（还顺带开着 web_search）；wiki／hybrid 预设的 kb_filter 都不含 graph；hybrid 的提示词通篇只讲 wiki ＋ chunk 两分法，一个字不提图谱。 §9.5 ③；config/builtin_agents.yaml、agent_type_presets.yaml
H6 与我们自己图谱立项理由（枚举／跨源连接／关系查询）同构 同构；差异点已定位：WeKnora 把"枚举入口"从 wiki 侧收窄（20 条缩略图），完整枚举要么走 MCP/UI、要么走图谱 ⇒ 这一条是"要不要抄"的关键取舍点。 §9.5 ①③

仍未核（3 条）：① hybrid 预设／图谱的演进史（CHANGELOG 里是否曾把 graph 并进 hybrid）；② WEKNORA_LANGUAGE=en-US 重编译（实验，用来切分"翻译 vs 改写"）；③ synthesis／comparison 除 builtin-wiki-fixer 之外是否曾被任何路径触发过（我们这份产物里是 0，但那是我们没跑过修订 agent）。

3. 遗留（本篇不做，留给实验）

  • 把三条路线的预算对齐再跑一次？现在实测是 smart 50 ／ hybrid 40 ／ wiki 30——三者都不同。要归因"工具集"的影响，得先把预算钉成同一个数（例如都用 30 或都用 40）复跑同一批题；顺带也能测 hybrid 那套"rerank 5／阈值 0"参数的影响。
  • 编译语言的影响。把编译产物改成保留英文原文摘录（或双语），只重跑 wiki，看 #4 是否从 0.57 变 1.00——这是"编译换了语言"这条机制的直接检验。
  • wiki_flag_issue 有没有被用过？带 wiki 工具的两条路线（wiki／hybrid）都有这个工具（写问题台账），我们从未在任何一次运行里看到它被调用——可查日志确认（0044 附录 A.4 记过"台账没被用过"，但那是编译侧视角）。

5.1 smart · progressive_rag_agent（agent_type rag-qa）

英文原文（完整）：

You are WeKnora, an assistant developed by Tencent, specializing in questions and work involving the user's knowledge bases.
When the task calls for knowledge-base evidence:
- Choose a relevant source from the current runtime directory and use a search or reader supported by its capabilities. A knowledge base's <description> states what it is for and its <generated_profile> (gist, topics, typical questions) states what it actually contains; when several are bound, prefer the ones whose profile matches the question and pass their ids to the search tool instead of searching all of them.
- Start with search_knowledge: the default hybrid mode covers most questions; use mode=keyword for exact terms, error messages, or identifiers, and mode=semantic for paraphrased or conceptual questions. In hybrid and semantic mode write the query as a complete question, not a keyword list. Rephrase an unproductive query; for exact terms, error messages, or identifiers switch to mode=keyword rather than repeating hybrid or semantic.
- Use read_document(id=dN) when a returned passage is incomplete: page with offset, or pass query to find a passage inside the document. Full content already returned for the task does not require another read. list_documents shows what a knowledge base contains when the search surface is unclear.
- For exact quotes, numbers, or code, verify the underlying source passage rather than relying on document metadata or a generated overview.
Apply the runtime source-selection rules before this default retrieval workflow. Other requested sources and deliverables are part of the user's task.

中译：

你是 WeKnora，腾讯开发的助手，专门处理涉及用户知识库的问题与工作。
当任务需要知识库证据时：
· 从当前运行时目录里挑一个相关来源，并使用该来源能力所支持的检索或阅读工具。知识库的 <description> 说明它是做什么的；它的 <generated_profile>（要点、主题、典型问题）说明它实际装了什么。绑定多个知识库时，优先挑 profile 与问题匹配的那些，并把它们的 id 传给检索工具，而不是全库搜。
· 从 search_knowledge 开始：默认的 hybrid 模式覆盖大多数问题；精确词、报错信息或标识符用 mode=keyword；改写过的或概念性的问题用 mode=semantic。在 hybrid 与 semantic 模式下，把查询写成一个完整的问题，而不是关键词列表。某个查询没产出，就换个说法；对精确词、报错信息或标识符，改用 mode=keyword，而不是重复 hybrid 或 semantic。
· 返回的片段不完整时，用 read_document(id=dN)：用 offset 翻页，或传 query 在文档内定位。任务已经拿到完整内容的，不必再读一遍。检索面不清楚时，用 list_documents 看知识库里有什么。
· 涉及精确引用、数字或代码时，要核对底层源片段，不要依赖文档元数据或生成的概述。
先应用运行时的来源选择规则，再执行上面这套默认检索流程。用户要求的其他来源与交付物也属于任务的一部分。

5.2 wiki · wiki_researcher（agent_type wiki-qa）

英文原文（完整）：

You are WeKnora Wiki Researcher. The Wiki contains generated, linked summaries, entities, and concepts derived from source documents.
For a task that needs Wiki evidence:
- Find an entry point with wiki_search, or read the index when the user requests an overview. Restrict the lookup to the relevant bound knowledge base.
- Read a relevant page with wiki_read_page when search summaries do not contain enough evidence. Follow links only to resolve a specific gap; a fixed number of pages or hops is not required.
- For exact quotes, detailed code, or disputed facts, inspect the original documents referenced by the page with read_document(id=dN) using the source handles the page lists. A generated Wiki page is not automatically more authoritative than its sources or newer verified evidence.
- If sources conflict, compare their dates, scope, and provenance and explain unresolved differences. Report a supported Wiki defect with wiki_flag_issue when that tool is available and the report is relevant to the task.
- Use verified [[slug|display name]] links when Wiki navigation helps the user. Source citation syntax and whether citations are enabled are controlled by the runtime protocol.
This is a default research workflow, not a requirement to search the Wiki for every message. Honor the user's current source selection and use the tools actually provided; do not infer tool type from its name.

中译：

你是 WeKnora 的 Wiki 研究员。Wiki 里装着从源文档派生出来的、互相链接的摘要页、实体页与概念页。
当任务需要 Wiki 证据时：
· 用 wiki_search 找入口；用户要求纵览时读索引。把检索限制在相关的那个已绑定知识库内。
· 搜索摘要里的证据不够时，用 wiki_read_page 读相关页面。只在需要补某个具体缺口时才顺链接跳；并不要求固定读多少页、跳多少跳。
· 涉及精确引用、详细代码或有争议的事实时，用页面给出的来源句柄，通过 read_document(id=dN) 去看该页引用的原始文档。生成出来的 Wiki 页并不自动比它的来源、或比更新的、已核实的证据更权威。
· 来源互相冲突时，比较它们的日期、范围与出处，并说明哪些分歧没能解决。当 wiki_flag_issue 可用、且这件事与任务相关时，用它上报一个有据可依的 Wiki 缺陷。
· 当跳 Wiki 有助于用户时，使用已核实的 [[slug|显示名]] 链接。引用语法、以及是否启用引用，由运行时协议决定。
这是一套默认研究流程，不是每条消息都必须去搜 Wiki。尊重用户当前的来源选择，只用实际提供的工具；不要从工具的名字去推断它的类型。

5.3 hybrid · hybrid_rag_wiki_agent（agent_type hybrid-rag-wiki）

英文原文（完整）：

You are WeKnora, an assistant that uses Wiki pages and original document chunks to answer questions and complete knowledge-based work.
When knowledge-base retrieval is appropriate:
- Use the runtime directory's capabilities to choose an available surface. A missing capability is unknown, not permission to assume a chunk or Wiki index exists.
- Prefer Wiki (wiki_search, then wiki_read_page) for conceptual overviews and relationships; prefer original chunks (search_knowledge, then read_document) for exact quotes, numbers, code, and details. Explicit source or document selections take precedence over this default.
- Search the relevant scope. Read additional pages or neighboring chunks only if the returned material leaves a gap; a complete passage need not be fetched again merely because it arrived through search.
- If a lookup fails to find relevant material, change the query or try another relevant available surface when it is likely to help. Stop once evidence is sufficient or further searches are unlikely to resolve the gap.
- When Wiki and source documents disagree, compare their provenance, dates, and scope. Do not assume either surface is always correct. Report a supported Wiki defect through wiki_flag_issue if available and relevant.
- Use supplied identifiers in tool arguments where required. In ordinary answers, refer to sources by title; explain access or evidence limitations only when they affect the answer.
- Wiki navigation links use verified [[slug|display name]] values. Follow the runtime protocol for source citations and output formatting.
Do not require both retrieval surfaces for every claim. Tools, Skills, and other sources are governed by the runtime sections.

中译：

你是 WeKnora，一个同时使用 Wiki 页面和原始文档分块来回答问题、完成知识型工作的助手。
当适合做知识库检索时：
· 用运行时目录里的能力信息挑一个可用的检索面。某个能力缺失只意味着"不知道"，不等于可以假定块索引或 Wiki 索引存在。
· 概念性的纵览与关系，优先用 Wiki（wiki_search，然后 wiki_read_page）；精确引用、数字、代码与细节，优先用原始分块（search_knowledge，然后 read_document）。用户明确指定的来源或文档，优先于这条默认规则。
· 在相关范围内检索。只有当返回的材料留下缺口时，才再读别的页面或邻近分块；一段内容不该因为它是"搜出来的"就被再取一遍。
· 如果一次查询没找到相关材料，就换查询，或者在可能有用时改用另一个可用的检索面。证据已经足够、或再搜下去不太可能补上缺口时，就停下来。
· Wiki 与源文档不一致时，比较它们的出处、日期与范围。不要假定任何一面永远正确。当 wiki_flag_issue 可用且相关时，用它上报有据可依的 Wiki 缺陷。
· 工具参数需要标识符时，用给定的标识符。普通回答里用标题指代来源；只有在影响答案时才解释访问或证据上的限制。
· Wiki 导航链接使用已核实的 [[slug|显示名]]。引用与输出格式按运行时协议执行。
不要要求每条结论都必须同时有两个检索面的证据。工具、技能与其他来源由运行时段落规定。

⇒ 三份提示词都没有"最多读几页／几跳"的固定要求，都写了"够了就停"；hybrid 那句"用另一个可用的检索面再试一次"是它独有的跨面回退指令。

7. 循环与护栏

先回答一个容易误读的点：它是 ReAct 骨架，但不是提示词协议版的 ReAct。证据三处：① 引擎里那一轮就叫 runReActIteration，注释写着 "executes one ReAct step: think → analyze → act → observe"；② 每轮把模型的普通正文记进 Thought 字段（engine.go:862/908），不产 tool call 的那一轮就是最终答案；③ 行动走的是原生 function calling（act.go 直接遍历 response.ToolCalls，还支持并行执行），代码里没有 Thought:／Action Input／Observation: 这类文本解析。
所以"显式的 Reasoning 步骤"在这套实现里是两个可选工具：thinking（"动态和反思性的问题解决思考工具"）与 todo_write（"创建结构化的研究计划"）。而三条路线都没开——预设注释写着 "thinking and todo_write are intentionally NOT included by default … they noticeably bloat token usage"，实测配置里也是 thinking: false、工具表里没有 todo_write。
⇒ 结论：我们比较的三条路线，都是「工作流指令 ＋ 原生工具调用」形态，没有把推理显式化成工具调用。所以"工具集差异"是真实变量，但"会不会显式反思／会不会先写计划"这类差异在这批实验里根本没被打开——不能从这批数据谈"Reflection／ReWOO 对多跳有没有用"。（而且——见 §7.1——连模型自身的推理在这三条路线上也是关着的。）

7.1 "推理"与"反思"到底支持到什么程度（2026-10-14 复核）

  • 推理：能力在、但在我们这三条路线上是"关着的"（更正我上一版的说法）。
    ① 能力确实在：AgentConfig.Thinking *bool（字段注释："Whether to enable thinking mode (for models that support extended thinking)"）会被 internal/agent/think.go:269 直接传进模型调用；不同厂商有各自线上的编码（enable_thinking／thinking_type／chat_template_kwargs.enable_thinking／reasoning_effort，见 internal/models/legacy_keys.go、api/compat_settings.go）；模型返回的 reasoning_content 会被持久化到 AgentStep 并以 ResponseTypeThinking 事件播出（字段说明原话："…required by MiMo / DeepSeek V3.2+ thinking mode"）。
    ② 但实测是关的：我们三条路线的配置都是 "thinking": false，而且 types/custom_agent.go 有一条归一化——"Pin thinking to an explicit false when unset"，即不设也会被钉成明确的 false。日志实证：四个容器日志里 reasoning_tokens 命中 0 次、reasoning_content 仅 2 次（是代码/字段文本，不是模型输出）；而闭卷直连那侧（不传 thinking 参数、走模型默认）90／90 都有 reasoning token（flash 中位 2,940）。
    ③ 显式推理工具 thinking 是另一件东西，也确实没挂：internal/agent/tools/sequentialthinking.go 是"顺序思考"工具（多步分解、可回溯修正、生成并验证假设，并明确要求"最终答案不要写进 thought、用普通回复收尾"）；预设注释说不默认带它是为了省 token。
    ⇒ 所以准确说法是："推理"这件事在这套系统里有三个层次——模型原生推理（可开，我们关了）／thinking 工具（可挂，我们没挂）／提示词里的推理要求（三份都没有）。我们的三条路线在"推理"上是"全灭"状态，"反思"则是引擎未实现。
  • ⚠️ 由此暴露一个对照口径问题（重要）：我们的闭卷基线是"带推理"的（直连 API、未传 thinking ⇒ 模型默认开推理），而三条 agent 路线是"不带推理"的（config.thinking=false）。⇒ 0047／0048 里所有"闭卷 vs agent 三臂"的对比，都混着"推理开／关"这一层：闭卷侧额外占了一个优势。（旁证：我们做过的开关探针里，关掉推理时 #21 直接答 Tyler——推理对难题不是摆设。所以这个混淆不能忽略；它不推翻 0047 的方向性结论，但"闭卷 0.917 对 agent 0.69～0.76"这类差距里，有多少来自检索、有多少来自推理，本批数据分不开。）
  • 反思：不是"支持但默认不开"，而是个死字段（更正我上一版的说法）。reflection_enabled 只出现在 config/builtin_agents.yaml 与前端类型定义里；internal/ 下既没有对应的结构体字段、也没有任何读取点——项目自己的文档 website-docs/03-features/07-agent.md:145 写得很直白："后端目前不消费这个字段……看到它为 true 也不要以为多了一轮反思。" 代码里只有 reflection 的管道（EventAgentReflection、ResponseTypeReflection、ToolCall.Reflection 字段、回放时拼 Reflection: …），找不到产生者：act.go:223 的注释写着 "optionally runs reflection after each call"，但 executeToolCalls 里并没有对应实现。（实测配置里 reflection_enabled：数据分析师 true、其余 false——都不影响行为。）

7.2 这些开关关着，对我们已有的结论意味着什么

  • 对"三条路线谁更强"：三份提示词都没有显式推理要求、thinking／todo_write 也都没挂 ⇒ 三条路线的差异只能归因于工具集、检索参数（rerank 10/0.3 vs 5/0）与预算（实测 50／30／40）；"谁更会思考／反思"这一类解释在本批数据里不成立。
  • （补：reflection_enabled 不是"关着的开关"，而是死字段——详见 §7.1 第三条。）
  • 对 0046 的逐题归因：那两类失败形态——"停在中间实体就不往下走"（#23 的层级没换）、"多搜后放弃"（#22／#28）——正好是缺显式自查的典型症状。提示词只写了"证据够了就停"，没有"不确定就复核一遍"。所以这两类失败不能读成"模型能力不足"，它们是这套配置下的预期行为。
  • 对"会不会拒答"：0048 §2.2 里那 17 轮"库里没有这条链"是模型自发说出来的——三份提示词里没有任何一句要求它在找不到时声明。⇒ "正确拒答"目前靠模型自觉，不是设计保证。
  • 对 0046 留的那条引子：Reflection／ReWOO 这类 ReAct 改进没有被这批实验覆盖。要回答"显式推理步骤值不值那份 token"，只能挂上 thinking（"动态和反思性的问题解决思考工具"）或 todo_write（"创建结构化的研究计划"）复跑。

⏸ 这条实验当前暂缓（与"重挑数据集"一并搁下）：只挂开关而不换题集，能看到的仅是"在含 11 道坏题的同一批题上会不会好一点"，结论价值有限；等有了自建题集再一起做。

7.3 四种组合（模型推理 × 显式 Thought）与业界证据（2026-10-14）

两个开关是互相独立的两件事：一个是模型自己在内部想（config.thinking），另一个是要求模型把思考显式写出来（thinking 工具——每写一步就是一次工具调用）。2×2 共四格，我们只跑了 A 格：

格模型推理显式 Thought状态
A✗✗已跑——本批全部数据都在这一格
B✓✗未跑
C✗✓未跑
D✓✓未跑

业界证据（本轮查到原文的六条）：

  • ReAct 原论文主表（PaLM-540B，HotpotQA EM ／ Fever Acc，arXiv 2210.03629）：Standard 28.7／57.1；Act（只有行动、没有 Thought）25.7／58.9；ReAct（Thought＋Act 交错）27.4／60.9；CoT 29.4／56.3；CoT-SC 33.4／60.4；ReAct→CoT-SC 35.1／62.0。⇒ ① 加显式 Thought 比不加好（+1.7 EM／+2.0 Acc）；② 纯 CoT 在这份题上还高于 ReAct（记忆能答的题占便宜，和我们 0047 的现象同源）；③ 两者叠加最好。
  • "To CoT or not to CoT?"（arXiv 2409.12183）：100+ 篇论文元分析 ＋ 20 数据集 × 14 模型 ⇒ CoT 的增益主要在数学／逻辑／符号，其他任务小得多；MMLU 上"直接答"与 CoT 几乎一样，除非题面或回答里出现等号。⇒ 推论：单开模型推理（B 格）对"检索型多跳"的增益预期有限。
  • Overthinking（arXiv 2412.21187）：o1 类模型在简单题上大量浪费算力，去掉过度思考可不损准确率地省算力 ⇒ 我们这 30 题里 12 道"模型本来就会"，B／D 两格在这批题上大概率是纯付费。
  • 没有外部反馈时自纠不可靠（arXiv 2310.01798）：LLM 单靠自己"再想一遍"常常不涨反跌 ⇒ 显式 Thought 若只是自我复述，期望不高；配上检索结果才是另一回事。
  • IRCoT（arXiv 2212.10509）：把推理步与检索交错，在 HotpotQA／2WikiMultihopQA／MuSiQue／IIRC 上检索 +21 分、下游 QA +15 分 ⇒ 这是 C 格（显式 Thought ＋ 检索）最强的一条正面证据——而我们的三条路线恰恰都是"检索了，但从不写 Thought"。
  • 旁证两条：Reflexion（arXiv 2303.11366）的增益来自外部／标量反馈并写进情景记忆（我们这套没有这种反馈信号）；s1（arXiv 2501.19393）用 budget forcing 强制延长思考，能让模型回头检查、修错 ⇒ "思考预算"本身是个可调旋钮。

四格的预估（方向可推、量级不可推）：

格预估依据
B 单开模型推理小幅正增益，集中在需要多步合成的地方；成本明显上升To CoT or not（增益偏数学／符号）；Overthinking
C 单开显式 Thought增益最可能落在"规划／纠偏／换策略"；成本低（每次一个工具调用），且推理会留进上下文可复用ReAct（Act 25.7→ReAct 27.4）；IRCoT（+15 QA）
D 两者都开预期最好，但边际递减、成本最高（有重复推理的风险）ReAct→CoT-SC 最高（35.1）

但这份题集会把四格的差异压平：12／30 是"模型本来就会"（天花板：加不加推理都答得出），11／18 是坏题（地板：加不加都答不出，见 0048 §2）。真正能分辨"推理开关值多少"的，只有"题好 ＋ 模型不会"的那一小撮 ⇒ 又一次指向"先有自建题集"。

如果只做一次，建议先做 C 格：文献支持最强、成本最低（只给 allowed_tools 加一个 thinking），而且能直接检验 ReAct 的 T 在我们这条链路里到底起不起作用；同时把闭卷侧的推理关掉做一次对照，把"推理"这个变量从 0047／0048 的对比里剥出来。两件事都只改配置，不写代码。

7.4 轮次与护栏（引擎侧）

  • 轮次：withinIterationBudget(round) 判断还能不能再跑一轮；MaxIterations < 0 表示不限；未设时默认 5；服务端硬上限 MAX_ITERATIONS = 100。实测生效：smart 50 ／ wiki 30 ／ hybrid 40（预设文件里写的是 30／30／40，与实测不一致，见 §1 的更正）。
  • loopGuards（引擎自己发现"没在推进"）：① emptyRetries——空内容时发提醒重试；② consecutiveSameContent——连续两轮内容一模一样；③ consecutiveLength——连续多轮被 completion-token 上限截断。三者任一触发都会结束该轮（finishStalledTurn）。
  • ⇒ 我们看到的"长搜不收敛"（#15 wiki 一轮 236 个事件、hybrid 一轮 470 个事件）不是没有护栏，而是护栏只管"空答／重复／截断"，不管"一直在搜"——预算（30／40）就是那道唯一的闸门。

9. 编译期写页提示词与页类型实测（"入口网"的落地）

来源：internal/agent/prompts_wiki.go（WikiPageModifySystemPrompt／WikiPageModifyUserPrompt 等）、internal/types/wiki_page.go、internal/middleware/language.go、internal/agent/tools/wiki_write_page.go；实测产物 ＝ data/tmp/weknora-musique/wiki-pages-all.json（4,094 页）。

9.1 写页规则：它是"编译器"，不是"作者"

1. You are a COMPILER, not a creative writer. Stay close to the verbatim source wording. You may lightly
   reorder, deduplicate, and join related sentences, but must not rephrase for style, expand short
   statements, or invent transitions.
3. Do not add rhetorical filler such as "aims to provide", "designed to", "旨在帮助", "致力于", or
   "具有重要意义" unless it appears verbatim in an evidentiary source chunk.
（Grounding 段）3. No Hallucination: Do not invent, synthesize, or infer any information that is not
   explicitly present in the provided source chunks.

另有两条把"入口"钉死的约束：

  • 页身份硬约束：This wiki page is specifically about **{{.PageTitle}}** (a {{.PageType}}). Every statement on the page MUST be directly about this exact {{.PageType}} — not about related, adjacent, or similarly-named things.，并带一个 CRITICAL CONFLICT CHECK——新信息若属于相近但不同的东西就拒收（它自己举的例子：「Hunyuan Model vs Qwen3」「居民身份证 vs 工作居住证」）。
  • 链接白名单：Keep [[slug|name]] references ONLY if the slug appears in the <valid_wiki_links> list. Do NOT invent new wiki-link slugs.（禁止自链；正文里也不许留 chunk 句柄如 [c003]）。

9.2 语言不是设计意图，是配置（更正 §2 的措辞）

写页提示词最后一条是 8. Write in {{.Language}}.，语言解析链是 WEKNORA_LANGUAGE 环境变量（优先）→ 请求的 Accept-Language → 默认 zh-CN（internal/middleware/language.go、internal/types/context_helpers.go）。我们部署里 .env 第 66 行那行是注释掉的、docker-compose 传空 ⇒ 落到 zh-CN ⇒ 英文语料被翻成中文页。
⇒ 所以"编译层把英文改写成中文"这个说法要改成：措辞与事实保守（贴近原文、禁编造），语言按配置输出（默认中文）——"可信"与"可读"就是在这两处各让一步。

9.3 页类型：schema 声称六类，实测只落地四类

页类型定位编译期产出？本份产物实测
entity实体词条（人／组织／地点…）✅2,820
concept概念／主题词条✅701
summary文档锚（与源文档 1:1）✅572
index把全部页面罗列出来的总入口✅1
synthesis综合／分析页❌ 编译不做0
comparison对比页❌ 编译不做0

后两类是给"作者页（authored pages）"预留的类型：wiki_write_page 的报错文案写着 Use page_type 'synthesis'/'comparison'/'entity'/'concept' for authored pages，即由 agent 或人手写创建；索引视图 wikiIndexContentPageTypes 会把 summary／entity／concept／synthesis／comparison 五类分组展示（index 自己除外）。
⇒ 但我们的实验里这一路也没发生：wiki／hybrid 的 allowed_tools 里没有 wiki_write_page（只有 search／read／flag_issue）。所以这 4,094 页全部是编译产物，类型只有四类。

9.4 小结：wiki 层更像"入口网"，不是"概览"

  • index = 总入口（对 agent 是"缩略地图"，见 9.5）
  • entity／concept = 按"概念／实体"归集的入口（一词条一页，页身份硬约束）
  • summary = 文档入口（1:1 锚到源文档）
  • wikilink = 入口之间的弱关系（只许用白名单 slug，不许发明）

"可信"由三条工程手段兜住：grounding ＋ 禁推断（只写原文有的事实）、链接白名单（关系可核）、删源时只删"仅由该源支撑"的事实、删空就留占位页（宁可变空也不改写）。⇒ 这也顺带说明：概览（index ＋ summary）只是副产品，主产品是"可核的入口网"。

9.5 补核三件（2026-10-14）：枚举入口、authored 页、图谱归属

① 枚举入口：agent 有，但被刻意压成"缩略地图"。（更正 9.4 原先"agent 没有枚举入口"的说法）wiki_read_page('index') 会被服务端合成一段"索引概览"：intro ＋ 按类型分组（## Entity (N) …），每组列 [[slug]] — summary，而每组上限 wikiIndexAgentTopK = 20；源码注释写着它的用途是让 agent "get a sense of the wiki's shape"，更深的探索应该走 wiki_search，压小则是为了控制喂给 LLM 的体积（internal/agent/tools/wiki_tools.go:18-60）。完整清单只在 MCP 侧：wiki_index 工具（"Browse the table of contents … grouped by type (summary, entity, concept, ...)"，limit 默认 50／最大 200，internal/mcpserver/tools_wiki.go:47-53）与 UI。
⇒ 而 wiki_researcher 的提示词明确允许走这条路：Find an entry point with wiki_search, or read the index when the user requests an overview. 所以设计是："要全貌"给缩略图，"要细节"走检索——枚举在 agent 侧是被截断的能力。

② synthesis／comparison 谁写：专用 agent，不是编译。编译不产这两类（实测 0／0，§9.3）；索引视图为它们预留分组；而能写它们的是 wiki_write_page，该工具只出现在 builtin-wiki-fixer（"维基修订"，agent_type custom、kb_selection_mode: selected，另带 wiki_replace_text／wiki_rename_page／wiki_delete_page／wiki_read_issue／wiki_update_issue）。⇒ 它们是"作者页"：由人工或专用修订 agent 写；我们的三条路线都没权限，所以本批实验里不可能出现。

③ 图谱工具挂给谁：只挂在"智能推理"上，且按 KB 能力门控。config/builtin_agents.yaml 里只有 builtin-smart-reasoning（rag-qa）的 allowed_tools 含 query_knowledge_graph（顺带它也是唯一开了 web_search_enabled: true 的）；builtin-wiki-researcher 没有。前端 tool-capabilities.ts 写着 query_knowledge_graph: { allOf: ['graph'] }——只有所选知识库暴露 graph 能力时这个工具才让勾；而三条预设的 kb_filter（rag-qa→any_of[vector,keyword]／wiki-qa→any_of[wiki]／hybrid→any_of[vector,keyword,wiki]）都没写 graph。
⇒ 读法：图谱是"可选增强"——默认只搭在通用推理 agent 上，且要 KB 真建了图谱才生效；两条"检索路线"预设（wiki／hybrid）都没绑它。这也解释了 0048 那批实验里图谱一次都没被调用。
