第一部分 · 思路简要描述 ＋ 结论

这一部分是给未来的自己复习用的：先讲当时在想什么、最后落到什么结论。要复原过程（源码片段、语料对账、疑点）跳到第二部分 · 现场细节。

1. 一句话结论

它换掉的只是第 0 步（选材料），第 1–4 步原样复用。默认路径是"用户填一个层号 → 拿 level <= N 的全部报告"；Dynamic 是"从根层开始，逐社区按 query 打相关度分，相关的收下并继续下探它的子社区"，最后把选中的那批（可跨层）交给同一套 map-reduce。

它换来了什么：粒度不再由用户一维地猜，而是"相关就下探"——正好回应 0031 提炼的判据（相关性归 query，可得深度归数据）。
它换掉了什么（2026-09-27 沛东再纠偏）：把"隐式的、外包给用户的判断"换成了"显式的、由系统执行的判断"。默认路径里，"这份材料该看多细"这个判断并没有消失——它被藏起来、外包给了调用方，而调用方手里只有一个一维层号可用，于是判断的失真伪装成了"参数没调好"；Dynamic 把这个判断显式化：逐社区按 query 打分 ＋ 阈值截断，可观察、可调、也会可错（判错就漏召回）。成本也从本地变成"每个候选社区一次 LLM 调用"。
顺带一个读代码才发现的差别：dynamic 的打分是孤立判断——一次只把一份报告和问题丢给模型（"这份材料对回答这个问题有帮助吗？"），不跟别的社区比。所以它天生没有 0035 §4.2 那个"批内相对分不可比"的毛病；代价是阈值必须独自承担"多少算够"的绝对尺度——而它默认只有 1/5，是个没有任何先验的裸参数。
它不需要解决、也解决不了的（2026-09-27 沛东纠偏）：可得深度是索引期就定死的——某棵子树没长下去，就等于库里不存在更细的报告。这是上游边界，不是 query 阶段的欠账：任何查询期方法都造不出不存在的层次。query 侧唯一相关的事是披露（"这块最细可得是哪层"），而它没做——连 level 都没进上下文表。

3. 算法：自顶向下剪枝（📄 源码）

起点 = level 0 里"有报告"的社区
循环：
  并发给队列里每个社区打分（0–5）
    ≥ threshold(默认 1) ⇒ 收进结果 + 把它的 children 入队
    keep_parent=False   ⇒ 把这个社区的 parent 从结果里剔除
  队列 = 下一轮要评的子社区
直到队列空

一条容易漏读的兜底机制：如果某一轮队列空、而且至今一个相关社区都没有，且下一层存在且 <= max_level ⇒ 把那一层的所有社区塞进队列，再评一轮。

由此出来的反直觉成本曲线：越不相关，反而越贵——根层全军覆没时会触发"整层全评"的兜底（逐层放大到 max_level）；反而只要有一条相关，之后就只沿着相关分支往下走。设计意图像是"保底召回"，但成本方向跟人的直觉相反。

三个直接推论：① 输出是一组可能跨层的社区，不是一个层；② keep_parent=False 做的恰好是"子相关就丢父"——和默认路径那个失效的 roll-up 是同一个语义，这里反而是生效的；③ 选出来的报告之后仍走 0035 里那套装配（权重／rank／打散／切批），所以"批内相对分""两处静默损耗""引用只到报告级"全部照旧。

4. 打分器：四件必须知道的事（📄 源码）

事实含义

最后一条是这条路最值得写成文章的失败模式：默认路径的失败是"丢一批"（安静地少一块），这里的失败是"多花一轮 ＋ 引入噪声"（安静地变贵、变脏）。

6. 已经钉住的三个坑（✅ 实测 ＋ 📄）

  1. 有社区没有报告 ⇒ 剪枝到那里就断。我们掘金语料 64 个社区只生成了 52 份报告（缺 12 个：1 个 L0 ＋ 11 个 L1）。翻索引日志，同一个 run 里正好 12 条 No report found for community，名单与缺失清单一个不差——是索引期报告抽取失败（extractor 返回 None，只 warning 不报错）。而 DynamicCommunitySelection 只把"有报告"的社区放进层级表，遇到没报告的子社区只在 debug 日志里跳过，代码里那句 TODO check why some sub_communities are NOT in report_df 说的就是这个。
  2. 根层空 ⇒ 构造就炸。构造函数直接取 self.levels["0"]：如果索引里根层一个社区都没有报告，这里会 KeyError。我们根层 13 个社区只有 12 份报告，刚好没踩上。
  3. level 是字符串。数据模型 Community.level: str、读表时 to_str，算法里也是 self.levels[str(level)] ⇒ 配置／日志里 "2" 和 2 不能混着理解。

另外一条不算坑的观察：算法回传的统计只有 llm_calls / prompt_tokens / output_tokens（会累加进检索结果），逐社区的评分明细 ratings 只进 debug 日志，不上浮给调用方——想拿它做分析得自己接日志。

四、与已有结论的接续

  • 0031 的判据：静态层号把二维量（相关性 × 可得深度）压成一维标量；查询驱动的树遍历让两个维度各归其位——dynamic 就是后者的实现。
  • 边界要分清：它解决的是"该不该要"（相关性）；"能不能给"（可得深度）由索引期决定，不归 query 阶段——没长下去的子树、没生成报告的社区，它在结构上就提供不出更细的东西，这不是它"欠"的。query 侧真正欠的是披露："你问的这块，库里最细只有这一层"。
  • 0035 对外稿 §6.2 已经把这条路写成"下一篇引子"，本文（0034）是把它展开前的底稿。

五、本轮沉淀的两条判据（可复用）

判据①「先划清管辖范围，再评价这个组件」（2026-09-27 沛东纠偏）
评价任何组件前，先声明它负责系统的哪一段，再看它做得好不好。
· 边界之外的事不算欠账：可得深度由索引期的社区层次决定——某棵子树没长下去，就是库里没有更细的报告，换任何查询策略都一样；把它记成"dynamic 没解决"就是让一个查询策略背整条流水线的账。
· 边界之内该做没做的才算：query 侧唯一相关的是"披露最细可得"，这条它没做（连 level 都没进上下文表）。
与 AGENTS.md 判据纪律①「要求由角色反推」同源：不用于某目的的产物，别按那个目的的标准验收；反过来，不属于某组件职责的锅，也别扣在它头上。
判据②「判断不会消失，只会被挪位置」（2026-09-27 沛东纠偏）
讨论一个"该谁决定"的设计时，先问三件事：
① 这个判断在谁手里——用户，还是系统？
② 它有没有载体——一个标量（层号）？一套逐条打分（dynamic）？还是压根没有载体？
③ 它失真时会伪装成什么症状——"参数没调好"，还是"答案漏了一块"？
实例：默认路径把"这块材料该看多细"这个判断压进一个一维层号（隐式、外包），于是失真伪装成"层号选得不对"；dynamic 把它摊成逐社区打分（显式、孤立），失真就显形为"漏召回"。
衍生观察：显式化总是伴随一个裸参数（层号 ↔ 阈值），因为"多少算够"这个绝对尺度总得有人定——差别只在它有没有先验、能不能被观察和调。

6.2 判"剪得对不对"的尺子：社区 ↔ 文档映射

方法：社区的 text_unit_ids → text unit → 文档，取"主导文档"（该社区文本块最多归属的那篇）。如此每次选择都能对账：选中集合覆盖了哪几篇、该问题真正需要的那几篇有没有代表被漏掉。脚本 _check_mapping.py / _analyze_run.py，跑完新索引再出数。

两条方法性经验：① 不要用"答案引用的报告 id 按文档分布"判答案取材——实测引用的 id 恰好等于"它那一批读到的 id"，而批次是打散的，所以它只反映批次构成；② 判"剪得准不准"要看选中集合的域分布。

所以对"这是提示词问题"的判断，我的看法是一半对：
· 对的一半：这条提示词是通用、与领域无关的（甚至不能配），措辞（"useful in answering… even if it is only partially relevant"）会把"只覆盖问题的一半"判成 2–3 分——从 17 条理由看，模型确实是这么想的，而且它明说"需要用户自行类比迁移"。

2026-09-27 更正：上面"建议先做①"被沛东否了，理由成立——17 个根的重放显示评分抖动很大（1→5、2→0、2→4…），抖动不解决，调阈值只是在一条不可靠的分数上挪切线。顺序应当反过来：先解决打分稳定性（num_repeats 多数投票 / 提示词档位定义），再谈阈值。

6.12 两条设计层批评（沛东 2026-09-27，含压缩率实测）

批评一：不该让用户填"最大社区深度"——到哪停该由系统判断。

先把机制摆正（避免两个不同的东西混在一起）：community_level 是入口处的预过滤 cap（level <= N）；而下探过程本身没有深度上限——只要某社区评分 ≥ 阈值，它的子社区就进队列，直到叶子或撞上 cap。配置里的 dynamic_search_max_level 只在"一个相关的都没有"时当兜底上限，不是主控。⇒ 用户确实必须填一个"最深到哪层"的 cap，而他无从知道该填几。

更根本的是：整条链上没有任何一步在问"这些材料够不够回答问题了"——它问的是"这份材料相不相关"。相关 ≠ 够用：跨域那一问里 74/135 个报告都只是"部分相关"，于是全部留下，却没有一个能单独回答问题。
沛东的提法：既然已经在判断"要不要用这份材料"，就该智能到底——由系统决定是否继续深入，判据是"这份材料能不能给用户问题一个较好的回答"（充分性），而不是"相不相关"（相关性）。这样层号 cap 可以降级成系统内部的安全上限。

再加第三条（比成本更致命）：信息形态——实体/关系型事实（谁对谁做了什么）天然贴合图结构、可无损折叠；而论证链（前提→结论）被拆成实体共现后会失真，这就是为什么我们的报告不但没压缩，还丢了原文的推理结构。

论文自己也这么说（§6.1 Limitations 原文）："Our evaluation to date has focused on sensemaking questions specific to two corpora each containing approximately 1 million tokens. More work is needed to understand how performance generalizes to datasets from various domains with different use cases." ⇒ "适用范围可能远小于我们以为的"这个判断，作者本人在论文里就挂了这个免责声明；我们只是把它量化了。

实操含义：在这种"小语料 + 低冗余 + 论证型"的场景下，省 token 的正确做法不是"社区报告 + global search"，而是直接对原文做分层摘要（TS）或按段落主题建索引——这正好落回 0028 立项的"三档检索原语对比"里 (ii) 段落主题标签 那一档。

6.14 总体判断（结合全量索引 / 增量索引 / Global Search 三轮，沛东 2026-09-27 提出，我基本认同）

一句话：GraphRAG 更像论文方法的研究参考实现，而不是可以直接当基础的工业软件；而且它的适用区间比"论文给人的印象"窄得多——收益承诺是有条件的。
合成三条证据：
① 收益有条件（6.13）：论文的 2.3–2.6% 来自"1M token 语料 + 每社区 ~30k 源 token + ~780 token 报告"；我们这份语料是129%（反过来了）。差距可由"每社区材料量 × 报告长度"两个乘数解释（差 20–40 倍）。
② 工程成熟度偏研究项目（6.11）：失败静默（47/278 份报告因坏 JSON 被丢、退出码 0）、文档与代码漂移（roll-up 空操作 #2573、"选一层"实为 ≤N、full_context vs full_content）、可选路径缺维护承诺（Dynamic 的文档为零、单测不被收集、发布定级 patch:、崩溃级 bug 的修复 PR 未合入）。
③ 增量那条线更弱（0030/0034）：增量索引是 append-only 追加，不重算社区与度数，还会让跨批主题失去预汇总落脚点 —— 等于侵蚀论文自己的"图的模块性"前提。
适用区间的三个条件（反向即不适用）：语料够大（每社区材料 ≫ 报告长度）· 跨文档冗余高（同一事实被反复覆盖、可折叠）· 以实体/关系型事实为主（论证链会被拆成实体共现而失真）。新闻/播客三条都满足；我们这几篇方法论笔记三条都不满足。
但不要推到"没用"：主路径（索引 → local/global/basic + OpenAI）结构完整、有发布与 CI；它的价值在"帮你把非结构化语料摊成可枚举、可跨源连接的图"，而不是"替你省 token 做摘要"。

6.16 换到论文那份语料：MultiHop-RAG（2026-09-27 20:40 起）

先做了产物备份（沛东要求）：data/tmp/_backup_index_runs.py 把 7 个 run 的原始产物集中快照到 data/backup/graphrag-index/（375 MB，含六张 parquet、settings.yaml、当次提示词、原始输入、脱敏日志、cache/ 原始 LLM 响应；向量库只记大小不备份，可由 parquet 重算），并生成 MANIFEST.md。已知缺失：第一版 dynamic 的产物（278 社区 / 231 报告、被污染那版）在"从 0 重来"时删掉了，只剩笔记里的统计数字。

论文那两份语料的出处（查证）：① News = MultiHop-RAG（Tang & Yang, 2024, arXiv 2401.15391）——HuggingFace yixuantt/MultiHopRAG 的 corpus.json（6.79 MB、ODC-BY），实测 609 篇 / 1,381,153 token（sports 211 · technology 172 · entertainment 114 · business 81 · science 21 · health 10；时间集中在 2023-09～12）；② Podcast = Behind the Tech 官网转录稿（无打包，需自抓）。另外核实一句论文原文：图索引用的是"generic prompts … with entity types and few-shot examples tailored to the domain of the data"——所以它也是按领域定制类型的，做法与 prompt-tune 一致。

切子集：为做"同规模、不同语料类型"的对照，按分类比例分层抽了 51 篇 / 122,387 token（固定种子 42），附 subset_manifest.json（文件 ↔ 原标题/URL/分类/日期/token，供后续"社区→文档"对账）。

又抓到一个提示词坑（这次是 prompt-tune 自己）：第一次跑 prompt-tune，它从样本里推断出 体育域——11 类实体全是 sports league / athlete / coach / film / video game…，社区报告的角色写成 "expert sports journalist"；原因是子集里 sports+entertainment 占 61%。
处置：显式给域描述 --domain "news articles across sports, technology, entertainment, business, health and science" + --language English 重跑 ⇒ 10 类中性实体（organization / person / location / event / technology platform / sports team / broadcast media / occupation / entertainment work / financial metric），报告角色 = 媒体与传播研究的计算社会科学家。

6.20 沛东的机制解读（2026-09-27）："5–10 条 findings"其实是粒度控制器——实测证实高层报告根本没读子报告，并把"输出带宽固定"量化

沛东的提法：findings 的上下限就是在限制不同层级的粗细度——L0 要覆盖的东西多，但有 10 条上限 ⇒ 只能写粗；深社区材料少，但至少 5 条 ⇒ 被迫写细。如果去掉这个约束，就无法保证"越高层越粗"，模型很可能把下层的东西直接复制上来。

核实一：论文自己怎么描述"越高越粗"（📎 原文两处）

① 摘要："…these community summaries are generated in a bottom-up manner … with summaries at higher levels of the hierarchy recursively incorporating lower-level summaries."
② §3.1.5（实际规则）："Higher-level communities. If all element summaries fit within the token limit of the context window, proceed as for leaf-level communities and summarize all element summaries within the community. Otherwise, rank sub-communities … and iteratively substitute sub-community summaries (shorter) for their associated element summaries (longer) until they fit."

⇒ 论文的机制是"只有塞不下时才用子社区摘要替换"；塞得下的时候，高层与叶子一样，都是直接摘要元素（实体/关系/claim）。那句"recursively incorporating lower-level summaries"只在超限路径上成立。

核实二：我们这份语料走的是哪条路（✅ 实测，_diag_reports.py）

eval 语料 1,185 个社区的 context_size（元素摘要拼成的本地上下文，上限 max_input_length=8,000）——context_exceed_limit=True 的数量是 0。也就是说：全程没有发生"用子社区摘要替换"的步骤，高层报告从来没有读过低层报告。

结论：沛东的解读成立，而且是当前实现里唯一在起作用的机制。在没有替换路径的情况下，"越上层越粗"只能靠两件事：① 材料更大（高层社区的子图包含更多实体/关系元素）；② 输出带宽固定——"5–10 条 findings ＋（本该有的）长度上限"。
换句话说：如果按沛东说的把上下限去掉，高层报告最可能的走向不是"变细"，而是把元素摘要罗列/复述一遍 ⇒ 报告长度随材料线性增长，"越高越粗"的梯度就没有任何东西保证了。
反过来说，这两条恰恰都是"经验值"：上限 10 条、下限 5 条、长度 2,000 词——而长度那条还被 prompt-tune 静默丢掉了一半（见 6.19）。
便宜的验证建议：把 community_reports.max_input_length 压到约 2,000，强制进入替换路径，在同一份小语料（143 份报告、约 15 分钟）上看：① 高层报告是否变成"子报告拼盘"（即沛东担心的"抄上来"）；② 长度是否失控；③ 层级粒度梯度是否还存在。

对"GraphRAG 能不能当工业基础"的判断（2026-09-27 沛东纠偏后重写）
先认一个错：我上一版拿"报告静默丢失 / 文档漂移 / 可选路径缺维护"来论证不成熟，落点错了——那些是可修的工程债，用它们判成熟度是弱论证。（原判断：主路径结构完整、有版本与 CI，但三处偏"研究参考实现"；这段现在降级为"症状"，见下。）
沛东的纠偏（结构性缺口）：真正的理由是——它把"必须由领域设计完成"的一整套环节（角色 → 实体类型 → 语料适配性 → 参数标定 → 验收）留给用户，却不提供方法。两件事是连着的：正因为没有方法，用户被逼自己去补设计；而手边唯一的工具 prompt-tune 做的还是另一种推断。
官方的空白（原文）：RAI FAQ 的 Limitations 只列两条——① "依赖构造良好的索引提示词……独特数据集上有效索引取决于能否正确识别领域概念"；② "索引相对昂贵" ＋ 建议"先在目标域做小数据集试点"。⇒ "没有落地指南"不是我推测，是官方自己留下的空白，而它给出的唯一建议就是"先试试"。
最容易错的一步：两种 persona，方向相反（本轮最值得记的辨析）
· 论文评测里的 persona ＝ 提问者的角色。0029 已核：125 道题由 LLM 从语料描述（不是语料内容）生成 personas → tasks → questions——角色是设计起点，问题、以及"需要哪些实体类型"都从它往下推；
· prompt-tune 的 persona ＝ 报告作者的角色（它给 MultiHop 生成的是 "expert sports journalist"）——从语料样本推断"这是什么域"，是自下而上。
⇒ 两者同名、方向相反。用"自下而上推断"去顶替"自上而下的角色设计"，正是我们踩过的两个坑的来源（推断出体育域、主题被写死）。
实操结论：要走这条线，索引侧得自己补角色与实体类型表，Dynamic 那条路还得自己拥有打分提示词、阈值语义、打分稳定性（官方都没给）。工程债仍在（报告静默丢失、roll-up 空操作、文档漂移），但它们是"补方法时会更贵"的放大器，不是不成熟的理由本身。

⑦ 检索侧另算（层号 / dynamic / 阈值那些问题在 query 阶段）。

6.23 索引期与查询期的分工判据（2026-09-27，由沛东两问逼出）

起点是沛东的两句判断：① "落地要花大力气的，是'到底该如何设计 GraphRAG'，即索引期和查询期到底该如何分工协作"；② "知识提取其实是目标相关的东西——一千个哈姆雷特"。下面把它形式化。

判据一 · 分工表
与具体问题无关（可复用）与具体问题相关
索引期✅ 该物化：实体 / 关系 / 逐字证据、社区划分、覆盖度与连通性、社区规模❌ 不该冻结：报告视角、评分口径、抽象层次
查询期（没必要，重复算就是浪费）✅ 该做：选哪些、怎么排序、怎么组织成答案
判据二 · 真正的取舍标准：判断放晚了不是免费的——dynamic selection 就是实测代价：跨域场景 token +53%、时间 +33%，且打分抖动大（1→5、2→0 都出现过）。索引期做判断的好处恰是这三条的反面：便宜（一次）、快（查表）、稳定（写死）。所以判据不是"越晚越好"，而是：
把每个判断放在"它需要的上下文最便宜可得"的那一期。
· 需要全语料结构信息（谁和谁连、覆盖多少）⇒ 放索引期，查询期拿不到；
· 需要具体问题（这问题在问什么）⇒ 放查询期，索引期不知道；
· 两样都需要 ⇒ 索引期物化原料，查询期做判断（我们那条路线的位置）。
回看 GraphRAG：错配是单向的
· 站得住的一侧：实体 / 关系 / 证据抽取（只需原文）、社区划分与度数（需全语料结构）都在索引期——分对了；rank（0–10 相关性）、size、level 这些结构量也确实算好并持久化在 parquet 里——这一侧它做对了。
· 站不住的一侧：报告视角、评分口径、层级粒度常数（max_cluster_size=10、findings 5–10 条）都落在索引期，可它们需要知道"用户要什么"——在不知道问题的时期做了依赖问题的决定。
2026-09-27 更正（撤回一条）：我原先还主张"反向错配——该物化的结构量（社区权重）在查询期现算"。沛东质疑后核代码：read_indexer_reports 不传 attributes_cols ⇒ attributes 为空 ⇒ query/context_builder/community_context.py:82-90 的条件"attributes 里没这个键就重算"恒真 ⇒ 确实每次查询都算（索引表里也没有这一列）。但"该在索引期固化"这个判断是错的：① 该函数只有三十行、纯内存拼接去重，毫秒级；② 它只是 entities 表的函数，而 entities 在 global search 里本就要读进内存；③ 索引期从未产出过这个量，谈不上"该物化却没物化"。⇒ 撤回"双向错配"，改为单向。
判据三 · 目标适配的"时机"——论文 vs TS 那场对比的准确位置
目标适配发生在代价 / 收益
TS（baseline）查询期——map 每一块都对着问题读保留对任意问题的适配性；代价是每次查询全量扫
GraphRAG索引期——报告角色、评分口径、粒度那时定死省 token（根层 2.6%）；代价是放弃查询期的适配性
沛东的判断（本轮）：论文拿 GraphRAG 去和 TS 比 token 是不公平的——因为 GraphRAG 预设了用户角色（＝预设了应用目标）并据此预造了各粒度报告，而 TS 按构造不预设目标。
我把它精确化：不公平不在于"它做了领域定制"（方法有权这么做），而在于它把这个前置条件隐去了，然后把结果当作通用能力来报。所以"2.6% vs 100%"缺的限定语是："在问题形状与索引期预设一致的前提下"。
而且这个限定语是可实测的——6.22 就是那个"换框定"实验：同语料只把抽取框定从 6 域换成 2 域，根层压比 27.2% ⇄ 38.0%。⇒ GraphRAG 的压缩比是"目标的函数"，不是"语料的函数"；论文报了一个数，却没报这个函数。
（顺带纠正一个常被默认的前提：TS 并不是"适配任何领域"，它是"在查询期适配"——它一样需要目标，只是拿到问题之后才适配。所以那场对比不是"专用 vs 通用"，而是"两种不同的适配策略"，却只报了其中一边的成本。）
判据四 · "图的模块性"到底有多重要
· 它真正依赖的不是"模块性"，而是更弱的"可层级摘要性"：语料能被切成相对自包含的小块，且小块摘要能替代原文。把假设从"图论性质"降到"文本性质"，可验证性好得多。
· 论文自己的数据就把质量那根柱子拆了：它对 TS 在 comprehensiveness、diversity 上无统计显著差异 ⇒ 图的质量贡献未被证明。三根立柱（质量 / 成本 / 规模）里，质量未立、规模未测，只剩成本一根，而成本是目标条件性的。
· 但边界要卡住：模块性对全局摘要型问答不重要（至少未被证明）；对枚举 / 跨源连接 / 关系查询（"哪些 X 提到过 Y""这两篇观点哪里冲突"）可能仍然重要——而论文的 125 道题是 LLM 从语料描述（不是语料内容）生成的 personas → tasks → questions，天然是"整体在讲什么"的抽象题，恰好全落在模块性最不重要的那一类。
⇒ 一句话总结：GraphRAG 的成本优势，是"目标对齐条件下的条件性优势"；条件是它可以被换掉，一换就现原形。

影响面（要紧）：我们此前用 prompt-tune 产物建的每一个索引，few-shot 都是自相矛盾的——抽取提示词在示范"给一段文本、输出另一段文本里的实体"，等于教模型可以无视输入。此前观察到的"串味"、莫名其妙的桶（A1 臂 athlete 占 32%）、报告里混进别的主题，都可能与它有关。⇒ 既往结论里凡把问题归因到"抽取质量差"的，都要重估；这条与 6.4"换语料没换提示词"并列，同属索引侧的基础件缺陷。
2026-09-28 更正（做过对照实验后撤回上述推断）：脚本 _probe_example_pollution.py——同语料、同类型表、只换 -Examples- 段（A 错配／B 正配／C 无示例），再用同一提示词抽 3 个留出块、每臂每块 3 次。结果：三臂泄漏率全是 0（错配臂的示例输出是 Inter Miami 那篇的实体，测试块与它无关，一条都没被抄过去）；grounded 率 93.9% / 92.0% / 94.3%，无实质差别；无示例那臂实体反而最多（211 vs 196/199）。⇒ "范例在教模型无视输入"这个推断不成立：这个缺陷的确定危害是"示例无效"（对不上输入，纯占位），不是"示例有害"；athlete 那 32% 更该记在"类型表本身窄 + 语料 41% 是体育文"头上。局限：3 块 × 3 次、单模型、grounded 只用实体名匹配近似。
结论
① 不能靠 prompt-tune 现推类型表——它在 auto 下是"从 4 个 chunk 猜域"，猜的过程既不可复现、又可能自相矛盾。这给 6.21"类型表应由角色自上而下定"和 6.23"知识提取是目标相关的"提供了硬证据。
② 实操清单升级：a) 必须显式给 --domain 与 --language；b) 采样别用 auto；c) 跑完做三项检查——主题有没有写死（6.4）、示例输入输出是否一致（本轮新增）、长度占位符有没有被丢（6.19）。
③ 进阶结论（待验证）：既然 few-shot 系统性错配，那么"干脆不带示例"可能不比现在差——这是个便宜且值得做的对照。

示例是怎么来的（理解根因二的关键）
第 6 步不是"套模板"，而是"让模型在你自己的语料上先跑一遍抽取"：对选中的每个块发一次请求（上限 MAX_EXAMPLES = 5）——system ＝ persona，user ＝ ENTITY_RELATIONSHIPS_GENERATION_PROMPT（📄 prompt/entity_relationship.py:6）——这个提示词本身就是完整的抽取任务（识别所有实体与关系，输出 ("entity"<|>名称<|>类型<|>描述) 格式），模型的返回被原样存成 examples[i]。
然后 create_extract_graph_prompt（📄 generator/extract_graph_prompt.py:73-92）把两者逐条配对拼进最终提示词：Example n → entity_types: [...] → text: docs[i] → ------------------------ → output: examples[i]。
拼接规则两条：至少 min_examples_required（默认 2）条；之后只要超出 max_tokens（默认 2000）预算就停。
所以示例的性质是：模型对你自己语料的抽取结果，不是人写的范例。好处是贴合语料；代价是示例质量 ＝ 抽取质量——一旦错配（根因二），就等于把"可以无视输入"当成范例教给索引器。这正是根因二比根因一更该记的原因：它污染的是索引本身的行为方式，而不是选样范围。
