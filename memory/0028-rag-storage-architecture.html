第一部分 · 思路简要描述 + 结论（复习先读这里）

一句话主线：判官冻结后，Agent 检索层修复提上主线；但检索修复不先想清楚"存储结构要为哪些检索需求服务"，就会在纯稠密向量上调参白做。本篇记录这个判断的推导过程与初步方向：以"内容单元 + 编译层对象图"替代"纯稠密 top-k 主路由"，原文单元仍是事实源，稠密检索降为兜底。

开宗明义：RAG 的本义是"增强生成"，不是"向量检索"

RAG（Retrieval-Augmented Generation）这个词在工业落地中被窄化成了技术栈清单——向量检索、BM25、重排序——重心从"生成"滑到"检索"：手段反客为主。这不是语义洁癖，是注意力与验收标准的错配：把 RAG 当检索问题，就会用"检索命中率"验收系统，而用户真正要的是"生成有没有被恰当增强"。我们自己的评测（覆盖性 / 引用真实性 / 遗漏透明）正是"增强生成"侧的验收——判官校准工作台之所以主流工具缺位，也因主流把 RAG 当检索问题、评测聚焦检索指标。结论：项目语境里 RAG 取本质义，向量检索只是"取块"一环的候选实现，不是 RAG 本身。

结论速查（2026-09-08 开篇定）

  • 纯稠密向量检索在学习大类场景不适合做主路由：宽问法（跨文档全景对比）下，query 是复合的，没有任何一个 chunk 包含"整题"；语义距离"宽问题 → 章节"被无关块稀释，目标章节被挤出 top-100（诊断数据见考古层第一段）。
  • "文档"不是合适的第一层定位单位：容量跨度太大（书 928 块 vs 文章 19 块）；书的"主题节"（20–44 块）与单篇文章同量级——第一层定位到内容单元（容量≈一篇文章的 10–40 块）。
  • 编译层 = 地图 / 索引，原文单元 = 事实源：LLM Wiki 式编译产物不能成为最终事实来源，否则引用真实性审计链在编译处断裂（硬约束，非保守）。
  • 检索需求类型学决定存储结构：出处指代型 / 概念定位型 / 主题对比型 / 学习任务型，各配不同索引；不是"一个稠密索引硬扛所有访问模式"。
  • L0–L3 四层不是通用架构：是"素材恰为一本大书"时树形展开的特例；通用模型 = 内容单元 + 单元之上的对象图（概念页 / 关系边 / 可比面）。
  • 落地前提：入库 chunk 已带 source_id + section_path，单元树骨架免费；语料为精选书/课/文章、量级数千块，半自动编译 + 关键页人工复核成本可控。

真待定（2026-09-08）

  • 对象模型草案的节点 / 边 / 出处链最小集，以及与 0025 现管线的部署点（对象图路由先行、原 dense top-25 降为兜底）；
  • 是否先用 O2 + A5 + T1 相关章节做小切片概念/关系抽取，人工过编译产物质量；
  • 编译流程的半自动形态与人工复核范围（哪些关键页必审）。

第二部分 · 现场细节（考古层第一段：问题 → 分析 → 初步方向）

起因：判官冻结后，Agent 检索层修复怎么开刀

问题：宽问法在纯稠密检索下的系统性失败（诊断数据）

诊断脚本 backend/data/tmp/diag_retrieval_s2.py（不入库，结论沉淀于此）对 cmp-002（Run#132）/ cmp-003、004（Run#134）做了全库稠密 top-100 定位实验：

  • 用原始用户 query（宽问法、跨文全景）检索，T1 素材占 top-100 的 58–62 条，O2/A5 目标章节被严重挤后：cmp-002 的 o2-e2 #59、o2-e4 #47、o2-e5 #89，a5-c3 与 o2-e3 未进 top-100；
  • cmp-004（口语模糊版）query 点名 OpenAI/Anthropic，top-20 却无 O2/A5 命中（T1 18 条）——文档级路由彻底失败；
  • 对照：用点表探针 text 定向检索时，同一批目标 section 能排 #1–40（a5-c3 #1、a5-e1 #1、o2-e4 #17、o2-e2 #40）。

推论：内容在库、单点能检到；失败发生在"宽问题 → 章节"的语义路由——query 是复合的，纯稠密 top-k 在无关块稀释下无法完成分解与定位。这是机制性的，不是调参能修的。

分析 1：容量视角——"文档"这个概念在存储层不成立

按当前入库方式，同一"文档"容量跨度极大：李博杰的书 T1 928 块 vs OpenAI 单篇文章 O2 19 块 / Anthropic A5 24 块。但 T1 的"主题节"约 20–44 块，与单篇文章同量级——如果按内容容量而非物理文件分层，书的章节与单篇文章是同一层级的"内容单元"。这决定检索第一跳应该落在"容量≈一篇文章"的单元上，而不是"文档"上（文档只作为出处属性存在）。

分析 2：LLM Wiki 联想——"存储结构匹配检索需求"

讨论中想到 Karpathy 2026-04 的 LLM Wiki：把 LLM 当"知识编译器"，将原始资料编译成结构化互链的 Wiki（Obsidian 作 IDE、Wiki 作代码库），知识沉淀为可复利资产而非每次临时 RAG。沛东确认"我们是要做一个类似 LLM Wiki 的东西"，并补了关键一句：底层思路简单——检索才是真正的需求，存储结构需要与检索需求匹配。

对照业界窄化（开宗明义）：纯稠密向量是"一个入口适配所有需求"，而学习场景的检索需求至少可分四类，每类需要的索引键不同：

  • 出处指代型（"OpenAI 那篇""harness 那篇"）→ 文档/章节树 + 来源行（v1 已用"来源行拼 chunk"修掉大半，0025 实测）；
  • 概念定位型（"什么是安全围堵"）→ 概念页：概念 → 各源相关单元/章节；
  • 主题/对比型（cmp 家族宽问法）→ 主题图 + 可比面（如 containment 下 O2 组织层关卡 vs A5 环境层围堵）；这是纯稠密系统性失败的地方，可比面是语料里的先验结构，不该每次用向量碰运气；
  • 学习任务型（"怎么学 / 复习"）→ 知识地图 + 前驱关系 + 用户进度（再上一层产品功能）。

换个说法：学习助手的"检索"实际是三个动作——定位（内容在哪个单元）、取证（单元内哪些块）、导航（概念/路径怎么串），三种存储结构分别对应：单元/路径索引、原文 chunk + 组内选择、对象图。

分析 3：一个硬约束——编译层不能成为事实源

Karpathy 的 LLM Wiki 让编译后的 wiki 成为知识库主体；我们不能照搬：答案要过判官的引用真实性审计，claim 必须锚到原文 chunk。若编译页成为事实源，审计就变成对"二手编译"的审计，链在编译那一步断裂。因此编译层在我们这里只承担"地图/索引"角色；唯一可放心引用编译层的是"语料结构/关系"类陈述（如"两篇在围堵思路上互补"），内容类 claim 必须锚回原文。这与"存储结构匹配检索需求"互为表里。

分析 4：L0–L3 四层不是通用架构

沛东质疑"统一分 L0–L3 四层是否合适、有无扩展性更好的方式"。结论：四层只是"素材恰是一本大书"时树形展开的特例；换成单篇文章集合就塌成两层（单元内）。通用模型 = 内容单元（容量≈一篇文章，10–40 块）+ 单元之上的对象图（概念页 / 关系边 / 可比面），层级深度是单元内部自己的事，不进全局 schema。

初步方向与落地路径（2026-09-08）

  • 复用现成骨架：入库 chunk 已带 source_id + section_path，单元树免费——编译是在现有 chunk 上叠索引层，不是重新切库；
  • 主路由替换：宽问题 → 先经对象图/知识地图定位内容单元集 → 单元内稠密取块；原"每源宽候选 top-25 → 门控 → 注入预算"保留为单元内选择层，全库 top-k 降为兜底；
  • 编译层内容：概念页（概念 → 各源相关单元/章节 + 摘要 + 指向 chunk）、关系边（O2↔A5 互补对照与可比面）、单元目录（容量、路径、覆盖范围）；
  • 流程：半自动编译（LLM 对每个内容单元抽概念/关系/关键问题）+ 人工复核关键页；语料增量时局部重编译相关支线；
  • 验证靶子：先用 O2/A5 两篇 + T1 相关章节做小切片编译，人工过产物质量，验证"编译层信息只来自语料、无金标准污染"前提。

考古层第二段 · 对象图的"对象"到底是什么（2026-09-08 上午–午间）

起题：概念图（docs/rag-storage-structure.html v0.1）画出后，沛东盯着图问："对象图中的对象，是啥？是容器吗？"——一图引出三轮质询，把对象模型从"直觉版"逼成"可判定版"（v0.2）。

  • 质询 1：对象是容器吗？答：不是。对象图中的对象是概念层语义对象（概念页 / 主题 / 可比面），容器是概念的"证据落点"，不是对象图节点。理由：①概念跨容器（harness 概念散在多个容器，以容器为节点会重复碎裂）；②宽问法路由需要的是"问题涉及哪些概念面"而非"哪些容器字面相关"；③学习导航（前驱/分歧/互补）本质是概念关系。图 v0.1 的边端点误用了容器名，是表述歧义，v0.2 修正。
  • 质询 2：这些词是新造的吗？查证：几乎都有成熟领域对应——对象图 ≈ 知识图谱最小子集；概念页 ≈ 实体页 / LLM Wiki page；可比面 ≈ 分面分类（faceted classification，Ranganathan）的 facet / dimension；归属边 ≈ grounding / provenance / mention 边；语义边 ≈ 知识图谱谓词关系；容器/分片 ≈ document/chunk。结论：模型是"分面分类 + 知识图谱最小子集 + RAG 出处层"三者按需求焊合，不是自造轮子；术语表应显式登记（见 v0.2 图内对照表）。
  • 质询 3：文章本身要建模为概念节点吗？答：不要。文章 = 容器树根 + 元数据（作者/平台/标题/时间），只承担出处身份；"文章互补于文章"无意义，互补的是文内概念/主张。出处指代（"harness 那篇"）由来源行 + 文档树解决；出处归属由"归属边 → 容器片段 → 容器根"链回答；文章级问答是容器页（编译摘要）功能，均不需要文章进对象图。
  • 质询 4：可比面貌似不是节点，是关系的限定？确认，v0.1 把 facet 过度实体化了。v0.2 修正：可比面 = 概念的维度（facet），同时充当对比/互补关系的限定标签；归属边可带维度标注用于定位片段。维度三态判据（沛东逼出）：①会被独立提问吗 → 会则升格节点（可独立寻址 = 节点定义，"查询需求决定本体"）；②被多个概念共享吗 → 共享则是一根独立"轴"（dimension），不是任何概念的私有属性；③需要被遍历/组织吗 → 需要则轴也有节点身份，仅当标签/过滤器则作属性键。依附型 = 概念内嵌维度字段；共享型 + 可独立提问 = 独立节点类别；共享型仅作标签 = 属性键。
  • 微型实例（O2×A5 containment 主题，schema 完备）：容器树（文章→小节 + 物理分片，单节多块合并取段）、概念页 2（containment 跨源 / blast radius 单源，各示一种立页理由）、维度 1（关卡层级，依附型内嵌 containment）、归属边 3（含维度标注）、语义边 2（互补 @关卡层级 / 支持细化）。未出现：分歧边、前驱边、共享型轴、书级嵌套容器——属切片范围，非模型缺类。

结论（v0.2 schema）：对象图节点 = 概念（内嵌维度，必要时升格共享轴为独立节点）；边 = 语义边（互补/分歧/支持/前驱，带维度限定）+ 归属边（概念→容器片段，可带维度）；出处树 = 容器层级 + 元数据（不入对象图）。语义边界从物理切块手里拿回给 section；树是骨架、图是大脑、chunk 只计分。

考古层第三段 · 从 v0.2 到 v0.3：被连续追问逼出的 KG 素养（2026-09-08 14:00–15:10）

起题：沛东对着 v0.2 概念图逐条质询，每次都顶在记号不干净的地方——这几轮"追问→修正"把模型从自造词逼回成熟领域。

  • 质询 5：语义边若只连声明，"blast radius → containment(A5)"怎么解释？答：端点同样必须是声明——blast radius 在 A5 的具体论述（"爆炸半径随能力与访问扩张而增长、要 cap 它"）支撑 A5 的守卫声明（"守卫置于环境层、封顶可达范围"）。此问暴露了记号混乱：`blast radius` 写了纯概念、`containment(A5)` 写了"概念×来源"，两种记号在边上混连。修正 = 概念不直接连论证边，只聚合同名声明。
  • 质询 6：更普遍的是 harness 及其下各种常见手段，明显是概念之间的语义关系（从属）。答：对，且这戳破"所有语义边都连声明"的收紧——概念之间的从属/包含/实现关系真实存在且更基础（harness ⊇ linter / 结构测试 / 仓库知识 / CI 闸门 / 评审自动化）。于是边分两层：概念结构层（从属/包含、实现/手段、前置：概念↔概念）+ 声明论证层（互补/分歧/支持/细化：声明↔声明）。对象图实为"concept structure + claim argumentation"两张图叠加。
  • 质询 7：知识图谱是最久的方法，它也做"区分"吗？都是实体？声明对应啥？答：KG 恰恰不做节点形态二分——图元素统一为实体 + 关系，区分靠实体类型（ontology class）。因此：概念 = concept 类实体；声明 = 带出处的命题实体（reified statement / proposition with provenance），本质是 Subject（概念）— Predicate（维度）— Object（取值）三元组 + source 标注。从属/包含/前置 = 对象属性（subClassOf / partOf / involves）；互补/分歧/支持 = 论证框架关系（support / attack / complement）——support/attack 正是论证挖掘（argument mining）的标准关系，非自创。
  • 质询 8：文章在 KG 里定义成啥？也是实体？答：是，`rdf:type = document`（信息内容实体，IAO 常用类），带元数据（作者/标题/时间/平台）。文章是信息载体不是观点源；它只走文档层关系（cites / partOf / asserts 承载声明），不进语义层的互补/分歧。文章之间用 cites，不用"互补"——两篇文章无立场可比，可比的是文内命题。
  • 质询 9：术语漂移（harness 早期多名、后统一）如何建模？答：概念与术语分离（concept-term split）。概念实体稳定（canonical 名 `harness`）；每个历史/各家叫法是一个术语实体，经 `denotes` 边指示概念；演变挂时态（term 带 `valid_from / valid_to` 或对命名断言 reification 加时间戳）；归并用 `owl:sameAs`（旧词 term 保留不删，删了就丢考古证据）。
  • 质询 10：术语也是一种实体吗？答：是，但不必然——需挂时态/来源、或要作检索入口节点时才升为实体；仅需别名则用 `skos:altLabel` 字符串即可。判据与 facet 三态同源：能否独立提问 / 需不需要挂属性 / 要不要被图命中。我们场景（术语未收敛窗口期、金标准防时间线污染）需要"谁在何时用了哪个词"，字符串挂不上，故必须实体化。

结论（v0.3 schema，2026-09-08 15:10）：以 KG 标准模型打底，四种实体类型 + 各自谓词——概念（concept：稳定，canonical 名；结构层关系 subClassOf/partOf/involves、聚合命题）、命题/声明（proposition：带出处三元组；论证层关系 support/attack/complement）、文档（document：信息内容实体，只走 cites/partOf/asserts，不进语义层）、术语（term：denotes 概念，带时态与来源，不必然实体化）。概念-命题-文档-术语不再被我们自创成异构"对象图"，统一落在 KG 实体-类型-谓词模型上。

三个真正自研的增量（复用 KG 之外的贡献）：①检索路由视角——哪些概念/命题提升为"可命中入口"，宽问题经它定位容器集；②维度/可比面组织——facet 作比较轴排布，支撑多方对照；③出处链与引用锚对接——"命题/声明→容器片段"链接上判官引用锚（连续块组），使对象图节点、引用审计单元、存储落点三粒度对齐。其余全部复用 KG 标准（facet=分面分类、支持/攻击=论证框架、声明=reified proposition、归属=provenance/mention）。

一条铁律（随术语层落地）：不把"今天统一后的名"回填到过去——早期文章的金标准/检索/判定应按当时语境解析其词（术语 valid_to 防的就是这个）。这是 0024/0026 反复强调的"时间线污染"在对象模型层的对应物。

考古层第四段 · 命题归位与四级分层：把"自创"从概念里挤出去（2026-09-08 15:30）

起题：沛东两问把模型从"看起来很完备"逼到"自洽但过度"，再逼到"其实早有标准"。问一："命题/声明真的需要单独做实体吗？不就是'实体—谓词—实体'？"问二："不同领域本体各不同，那 proposition 这种跨领域实体怎么会有？"——分别指向命题的建模地位与概念来源的层级。

  • 结论 1 · 命题 = 可选择性 reify 的三元组（v0.4 定稿）：命题本质不是"一方实体"，是一条 (subject—predicate—object) 三元组、一条边。何时才 reify（把断言本身对象化为可引用节点）——四个触发场景：①加 provenance（这条断言来自哪段）；②加时态/可信度/主张主体；③成为 support/attack 论证边的端点；④被引用审计（我们判官核对"声明被哪些块支撑"，引用锚指向的就是这个整体）。不触发就只是边；触发才升为 proposition 节点。 v0.3 把命题列为"第四类固定实体"属过度，v0.4 纠正。
  • 结论 2 · 四级分层（回答"为何有跨领域实体"）：①元模型（RDF/RDFS/OWL 自身：rdf:type / rdfs:Class / subClassOf / ObjectProperty，管"类型"这个动作）；②顶层本体 / 基础本体（BFO/DOLCE/IAO：跨领域的"存在普遍范畴"，proposition 属"信息内容实体"一类，任何领域都可断言/评价真假的信息内容都归它）；③领域本体（我们：harness / containment / 守卫 / 关卡层级；FOAF；GO）；④实例（具体三元组）。RDF 统一"事实怎么表达"，顶层本体统一"存在物分哪几大类"，领域本体才各管各的。 proposition 在顶层本体，故天生跨领域——不是我们领域的东西。
  • 结论 3 · 我们的类不是自创：v0.3 的 concept / proposition / document / term 都是借鉴顶层本体的通用范畴（concept、information content entity、document、agent 均有成熟原型），不是头脑一热发明。真正需要我们自研的只有：领域本体（harness 谱系、facet 维度、守卫立场）+ 三个自研增量（检索路由入口 / facet 组织 / 出处链与引用锚对接）。"自创对象图"的提法从概念里被挤出——架子早有人立好，我们填的是领域内容与检索视角。

概念层面的自检：至此"对象图"不再是自造异构，而是 KG 标准模型（实体-类型-谓词 + 分层）+ 我们三个检索向增量。沛东层面确认：概念已清，可进入落地讨论（哪些概念立页 / facet 怎么排 / 路由入口怎么定），不再纠结词汇归属。

考古层第五段 · 维度/谓词/边/标签，到底谁是"关系"（2026-09-08 15:53）

起题：沛东对着 v0.4 图连着追问，把"维度要不要单独建模""升级为独立轴是实体吗""私有属性怎么建模""边/谓词/标签是不是一回事"串成一条线，最后逼出一条通用定律——这轮把"关系"这一侧彻底理清了。

  • 结论 1 · 维度（facet）必然是谓词，不设"私有/共享"分档（2026-09-08 16:10 再简化）：facet 是三元的中间项（subject —维度— 取值），本质就是谓词（OWL 里即 object/data property，同一物）。"私有/共享"只说明这条谓词当前被几个概念引用（1 个 vs 多个），是自然事实，不是建模决策，无需单独强调成档。修正掉 v0.5 里"依附型/共享型"作为建模分档的表述："containment 防线层级置于 组织层"中的"防线层级置于"就是谓词。
  • 结论 2 · "升级为独立轴"唯一分界 = 是否 reify：维度默认是谓词，住在边上；只有 可独立提问 / 需挂属性 / 需被图遍历命中 时才 reify 成轴实体节点（可命中可导航）。未 reify 就只是谓词——没有"对象属性 vs 轴节点"两档（对象属性就是谓词的 OWL 别称）。与"私有/共享"无关：私有谓词若被独立提问也该升，共享谓词若不独立提问也不用升。
  • 结论 3 · 谓词 vs 边 vs 标签是三层：①谓词=关系类型定义（owl:ObjectProperty / rdf:Property，是"类"）；②边（三元组）=谓词的一次实例化（连接两个具体对象的"事实"）；③标签=命名（rdfs:label / skos:altLabel，本质是字符串属性）。三者都不是"图两端的对象"，默认都不做节点；当需被单独寻址（提问/引用/遍历）时各自对象化。
  • 结论 4 · reify 通用定律（贯穿多轮的主线）：对象默认呆在它"在的地方"（节点或边的位置），仅当需要被单独寻址 / 作为整体被引用时才对象化（reify）。触发判据三连：能否独立提问 / 需不需要挂属性 / 要不要被图遍历命中（即"查询需求决定本体"）。命题从边升、维度从谓词升、术语从标签升——同一个模式，三个起点。这三者被三个不同名字（proposition 节点/轴实体节点/term 实体节点）包装，实为一条定律。
  • 结论 5 · 自研增量②再讲清（facet 作比较轴）：多方对照的难点不是"找到两段话"，而是"这两段话在哪个轴上可比"。facet 作比较轴，是预先给可比较的概念标好"从哪些轴比"——检索先命中轴、再沿轴取各源立场。cmp-002：命中"防线层级"轴 → 取组织层（O2）/环境层（A5）两端 → 落到容器片段。与①的区别：①回答"命中谁"，②回答"命中后如何把宽问题拆成可比的子项"。这是产品层决策，KG 无现成答案，故归自研。

语义不重复标注原则：凡语义已内嵌在节点或谓词里的，不在边上重复标注。维度住在谓词里（决定命题取值轴），边只承载"连到谁、什么关系"。维度标注仅在两种情况下有用：a) facet 已升级为独立轴实体、被命题引用时（标"@哪个轴"）；b) 归属边起点是概念（多维度需消歧）而非命题时。起点已是命题则不带。
