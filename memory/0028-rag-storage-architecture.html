第一部分 · 思路简要描述 + 结论（复习先读这里）

一句话主线：判官冻结后，Agent 检索层修复提上主线；但检索修复不先想清楚"存储结构要为哪些检索需求服务"，就会在纯稠密向量上调参白做。本篇记录这个判断的推导过程与初步方向：以"内容单元 + 编译层对象图"替代"纯稠密 top-k 主路由"，原文单元仍是事实源，稠密检索降为兜底。

开宗明义：RAG 的本义是"增强生成"，不是"向量检索"

RAG（Retrieval-Augmented Generation）这个词在工业落地中被窄化成了技术栈清单——向量检索、BM25、重排序——重心从"生成"滑到"检索"：手段反客为主。这不是语义洁癖，是注意力与验收标准的错配：把 RAG 当检索问题，就会用"检索命中率"验收系统，而用户真正要的是"生成有没有被恰当增强"。我们自己的评测（覆盖性 / 引用真实性 / 遗漏透明）正是"增强生成"侧的验收——判官校准工作台之所以主流工具缺位，也因主流把 RAG 当检索问题、评测聚焦检索指标。结论：项目语境里 RAG 取本质义，向量检索只是"取块"一环的候选实现，不是 RAG 本身。

结论速查（2026-09-08 开篇定）

  • 纯稠密向量检索在学习大类场景不适合做主路由：宽问法（跨文档全景对比）下，query 是复合的，没有任何一个 chunk 包含"整题"；语义距离"宽问题 → 章节"被无关块稀释，目标章节被挤出 top-100（诊断数据见考古层第一段）。
  • "文档"不是合适的第一层定位单位：容量跨度太大（书 928 块 vs 文章 19 块）；书的"主题节"（20–44 块）与单篇文章同量级——第一层定位到内容单元（容量≈一篇文章的 10–40 块）。
  • 编译层 = 地图 / 索引，原文单元 = 事实源：LLM Wiki 式编译产物不能成为最终事实来源，否则引用真实性审计链在编译处断裂（硬约束，非保守）。
  • 检索需求类型学决定存储结构：出处指代型 / 概念定位型 / 主题对比型 / 学习任务型，各配不同索引；不是"一个稠密索引硬扛所有访问模式"。
  • L0–L3 四层不是通用架构：是"素材恰为一本大书"时树形展开的特例；通用模型 = 内容单元 + 单元之上的对象图（概念页 / 关系边 / 可比面）。
  • 落地前提：入库 chunk 已带 source_id + section_path，单元树骨架免费；语料为精选书/课/文章、量级数千块，半自动编译 + 关键页人工复核成本可控。
  • 检索三段定调（2026-09-09 11:19）：向量=入口（概念/命题）+ 兜底（chunk），图=主路由，不做 chunk 重排器；纯符号/异名入口对 paraphrase、术语漂移脆弱（harness 多家叫法是反例）；与 GraphRAG 的关系=借用其骨架、差异化在类型化命题/判官对齐/确定性/人工复核。
  • 编译噪声可控，引入划算（2026-09-09 11:37）：人工复核粒度=基础件（编译 prompt/claim_type 词表/grounding 规则/校验门），非产物；噪声分两类——结构性由程序校验拦、语义性由判官/引用审计当自动门 + 抽样；关键是把噪声爆炸半径锁死在"路由"（chunk=事实源、编译=索引），进不了"事实"；故引入图建模检索层即便有噪声也划算。
  • 编译层设计定调（2026-09-09 12:10）：编译源=清洗后原文（非 chunk）；粒度=内容单元（虚概念、仅编译时用、token 上限定 12k）；编译=一次带类型 pass（文档/概念+异名/边/具体化陈述）；reify 判据=预测+修补（预测：claim_type 被查词表〔由业界数据+产品定位正推〕/概念中心度/论证端点；立场性不入触发——由 asserted_by+provenance 承载；修补：dense 兜底/判官 miss 驱动 promote/周期清扫）；chunk 补"清洗后原文偏移"（按文件、file_idx 区分；单文件源即全局），grounding=证据 chunk 集合（多对多）；内容单元=语义边界优先的连贯窗口（section_path 仅作边界启发式、非强制切分点；整篇 < 12k 时整篇即一个单元）、不在 chunk/偏移层做、不落库、跨单元归并/去重；校验层+质量门为一等项。
  • claim_type 词表按场景收敛、不照搬权威词表（2026-09-09 下午）：从权威词表（AZ/CoreSC、Argument Mining、SemMedDB）拿到的 5–6 类，用真实场景一验大多数用不上——权威词表服务"语料标注/文本结构分析"（须穷举标全部句子），我们只标"被 reify + 要按角色过滤"的交集；问题空间（按"角色"过滤的题型）本就很窄、且由产品定位固定——语料量只是二阶因子（再多文档只提高概念陈述集异构/激活度，引出的异名/术语漂移落在入口侧，均撑不大类型集合）；LLM 把"理解"挪出类型系统（入口映射/回答生成+判官/其它结构边各自接活）。核心词表 = {Limitation, Outlook}；Stance 不当类型（走文档→asserts→chunk）；Definition/Method 不当类型（概念路径可覆盖）；其余按"概念陈述集异构 + 用户按角色过滤"动态 promote。原则：分类粒度由所服务的决策/查询决定，不由数据丰富度决定。
  • 编译输出 schema + reify 触发收敛（2026-09-09 傍晚）：编译器每内容单元产 content_unit/document/concept/term/statement/edge。id = 全局唯一、无业务含义（数据库主键，ULID/序列），展示/自然键另用（document.ref=O2/A5、concept.canonical、term.label），不拿名字当主键；引用一律用 id（term.denotes→concept.id），concept.aliases=字符串（需漂移/来源才升级 term 实体）。statement 含 reify_reasons=[type_filter/argument_endpoint/concept_central]（可多选、列所有命中项）、claim_type（仅当 type_filter 在场且为局限/展望时赋值 Limitation/Outlook）、evidence_texts（逐字连续原文引文数组）、clean_ref（引文锚定算出）、asserted_by（立场由此承载）、evidence_chunks（引文锚定逐段并集）。reify 触发由 4 类收敛为 3 类（删"立场性"）；claim_type 词表=业界数据候选 + 产品定位正推收敛，非判官/a5-cmp 反推。edge 带 produced_by=compile/compile-hypothesis/auto 三值（含义见架构文档）。无 per-entity draft 标记（人工复核=审基础件，非逐产物）。
  • 图里收什么：宽提取 + 受控关系筛选（2026-09-15 定）：Pass 1 宽提取保召回，图的边只收"能归入受控关系（39 条）"的；不做"先段落主旨、再抽三元组"的中间摘要——主旨是有损压缩（丢的正是关系细节）、主旨句无法引文锚定（破坏"编译层不能成为事实源"这条硬约束）、前置有损不可逆。四档处置：① 能归入 → 进图；② 谓词糊（≥4 词 / 含并列 / 含从句标记 / 含否定 / 含情态词）→ 清洗（predicate_clean，只删不改）；③ 造表外词但表里有对应（模型的锅）→ 强制归入（forced + predicate_nearest）；④ 真缺概念（表的锅）→ 待定（pending，不进图、报告列出、定期收敛进表，长期待定才丢）。归一步因此输出三态 mapped/forced/pending，图只收前两者；表外词按篇累积进 backend/data/compile/_outside_words.json，作为"残差 → 定期收敛"的台账。细节检索一律由 chunk + 向量兜底，问答侧做"入口向量 / 图路由 / 兜底保真"三段融合。

分析 1：容量视角——"文档"这个概念在存储层不成立

按当前入库方式，同一"文档"容量跨度极大：李博杰的书 T1 928 块 vs OpenAI 单篇文章 O2 19 块 / Anthropic A5 24 块。但 T1 的"主题节"约 20–44 块，与单篇文章同量级——如果按内容容量而非物理文件分层，书的章节与单篇文章是同一层级的"内容单元"。这决定检索第一跳应该落在"容量≈一篇文章"的单元上，而不是"文档"上（文档只作为出处属性存在）。

分析 2：LLM Wiki 联想——"存储结构匹配检索需求"

讨论中想到 Karpathy 2026-04 的 LLM Wiki：把 LLM 当"知识编译器"，将原始资料编译成结构化互链的 Wiki（Obsidian 作 IDE、Wiki 作代码库），知识沉淀为可复利资产而非每次临时 RAG。沛东确认"我们是要做一个类似 LLM Wiki 的东西"，并补了关键一句：底层思路简单——检索才是真正的需求，存储结构需要与检索需求匹配。

对照业界窄化（开宗明义）：纯稠密向量是"一个入口适配所有需求"，而学习场景的检索需求至少可分四类，每类需要的索引键不同：

  • 出处指代型（"OpenAI 那篇""harness 那篇"）→ 文档/章节树 + 来源行（v1 已用"来源行拼 chunk"修掉大半，0025 实测）；
  • 概念定位型（"什么是安全围堵"）→ 概念页：概念 → 各源相关单元/章节；
  • 主题/对比型（cmp 家族宽问法）→ 主题图 + 可比面（如 containment 下 O2 组织层关卡 vs A5 环境层围堵）；这是纯稠密系统性失败的地方，可比面是语料里的先验结构，不该每次用向量碰运气；
  • 学习任务型（"怎么学 / 复习"）→ 知识地图 + 前驱关系 + 用户进度（再上一层产品功能）。

换个说法：学习助手的"检索"实际是三个动作——定位（内容在哪个单元）、取证（单元内哪些块）、导航（概念/路径怎么串），三种存储结构分别对应：单元/路径索引、原文 chunk + 组内选择、对象图。

分析 3：一个硬约束——编译层不能成为事实源

Karpathy 的 LLM Wiki 让编译后的 wiki 成为知识库主体；我们不能照搬：答案要过判官的引用真实性审计，claim 必须锚到原文 chunk。若编译页成为事实源，审计就变成对"二手编译"的审计，链在编译那一步断裂。因此编译层在我们这里只承担"地图/索引"角色；唯一可放心引用编译层的是"语料结构/关系"类陈述（如"两篇在围堵思路上互补"），内容类 claim 必须锚回原文。这与"存储结构匹配检索需求"互为表里。

分析 4：L0–L3 四层不是通用架构

沛东质疑"统一分 L0–L3 四层是否合适、有无扩展性更好的方式"。结论：四层只是"素材恰是一本大书"时树形展开的特例；换成单篇文章集合就塌成两层（单元内）。通用模型 = 内容单元（容量≈一篇文章，10–40 块）+ 单元之上的对象图（概念页 / 关系边 / 可比面），层级深度是单元内部自己的事，不进全局 schema。

初步方向与落地路径（2026-09-08）

  • 复用现成骨架：入库 chunk 已带 source_id + section_path，单元树免费——编译是在现有 chunk 上叠索引层，不是重新切库；
  • 主路由替换：宽问题 → 先经对象图/知识地图定位内容单元集 → 单元内稠密取块；原"每源宽候选 top-25 → 门控 → 注入预算"保留为单元内选择层，全库 top-k 降为兜底；
  • 编译层内容：概念页（概念 → 各源相关单元/章节 + 摘要 + 指向 chunk）、关系边（O2↔A5 互补对照与可比面）、单元目录（容量、路径、覆盖范围）；
  • 流程：半自动编译（LLM 对每个内容单元抽概念/关系/关键问题）+ 人工复核关键页；语料增量时局部重编译相关支线；
  • 验证靶子：先用 O2/A5 两篇 + T1 相关章节做小切片编译，人工过产物质量，验证"编译层信息只来自语料、无金标准污染"前提。

考古层第二段 · 对象图的"对象"到底是什么（2026-09-08 上午–午间）

起题：概念图（docs/rag-storage-structure.html v0.1）画出后，沛东盯着图问："对象图中的对象，是啥？是容器吗？"——一图引出三轮质询，把对象模型从"直觉版"逼成"可判定版"（v0.2）。

  • 质询 1：对象是容器吗？答：不是。对象图中的对象是概念层语义对象（概念页 / 主题 / 可比面），容器是概念的"证据落点"，不是对象图节点。理由：①概念跨容器（harness 概念散在多个容器，以容器为节点会重复碎裂）；②宽问法路由需要的是"问题涉及哪些概念面"而非"哪些容器字面相关"；③学习导航（前驱/分歧/互补）本质是概念关系。图 v0.1 的边端点误用了容器名，是表述歧义，v0.2 修正。
  • 质询 2：这些词是新造的吗？查证：几乎都有成熟领域对应——对象图 ≈ 知识图谱最小子集；概念页 ≈ 实体页 / LLM Wiki page；可比面 ≈ 分面分类（faceted classification，Ranganathan）的 facet / dimension；归属边 ≈ grounding / provenance / mention 边；语义边 ≈ 知识图谱谓词关系；容器/分片 ≈ document/chunk。结论：模型是"分面分类 + 知识图谱最小子集 + RAG 出处层"三者按需求焊合，不是自造轮子；术语表应显式登记（见 v0.2 图内对照表）。
  • 质询 3：文章本身要建模为概念节点吗？答：不要。文章 = 容器树根 + 元数据（作者/平台/标题/时间），只承担出处身份；"文章互补于文章"无意义，互补的是文内概念/主张。出处指代（"harness 那篇"）由来源行 + 文档树解决；出处归属由"归属边 → 容器片段 → 容器根"链回答；文章级问答是容器页（编译摘要）功能，均不需要文章进对象图。
  • 质询 4：可比面貌似不是节点，是关系的限定？确认，v0.1 把 facet 过度实体化了。v0.2 修正：可比面 = 概念的维度（facet），同时充当对比/互补关系的限定标签；归属边可带维度标注用于定位片段。维度三态判据（沛东逼出）：①会被独立提问吗 → 会则升格节点（可独立寻址 = 节点定义，"查询需求决定本体"）；②被多个概念共享吗 → 共享则是一根独立"轴"（dimension），不是任何概念的私有属性；③需要被遍历/组织吗 → 需要则轴也有节点身份，仅当标签/过滤器则作属性键。依附型 = 概念内嵌维度字段；共享型 + 可独立提问 = 独立节点类别；共享型仅作标签 = 属性键。
  • 微型实例（O2×A5 containment 主题，schema 完备）：容器树（文章→小节 + 物理分片，单节多块合并取段）、概念页 2（containment 跨源 / blast radius 单源，各示一种立页理由）、维度 1（关卡层级，依附型内嵌 containment）、归属边 3（含维度标注）、语义边 2（互补 @关卡层级 / 支持细化）。未出现：分歧边、前驱边、共享型轴、书级嵌套容器——属切片范围，非模型缺类。

结论（v0.2 schema）：对象图节点 = 概念（内嵌维度，必要时升格共享轴为独立节点）；边 = 语义边（互补/分歧/支持/前驱，带维度限定）+ 归属边（概念→容器片段，可带维度）；出处树 = 容器层级 + 元数据（不入对象图）。语义边界从物理切块手里拿回给 section；树是骨架、图是大脑、chunk 只计分。

考古层第三段 · 从 v0.2 到 v0.3：被连续追问逼出的 KG 素养（2026-09-08 14:00–15:10）

起题：沛东对着 v0.2 概念图逐条质询，每次都顶在记号不干净的地方——这几轮"追问→修正"把模型从自造词逼回成熟领域。

  • 质询 5：语义边若只连声明，"blast radius → containment(A5)"怎么解释？答：端点同样必须是声明——blast radius 在 A5 的具体论述（"爆炸半径随能力与访问扩张而增长、要 cap 它"）支撑 A5 的守卫声明（"守卫置于环境层、封顶可达范围"）。此问暴露了记号混乱：`blast radius` 写了纯概念、`containment(A5)` 写了"概念×来源"，两种记号在边上混连。修正 = 概念不直接连论证边，只聚合同名声明。
  • 质询 6：更普遍的是 harness 及其下各种常见手段，明显是概念之间的语义关系（从属）。答：对，且这戳破"所有语义边都连声明"的收紧——概念之间的从属/包含/实现关系真实存在且更基础（harness ⊇ linter / 结构测试 / 仓库知识 / CI 闸门 / 评审自动化）。于是边分两层：概念结构层（从属/包含、实现/手段、前置：概念↔概念）+ 声明论证层（互补/分歧/支持/细化：声明↔声明）。对象图实为"concept structure + claim argumentation"两张图叠加。
  • 质询 7：知识图谱是最久的方法，它也做"区分"吗？都是实体？声明对应啥？答：KG 恰恰不做节点形态二分——图元素统一为实体 + 关系，区分靠实体类型（ontology class）。因此：概念 = concept 类实体；声明 = 带出处的命题实体（reified statement / proposition with provenance），本质是 Subject（概念）— Predicate（维度）— Object（取值）三元组 + source 标注。从属/包含/前置 = 对象属性（subClassOf / partOf / involves）；互补/分歧/支持 = 论证框架关系（support / attack / complement）——support/attack 正是论证挖掘（argument mining）的标准关系，非自创。
  • 质询 8：文章在 KG 里定义成啥？也是实体？答：是，`rdf:type = document`（信息内容实体，IAO 常用类），带元数据（作者/标题/时间/平台）。文章是信息载体不是观点源；它只走文档层关系（cites / partOf / asserts 承载声明），不进语义层的互补/分歧。文章之间用 cites，不用"互补"——两篇文章无立场可比，可比的是文内命题。
  • 质询 9：术语漂移（harness 早期多名、后统一）如何建模？答：概念与术语分离（concept-term split）。概念实体稳定（canonical 名 `harness`）；每个历史/各家叫法是一个术语实体，经 `denotes` 边指示概念；演变挂时态（term 带 `valid_from / valid_to` 或对命名断言 reification 加时间戳）；归并用 `owl:sameAs`（旧词 term 保留不删，删了就丢考古证据）。
  • 质询 10：术语也是一种实体吗？答：是，但不必然——需挂时态/来源、或要作检索入口节点时才升为实体；仅需别名则用 `skos:altLabel` 字符串即可。判据与 facet 三态同源：能否独立提问 / 需不需要挂属性 / 要不要被图命中。我们场景（术语未收敛窗口期、金标准防时间线污染）需要"谁在何时用了哪个词"，字符串挂不上，故必须实体化。

结论（v0.3 schema，2026-09-08 15:10）：以 KG 标准模型打底，四种实体类型 + 各自谓词——概念（concept：稳定，canonical 名；结构层关系 subClassOf/partOf/involves、聚合命题）、命题/声明（proposition：带出处三元组；论证层关系 support/attack/complement）、文档（document：信息内容实体，只走 cites/partOf/asserts，不进语义层）、术语（term：denotes 概念，带时态与来源，不必然实体化）。概念-命题-文档-术语不再被我们自创成异构"对象图"，统一落在 KG 实体-类型-谓词模型上。

三个真正自研的增量（复用 KG 之外的贡献）：①检索路由视角——哪些概念/命题提升为"可命中入口"，宽问题经它定位容器集；②维度/可比面组织——facet 作比较轴排布，支撑多方对照；③出处链与引用锚对接——"命题/声明→容器片段"链接上判官引用锚（连续块组），使对象图节点、引用审计单元、存储落点三粒度对齐。其余全部复用 KG 标准（facet=分面分类、支持/攻击=论证框架、声明=reified proposition、归属=provenance/mention）。

一条铁律（随术语层落地）：不把"今天统一后的名"回填到过去——早期文章的金标准/检索/判定应按当时语境解析其词（术语 valid_to 防的就是这个）。这是 0024/0026 反复强调的"时间线污染"在对象模型层的对应物。

考古层第四段 · 命题归位与四级分层：把"自创"从概念里挤出去（2026-09-08 15:30）

起题：沛东两问把模型从"看起来很完备"逼到"自洽但过度"，再逼到"其实早有标准"。问一："命题/声明真的需要单独做实体吗？不就是'实体—谓词—实体'？"问二："不同领域本体各不同，那 proposition 这种跨领域实体怎么会有？"——分别指向命题的建模地位与概念来源的层级。

  • 结论 1 · 命题 = 可选择性 reify 的三元组（v0.4 定稿）：命题本质不是"一方实体"，是一条 (subject—predicate—object) 三元组、一条边。何时才 reify（把断言本身对象化为可引用节点）——四个触发场景：①加 provenance（这条断言来自哪段）；②加时态/可信度/主张主体；③成为 support/attack 论证边的端点；④被引用审计（我们判官核对"声明被哪些块支撑"，引用锚指向的就是这个整体）。不触发就只是边；触发才升为 proposition 节点。 v0.3 把命题列为"第四类固定实体"属过度，v0.4 纠正。
  • 结论 2 · 四级分层（回答"为何有跨领域实体"）：①元模型（RDF/RDFS/OWL 自身：rdf:type / rdfs:Class / subClassOf / ObjectProperty，管"类型"这个动作）；②顶层本体 / 基础本体（BFO/DOLCE/IAO：跨领域的"存在普遍范畴"，proposition 属"信息内容实体"一类，任何领域都可断言/评价真假的信息内容都归它）；③领域本体（我们：harness / containment / 守卫 / 关卡层级；FOAF；GO）；④实例（具体三元组）。RDF 统一"事实怎么表达"，顶层本体统一"存在物分哪几大类"，领域本体才各管各的。 proposition 在顶层本体，故天生跨领域——不是我们领域的东西。
  • 结论 3 · 我们的类不是自创：v0.3 的 concept / proposition / document / term 都是借鉴顶层本体的通用范畴（concept、information content entity、document、agent 均有成熟原型），不是头脑一热发明。真正需要我们自研的只有：领域本体（harness 谱系、facet 维度、守卫立场）+ 三个自研增量（检索路由入口 / facet 组织 / 出处链与引用锚对接）。"自创对象图"的提法从概念里被挤出——架子早有人立好，我们填的是领域内容与检索视角。

概念层面的自检：至此"对象图"不再是自造异构，而是 KG 标准模型（实体-类型-谓词 + 分层）+ 我们三个检索向增量。沛东层面确认：概念已清，可进入落地讨论（哪些概念立页 / facet 怎么排 / 路由入口怎么定），不再纠结词汇归属。

考古层第五段 · 维度/谓词/边/标签，到底谁是"关系"（2026-09-08 15:53）

起题：沛东对着 v0.4 图连着追问，把"维度要不要单独建模""升级为独立轴是实体吗""私有属性怎么建模""边/谓词/标签是不是一回事"串成一条线，最后逼出一条通用定律——这轮把"关系"这一侧彻底理清了。

  • 结论 1 · 维度（facet）必然是谓词，不设"私有/共享"分档（2026-09-08 16:10 再简化）：facet 是三元的中间项（subject —维度— 取值），本质就是谓词（OWL 里即 object/data property，同一物）。"私有/共享"只说明这条谓词当前被几个概念引用（1 个 vs 多个），是自然事实，不是建模决策，无需单独强调成档。修正掉 v0.5 里"依附型/共享型"作为建模分档的表述："containment 防线层级置于 组织层"中的"防线层级置于"就是谓词。
  • 结论 2 · "升级为独立轴"唯一分界 = 是否 reify：维度默认是谓词，住在边上；只有 可独立提问 / 需挂属性 / 需被图遍历命中 时才 reify 成轴实体节点（可命中可导航）。未 reify 就只是谓词——没有"对象属性 vs 轴节点"两档（对象属性就是谓词的 OWL 别称）。与"私有/共享"无关：私有谓词若被独立提问也该升，共享谓词若不独立提问也不用升。
  • 结论 3 · 谓词 vs 边 vs 标签是三层：①谓词=关系类型定义（owl:ObjectProperty / rdf:Property，是"类"）；②边（三元组）=谓词的一次实例化（连接两个具体对象的"事实"）；③标签=命名（rdfs:label / skos:altLabel，本质是字符串属性）。三者都不是"图两端的对象"，默认都不做节点；当需被单独寻址（提问/引用/遍历）时各自对象化。
  • 结论 4 · reify 通用定律（贯穿多轮的主线）：对象默认呆在它"在的地方"（节点或边的位置），仅当需要被单独寻址 / 作为整体被引用时才对象化（reify）。触发判据三连：能否独立提问 / 需不需要挂属性 / 要不要被图遍历命中（即"查询需求决定本体"）。命题从边升、维度从谓词升、术语从标签升——同一个模式，三个起点。这三者被三个不同名字（proposition 节点/轴实体节点/term 实体节点）包装，实为一条定律。
  • 结论 5 · 自研增量②再讲清（facet 作比较轴）：多方对照的难点不是"找到两段话"，而是"这两段话在哪个轴上可比"。facet 作比较轴，是预先给可比较的概念标好"从哪些轴比"——检索先命中轴、再沿轴取各源立场。cmp-002：命中"防线层级"轴 → 取组织层（O2）/环境层（A5）两端 → 落到容器片段。与①的区别：①回答"命中谁"，②回答"命中后如何把宽问题拆成可比的子项"。这是产品层决策，KG 无现成答案，故归自研。

语义不重复标注原则：凡语义已内嵌在节点或谓词里的，不在边上重复标注。维度住在谓词里（决定命题取值轴），边只承载"连到谁、什么关系"。维度标注仅在两种情况下有用：a) facet 已升级为独立轴实体、被命题引用时（标"@哪个轴"）；b) 归属边起点是概念（多维度需消歧）而非命题时。起点已是命题则不带。

考古层第七段 · 复杂度警报与减法：把"主题"删掉，模型收敛成三样（2026-09-08 16:45–16:51）

起题：套用例越套越多概念（轴 / facet / claim_type / topic…），沛东一句"擦，我咋觉得越来越复杂了，主题到底是啥？是边的集合？命题的集合？"——这是复杂度过载的警报。回头看，复杂度主要由反复引入新词造成，本可以更朴素。

  • 结论 2 · "topic vs dimension"待定项落定——没有 topic：之前"主题 vs 轴"纠结，是把"概念（聚合侧）"和"维度（对比侧）"当成需二选一，其实两者都由 concept / 谓词承担。单独 topic 类别删掉；dimension = 谓词（可再 reify 成轴节点）。就这两个。
  • 结论 3 · 模型收敛为三样：实体 = 概念 / 文档 / 异名（三个）；命题 = 可 reify 的边（带类型 + 出处）；谓词 = 维度。检索就两种机制：沿概念/轴的语义路由（宽问法、对比异同）+ 沿命题类型的过滤路由（006/007 捞同类）。无第四样。
  • 结论 5 · 术语更名为"异名"（消除通用含义歧义）："术语"在中文通用含义太强（= 专业性词汇），用它专指"概念的演化叫法"词不达意。改名为异名（alias）——概念在特定来源/时期的叫法，非 canonical 名；默认是 skos:altLabel，需挂时态/来源或作入口时才 reify 成 term 实体。与之对照：canonical 名（主名）= 概念自身的身份（rdfs:label），不单独建实体。注：本文档历史段（质询 9/10、v0.3 schema、一条铁律等）里的"术语"即现在的"异名"，属考古记录用词，保留原样。
  • 结论 4 · 弯路复盘：话题/主题被我叫过 topic，维度被我叫过轴 / facet / 可比面，命题类型被我混进命题过——这些词都归并入三样，不再保留独立概念。复杂度过载是"为区分而造词"的代价，收敛后回到"实体 + 命题 + 谓词"。

结论（v0.7）：对象模型 = 三类实体（概念 / 文档 / 异名）+ 可 reify 的命题边 + 维度谓词；主题 = 概念（内容标签用法），不是独立类别；检索 = 概念/轴语义路由 + 命题类型过滤路由。无 topic。

考古层第八段 · 用用户视角否掉"维度"：模型回到概念+命题+语义边（2026-09-08 收官）

起题：一套用 v0.7 后，沛东连续追问"维度"到底是不是实体/类/谓词、"防线层级"是不是该进概念——一路逼出关键质疑："用户真的会问'OpenAI 的防线放到哪一层'吗？没读过原文，他更会问的是'OpenAI 如何给 Agent 做防护'，或比较时问'两家防护有何异同'。"这从用户视角否掉了"维度"的存在必要。

  • 查证原文（关键证据）：O2 讲"enforce mechanically——linter、结构测试、CI、doc-gardening"，堵的是代码依赖方向；A5 讲"supervise what it's able to do——沙箱/VM/文件系统边界/egress 控制，set a hard boundary on what an agent can reach"。两篇都讲"用什么工具/机制设防"，从未出现"组织层/环境层"字样——那个对立是我们事后概括的抽象。
  • 结论 1 · "维度/防线层级"不是语料实体，也不是用户提问语言：普通用户问的是"怎么防护/有何异同"（命中 concept 防护 + 各源 proposition + 语义边），不是"防线放哪层"。"防线层级/组织层/环境层"是我们做对比分析时脑内概括的抽象，不该进对象图。
  • 结论 2 · 多源对比不需要"比较轴"中介：对比 = 同一 concept 下的多条 proposition，经语义边（complement/attack/support）关联。P1（OpenAI 用 linter/CI）与 P2（Anthropic 用沙箱/VM），同为"给 agent 设防"，complement 直接连，无需"防线层级"当桥梁。
  • 结论 3 · 模型回到朴素结构：概念（+文档/异名实体）+ 命题（可 reify 的 rdf:Statement，带 claim_type）+ 语义边（概念结构边 / 命题论证边）+ 归属边（grounding）。无 topic、无维度/轴/facet/比较轴——这些是我们为"抽象概括差异"造的词，不是检索对象。
  • 结论 4 · 自研增量②重定位：原"facet 作比较轴"取消；改为"多源对照 = 同 concept 下多条 proposition 经语义边关联"（原本就是这个概念，只是不需要"轴"这个中介标签）。三个增量收为：① 路由入口选择；② 多源对照组织（concept→proposition→语义边）；③ 出处链与引用锚对接。

结论（v0.8，收官）：对象模型 = 概念 + 命题 + 语义边 + claim_type + 归属边（实体：概念/文档/异名；命题：可 reify 的 rdf:Statement；语义边：结构/论证；归属边：grounding）。删除"维度/轴/facet/比较轴"——它们是分析抽象，非语料实体、非用户提问语言；用户视角是"怎么做防护/有何异同"，对比天然发生在同 concept 的 proposition 之间。这是整轮概念讨论的最终收敛，把 v0.2–v0.7 反复纠结的"维度怎么建模"整体化解为"不需要它"。

考古层第九段 · reify 的真正动机：只有实体能指向 chunk（2026-09-09 09:59）

起题：v0.8 删除"维度"后，沛东对"命题是否还需要 reify、'多Agent协同未解决'到底该建模成什么"连续提出质疑，最终自己推出一条干净的因果链，把 reify 的真正动机说透了——比我们此前任何论证都深。

  • 因果链（沛东，关键）：① 在 KG 模型里，只有实体才能作为边的端点去指向具体 chunk（target 必须是资源/实体，不能是字面值）；② "多Agent协同未解决"是一个实体（概念），但它指向不了 chunk——它是"被讲到的东西"这个跨段议题，不锚定在某段；③ 只有"O2 承认多Agent协同未解决"这条边（断言）才会、也需要指向某个 chunk——因为是"这句具体的话"落在某段原文里，需要 groundedIn。
  • 结论 · 命题 = 因"要指向 chunk"而 reify 成实体的断言：要让"指向 chunk"（groundedIn）能发生，必须把这条断言 reify 成实体（我们叫命题）。原生边（三元组）不是实体、不能当 chunk 的指向端点。这就把"命题必须 reify"从多个零散理由（我此前误引用审计等）收敛为一条本质原因。
  • 判据（由此得到）：要不要 groundedIn 到 chunk = 要不要 reify 成命题。一条信息若不指向具体 chunk（只是概念间关联），不 reify；若需定位到原文段落，必须 reify 成命题。干净、可判。
  • 概念 ≠ 命题（宾语所指 vs 断言）："多Agent协同未解决"是概念（宾语所指），不是命题；"O2 承认它"才是命题（断言）。同一概念可被多篇以不同方式论述（承认/展望），每条是不同的命题，但指向同一宾语概念。命题 = "谁—如何—针对什么"的断言（可 reify 的 rdf:Statement）；概念 = 所说的对象。
  • 勘误：此前曾以"引用审计要求命题 reify"为论据——错。引用审计是模型输出之后的事（针对模型输出的引用核对），与知识库建模（命题/字段）无关。reify 的真实动机纯粹是"能指向 chunk"（检索阶段），与输出审计两不相涉。

结论（v0.9）：命题 = 因"要 groundedIn 到 chunk"而 reify 成实体的断言（"谁—如何—针对什么"，rdf:Statement）；概念 = 所述的宾语对象（不一定能直接指 chunk）。判据：要不要指向 chunk = 要不要 reify 成命题。这修正了 v0.8 对"命题"只给定义、没给"为什么必须 reify"的不足。

补充 · 文档 → 命题 → chunk 链（2026-09-09 10:03）：文档实体可经 :asserts（对象属性）连接到其下命题——:O2 :asserts :P1（P1 为 LimitationStatement），:P1 :groundedIn :chunk_x。即"文档怎么找它的局限"：?doc :asserts ?p . ?p rdf:type :LimitationStatement . ?p :groundedIn ?chunk。文档是入口、命题是承载断言、chunk 是证据落点。与文档层其它关系区分：cites（文档↔文档）/ partOf（归属）/ asserts（文档→命题）三者并列。

考古层第十段 · 术语定名与标准核实：命题/断言 = KG 已有 rdf:Statement，非自造（2026-09-09 10:42）

起题：v0.9 后，沛东追问"断言这个概念是 KG 本来就有的，还是我们造的？遇到'主谓宾装不下完整语义'，KG 怎么处理？"——把"命题/断言"从我们的动词推向标准术语归属确认，并顺带核实"概念→命题"这条边该怎么命名。

  • 结论 1 · 命题/断言 = KG 固有概念，标准名 reified statement（rdf:Statement）：RDF 内置 reification 机制，官方用途正是记录 provenance（何时/何地/谁说的）。我们把断言 reify 成实体、挂 claim_type（rdf:type 子类）/ 出处（provenance）/ 主题，就是对 reified statement 的标准语义扩展，完全非自造。
  • 结论 2 · "主谓宾装不下"KG 已有三套标准方案：① RDF reification——三元组对象化为 rdf:Statement，rdf:subject/predicate/object 拆回，可挂任意属性；② N-ary relation / relation-as-class——把关系本身建模成类；③ Named Graph——按语境给三元组分组建图。咱们的命题采用 ①，理由：需要逐条断言挂"出处 / 主题 / claim_type"，且要让断言本身就成 groundedIn 与论证边的端点——只有对象化能让单条断言可寻址、可命中。named graph 适合按整组切分，n-ary 适合关系自身属性复杂，均不如 reification 直接对应"单条断言可定位"的需求。
  • 结论 3 · hasStatement 不是标准 RDF 谓词，需对齐到 dcterms:subject：查证 hasStatement（初稿拟 hasClaim，后经沛东敲定为 hasStatement）非 W3C 标准词汇，是自定义 ObjectProperty（与 :asserts / :groundedIn 同类，RDF 合法）。其标准语义是——"具体化陈述关于某概念"＝P dcterms:subject 概念（Dublin Core 标准，"资源的主题"）。故"概念→具体化陈述（主题）"是反向遍历 dcterms:subject。文档→具体化陈述（来源）与概念←→具体化陈述（主题）是两条不同关系，前者 :asserts、后者 dcterms:subject，不可混用。

结论（v0.10，2026-09-09 10:42）：术语定名——"命题"统一为"具体化陈述（reified statement，rdf:Statement）"；"断言"保留给未 reify 的陈述内容；"概念→具体化陈述"边命名为"陈述边 hasStatement"、标准映射 dcterms:subject。这是"无自造词"原则的收口：从"概念要不要 reify"到"边叫什么名"，全部钉到 KG 标准上。

考古层第十一段 · 检索角色定调：向量=入口+兜底，图=主路由；收敛到 GraphRAG 骨架（2026-09-09 11:19）

起题：v0.10 后，沛东逼问"能不能直接用图数据库、把向量库整个去掉？"——把"编译层+chunk 层"的存储落地方式摊开，又借微软 GraphRAG 反照我们的设计，最后定下检索三段的角色分工。

  • 结论 1 · 检索分两段，图只解决"里面怎么走"，不解决"从哪进"：①入口映射——自由文本 query → 图入口节点（哪个概念 / 命题 / claim_type）；②图内遍历——概念→hasStatement→groundedIn→chunk、论证边、claim_type 过滤。第 ② 段是纯图遍历、不需向量；第 ① 段才是向量真正扛的活，也是想"去掉向量"时必须用别的东西（符号/异名 + LLM）顶上的一步。图回答"进了之后怎么走"，不回答"你的 query 该从哪个节点进"。
  • 结论 2 · 查证微软 GraphRAG，融合点=向量从哪进、图怎么找全：两阶段（离线索引 + 查询）。Local Search = 实体概要 embedding 命中种子实体 → 图邻域扩展 → 关联文本块；Global Search = 社区摘要 map-reduce（不用块级检索）；DRIFT = 全局+局部的结合。它把"query→实体"用向量、"实体→邻域→文本块"用图、文本块做证据——正是"向量入口 + 图组织 + 原文证据"。
  • 结论 3 · 我们独立推出的=GraphRAG 挖除社区块的主体骨架（沛东观察，确认）：差异帧在 GraphRAG 给不了的部分——类型化命题 + claim_type（对齐判官金标准，GraphRAG 的 claim/relation 是自由串）、judge 对齐的 grounding（每条命题 groundedIn 到具体 chunk）、确定性 + 学习任务视角（多维审约束）、编译人工复核。故主架构既然已知，接下来"怎么编译"不做骨架发明，而是把精力放在这些差异化点 + 借用其成熟的 LLM 抽取/归并/分块做法。
  • 结论 4 · 检索角色定调（沛东拍板）：向量=入口 + 兜底，图=主路由——入口向量打概念/命题（query→图节点），兜底向量打 chunk（图没命中/问题未建模时捞证据）；不做 chunk 级重排器（证据侧排序由图信号确定性完成，如到种子实体距离 / 命中数 / claim_type）。纯符号/异名匹配被否：对 paraphrase 与术语漂移脆弱（harness 多家叫法是反例）。
  • 结论 5 · 存储落地不必然上图数据库：语料千级块 + 几百概念/命题，量级用现有 SQLite 建边表即可跑通图遍历，比引入 Neo4j / Jena Fuseki 轻；"图"是结构语义概念，落地未必专用图库。
  • 待验证（求真戒直觉）：以上"向量入口命中 / 图遍历聚齐 / 兜底兜住未建模"目前是直觉，需搭最小切片（O2/A5 几十块 + 手搭几十节点图 + 嵌入）跑真实用例验证三点：①向量入口 vs 纯符号的命中率；②命中后图遍历能否聚齐该用例证据块；③未建模探索性 query 兜底能否兜住且不破坏引用审计。

结论（v0.11，2026-09-09 11:19）：检索三段定调——向量=入口（概念/命题）+ 兜底（chunk），图=主路由（hasStatement/论证边/groundedIn/claim_type 过滤），不做 chunk 重排器；与 GraphRAG 的关系=借用其骨架（索引即图）+ 差异化（类型化命题/判官对齐 grounding/确定性/学习任务/人工复核），并明确其"编译结果当事实源"面（Global/community 摘要）被我们的硬约束否掉。

考古层第十二段 · 引入图建模检索层：不追求完美，噪声可控，值得（2026-09-09 11:37）

起题：沛东追问"LLM 编译出三元组会有很多噪声、需要人审；别说十万级文档库，就咱们这几千条，人审基本落不了地"——把"编译人工复核"这个假设从可行推向怀疑，也逼我们把"引入这套结构"的权衡算清楚。

  • 结论 1 · 人工复核的粒度是"基础件"，不是"产物"：人审编译 prompt / claim_type 词表（复用 ISR/FrameNet 收敛）/ grounding 规则 / 校验门，几十条就够；审的是"规则"，不是"每条产物"。这与项目"基础件人工复核"纪律一致——我们一向审金标准/判官提示词/系统提示词/工具契约，从不逐个审输出。
  • 结论 2 · 噪声分两类，各有自动化的挡法：①结构性（id 不存在、claim_type 不在词表、groundedIn 指向不存在的块、违反基数）→ 程序化校验直接拦（同判官"校验闸门"做法）；②语义性（主张内容错、关系类型标错、异名归并错）→ 判官/引用审计当自动质量门（覆盖性/引用真实性）+ 定时抽样看漂移。
  • 结论 3 · 关键：噪声的爆炸半径锁死在"路由"，进不了"事实"：因为 chunk=事实源、编译=索引（第 3 条硬约束），答案从 chunk 生成；某条命题哪怕抽错/归并错/type 错，最坏结果=漏块/路由偏差，判官的覆盖性/引用真实性会把它当 miss 揪出来；它不会变成一句编错的事实被当成答案。LLM 编译噪声只毒害"取到哪些块"，不毒害"回答什么"——而前者能用判官自动兜住。
  • 结论 4 · 权衡（沛东拍板）：引入图建模检索层不追求完美；即便有噪声，它已解决大量问题；剩余问题被上述机制（校验 + 判官门 + 抽样 + 噪声锁死在路由）兜住，不会让引入弊大于利——这个权衡够清楚、够划算。
  • 落点：编译层设计必须把"校验层 + 质量门"当一等设计项（schema 校验 / claim_type 词表约束 / grounding 一致性 / 判官引用审计在编译侧复用），不能指望"人审产物"兜底；库越大越依赖机器门，而门制是可扩的。

结论（2026-09-09 11:37）：编译噪声是真实存在但可控的——人工复核=审基础件＋程序结构校验＋判官自动门＋抽样，而非"人审每条产物"；关键设计约束是把噪声爆炸半径锁死在"路由"（chunk=事实源、编译=索引）。综上，引入图建模检索层即便有噪声也划算，胜过无结构的纯稠密 top-k。

考古层第十三段 · 编译层设计定调：源=清洗后原文、粒度=内容单元、reify=预测+修补（2026-09-09 12:10）

起题：过了"检索角色定调 / 噪声可控"后，真正进入"怎么编译"。沛东连追三问把编译层从"想象"推到"可落地"：①该直接抽具体化陈述吗？还是文档/概念/边/具体化陈述一起？reify 判据？②从哪编译（原文？chunk？）？③内容单元是不是虚概念、要不要长度上限？

  • 结论 2 · 编译源=清洗后原文（切片为 chunk 的输入），非 chunk：chunk 拆散论断、缺完整上下文；即便"引用锚=连续块组"也是拆后聚合、非原文连续（查证 _resolve_citation_groups 聚"声明组"、_marker_groups 按模型输出连续 [n] 切段，均非原文连续）。
  • 结论 3 · reify 本质是预测（无法预先知道会不会被问）→ 需"预测+修补"两段：预测（编译时）——claim_type 在被查词表（从判官/a5-cmp 反推的检索需求类型学）/ 立场性"谁—这么认为" / 概念中心度（跨单元/来源、命名主题）/ 需作论证端点，命中任一即 reify；纯结构关系（partOf/involves/precedes）与纯属性留边/标签。修补（查询/回答时）——①dense 兜底先接住（信息仍在证据里，只是没组织成陈述，不丢事实）；②判官 miss 驱动 promote（信息在但没组织→提升为具体化陈述）；③周期清扫批量 promote → 自愈索引。复用判官/覆盖性机制。
  • 结论 4 · 内容单元=虚概念、仅编译时用、不落库：语义边界（标题/小节）优先，token 上限 12k（约 1.5–2.5 万字）兜底；超限在小节/段界切、留 overlap；跨单元同概念归并（sameAs/denotes）、声明合并、去重。
  • 结论 5 · chunk 补"清洗后原文偏移"，实现里是"按文件"坐标：chunk_offsets 表存 chunk_id/source_id/section_path/file_idx/start_pos/end_pos；偏移按文件计——多文件源（如 T2 课程 149 个文件）用 file_idx 区分、各文件坐标从 0 起；单文件源（如大 PDF 书）file_idx=0、偏移即全书全局。若只靠"section+内容"匹配就只能弱锚。内容单元划分是编译层职责：在文件内按 section_path 分组切出章节/小节作为编译窗口（≤12k token 兜底），非 chunk/偏移层做。grounding=证据 chunk 集合（多对多，判官"声明组"口径）。
  • 结论 6 · 校验层+质量门为一等设计项：人审基础件 / 程序结构校验 / 判官/引用审计自动门 / 抽样；噪声爆炸半径锁死在"路由"（chunk=事实源、编译=索引），进不了"事实"。

结论：编译层"="清洗后原文 → 内容单元（≤12k token）→ 一次带类型抽取 → 跨单元归并 → 校验层+质量门"；产出"对象图（概念/异名/文档 + 具体化陈述 + 边）+ 证据 chunk 集合"；reify 由"预测+修补"决定，替代旧的"对齐 chunk"判据。

考古层第十四段 · claim_type 为何必须按场景收敛：用途不同、全集≠交集、LLM 把理解挪出类型系统（2026-09-09 下午）

起题：沛东对着"从权威参考资料拿到的 5–6 类 claim_type 用场景一验、大部分用不上"追问根因——"是因为我们其实有了 LLM 加持来生成吗？"这一问把"为何词表该薄"逼成了可复用的论证，也顺带产出一条判别原则。

  • 结论 1 · 根因是"用途不同"，不是"LLM 加持"：权威词表（AZ/CoreSC：Background/Method/Result/Conclusion/Limitation/Future Work；Argument Mining 的 claim/premise、interpretation/evaluation/agreement/disagreement；SemMedDB 谓词）服务于语料标注 / 文本结构分析，必须穷举标全部句子；我们的 claim_type 只是路由过滤标签，只标"被 reify + 需要按角色过滤"的交集。一个"描述型词表"和一个"运营型索引"，粒度天然不是一个量级。
  • 结论 2 · 其余三个次因：① 词表要标注"全部"，我们只标注"被 reify + 需要过滤"的极小交叠（多数断言走概念/结构/论证/出处边就到了）；② 负荷在问题空间——按"角色"过滤的题型就那十几种、且由产品定位固定；语料量只是二阶因子（再多文档只提高概念陈述集的异构/激活度、催动 reify 修补侧 promote，引出的异名/术语漂移落在入口/异名侧），撑不大类型集合；③ LLM 把"理解"挪出了类型系统——入口映射解"什么是 X"到概念、回答生成+判官管语义对不对、框架走 partOf、为什么走 support、出处走 provenance/groundedIn。前三样接走理解，类型系统只剩"确定性可过滤"那一小块。
  • 结论 3 · 用产品视角 tag 反向验证（0027 题型/环节）：11 题型 / 10 环节里，绝大多数走"概念路径 / 结构边 / 论证边 / 出处边 / 生成"就到；真正按"论述角色过滤"的硬需求只有局限 / 展望（探针 cmp-006 逼出）。故 Definition / Method / Stance 都不该占类型——Stance（"谁这么说"）走 文档→asserts→chunk，Definition/Method 走概念路径；核心词表 = {Limitation, Outlook}，其余按"概念陈述集异构 + 用户按角色过滤"走 reify 修补侧动态 promote。
  • 结论 4 · 一条判别原则：分类的粒度应由它服务的那个决策/查询决定，而不是由数据本身的丰富度决定。权威词表丰富，因为它服务"把文本讲清楚"这一丰富任务；我们薄，因为服务"把用户问题路由到证据"这一窄任务。照搬学术词表 = 为不同目标函数做优化。
  • 诚实的代价：类型薄 → 路由那一步更依赖 LLM 语义消歧，确定性弱一点（与我们之前否掉纯符号、质疑向量入口是同一矛盾）。平衡点 = 确定性强的核心（局限/展望）留给类型，模糊的留给 LLM。

结论（2026-09-09 下午）：claim_type 词表该薄、且必须按场景收敛，不能照搬权威词表；它是"被 reify + 要按角色过滤"的交集标签，而非穷举的文本结构标注；LLM 的加持是"让词表能薄"的使能条件而非根因。核心词表待成文：{局限, 展望}（+ 动态 promote 规则）。

考古层第十五段 · 编译输出 schema：id 无业务含义、reify 触发收敛为 3 类、claim_type 正推（2026-09-09 傍晚）

起题：把这个 schema 拉成草案后，沛东一连五问逼出 schema 该有的严谨度——id 用名称合适吗？term/canonical/aliases 到底用 id 还是名字？reify_reason 跟"指向 chunk/挂属性"偏离、还把刚否掉的 stance 又拉了进来？statement 怎么被检索？produced_by 三个取值分别是啥？这轮把 schema 的引用键、触发、语义键、产出方四项都捋清了。

  • 结论 1 · id 与名字分离：id 是私钥、全局唯一、无业务含义（数据库主键，ULID/序列），不拿名字当主键——名字会改（术语统一、harness 多家叫法）、会撞名；展示/自然键另用字段（document.ref=O2/A5、concept.canonical、term.label）供人读与编译期去重。避免重命名/撞名破坏引用。
  • 结论 2 · 引用一律用 id：term.denotes→concept.id（不是 canonical——名可能撞/改）；concept.aliases=字符串数组（只是别的名字，供入口匹配），需记漂移/来源的别名才升级成 term 实体（有 id、denotes→concept.id）。aliases（字符串）与 term（实体）不冲突。
  • 结论 3 · reify_reason 收敛为 3 类：type_filter（claim_type 在被查词表）/ argument_endpoint（作论证边端点）/ concept_central（跨单元/来源、命名主题的枢纽）。删"立场性"——"谁说的"由 asserted_by（文档→陈述）+ provenance 承载，走 文档→asserts→陈述 就到，不必为 stance 触发 reify；这也与"已否掉 stance 为 claim_type"保持一致。
  • 结论 4 · claim_type 是"正推"非"反推"：词表来源 = 业界数据（AZ/CoreSC、Argument Mining、SemMedDB）作候选 + 产品定位/问题空间（题型、环节）正推收敛，不是"由判官 / a5-cmp 反推"——决策 9 原措辞"由判官/a5-cmp 反推的检索需求类型学"已改。
  • 结论 5 · statement 的可检索性：statement 是路由节点，非被扫描——到达它靠入口（向量/LLM 把 query 解到概念/文档/claim_type），离开它落 chunk。about/subject/object=语义键、claim_type=过滤键、evidence_chunks/groundedIn=证据键；三种路径（概念→hasStatement→陈述→groundedIn→chunk；陈述→groundedIn→chunk；文档→asserts→陈述〔按 claim_type 过滤〕→groundedIn→chunk）。
  • 结论 6 · produced_by 三值：compile=编译器从原文直接抽出、有 span 背书（概念/文档/结构边/asserts/有原文支撑的陈述），低风险；compile-hypothesis=编译器推断的关系、无单一 span 背书（主要是 support/attack/complement 论证边），标注为假设、待 C 自动判定/判官兜底，风险较高；auto=程序算的（groundedIn 由引文锚定重叠、provenance 派生），确定性输出。
  • 结论 7 · 无 per-entity draft：早期草稿给 concept 加了 draft 待确认标记，被否——那意味着逐产物人工复核，与"人工复核=审基础件（非产物）"冲突；质量门=程序校验+判官/审计+抽样，不在每条概念上挂人审标记。

结论：编译输出 schema 定为"每内容单元一份 bundle（content_unit/document/concept/term/statement/edge）"，id=无业务含义私钥、statement 带 reify_reasons(3 类、可多选) + claim_type(可选) + clean_ref/asserted_by/evidence_chunks、edge 带 produced_by 三值 + 谓词词表；架构文档 ④ 已落 schema 小节，0028 同步。

考古层第十六段 · B6 编译层真实落地：一串"输出上限 + LLM 不稳定"逼出的权衡与转折（2026-09-09 晚）

起题：A2/A4 schema 定稿后，B6 用真实语料 O2/A5 验证编译层能否落地。一跑就连续暴露"输出上限"与"LLM 不稳定"，每一步都是权衡转折，且多为沛东先提出、我在实现中验证/修正。过程值当考古。

  • 转折 1 · 内容单元=整篇 O2/A5，不按小节拆：内容单元是"语义边界优先的连贯窗口"，section_path 只是边界启发式、非强制切分点；O2(5.4k)/A5(7.5k) token 均在 12k 内，整篇即一个单元。拆子标题会主动隐藏上下文（"跨单元归并"只在真正大文档 T1 才值得测）——纠正了"能切≠该切"的偏差。
  • 转折 2 · 引文锚定替代"LLM 给数字 span"：LLM 标精确数字偏移不可靠；改为 LLM复现逐字证据、程序归一化匹配定位 + 与 chunk_offsets 重叠。原因：LLM 擅复现文本、不擅标数；定位交给程序才确定。
  • 转折 3 · evidence_text 单串 → evidence_texts[] 数组：LLM 用 "..." 桥接跨段引文，破坏连续定位；证据本就是"块集合"（多对多、判官声明组口径）→ 改数组、每段连续、程序逐段定位取并集。原因：证据=集合，不连续是常态、非缺陷；逐段优雅降级。
  • 转折 4 · 单趟编译 → 两段式（Pass 1 抽取 + Pass 2 分类/建图）：单趟把"抽原子断言"和"判 claim_type/reify"混在一起，LLM 在两个判断间漂移（同判官不稳定一类）。拆成 Pass 1=宽召回机械抽取、Pass 2=精度分类建图。原因：抽取=召回、分类=精度，职责分离（借鉴判官 checklist 分步）。
  • 转折 5 · Pass 1 输出截断 → 窗口化：整篇 atomic claims + 引文超输出上限；Pass 1 是局部抽取、不需全局 → 按窗口（~5k 字符、段落界切）逐窗抽、合并。原因：局部抽取 clean_start 平移回全局；窗口小则不截断。
  • 转折 6 · 短锚（省输出 token + 定位更稳）：每支撑块给 1–2 句短锚，而非整段长文。原因：输出 token 单价远超输入（省钱） + 短锚精确匹配更抗偏差（定位率 75%→100%）+ 多锚（每块一条）保覆盖不丢。
  • 转折 7 · Pass 1 增多（186→197）不是重复，是粒度（重要纠误）：窗口化让 LLM 逐句穷举（实测 0 重复）；整篇时更挑。真因是"传入窗口大小在控制 LLM 抽取密度"。别把"增多"直接当"过度抽错"。
  • 转折 8 · 宽召回门槛（"重要性"的可行做法）：不加"挑重要"（那是把决策交给 LLM 自觉、不可控）；给可判定门槛——只抽"对可点名知识对象述说可引证之事；跳过叙述/过渡/复述/无新断言例子；拿不准就抽（宁多勿漏）"。原因：让"什么该抽"从自觉变成判据。

起题（沛东点破）：我们量"抽取稳定性"时，用主语与宾语字面相同当配对标准，得到"只有 27% 的 claim 能配上"，于是推出"抽取不稳定、要提高主宾字面一致率"。沛东指出这逻辑上就错了：

"我们搞谓词归一化的目的，是为了在后续阶段做实体合并。如果抽取阶段能把'主语宾语相同的 claim'变高，那岂不是提前把后续阶段该做的活儿干了？"

为什么这个批评成立（两点）

  • 配对口径错：`agents` / `the agent`、`Claude Code` / `the OS-level sandbox` 这类差异，本来就是实体合并层（形合并/义合并）要处理的东西；把它当"同一条断言"的门槛，等于把下游要解决的问题提前排除在样本之外。
  • 改进目标错：要求抽取"把主宾抽一致"，就是让按窗口跑、没有全文视野的抽取工序去干全局归一化——注定干不好，而且与"先抽全、再归类"的既定原则相冲。
  • 连带的错误归因也一并纠正：之前把"表面谓词不同的 13 对里标签只有 53.8% 一致"归因给抽取层——按分层框架，那 13 对恰恰是归一层该负责的场景（同一断言的不同措辞，归一本就该给同一标签），低分是归一的失分。

于是有了"各阶段量什么"的分工表：

沉淀：① 指标的"配对/分母口径"必须先定义清楚再解读——同一个"一致率"，分母换成"主宾字面相同"就变成另一个问题了；② 改进目标要落在这个阶段的职责范围内：给上游提一个"下游该干的事"，只会让它既做不好又丢掉本职（宽召回）；③ 稳定性是分清层的：抽取层多遍对比看"覆盖"，归一层固定输入看"标签"；④ 27% 那个数字的正确读法是"实体合并层的输入规模"，不是"抽取的质量"。

考古层第三十一段 · 体检（质量门）定稿 + 接进流水线与界面：第一次真跑就抓到指标缺陷（2026-09-11）

考古层第三十二段 · "段落主旨 vs 宽提取 + 受控关系筛选"：一次关于"KG 该抽什么"的判断（2026-09-15）

起题：沛东翻了一遍知识图谱资料，提出一个直觉：原文不适合直接抽三元组，更合适的做法是先让 LLM 做主旨提取（例如每个自然段一次，输出"数句更规范的表达"），再基于这些规范表达抽三元组；并指出这隐含一个假设——KG 只管关键脉络和关系，细节检索仍由向量支撑，问答侧要做融合。

AI 的判断：方向对，形式不对——"KG 管脉络 / 向量兜细节 / 问答侧融合"已经是我们架构里写死的分工（图=主路由 + 类型过滤 + 跨源聚合；向量=入口 + 兜底；chunk=事实源）；但"先主旨再抽"这一步不该做，四条理由：

  • 主旨是有损压缩，丢的恰好是关系细节：主旨在定义上就是概括（"X 通过 A/B/C 三种机制达成 Y" → "X 用机制达成 Y"），而三元组要的正是 A/B/C。金标准里的 approved roughly 93% of permission prompts、any probabilistic defense has a non-zero miss rate 这类断言，恰恰是主旨提取首先会压掉的——而它们是"局限/展望/对比"类问答的弹药。
  • 结构性反对：主旨句无法引文锚定。我们的硬约束是"编译层不能成为事实源"——每个产物都要能逐字指回原文（引用审计的根基）。主旨是"重新写的一句话"，原文里不存在 → LLM 说错了追不回原文、也无法验证"这是不是原文说的"。
  • 前置有损 + 后置抽取 = 双重损失且不可逆：主旨里没有的东西，后面永远抽不到。同源实测：在抽取阶段加要求会让召回掉（把 38 行词表塞进抽取 → 召回 1.00 → 0.80/0.85，最后拆成"抽取/归一"两步才救回来）。
  • 同源证据：对齐 > 信息量——我们试过"给整块原文 vs 给锚句 ± 邻句"，族级一致率 77.3% → 86.7%；主旨提取正好是反方向，把逐句对齐打散。
  • 业界对照（GraphRAG）：它的流水线是 text unit → entity/relationship extraction（带 gleaning 补抽）→ 合并 + 描述摘要 → 社区摘要——摘要在抽取之后（对实体描述做），不是前置；且抽出的实体/关系带 source text unit id（可回溯）。"先写主旨再抽三元组"它没有。

修正后的结论（沛东接受并补了更强的一句）：

"我们的宽提取 + 谓词归一，某种意义上已经在做这种主脉络的筛选了，只需要确定无法归类的谓词扔掉或者待定即可。这个更可控。虽然这种方式跟人类的方式（大概是先翻译成自身的语言、然后同时判断是否是重点）不同，但人类的方式不具有可重复性，不确定性太大——这个正是系统需要克服的地方。"

于是形成"图里收什么"的边界规则（四档处置，不能一刀切）：

沉淀：① 系统不需要复制人类认知——人靠"理解 + 择要"一体完成，代价是不可重复、不可审计；系统要的是"可重复的择要代理判据 + 可见的残差"，待定清单就是人能介入的位置（与"unsure 是过滤器/验收探针，不是判据"同源）；② 凡是破坏"可锚定"的中间产物，都不该进编译层——这条可以推广到以后任何"要不要在中间加一层加工"的判断；③ 这是"先抽全、再筛选"这条原则的第四次验证（前三次：Pass1/Pass2 拆分、抽取与谓词归一拆分、表不塞进抽取）。

考古层第三十三段 · 落地：谓词清洗 + 三态归一 + 表外词台账（含一次护栏误拒事故）（2026-09-15）

起题：第三十二段的四档规则讲完后，沛东一句"好，把这个待办做了"——指的是那段末尾写下的"落地（只差程序上的一步）"：① 归一步输出区分 mapped/forced/pending；② 图里只收前两者的边，pending 进报告；③ 待定词表按篇累积。

实现（三块）：

  • 谓词清洗（新增一步，排在谓词归一之前）：只把"糊谓词"洗成干净动词，只动 predicate 一个字段。触发条件是确定性的：≥4 词 / 含并列（and·or）/ 含从句标记 / 含否定 / 含情态词。提示词里的示例刻意不用本语料的句子（防"针对某篇过拟合"）——首版顺手写了 A5 原文里的两句，提交前已换成与语料无关的例子，并复跑一遍确认（14:49，claims 382→374、清洗 26、护栏误拒仍 0、红线过）。
  • 三态归一：mapped（直接落表）/ forced（模型造了表外词，但有 predicate_nearest → 强归，记 predicate_invented）/ pending（表里真没有 → 不进图、进报告"待定清单"）。_build_pass2_blocks 跳过 pending 不生成边。
  • 表外词台账：backend/data/compile/_outside_words.json，按词累积 mapped/forced/pending 次数 + 出现过的源 id——这是"残差 → 定期收敛（补表 or 确认丢弃）"的落点。

为什么清洗必须排在归一之前（这一步存在的理由）：像 should not be implicitly trusted 这种整句谓词，如果直接进归一步，会被静默塞进某条宽关系——表里总有笼统关系能装下它，结果就是一条看起来合法、实际把否定吃掉的边。这正是项目反复强调的悄悄错。先清洗成 trusted + polarity: negative，否定才有归宿。

清洗的护栏（"只删不改"）：① 只改 predicate，主宾与引文一个字不许动；② 清洗结果必须是原谓词的子序列（允许删词、允许时态/单复数形态变化，不许换词）；③ 被护栏拒了就保留原谓词并记 predicate_clean_rejected（记账，不静默吞）。

事故：第一次真跑，5 条合法清洗被自己的护栏拒了——A5 一遍跑下来 cleaned 51 / rejected 5，被拒的 5 条全是模型干得对、护栏认不出：is best known as → know、would have done → do、are kept deliberately minimal → keep、made them harder to audit → make、needs to be applied to → apply。根因：子序列校验最初只把词折成单一词干（placed → plac），而 keep/kept、make/made、know/known、do/done、apply/applied 这些不规则形态折不到一起 → 合法的清洗被判成"换词"。

修法（同一个不变式，两次补齐）：① 把"单一词干"改成"词形变体集合"比对，并补一张 不规则动词表（约 60 条：kept→keep、made→make、done→do、known→know…）——这一刀把误拒从 5 降到 1；② 剩下那 1 条 has authority to grant → have 是同一根因的另一面（第三人称 has → have 缺口）→ 补 has/had/does/goes/went/gone——误拒归零。补了 7 条回归探针（test_compile_predicate_clean.py），并留两个反例（换词 handle、乱序 read can 必须被拒），全量 219 passed。三次真跑的对照：

考古层第三十九段 · 一次纠正引出的自省：三条实现路径 vs 图谱，与"技术本位主义"归因（2026-09-17 五轮，20:30–20:55）

起题：沛东提出另一条实现路径——用问题分类做分支路由（"两篇全面对比"→ 把全文塞给模型；"跨文主题对比"→ 用"文章名 + 主题"做向量检索，依赖文章内 section 的向量化），甚至把这些能力封成工具交 LLM 用 ReAct 自主决策，问这两类的优劣。

我给的框架：这不是"三条路线选一条"，而是 三种原语 × 两种调度——原语＝相关性检索（现有）／范围枚举／跨源连接；调度＝确定性规则路由／LLM 自主。分水岭是"有没有一个可枚举的范围"，不是"谁来调度"。并用项目现有数据锚定：注入预算 ≤3600 token、每源 ≤25 dense 候选、cmp-002 自由文本判官 15–16/20 而清单式严格判官约 10/20、A5 24 块 / O2 19 块 vs T1 928 / T2 1422 块。结论：向量检索的问题不是"检不到"，而是"不能保证该有的都有"（覆盖语义）；"全文直读"在小文档上是真优解（无损、零编译误差），只有在"语料大到塞不进 / 需要跨源 join / 需要覆盖保证"时才轮到图谱。

沛东的纠正（本段关键）：我顺势建议"从编译产物投影出一张 doc × 主题 → 证据块 的扁平主题索引，作为便宜版基线"。沛东一句打回："你这个倾向是因为我们现在看的 A5 / O2 这两篇，它们的 section 已经对内容做了比较好的语义总结；而我们这个产品本来就要覆盖论文，论文的 section 标题十分格式化、基本不含语义。" 去语料里核实，确实如此：

  • A5（我们现在调优的那篇）：Risk we missed: Exfiltration through an approved domain、Pattern 2: The human-in-the-loop sandbox (Claude Code)——主题是白送的；O1（厂商 PDF）：What is an agent?、When should you build an agent?——同样语义化。
  • D1（现有语料里最接近论文的技术报告）：01 概述、02 WOWService 框架、03 实验结果、04 总结和展望；D2（VitaBench）：一、研究背景、二、理论基础、2.1 推理复杂度、四、实验结果与分析、4.4 典型失败案例分析——标题基本只剩结构，且已经出现 𝒞_reason 这类符号（分词 / 词形折叠 / 向量化都要另想办法）。

修正后的结论：被否掉的是"便宜版主题索引"，不是主题索引本身——主题键一旦不能从标题白拿，就必须从内容读出来；而"读内容 → 产出规范化的主题标签"这一步，就是编译。于是三档原语重新定位为：(i) 块向量（相关性）→ (ii) 段落主题标签（受控小词表、一遍 LLM、不抽实体不建边 ⇒ 范围枚举）→ (iii) 图谱（枚举 + 跨源连接 + 关系）。前一档成本约为后一档的 1/3，且买不到枚举与连接；每一档都必须由一类具体用例买单。

可预见的风险（论文类语料的"语料依赖清单"）：① 元主语比例会爆——论文满篇 we propose / our method / this paper，我们的元主语告警线（10%→20%）是按博客定的，几乎必然撞线；更麻烦的是语义变了（博客的 "we" 是作者/机构，论文的 "our method" 是所指确定的对象）→ 这条规则要重写，不是调阈值。② 符号与指代——𝒞_reason、Eq. 3、图 2、the former：S4.5 只认"以指代词开头"的字段，且窗口是"锚句前 1600 字符"，而论文的符号定义可能远在方法节甚至附录。③ "跨节数"指标退化——主要实体卡排序与复盘页的"跨 N 节"建立在 A5 的 15 个语义节上，论文只有 5–8 个大节。④ chunk 三段式（来源行 + 叶子节标题 + 正文）里的叶子标题失效——论文里是 3.2 这种，等于少掉一行有效上下文。这四条的共同点是：它们都是"语料偶然给的"，不是方法产生的。

决策（沛东拍板）：继续把图谱做完，再看图谱的效果——不因为存在另一条路径就掉头；同时把"论文类语料验证 + 语料依赖风险"与"新思路（三档原语 / 段落主题标签）的验证"正式记为待办（已写入 AGENTS.md 开放待办，并在架构文档 G 表留痕）。

沛东的归因（记下来，因为它比结论更重要）："我感觉我们产生这个可能的方向错误的原因，是因为我们其实在决定引入图谱来做检索结构支撑的时候，又犯了技术本位主义的毛病，没有真正扎实地从产品需求、约束的视角来完整进行分析，所导致的。" —— 这是 AGENTS.md「产品视角优先」原则的第二个实证锚点（第一个是 2026-09-04 的 cmp 阈值之争），已同步进 AGENTS.md。

沉淀：① "语料自带的结构"是最容易过拟合的隐形依赖（section 标题、段落规范、标点、语言）——定架构前先问"这个信号是语料偶然给的，还是方法本身要产出的"；② 比较技术选项要先对齐"原语"，再比"方案名"——本轮三条路其实共享同一组原语，拆开一比，讨论立刻收敛；③ 静默失败形态决定护栏设计——路由错的失败是"用错视角答题"、Agent 探索不足的失败是"只查一篇就下结论"、图谱漏抽的失败是"自信地说没有"，三者要的护栏完全不同（前两者靠覆盖性判官，后者靠编译层召回红线）；④ 不反复摇，但要留"何时掉头"的判据——图谱的价值必须落在"枚举 / 跨源连接 / 关系查询"三件上；若三档实验证明扁平主题标签已覆盖主要用例，图谱就降级为只做 claim_type 与跨源连接。
